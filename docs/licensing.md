# Licensing

Ricevanta is Apache-2.0. This file records what third-party code and rule sources may be used and under which conditions. Every new dependency or rule pack gets a row before code depends on it.

## Rules

- GPL code is never linked into Ricevanta and no GPL program ships with it; GPL tools appear only as lab test fixtures.
- The project's own eBPF programs are dual-licensed MIT and GPL-2.0, because the kernel accepts BPF LSM programs and GPL-only helpers only from GPL-compatible programs. They are separate objects loaded into the kernel, not linked into the agent, and the agent stays Apache-2.0.
- Reference projects are for learning; copying code requires a row in the table and attribution in `NOTICE`.
- Rule packs carry their own license record, author fields and signature from the first pack. Rule licenses are tracked separately from application code.
- Sigma rules under DRL 1.1 require the rule author to be shown wherever a match is displayed, including console alert views and exported events.
- An SBOM is produced for every release.
- Extensions carry an SPDX license expression in their manifest, which the console shows at install; a release SBOM covers first-party extensions. Connector contracts are project OpenAPI 3.1 documents and add no library.

## Console OSV exceptions

License permission does not waive vulnerability checks. The [console foundation exception contract](specs/console-foundation.md#dependency-audit-exceptions) requires committed `console/security/osv-exceptions.json` entries with advisory ID, package, exact version, full versioned dependency path, untrusted-input rationale and removal condition. Each entry requires independent Sol xhigh review. The audit fails on unlisted findings, entries that no longer match the lockfile, absent advisories, malformed entries or incomplete OSV results. Diagnostics name each advisory, package/version and path, including accepted exceptions and stale-entry reasons.

The permitted entry is `GHSA-vfj7-8cjw-p6xm` for `braces` 3.0.3 on `@intlify/unplugin-vue-i18n` 11.2.5 -> `fast-glob` 3.3.3 -> `micromatch` 4.0.8 -> `braces` 3.0.3. [OSV](https://osv.dev/vulnerability/GHSA-vfj7-8cjw-p6xm) lists stack exhaustion on deeply nested patterns, `last_affected: 3.0.3` and no fixed release. The path root must appear only in the console importer's `devDependencies` in both manifest and lockfile; promotion to `dependencies` or `optionalDependencies` fails even with identical versions. Only repository-controlled build patterns for the two bundled catalogues reach this path; external data cannot supply patterns, and no code on the path ships in console assets. Verify those boundaries in review. Remove the exception when a compatible fixed release at least 1,440 minutes old can be locked, the path changes or disappears, or OSV no longer reports the advisory. Untrusted pattern input or runtime use blocks acceptance until the dependency is safe; a changed path needs fresh review.

Reject no audit because unrelated findings would disappear, a nonexistent fixed `braces` override because it cannot be installed or verified, and forking because it creates private parser security and release maintenance. The spec holds the exact machine-readable entry and matching rules; [plan Task 1](plans/console-foundation.md#task-1-project-and-validation-harness) owns implementation and tests.
