# Server runtime implementation plan

Implement [the server runtime spec](../specs/server-runtime.md) in five tasks, each one pull request with failing tests first. The spec owns the contracts; this plan owns order, paths, commands and proof. Nothing here authorizes a database, identity, API, enrollment or any role other than `api`.

Roles: the coordinator owns dispatch, Git, CI evidence and landing; the implementer owns one task's paths; the independent code reviewer reviews each task and confirms fixes, with the adversarial pass on the console handler and TLS loading. The designer does not implement or approve. Workers never commit or push. Follow [workflow](../../instructions/workflow.md), [Go instructions](../../instructions/go.md), [testing](../../instructions/testing.md) and `server/AGENTS.md`.

## Boundaries and ordering

- Paths: `server/cmd/ricevanta-server/`, `server/internal/buildinfo/`, `server/internal/platform/{config,runtime,health}/`, `server/internal/transport/console/`, `.gitignore` entries for generated files, `.github/workflows/server.yml`, `scripts/ci/targets.toml`, `server/AGENTS.md` wording, `instructions/testing.md` command sections. Schema fixtures under `schemas/server/` change only through the designer.
- Dependencies: the standard library and `go.yaml.in/yaml/v3` v3.0.4, already in `go.mod`. Nothing else.
- Task 1 stands alone. Task 2 needs nothing from Task 1. Task 3 needs Task 1 for identity verification. Task 4 needs Tasks 1 to 3. Task 5 needs Task 4, a console build, and [release plan](release-builds.md) Tasks 1 and 3, because the embedded tree's `build-info.json` and the server's `generated.go` both come from `scripts/release/version.py` and the manifest from Task 3's `scripts/release/console_manifest.py`.
- Local checks are `gofmt -l`, `go vet` and `go test -count=1` on touched packages; race, the embedded-console smoke and the cross-component job run in CI. Commands run from `server/` unless stated.

Review focus: a request path that reaches the filesystem (Task 3); a header set that differs by one byte from `console/security/csp.txt` (Task 3); a sidecar served under its own name, an immutable cache on a non-manifest file, or `br;q=0` selecting the Brotli sidecar (Task 3); `tls.mode: none` accepted on a non-loopback address or a world-readable key accepted (Task 2); a `3xx` answer, a request whose content is read or drained, a content refusal without an expired read deadline, or an `OPTIONS *` answered by Go's built-in handler (Tasks 3 and 4); a blocked role that starts anyway (Task 4); a shutdown that exits 0 after the deadline (Task 4).

Confirm in that test that `scripts/release/version.py --out` output compiles into the package only with `-tags ricevanta_release`; `scripts/release/version.py` and `test_version.py` stay unchanged.

## Task 2. Configuration

Owner: implementer. Own `server/internal/platform/config/`. Produces `config.Load(path string, env func(string) (string, bool)) (Config, error)` with strict YAML decoding, the closed environment list, bounds and the semantic rules of spec section 3.

- [ ] Write tests that convert every case of [`schemas/server/config/v1/schema-cases.json`](../../schemas/server/config/v1/schema-cases.json) to YAML, load it and require the same verdict as `valid`; load the YAML form of [`example.json`](../../schemas/server/config/v1/example.json) and require the documented values. Add YAML-specific negatives: duplicate key (rejected by v3.0.4 itself, `mapping key ... already defined`), an anchor, an alias, an explicit `!!str` tag, two documents, a scalar document, a 65,537-byte document; and semantic negatives: `tls.mode: none` on `0.0.0.0:8080` (`plaintext_requires_loopback`), a key file with mode `0644`, a key file with mode `0640` whose group is not the process's, a key file with mode `0440` owned by root and the process's supplementary group accepted, the same key reached through a two-level symbolic link chain shaped like a Kubernetes Secret volume (`key -> ..data/key`, `..data -> ..<timestamp>`) accepted and judged by the target's mode, `RICEVANTA_SERVER_LISTEN_API_ADRESS` (misspelled) rejected, `--config` winning over `RICEVANTA_SERVER_CONFIG`, `RICEVANTA_SERVER_ROLES=api,agent` parsed but `agent` reported as `role_blocked` by the role table. Require red.
- [ ] Implement with `yaml.v3` `Decoder` and `KnownFields(true)` into closed structs, a `yaml.Node` pre-pass that rejects `Kind == AliasNode`, a nonempty `Anchor` and `Style & TaggedStyle != 0`, then the standard-library validator that repeats the schema bounds; `check-config` output as sorted-key JSON without file contents.
- [ ] Run `gofmt -l .`, `go vet ./internal/platform/config` and `go test -count=1 ./internal/platform/config`; require pass. Add `FuzzLoad` with the schema cases as seed corpus; Task 5 registers it in CI.
- [ ] CI proof: `server-unit` and `server-race`; the `go-fuzz:platform/config:FuzzLoad` leaf proves this task once Task 5 registers it.

## Task 3. Embedded console verification and handler

Owner: implementer; adversarial review required. Own `server/internal/transport/console/` including `testdata/dist/`, a small synthetic tree with `index.html`, `build-info.json`, `.vite/manifest.json`, two hashed assets with `.br` and `.gz` siblings, one unlisted asset, a `brand/` file and a `txt` notice, plus a `manifest.json` that validates against [`manifest.schema.json`](../../schemas/server/console-manifest/v1/manifest.schema.json).

- [ ] Write tests against the fixture tree: startup verification passes; a changed byte, a missing file, an extra file, an identity mismatch, a missing `build-info.json`, a malformed `.vite/manifest.json`, an unsorted or duplicate manifest and an unknown extension each fail with the named reason; every response carries the exact header set and the CSP equals both the Go constant and the repository file `console/security/csp.txt` read from the module path; `GET /assets/<hashed>` is immutable with `ETag`, `If-None-Match` yields 304, `Accept-Encoding: br` and `gzip` serve siblings with `Vary`, `br;q=0, gzip` serves the gzip sibling, `*;q=0` serves identity, a direct request for `<file>.br` is 404; the unlisted asset is `no-cache`; `/brand/<file>` has `max-age=86400`; `/` and `/devices/42` with `Accept: text/html` return `index.html` `no-cache`; `/devices/42` with `Accept: application/json` is a 404 problem body; `/devices/42` without an `Accept` field returns `index.html`; a malformed, unsorted or duplicate-path `manifest.json` fails with `console_manifest_invalid`; `/api/v1/devices`, `/agent/v1/checkin`, `/ext/x`, `/assets/missing.js`, `/metrics` are 404 problem bodies; `POST /` without content is 405 with `Allow: GET, HEAD`; `GET /` with `Content-Length: 1` or a chunked body is 413 with `Connection: close` and the content left unread; `OPTIONS *` reaches the handler and is 405 with the header set; paths with `..`, `/./`, `//`, `%2F`, NUL, backslash or 1,025 bytes are 404, and no request in the suite or in `FuzzPath` ever receives a `3xx` status; HEAD mirrors GET headers with no body; `console-manifest` output validates against the manifest schema. Require red.
- [ ] Implement the single root handler without `http.ServeMux`, the in-memory map, `//go:embed all:dist` and `manifest.json` under `//go:build ricevanta_console`, the empty FS under the negated tag, the closed MIME map, RFC 9110 weight parsing and `console-manifest` output; no `http.FileServer`, `ServeFile` or filesystem access in the handler.
- [ ] Run `gofmt -l .`, `go vet ./internal/transport/console` and `go test -count=1 ./internal/transport/console`; require pass with and without `-tags ricevanta_console` (the tagged build needs a copied fixture tree in a temporary module, which the test sets up). Add `FuzzPath` over request paths and `FuzzAcceptEncoding` over header values with the negative cases as seed corpora.
- [ ] CI proof: `server-unit` and `server-race`, then the `go-fuzz:transport/console:FuzzPath` and `go-fuzz:transport/console:FuzzAcceptEncoding` leaves once Task 5 registers them; the reviewer's adversarial report covers path handling, header completeness, negotiation and cache rules.

## Task 4. Runtime, health, TLS and graceful shutdown

Owner: implementer; adversarial review required for TLS loading. Own `server/internal/platform/{runtime,health}/` and the `serve`, `check-config` and `console-manifest` subcommands in `main.go`.

- [ ] Write black-box tests that build the binary and run `serve` on a loopback address with a test-generated certificate: `/healthz` is `{"status":"ok"}` while `/readyz` moves `starting` to `ready`; bodies validate against [`readiness.schema.json`](../../schemas/server/health/v1/readiness.schema.json); responses carry `no-store` and no version; `SIGTERM` during an in-flight request lets that request finish, flips `/readyz` to `503 stopping`, logs `stop_requested` and `shutdown_complete`, exits 0; a client that declares a 10-byte body and sends one byte per second, and one that sends a chunked body without end, each get 413 at once over HTTP/1.1, and the server closes the connection within 1 s of the response, its 500 ms `rstAvoidanceDelay` included; `SIGTERM` sent during the trickle still exits 0 within 2 s, the close delay plus `Shutdown`'s polling interval; over HTTP/2 a request that declares content gets 413 at once and the connection closes within 2 s after its last open stream ends, `goAwayTimeout` of 1 s included; a client that stops reading a large response is disconnected within the 10 s write-progress deadline and does not hold `Shutdown`; a TLS client that never completes its handshake is dropped after `read_header_timeout_ms`; `roles: [api, jobs]` exits 2 with `role_blocked` naming the gate, and `check-config` reports the same; a `listen.api` without `tls` exits 2; a `SIGTERM` sent right after start, before `/readyz` reports ready, exits 0 with `stop_requested` and `shutdown_complete` and never ends the process by the signal; an HTTP/2 client over TLS that opens large windows, requests a large asset on four streams and never reads is disconnected by the 10 s `WriteByteTimeout`, and a `SIGTERM` during that stall logs `shutdown_complete` within the write bound rather than `shutdown_timeout`; an HTTP/2 client that drains a few bytes every 5 s holds its stream past the write bound, and a `SIGTERM` during that trickle ends at the shutdown deadline with `shutdown_timeout` and exit 1, the residual spec section 4 states, with the observed hold time recorded in the test output; a configuration error and a stop during configuration loading each log a JSON line at `info` level or above before the configured level applies; a configuration without `roles` exits 2; a key file with mode `0644` exits 3; `tls.mode: none` on loopback serves HTTP/1.1 without HSTS and `tls.mode: file` serves HTTP/2 with HSTS; `console.enabled: true` without the tag exits 3 `console_missing`; every log line is one JSON object with `time`, `level`, `msg` from the catalogue. Require red.
- [ ] Add in-process tests in `internal/platform/runtime` that inject a handler blocking past the deadline and require `shutdown_timeout` and exit code 1 from the runtime's `Run` result, and that inject a stop request at each startup step boundary and require exit code 0 with nothing left open; no build of the binary carries a test hook or reads a test variable.
- [ ] Implement the lifecycle, readiness registry, `http.Server` with the configured timeouts, `DisableGeneralOptionsHandler` and `HTTP2: &http.HTTP2Config{WriteByteTimeout: 10 * time.Second}`, stop sources registered before configuration loads, the content refusal with its expired read deadline and the write-progress deadline through `http.ResponseController`, `signal.NotifyContext`, and the role table with gates.
- [ ] Run `gofmt -l .`, `go vet ./...` and `go test -count=1 ./...`; require pass.
- [ ] CI proof: `server-unit` and `server-race`, then `server-runtime-smoke` (the black-box suite as a named selected test) once Task 5 registers it.

## Task 5. Real console embedding, CI wiring and handoff

Owner: implementer, coordinated with the CI and release owners. Own `.github/workflows/server.yml` additions, `scripts/ci/targets.toml` entries, `server/AGENTS.md` and `instructions/testing.md` wording. Prerequisites: release plan Task 1 (`scripts/release/version.py`) and Task 3 (console identity generation) have landed.

- [ ] Add a `server-console-embed` job: run `scripts/release/version.py --root . --channel <validated channel> --ref <validated ref> --out "$RUNNER_TEMP/identity"` once; copy `build-info.ts` into the console's generated directory and build the console with the foundation commands so `dist/build-info.json` carries that identity; copy `generated.go` into `server/internal/buildinfo/`; copy `console/dist/` to `server/internal/transport/console/dist/` and write `manifest.json` beside it with release plan Task 3's `scripts/release/console_manifest.py`, the manifest's only producer; build with `go build -mod=readonly -trimpath -buildvcs=false -tags ricevanta_console,ricevanta_release ./cmd/ricevanta-server`; run `console-manifest`, validate it against the schema and require byte equality with the written manifest; then run the Task 4 smoke suite against the real tree, including the exact CSP equality with `console/security/csp.txt`, immutable caching only for `.vite/manifest.json` outputs, and a negative run with a mismatched `generated.go` that must fail `console_identity_mismatch`. Once `generated.go` is in the checkout, every `go` command in the job (`build`, `vet`, `test` and `run`) passes `-tags ricevanta_console,ricevanta_release`, because without the tag the package declares each constant twice and does not compile; the smoke suite drives only the built binary. A routing fixture selects the job for changes under `server/`, `console/` or `scripts/release/`.
- [ ] Register the CI selections the earlier tasks prove through, coordinated with the CI owner: `go-fuzz:platform/config:FuzzLoad`, `go-fuzz:transport/console:FuzzPath`, `go-fuzz:transport/console:FuzzAcceptEncoding` and `server-runtime-smoke` in `scripts/ci/targets.toml` with exact commands, wired in `.github/workflows/server.yml` and the receipt inventory, and a routing fixture that selects them for changes under `server/`.
- [ ] Keep `server/AGENTS.md` and the server paragraph of `instructions/testing.md` matching the executable, and label the new commands in `instructions/testing.md`.
- [ ] Refresh the permission coverage fixtures under `schemas/permissions/v1/fixtures/` with their validator: the `deployment-settings` exemption text names the unauthenticated `/healthz` and `/readyz` probes and the `serve`, `check-config`, `console-manifest` and `version` subcommands, and the `documents` digests are recomputed. This step is the server half of the single coverage-refresh task in `TODO.md` that names every drifted document ([permission catalogue spec section 7](../specs/permission-catalogue.md#7-fixtures-and-required-tests)); it runs with that task, not separately.
- [ ] Run `python -B -m unittest discover -s scripts/ci -p 'test_*.py' -v`, `python -B scripts/ci/check_policy.py --root .`, `actionlint .github/workflows/*.yml` and `git diff --check`; require pass.
- [ ] CI proof: `server-console-embed`, `server-runtime-smoke`, the fuzz leaves and `ci-required`; release plan Task 4 then consumes `server/cmd/ricevanta-server`, `server/internal/buildinfo/` and the `-tags ricevanta_console,ricevanta_release` recipe recorded in [release builds section 4](../specs/release-builds.md#4-reproducibility-and-toolchain-admission).

## Acceptance

The slice is complete when the binary serves the real console tree with the exact production headers, reports health and readiness, refuses every blocked role and stops within its bound on CI, with the adversarial reviews of Tasks 3 and 4 attached. It establishes no API, identity, database, enrollment or deployment capability; the deployment slice (analysis section 3.1 row 5) owns Compose and the image, and the console identity slice owns sessions and CSRF.
