# CI hardening implementation plan

Implement [the CI hardening spec](../specs/ci-hardening.md) in ten separate PRs, in dependency order. Both documents require independent `design_reviewer` approval before code starts. The designer authors contracts and does not implement or independently approve them.

Roles: the coordinator owns dispatch, Git, live CI evidence and landing; the implementer owns one task's paths; the troubleshooter owns unknown failures; the independent code reviewer reviews each completed task and confirms fixes. CI, bootstrap and catalogue changes require the adversarial pass. Workers never commit or push. Follow [workflow](../../instructions/workflow.md); use separate worktrees for concurrent writers and keep each review separate from authorship.

Use the project's task-by-task execution workflow, with `superpowers:subagent-driven-development` or `superpowers:executing-plans` as applicable. Each checkbox has a verifiable result. Do not turn unavailable tools, missing targets or absent evidence into skips.

## Contracts and checks

All paths are repository-relative. Commands run at the root unless a working directory is stated. In a workflow's bootstrap step, `python3` is the runner's preinstalled interpreter running the standard-library bootstrap (spec section 8). After the apply step, `python` and `python3` both name the admitted Python 3.14.8, and validator commands run in the venv created from it. Before Task 7 lands, use the existing design environment for lightweight tests and preserve its pins. Implementation commands below are requirements, not checks run by this design task.

- Native qualification remains Linux x64, Windows x64 and macOS ARM64, on the runner labels of [spec section 8](../specs/ci-hardening.md#runner-images-and-lock-platforms): `ubuntu-26.04`, `windows-2025` and `macos-26` once Task 10 lands, and `ubuntu-24.04`, `windows-2025` and `macos-15` before it. Assert actual OS/architecture before tests. These runners do not prove complete endpoint support.
- Existing component tool pins, all 23 main Go fuzz targets required by [extension-loader Task 5](extension-loader.md#task-5-ci-integration), both native loader gates, Rust property budgets, console production CSP in all three engines and both clean console builds remain required. The implemented inventory contains all 23 main fuzz targets and both native loader gates; preserve their tests and exact receipt coverage.
- Read component guides before changing tests. No production runtime behavior, permission name or OS mechanism changes in this plan.
- Light checks run locally. Race, timed fuzzing, extended properties, browsers and native matrices run in CI. Every negative control must fail for its intended defect, not a missing tool or broken fixture setup.
- Each task starts with the named failing regression, records that failure, implements the contract, runs the same command successfully, and obtains independent code review. The coordinator reads actual run URLs and SHAs before landing.
- Update consumer documentation in the same task that changes behavior. Do not leave `wip/**` pushes, dispatch substitutes or duplicate validator instructions described as the normal gate.

Review focus: stale integration SHAs after base movement (Task 2); deleted matrix rows despite green matrix summaries (Task 2); nested helpers returning zero without measurement and harness substitution through repository configuration (Task 4); semantically changed catalogue with a bumped revision (Task 5); validator environments that diverge after admission (Task 6); tool download chains, warm-cache bypasses and host packages (Task 7); a browser engine missing from one host or testing different bytes (Task 8); a job, matrix row or lock platform left on a superseded runner label or action pin (Task 10). Each receives an explicit negative control below.

## Schema validation and design checks

The design-owned schema uses [Draft 2020-12](https://json-schema.org/draft/2020-12/json-schema-core). From the repository root, validate each synthetic example without network references:

```sh
python3 -B - <<'PY'
import json
from pathlib import Path
from jsonschema import Draft202012Validator
root = Path('schemas/ci/v1')
schema = json.loads((root / 'contracts.schema.json').read_text())
Draft202012Validator.check_schema(schema)
validator = Draft202012Validator(schema)
examples = json.loads((root / 'examples.json').read_text())
for example in examples:
    validator.validate(example)
print(f'PASS CI schema and {len(examples)} examples')
PY
```

This light `Local and CI` command validates shape only.
