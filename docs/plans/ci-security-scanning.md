# CI security scanning implementation plan

Implement [the security scanning contract](../specs/ci-security-scanning.md) without changing runtime code or weakening the existing required gate. A `design_reviewer` must approve both documents before code starts. Two `implementer` jobs and bounded `troubleshooter` tasks own paths within one PR. Each troubleshooting handoff requires the primary agent to freeze overlapping implementation paths first. The primary agent coordinates their frozen CLI handoff and owns account operations, Git, evidence review and landing. Writers do not review their own changes.

Command checks must parse the complete production argv with the pinned native `ci` parser before relying on scanner fixtures. Require acceptance without `--strict`, and prove `ci --strict` is rejected before scanning. Retain supported `scan --strict` in cold controls. Test that zero-exit native report/core errors, including warning-level and special interfile-analysis errors, dependency-parser errors, timeouts and incomplete scans still fail the local gate. Keep `--no-suppress-errors`, product/engine selection, upload proof and severity gates unchanged; do not infer completion from successful argument parsing.

Skipped-target checks require the fixed `--verbose` flag and a native `paths.skipped` array. Test an oversized source target and an excluded target: sanitized diagnostics must retain each repository-relative path and reason, while successful supported scanning may still pass. Reject absent or malformed skip evidence; preserve the existing failure policy for scan errors and missing supported dependency inputs. Prove each original method runs once with unchanged arguments, returns unchanged objects and propagates exceptions. Reject wrong commit/repository/product sets, dry-run/saved-config/partial modes, supplied merge bases, handler/scan-ID swaps, missing or duplicate observations, completion `success: false`, stale summaries and mismatched invocation IDs. A success summary with failed CLI or local severity gate must still fail. Verify raw rule bodies, token values, findings and exception text never appear in published summaries. Confirm the hooks against the actual admitted CLI before treating fixture tests as upload or execution proof.

Code-work checks use the actual plan serialized inside `CoreRunner.invoke_semgrep_core` and its returned native core paths. Reject Java-only Code rules with Go-only SCA targets even when dependency parsing and upload succeed. Reject SCA-only pairs, unused Code rules, excluded Code targets, display-only plans, invalid rule indexes, absent or duplicate core/serialization calls, failed core execution, and pairs whose target or rule was skipped. A supported Code pair with no finding must pass this evidence check when native core reports the target scanned and all other gates pass. Verify configured counts stay distinct from applicable Code counts and that mixed-product CLI paths cannot replace execution evidence. Keep rule bodies, source text and skip details private. Do not require every file or language to have a rule.

CI qualification: cold admitted tools run synthetic positive and negative controls without credentials. Gitleaks includes a committed-then-deleted secret and a merge-only secret. Semgrep uses explicit `scan --oss-only --no-rewrite-rule-ids --strict` inside the admitted image with local fixture rules. Run required Go/Python/TypeScript positive controls separately from isolated Rust and Vue probes; require exact expected rule IDs and targets for the required controls. Retain token-free Pro hash, marker, installed-engine and version admission. Use supported lockfile fixtures and sanitized SCA failure fixtures, then require the actual authenticated `ci --code --supply-chain --pro` repository scan for production Code/SCA execution, dependency coverage and upload proof. Confirm that scan stays on the integration commit even when head differs. An OSS Vue probe cannot qualify Pro-only framework or template analysis. Missing real supported scan evidence fails; unsupported or unqualified analysis stays explicit.

Cold-control tests require explicit OSS selection, disabled rule-ID rewriting and no token, and reject fake-token/authentication-bypass paths. Verify the production command still requires Pro and that successful cold controls cannot replace authenticated completion evidence or produce its receipt. Test that optional unsupported Rust/Vue outcomes cannot hide failures in required controls or unrelated probe errors. Preserve existing admission failure tests for a missing or wrong Pro payload. Do not add token-bearing synthetic execution or an automatic OSS fallback to make qualification pass.
