# RADIUS design

How Ricevanta authorizes VPN and network access: the network-access identity and its binding to issued certificates, certificate-derived identity authorization, EAP-TLS termination, transport, authorization policy, accounting, Change of Authorization (CoA) and Disconnect, the endpoint side per OS, audit and failure behaviour, and high availability. The scope is `../blueprint.md` section 3.6. The `radius` role's listeners, key custody and deployment are in `../architecture.md` sections 3.1, 4 and 5 and `backend.md` sections 2, 3 and 6; certificate issuance is in `pki.md`; device compliance comes from the MDM design (`mdm.md`); gateway attributes and configuration are in `../specs/radius-gateway-profiles.md`. Decisions: RAD-01 to RAD-06, building on PKI-01, PKI-02, BE-03, BE-06, BE-07 and EV-03, in `../decisions.md`. This file defines the RADIUS contracts for C6 in `../analysis.md`; exact accounting, session-control, evidence and recovery schemas and gateway proofs remain implementation blockers in that file. Claims resting on vendor community pages or untested behaviour are marked "verify".

Abbreviations: NAS (network access server, the gateway or authenticator that sends RADIUS requests), SAN (subject alternative name), UPN (User Principal Name, a SAN `otherName`), MSK (master session key), EMS (TLS extended master secret, RFC 7627), RadSec (RADIUS over TLS, RFC 6614).

## 1. Network-access identity

Every accept names one network-access identity, and every identity is bound to certificates the Ricevanta PKI issued from the network-access issuing CA (`../architecture.md` section 4). Agent identity and management certificates never authorize network access: gateways and the EAP-TLS server trust the network-access issuing CA only.

- An identity is a row in the `pki` schema: `netid`, kind (`device` for a machine certificate, `user_device` for a user's certificate on one device), device uid, user uid for `user_device`, certificate profile, state. `netid` is `n` followed by 26 lowercase base32 characters of 128 random bits, minted by `jobs`, unique across the organization by a database constraint, never reused after retirement, and stable across renewals of the same device, user and profile.
- `jobs` writes the subject and SAN from that row and ignores any name in the certificate signing request (`pki.md` section 3): SAN `otherName` UPN `<netid>@<realm>`, SAN `dNSName` `<netid>.<realm>` and subject `CN=<netid>`, where `realm` is the organization's network realm setting. One value in three places lets FortiGate (UPN or DNS name), Cisco ASA (UPN or CN) and 802.1X supplicants (which send the CN as their EAP identity by default on Apple platforms) carry the same name. The identity-name table, not the certificate table, uniquely maps each UPN and DNS value to one identity. Certificate generations reference that identity and may carry the same names during the renewal overlap.
- Network-access certificates are issued only to approved device records (PKI-02, `pki.md` section 1). Renewal issues a new certificate for the same identity; the superseded certificate is revoked with reason `superseded` when the agent reports the new one installed, or 24 hours after issuance, whichever comes first.
- Revoking an identity's certificates, suspending its device (certificates placed on hold), retiring it (certificates revoked) as `mdm.md` section 1.2 defines, or retiring the user of a `user_device` identity changes the identity state and triggers session control (section 8).

A name that maps to no issued, unrevoked, unexpired certificate is rejected. In the certificate-derived architecture the gateway validates the certificate and RADIUS sees only a string; the string is trustworthy only because Ricevanta minted it, wrote it into exactly one identity's certificates, and the gateway trusts no other CA for that tunnel. A guessed name, a name of a retired device or a name typed into a password prompt is rejected with reason `identity_unknown` or `request_shape`. A name from another CA is rejected only because the gateway trusts no other CA for that peer or tunnel group: a certificate from any CA the gateway trusts that carries a real `netid` passes the lookup and the request-shape check. That configuration is a requirement of `../specs/radius-gateway-profiles.md` sections 4.3 and 5.2 (one `user peer` CA on the FortiGate; an ASA trustpoint `validation-usage` or a certificate map limited to the Ricevanta issuer), and qualification tests a foreign certificate carrying an issued `netid` (`../specs/platform-qualification.md` section 4).

## 2. The authorization snapshot

The `radius` role answers from an in-memory snapshot and never reads authoritative tables per request, following the handler rules of `backend.md` section 3 and BE-03.

- The `radius` module owns `radius.subjects`: one row per identity with `netid`, the issued certificates (serial, issuer, SHA-256 fingerprint, validity, revocation state), device uid, state, labels and groups, the compliance state with the time it was entered and the latest signed compliance statement (`../specs/baseline.md` sections 4.2 and 4.4), which replicas verify against the policy-signing certificate before use, the user uid with groups (BE-01) and its source (`certificate` for `user_device`; `device_link` for the user of a `device` certificate, taken only from the device's `assigned` link, otherwise its `enrollment` link, and never from a `session` link or the derived primary user, because the agent reports sessions and agent state must not become authority for network access; the `user` is absent when neither link exists), and a version from one sequence. The module's materializer runs in the `jobs` role, reads the `pki`, `devices`, `mdm` and `identity` modules through their Go interfaces (BE-04), and writes the rows. It runs a pass at least every 15 seconds and writes the heartbeat only after a pass that read every source module and wrote all rows up to a version; the heartbeat carries that version, and a replica whose own version is below it rejects with `authority_stale` until it has applied the rows through that version (section 10).
- `radius` replicas hold read-only database credentials on `radius.subjects`. A replica loads all rows at start, then applies rows above its last version on a `NOTIFY` from the materializer and on a 5-second poll. At 20,000 devices the snapshot is a few tens of megabytes (measured, section 11).
- The compiled `network` authorization table (`policy.md` section 3.3) reaches replicas through the `policy` module's interface with read-only credentials, held in memory and refreshed on a version notification; no exposed role can write policy rows (BE-03).
- Revocation, suspension and compliance changes propagate through the same channel; the target is 5 seconds at the 99th percentile from commit to every replica, measured.

## 3. Certificate-derived identity authorization

The gateway terminates the client's TLS or IKE, validates the client certificate against the network-access issuing CA with revocation checking through the `pki` module's OCSP responder or CRL, and asks Ricevanta to authorize the name it extracted. Gateway configuration is in `../specs/radius-gateway-profiles.md` sections 4 and 5.

1. The gateway sends `Access-Request` over RadSec or UDP. The replica drops a packet whose source matches no enabled `RadiusGateway` before parsing it, and silently discards one that fails the authenticity checks of section 5.
2. The replica checks the request shape the gateway's profile defines: on FortiGate, `User-Password` equals the gateway's binding token, a 32-byte random value set as the peer's `mfa-password` and never known to users (verify that FortiOS sends `mfa-password` as `User-Password` and what it sends when the value is empty); on Cisco ASA, `Service-Type` is Authorize-Only and no password is present (verify that an `authorize-only` server group sends exactly that). Any other shape on a certificate-derived path is rejected with `request_shape`, so a password login on the same gateway that reaches the same server cannot be turned into a certificate-derived accept.
3. `User-Name` is normalized in the form the profile names (UPN, DNS name or CN) and looked up in the snapshot; the lookup cannot tell which CA issued the certificate the gateway saw (section 1). No row, an identity not `active`, or no current certificate that is unrevoked and within validity by server time is a reject with the specific reason.
4. The device must be `active`. Policy evaluation (section 6) then decides with the device, user, groups, compliance state, identity-level facts, gateway and time. A name-only request has unknown certificate generation; no issued generation is selected to fill missing evidence.
5. The decision record is committed (section 10), and only then does the replica answer `Access-Accept` with the profile's attributes and `Class` carrying the decision uid, or `Access-Reject`.

A name-only request proves the network identity, not the certificate generation the gateway authenticated. The limitation applies even when the snapshot contains only one eligible generation; renewal may overlap generations, and the request supplies no certificate evidence. The gateway checks the actual certificate and Ricevanta checks identity eligibility. Exact-generation policy requires EAP-TLS or a separately qualified gateway profile that authenticates and transmits the exact certificate binding for this request; the FortiGate and ASA name-only profiles do not provide that binding. RadSec mutual TLS or a per-gateway secret authenticates the gateway, not the missing certificate fields.

## 4. EAP-TLS termination

Gateways that pass EAP to RADIUS (802.1X authenticators, FortiGate IKEv2 dialup with native clients) let Ricevanta validate the certificate itself. EAP-TLS is implemented in-project in Go (RAD-01), seeded from the MIT `radius-eap` state machine of the Ctere1 fork at a pinned commit and interoperability-tested against `wpa_supplicant` and the native supplicants of section 9.

- TLS engine: Go `crypto/tls` as the server over an in-memory connection that the EAP state machine feeds with reassembled TLS records. Versions TLS 1.3 (RFC 9190) and TLS 1.2 (RFC 5216); TLS 1.0 and 1.1 are refused. TLS 1.2 requires EMS, since Go's `ExportKeyingMaterial` returns an error without it from Go 1.22, and that refusal is the rule, not a fallback. TLS 1.3 suites are the three Go offers and are not configurable; TLS 1.2 suites are ECDHE with AES-GCM or ChaCha20-Poly1305 only. Client keys: ECDSA P-256 and P-384, RSA 2048 and above.
- Server identity: an EAP server certificate from the server issuing CA with a configured `dNSName`, held by the `radius` role under its role-scoped data key (`backend.md` section 6). Supplicant profiles pin the Ricevanta root, the issuing CA and that name, as Windows 11 requires.
- Client validation: the chain must run through the network-access issuing CA to the Ricevanta root, with `clientAuth` extended key usage and the network-access profile; the certificate's SHA-256 fingerprint must equal a certificate of the identity named in its SAN in the snapshot, current and unrevoked, and within validity by server time. Revocation is the `pki` module's authoritative state delivered in the snapshot, the same state its CRL and OCSP responses are built from, so no request waits on an OCSP fetch. The identity always comes from the certificate; `User-Name` and the EAP-Response/Identity are never used for authorization, and supplicant profiles send an anonymous outer identity `anonymous@<realm>` where the OS allows (RFC 9190 section 2.1.8).
- Keys: TLS 1.3 derives the MSK, EMSK, Method-Id and Session-Id with the exporter labels of RFC 9190 section 2.3; TLS 1.2 uses the RFC 5216 key material through the RFC 5705 exporter with the label `client EAP encryption` and no context. The MSK goes to the NAS in `MS-MPPE-Recv-Key` and `MS-MPPE-Send-Key` (RFC 2548) in the split that interoperates with `wpa_supplicant` and hostapd. TLS 1.3 sends the protected success indication (one application-data octet `0x00`) before EAP-Success.
- Resumption is excluded: `SessionTicketsDisabled` is set, no NewSessionTicket is sent, and every authentication runs a full handshake with fresh revocation, device and compliance checks. RFC 9190 lets a server require a full handshake, and Windows 11 never resumes EAP-TLS.
- Fragmentation (RFC 5216 section 2.1.5): at most 1,000 octets of TLS data per EAP request, lowered when `Framed-MTU` is smaller; fragments are acknowledged with empty EAP-TLS messages; a reassembled TLS message is capped at 64 KiB and a conversation at 40 round trips; RADIUS packets stay within 4,096 octets with `EAP-Message` split into 253-octet attributes.
- Conversation state is per replica (BE-07): keyed by gateway and a 128-bit random `State`, held 30 seconds idle and 60 seconds in total, capped per replica (default 2,048) and per gateway; on expiry, eviction or a replica restart the conversation is abandoned and the supplicant restarts it. Duplicates are matched by EAP Identifier.

After the handshake, the device, compliance and policy steps of section 3 steps 4 and 5 apply unchanged.

## 5. Transport and gateway registration

A `RadiusGateway` registration names the gateway, its profile, allowed source prefixes, enabled architectures, transport, the CoA target address and port, and its secrets. Creating a gateway registration, widening its source prefixes or enabling an architecture is a protected action (BE-02). Shared secrets and binding tokens are generated by Ricevanta (32 random bytes), shown once, sealed by `api` to the `radius` role's X25519 public sealing key (HPKE base mode, RFC 9180) so that only `radius` replicas can open them, and rotated with two values valid during a window. They never appear in GitOps files or API reads.

Routine sealing-key rotation assumes all participating replicas and deployment credentials are trusted: `jobs` generates a new X25519 pair under the current role wrapping key, trusted replicas re-seal stored secrets to its public key, `jobs` validates and installs the ciphertext, `api` switches to that key, and the old key is removed after the ordinary overlap. This procedure does not recover from compromise.

Compromise recovery excludes every copied credential and wrapping root before replacement private material is distributed:

1. Isolate the affected host or pod and stop its gateway traffic. Revoke its database, deployment, secret-store and KMS access, terminate existing database and RadSec connections, and revoke its TLS certificates. Rotate any shared credential it held across all trusted replicas. A replacement cannot inherit its service account, mounted credentials or secret-watch access. If the control plane or `jobs` custody is affected, keep serving sealed under `backend.md` section 6.1.
2. From an unaffected control plane, create a fresh role wrapping key, X25519 sealing pair and TLS keys under a never-reused custody generation. Provision the wrapping key through a trusted channel to rebuilt or verified replicas only; never encrypt it under the old role key or grant old database, deployment or KMS principals access to it. New private-key ciphertext is readable only by replacement principals. Fence obsolete credentials and custody generations before publishing the new public sealing key; old secret-update request rows cannot enter the new generation.
3. Generate fresh gateway shared secrets and binding tokens, rather than merely re-sealing compromised values. Apply them through trusted gateway administration, remove the old values without an overlap, and enable the registration only after both ends confirm the new generation. A gateway that cannot complete the cutover stays disabled. Remove old wrapping and private keys from serving deployments; retained backup ciphertext remains classified as compromised and cannot authorize the replacement generation.
4. Verify that all keys, credentials, connections and ciphertext copied from the compromised replica can neither read nor unwrap replacement material nor submit a secret update. Test retained database sessions, deployment watches and KMS permissions, not only new logins. The exact custody records, cutover and credential-revocation proofs remain implementation blockers (`../analysis.md` section 3).

- RadSec (RFC 6614, TCP 2083) is the default where the gateway supports it. Mutual TLS: the `radius` role presents a server certificate from the server issuing CA; the gateway presents a certificate from the `network-gateway` profile, issued by the server issuing CA from a certificate signing request the administrator uploads for that registration, or an external certificate pinned by SPKI (subject public key info) SHA-256 in the registration. The replica binds the connection to the registration whose pinned key matches, never by name alone. TLS 1.2 or 1.3, with the TLS 1.2 suites of section 4. Over RadSec the RADIUS shared secret is the fixed `radsec`, and requests without `Message-Authenticator` are accepted, as the transport authenticates them.
- UDP (1812 authentication, 1813 accounting) where RadSec is unavailable, which includes the Cisco ASA. Every `Access-Request` must carry a valid `Message-Authenticator` and is silently discarded otherwise; this is not configurable per gateway. Every response carries `Message-Authenticator` as its first attribute. These are the BlastRADIUS mitigations of `draft-ietf-radext-deprecating-radius`, an Internet-Draft, not an RFC. A `Proxy-State` attribute is refused, since Ricevanta accepts no proxies. Accounting requests are checked with the RFC 2866 request authenticator.
- Packets from a source outside every gateway's prefixes are dropped before parsing and counted. Rate limits: a token bucket per gateway (default 200 requests per second, 50 new EAP conversations per second) and one per replica; excess is dropped and counted.
- Duplicate detection follows RFC 5080 section 2.2.2: requests keyed by gateway, source address and port, Identifier and Request Authenticator; an answered duplicate gets the cached response for 30 seconds, an unanswered one is discarded.
- `layeh/radius` provides the packet codec and dictionaries only. It does not verify `Message-Authenticator` and has no RadSec, so listeners, TLS framing, authenticity checks and the duplicate cache are in-project; changes to its files stay MPL-2.0 (`../licensing.md`).

The `radius` role can run Go's FIPS 140-3 mode (`GODEBUG=fips140=on`) for gateways in FIPS mode; EAP-TLS cipher suites then narrow to the approved set (verify the module's validation status before claiming FIPS operation).

## 6. Authorization policy

`network` policies (`../specs/policy-envelope.md` sections 2 and 4) evaluate in the `radius` role with `cel-go` over the snapshot. Variables follow the required evidence contract in `../specs/cel-profile.md` section 5: `device` with `state`, `compliance` (`compliant`, `grace`, `noncompliant` or `unknown`, `../specs/baseline.md` section 4.2) and `compliance_time`, beside the existing `compliant`; `user` with `groups` and `source` (`certificate` or `device_link`, section 2); `certificate` with identity-level `identity`, `kind`, `profile` and `binding` (`exact` or `identity_only`), plus generation-specific `serial`, `fingerprint`, `issuer`, `not_before`, `not_after` only for an exact binding; `gateway` (`name`, `profile`, `labels`); `access` (`method` `eap_tls` or `certificate_derived`, `medium` `vpn`, `wired` or `wireless`, `ssid`, `nas_port_type`, `calling_station`, `tls_version`); `now`. Freshness is part of the compliance state: a device without a verified check-in within `staleAfter` is `unknown`.

For name-only requests, `certificate.binding` is `identity_only` and generation-specific keys are absent, not null or copied from a snapshot certificate. Exact fields describe only the authenticated generation. Compilation and gateway admission reject a policy deployment that needs those fields on a name-only path; conditional field access must have a proved exact-binding guard, otherwise validation rejects it. Unknown dynamic field access is rejected when the compiler cannot prove its evidence needs. Loss or ambiguity of required evidence at runtime rejects access with `certificate_binding_unknown`, rather than skipping the policy or filling fields from another generation. These rules also apply during session re-evaluation; exact session evidence stays bound to the original generation.

```yaml
apiVersion: ricevanta.io/v1alpha1
kind: Policy
metadata: { name: vpn-finance-compliant }
spec:
  domain: network
  scope: { include: [ { users: { groups: [finance] } } ] }
  trigger: { events: [authentication.logon] }
  condition: device.compliance == "compliant" && gateway.profile in ["fortigate", "cisco-asa"]
  actions: [ { type: accept, params: { profile: vpn-finance } } ]
  priority: 600
```

- Before policy, the fixed gates of sections 3 and 4 apply: authenticated gateway, valid request shape, issued and unrevoked certificate, active device. Policies cannot accept what a gate rejected.
- No matching enforcing policy is a reject (`no_policy`). The highest priority decides; at equal priority `reject` wins over `accept`; two accepts at equal priority naming different profiles reject with `policy_conflict` and raise an alert. `monitor` records the outcome only. A CEL error rejects (`policy_error`); `enforcement.fail` is fixed at `closed` for this domain.
- `accept` names a `NetworkAccessProfile` (`../specs/radius-gateway-profiles.md` section 2), which each gateway profile maps to its attributes; `alert` raises an alert beside either outcome.
- Group membership and labels come from the snapshot and change with it, not with a policy compile, so a removal from a group takes effect at the next authentication and, through section 8, on every possibly active session.
- Changes that widen network access (an exception, a broader scope, a weaker condition, a new or higher-priority `accept`) are protected actions under BE-02, as for DLP and EDR policies.

## 7. Accounting

Accounting (RFC 2866) arrives on UDP 1813 or the RadSec connection. A replica answers `Accounting-Response` only after the record is committed; when it cannot commit it does not answer, and the gateway retries or fails over, as RFC 2866 section 2 requires.

- Each committed accept creates a possibly active decision record before the reply, even if Accounting-Start never arrives. A linked session has an internal uid, gateway registration and boot generation, `Acct-Session-Id` (plus `Acct-Multi-Session-Id` where sent), echoed decision uid from `Class`, netid, device and user, exact certificate evidence or `identity_only`, session selectors, original authorization attributes and a qualified upper expiry bound. Reused NAS session ids never reuse the internal uid. An event without a proved decision link remains unlinked; a name match is correlation, not proof of the decision or session generation.
- Keep immutable accounting events with arrival time, `Event-Timestamp` where supplied, `Acct-Delay-Time`, `Acct-Session-Time`, status, counters with gigaword carry and termination cause. Event time uses a profile-qualified NAS clock or an uncertainty interval derived from arrival minus delay; arrival order never defines lifecycle order. A semantic deduplication key excludes changing retransmission delay and packet identifiers. [RFC 2866 section 5.2](https://www.rfc-editor.org/rfc/rfc2866.html#section-5.2) describes delay-derived approximate event time; [RFC 2869 section 5.3](https://www.rfc-editor.org/rfc/rfc2869.html#section-5.3) defines the NAS event timestamp.
- Start, Interim and Stop transitions are idempotent for the exact internal session and boot generation. A delayed Start cannot reopen a stopped generation; a delayed Stop cannot close a newer one. Keep unmatched Stop evidence as a tombstone until matching evidence arrives. Counters and lifecycle watermarks never regress. Ambiguous timing, id reuse or linkage preserves possibly active state and raises an accounting-health event.
- Persist gateway boot generations from profile-qualified reboot evidence. Accounting-On or Accounting-Off applies only to sessions proved to precede that event's boot boundary; a delayed or duplicate event cannot advance the current boot generation or close later sessions. Neither status alone proves that user sessions ended. Close with `nas_reboot` only when the qualified gateway behavior proves termination of those exact sessions; otherwise retain them as possibly active.
- Three missing interim intervals mark `accounting_stale`, not closed. Section 8 targets possibly active, stale, unlinked and awaiting-Start records. Close only after a proved Stop, qualified Disconnect or reboot termination, or a qualified enforced expiry of that exact session. The expiry derives from the original enforced timeout and a proved upper establishment-time bound, never the last accounting arrival or an arbitrary grace period. CoA cannot extend that bound. Missing timeout or timing proof leaves the record possibly active.
- Retention follows EV-01 for closed evidence (default 30 days), configurable. Possibly active records remain available to session control regardless of that retention window; the console distinguishes observed activity, stale accounting and ambiguous lifecycle.

Exact event and session schemas, semantic deduplication, boot-generation evidence, time-error bounds and transition fixtures are implementation blockers in `../analysis.md` section 3. [RFC 5080 section 2.2.1](https://www.rfc-editor.org/rfc/rfc5080.html#section-2.2.1) permits accounting retries until acknowledgement; the packet cache of section 5 is not a lifecycle deduplication rule.

## 8. Change of Authorization and Disconnect

Triggers: certificate revocation, an identity, device or user leaving `active`, compliance, group or label changes, and publication of a `network` authorization table. `jobs` re-evaluates every affected possibly active record against one committed authority projection. Name-only evidence cannot prove that a session used another eligible certificate; revocation of a generation therefore targets every possibly active name-only session of that identity with Disconnect. Exact session evidence may exclude a different generation.

1. Maintain one desired-state row per internal session uid with `(recovery_epoch, desired_version)`, source authority versions, outcome and canonical attribute set. `jobs` serializes writes for that session, increments the version without reuse and supersedes older unsent work. Recheck source authority before publication so an older evaluation cannot overwrite a newer state. Keep the last proved applied state and every unresolved transmission separately from desired state.
2. Claim the session, not independent control rows. At most one dispatcher may transmit for a session. A durable dispatch fence, current desired version, live authority fence and exact session selectors are checked before each send and retry. Persist the packet identity, desired version and attempt before sending. Taking over after a crash cancels obsolete unsent work and reconciles transmitted work; `SKIP LOCKED` alone cannot fence a sender or packet already in flight.
3. Disconnect for reject. For an accepted state change, compare the last proved applied attributes with the complete desired set, even when the profile name is unchanged. CoA is permitted only when the exact old-to-new transition, additions, replacements, removals, atomic application and stale-packet exclusion are qualified for that gateway variant (`../specs/radius-gateway-profiles.md` section 3.1). Any unsupported removal, unknown applied state or unproved ordering selects Disconnect and fresh authentication.
4. A transmitted obsolete CoA is unresolved until its possible application and replay are excluded. Stop its retries immediately; do not send a later CoA or grant while an older packet can still overwrite it. An ACK establishes only that attempt's qualified result, never the current desired state. Late replies update their own attempts and cannot lower the applied version or complete newer work. A local version is not a RADIUS wire-order guarantee. Without a qualified gateway barrier or expiry-and-replay proof covering every older transmission, use Disconnect, confirm termination, and require a new session uid and current authentication.
5. Send RFC 5176 packets to the qualified target port. Disconnect carries only the qualified session selectors plus `Event-Timestamp` and `Message-Authenticator`; CoA also carries the exact qualified authorization transition. Identical retries preserve the RFC packet identity and source port; retry at most three times only while the version and fences remain current. Timeout, sender loss or unverifiable reply leaves `control_unknown`, blocks further CoA and triggers Disconnect reconciliation. A NAK, including 503, closes a record only when the exact-generation selector and gateway qualification prove that session is absent. Otherwise retain possible activity and alert. `jobs` alerts on unknown outcomes, NAKs without absence proof and work unclaimed after 30 seconds.

Mass changes are rate-limited (default 20 requests per second per gateway); progress reports desired, proved applied, disconnected and unknown counts. Gateways without qualified Disconnect use only a qualified enforced timeout (default 8 hours for VPN, 1 hour for 802.1X with reauthentication). The original session's bound remains in force and the console shows the residual access window. Failure to prove either termination or that bound blocks the required gateway unit; alerts do not establish revocation.

Implementation blockers: exact desired-state, attempt and fence schemas, the per-session send/retry/takeover protocol, packet-exclusion and session-selector proofs, and fault-injection interleavings. The journal protocol in `backend.md` section 6.1 is also required; neither a database claim nor a journal writer fence orders packets the gateway already holds.

## 9. Endpoint side per OS

The device holds the network-access key and the client that presents it; issuance follows `pki.md` and delivery of payloads follows `mdm.md`. The agent adds no resident process or memory for RADIUS: renewal of an agent-managed network-access certificate uses the private device-signed protocol at two-thirds of its lifetime, while native payload and third-party clients use standard ACME (`pki.md` section 2) and supplicant profiles are written on policy change.

| | macOS | Windows | Linux |
|---|---|---|---|
| Key and certificate | Apple MDM ACME payload with a hardware-bound Secure Enclave key for 802.1X and the built-in IKEv2 client; for FortiClient and Cisco Secure Client, an identity in the System keychain those clients can read (verify whether they can use a hardware-bound identity) | TPM key through the Microsoft Platform Crypto Provider in the machine store (`device`) or the user store through the session helper (`user_device`), used by the native supplicant and IKEv2 client and by FortiClient and Secure Client (verify for both) | TPM key through `tpm2-pkcs11` for NetworkManager; FortiClient and Secure Client read file or NSS stores (verify), so their key is a root-only or user-only software key flagged per device |
| 802.1X supplicant | MDM Wi-Fi and Ethernet payloads naming the ACME identity, EAP type 13, the pinned CA and server name; EAP-TLS 1.3 from macOS 14 | WLAN and LAN profiles applied by the agent or OMA-DM; EAP-TLS uses TLS 1.3 by default and never resumes | NetworkManager connection written by the agent with a `pkcs11:` key URI, `wpa_supplicant` underneath |
| VPN client | FortiClient or Secure Client (certificate-derived); built-in IKEv2 with EAP-TLS to FortiGate (verify) | FortiClient or Secure Client (certificate-derived); native IKEv2 with EAP-TLS to FortiGate | FortiClient or Secure Client (certificate-derived); strongSwan through NetworkManager with EAP-TLS to FortiGate (verify) |

OS-imposed limits: the Linux VPN clients' key storage and third-party access to Secure Enclave identities on macOS are vendor limits pending verification; where confirmed they are recorded in `../platform-support.md` with the software-key flag shown per device, as for Linux without a TPM.

## 10. Audit, failure behaviour and metrics

Every decision, accounting record and session-control outcome is an OCSF event (EV-03, `../specs/ocsf-profile.md`) sharing a correlation uid: `authentication` (3002) activity Logon with status success or failure, `status_detail` the reason code, `auth_protocol_id` 9 (EAP) with `auth_protocol` `EAP-TLS` or 99 with `certificate-derived`, `certificate` with serial, issuer and fingerprint only for exact observed binding, the device, user, gateway, snapshot version, compliance state and time, and the `network` table version and policy that decided; `network_activity` (4001) Open, Traffic and Close for accounting Start, Interim-Update and Stop with `traffic` counters; `network_remediation_activity` (7004) Evict for Disconnect-Request and Other for CoA-Request with `command_uid` the session-control attempt.

Name-only decisions record `netid`, `binding = identity_only` and unknown generation in the Ricevanta evidence fields; they omit the OCSF certificate object and never fill it from inventory. Accounting retains that original evidence limit.

Session-control events record desired and attempt versions, applied-state proof or `control_unknown`, not merely ACK as current success. Exact OCSF extension fields remain a schema blocker (`../analysis.md` section 3).

Reason codes: `accepted`, `request_shape`, `identity_unknown`, `certificate_revoked`, `certificate_expired`, `certificate_unknown`, `certificate_binding_unknown`, `device_not_active`, `no_policy`, `policy_reject`, `policy_conflict`, `policy_error`, `eap_tls_failed`, `eap_timeout`, `authority_stale`, `record_failed`.

Decision rule: network access fails closed. A replica answers `Access-Accept` only after the decision event is committed to PostgreSQL with synchronous commit, through a group commit of at most 10 milliseconds, so there is no unrecorded accept. When PostgreSQL is unreachable, accepts cannot commit and every request is rejected with `record_failed`, accounting goes unanswered, and rejects are written to the structured log and counted. When the materializer heartbeat is older than 120 seconds (configurable from 30 seconds to 15 minutes), because `jobs` or the `pki`, `devices` or `mdm` data behind it is unavailable, revocations may be missing and the replica rejects with `authority_stale`; a failed pass writes no heartbeat, so a partial read of the sources ages the heartbeat the same way. A replica whose own snapshot version is below the heartbeat's version rejects with the same reason. A replica that cannot confirm its `network` table is the published version for the same 120 seconds also rejects with `authority_stale`. Operators who need RADIUS during database maintenance run PostgreSQL with high availability; there is no cached-accept mode.

`jobs` audits accepts within one minute: for exact bindings, verify that the observed certificate belonged to the identity and was unrevoked at decision time, allowing the propagation bound; for name-only bindings, verify identity eligibility without claiming which certificate the gateway used. Both checks verify the active device and committed policy decision. Raise a critical alert on a mismatch or accounting with no proved committed-accept link.

Metrics on `/metrics`: requests by gateway, code, outcome and reason; dropped packets by cause (unknown source, authenticator, missing `Message-Authenticator`, rate limit, duplicate); decision and commit latency histograms; EAP conversations active, evicted and round trips; snapshot age and version lag; session-control outcomes; accounting commit failures.

## 11. High availability, scale and performance

Docker Compose runs the role in the all-roles container. Helm runs two or more `radius` replicas behind separate UDP and TCP `LoadBalancer` services with local traffic policy and client-IP hashing (BE-07), so a gateway's packets, EAP conversation and RadSec connections stay on one replica; gateways list a primary and a secondary address. Client-IP hashing concentrates a gateway's load on one replica, which suits the few large gateways a deployment has; a replica loss abandons its EAP conversations and the supplicants restart them.

Targets, measured on the qualification hardware, not assumed (`../specs/platform-qualification.md` section 7): certificate-derived decision under 20 ms at the 99th percentile including the commit; EAP-TLS server work under 50 ms per authentication excluding round trips; per replica with 2 vCPU, 300 EAP-TLS authentications and 3,000 certificate-derived decisions per second; a reconnect storm of 20,000 endpoints within 5 minutes; snapshot memory and EAP conversation memory within the replica's limit at the cap.

## 12. Trust boundaries

A compromised `radius` replica holds its TLS keys, the gateway secrets and read access to the snapshot. It cannot mint identities: it holds no CA key and cannot write identity, certificate, device, approval, policy or compliance rows or create session-control requests (BE-03), and it cannot change another replica's decisions. Within its own answers it can accept a request the policy would reject, since a RADIUS server is the gateway's authority. That reach is bounded: in the certificate-derived architecture the gateway still requires a certificate from the network-access issuing CA and its private key; the `jobs` accept audit and the accounting link expose accepts without a valid committed decision; and the operator excludes the compromised host, copied credentials and wrapping key before distributing replacement private material and cutting over gateway secrets (section 5). It can also forge CoA and Disconnect requests to any gateway whose secret it holds; the gateway's accounting and the `jobs` audit of session attributes against committed decisions expose a session whose attributes exceed its decision. It can also withhold a Disconnect-Request it claimed; `jobs` alerts, fences the sender and reconciles the unresolved attempt before another replica dispatches. Blind re-claiming does not prove session order or termination.

## 13. Benefits, trade-offs, dependencies, limits, alternatives

Benefits: every accept names an eligible network identity, its exact certificate evidence where observed, an active device, a signed compliance statement and the policy and table version that decided, committed before the answer; the binding token and authorize-only rules stop a password path on the same gateway from reaching certificate-derived authorization; per-request work touches memory only; revocation targets every possibly active session through qualified Disconnect or a proved original session-timeout bound.

Trade-offs: committing before answering ties RADIUS availability to PostgreSQL, accepted because an unrecorded or unrevocable accept is the worse failure; no resumption costs a full handshake per authentication, which Windows clients do anyway; client-IP hashing trades even load for EAP locality; certificate-derived authorization cannot tell which of an identity's certificates the gateway saw.

Dependencies: `layeh/radius` (MPL-2.0, untagged and without recent maintenance, used as codec only), the `radius-eap` Ctere1 fork (MIT), Go `crypto/tls`, `cel-go`, `pgx`; all with rows in `../licensing.md`. Test fixtures: hostapd and `wpa_supplicant` (BSD-3-Clause) and strongSwan (GPL-2.0, run as a separate lab process, never distributed), rows proposed.

Limits: accounting, session-control, evidence-availability and compromise-recovery protocols remain blocked on the schemas and proofs named in sections 5 to 8; no passing runtime or gateway evidence is claimed. The Cisco ASA has no documented RadSec, so ASA gateways rely on per-gateway secrets, source restriction and `Message-Authenticator`; FortiClient and Cisco Secure Client do not initiate EAP-TLS to these gateways, so their users are served by certificate-derived authorization only; dynamic authorization on FortiGate IPsec dialup and on the ASA from a non-ISE server is unconfirmed until qualification, and the session-timeout bound applies where it fails.

Alternatives considered: FreeRADIUS as the EAP server (rejected by RAD-01: GPL-2.0); trusting the gateway's name without an issued-certificate lookup (rejected: any CA the gateway trusts, or a password path, would mint identities); TLS session resumption with fresh checks in `VerifyConnection` (not chosen: Windows never resumes and a ticket key would add a shared secret across replicas); online OCSP fetches per EAP-TLS handshake (rejected: a network dependency per request for data the snapshot already holds); answering from cached state when PostgreSQL is down (rejected: accepts without a committed record); a shared EAP state store across replicas (rejected by BE-07: Redis is a second stateful service); `wxccs/radius` for RadSec (rejected: no known importers and a module-path mismatch, verify); per-user certificates only (rejected: 802.1X machine authentication and always-on VPN need a device identity).
