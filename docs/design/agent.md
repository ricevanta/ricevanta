# Agent design

How `ricevanta-agent` and its companion processes are built: internal structure, OS adapters, the enforcement model, local IPC, local state, the memory budget and its enforcement, updates, and tamper resistance. The process topology and the server protocol are in `../architecture.md`; enrollment in `pki.md`; browser adapters in `extensions.md`; and the `ricevanta-ext` execution contract in `../specs/extension-agent-runtime.md`. Decisions: AG-01 to AG-09, and EXT-03 and EXT-06 for the agent side of extensions, in `../decisions.md`.

## 1. Internal structure of the core

```
ricevanta-agent
├── runtime        async executor, one OS thread per telemetry source, supervision of helpers, metering, health
├── identity       device identity, hardware-backed keys, enrollment, renewal
├── transport      server client: mTLS HTTPS, long-poll, upload
├── policy         bundle and command verification, CEL evaluation, compiled rule sets per enforcement point
├── events         OCSF event construction, filtering, spool, batching
├── state          SQLite: state.db (policy cache, inventory, action journal, helper state) and lineage.db
├── mdm            inventory collection, configuration, software, compliance
├── edr            telemetry normalization, Sigma evaluation, response actions
├── dlp            classification orchestration, channel decisions, evidence
├── lineage        file and process identity, edges, inheritance
├── ext            extension module installation, compile cache, capability calls to ricevanta-ext, browser adapters
└── os             traits implemented once per OS (section 2)
```

Domain modules depend on `runtime`, `policy`, `events`, `state`, `ext` and `os`. They do not depend on each other; lineage consumes EDR and DLP events through the event pipeline. Domain modules consume extension capability interfaces through `ext`: `dlp` calls `classifier` and `parser` modules, `mdm` calls `collector` modules, and `edr` executes `responder` plans as its own response actions. Module code runs only in `ricevanta-ext`, never in the core (`extensions.md` section 4). The `ext` host crate sits beside `scan` in the agent workspace.

## 2. OS adapter interface

Every OS-specific capability sits behind a trait in the `os` layer, implemented in one crate per OS (`os-macos`, `os-windows`, `os-linux`):

| Trait | Provides |
|---|---|
| `ProcessSource`, `FileSource`, `NetworkSource` | Telemetry streams from the mechanisms in the `../platform-support.md` capability matrix; Windows ETW through `windows-rs` bindings directly, since the dedicated ETW crate has had no release since 2024 (verify) |
| `Enforcer` | Installs compiled rule sets into the enforcement point; delivers content-decision requests with an open file descriptor or handle |
| `KeyStore` | Creates, signs with and, where the platform offers it, attests hardware-backed keys; `rustls` signing through `rustls-cng` on Windows, `security-framework` on macOS and `tss-esapi` on Linux; the Linux fallback is a root-only software key flagged per device |
| `Inventory` | Hardware, OS, software, security, users and update state in osquery-schema tables (`mdm.md` section 3) |
| `Installer` | Software install, update and removal (MDM-01) |
| `Session` | Enumerates login sessions and reaches the session helper |

A capability the OS cannot deliver returns an explicit `Unsupported(reason)` that the core reports to the server and the console shows per device (blueprint section 8).

OS eligibility and installation prerequisites come from `../platform-support.md`. The installer runs behavioral preflight with the production sensors: a Linux hook must deny its probe operation, not merely load; a Windows driver must load under the recorded HVCI and code-integrity configuration; macOS extensions and managed-browser settings must be active, and each browser adapter's bypass self-test must hold a transfer until the decision (`extensions.md` section 7.2). An unresolved mechanism on an eligible target is a design blocker, not an `Unsupported` implementation that completes the requirement. Qualification and its evidence are defined in `../specs/platform-qualification.md`.

## 3. Enforcement model

Enforcement points hold their own decision data. The core compiles the policy bundle into per-enforcement-point rule sets (path, process, signer, destination and device rules) and installs them incrementally (section 7): into the Endpoint Security extension over XPC, into the driver through its communication port, into BPF maps. A rule-only result is final locally only when the compiler proves that unresolved core policies and exceptions cannot change the global verdict or actions (`policy.md` section 3.2). Otherwise the enforcement point sends its candidate to the core under the same conflict plan and deadline. Proven local final decisions target under 1 ms at the 99th percentile, measured per OS. Authorization and permission rules are never throttled, sampled or muted by resource governance.

Content decisions (DLP) require an enforcement point that can hold the operation. For a file decision, it passes an open descriptor or handle to the core; the core passes it to `ricevanta-scan`; the answer returns within the per-policy deadline (default 2 s, bounded by the OS deadline). Every policy declares its fail mode for a missed deadline, a throttled check or an unavailable helper: `open` (allow and record an audit event, the default) or `closed` (block). A scanner crash is handled apart from a timeout: the decision is retried once with a fresh helper, and a second crash on the same content hash applies `closed` and raises an alert, and so does a second deadline miss on the same content hash within 24 hours, so a crafted slow document cannot pass under `open` every time.

Extension `parser` and `classifier` modules (EXT-03) run inside the same content decision and only in the DLP `ricevanta-ext` instance. The core passes the descriptor when the policy assigns a parser to the file's MIME type, which it can do only for formats `ricevanta-scan` does not extract, and passes the extracted text to each classifier the policy names. One monotonic deadline covers queue time, IPC, guest work, host imports, output and cleanup. Separate DLP process, executor, broker-worker and memory capacity keeps collectors and responders from starving or terminating these decisions. A DLP-instance crash follows the content retry and fail-mode contract; a batch-instance crash does not touch active DLP stores (`../specs/extension-agent-runtime.md` sections 1 to 3).

Browser content decisions use the browser's own hold point, because an extension's `webRequest` blocking callback is synchronous on Chrome and Edge and `asyncBlocking` applies only to `onAuthRequired`. The core implements one local content-analysis agent compatible with `content_analysis_sdk` (protobuf over a named pipe on Windows and a Unix socket elsewhere), and every browser whose adapter declares a connector reaches it (EXT-06). Three first-party adapters declare one: Chrome through the connector policies `OnFileAttachedEnterpriseConnector`, `OnBulkDataEntryEnterpriseConnector`, `OnPrintEnterpriseConnector` and `OnFileDownloadedEnterpriseConnector`, which Chromium marks `cloud_only`, so they reach the browser only from Chrome Enterprise Core, a Google-hosted management dependency the operator accepts per deployment; Edge through the same policies set by platform policy (Edge 137 and later on Windows, Edge 151 and later on macOS, per Microsoft's policy pages), with the further setup Microsoft requires (verify whether an Edge for Business sign-in is part of it); Firefox through the `ContentAnalysis` enterprise policy (Firefox 137 and later, downloads from 142 and ESR 140.2), which intercepts clipboard, drag and drop, upload, print and download (macOS and Linux coverage, verify). The Firefox policy sets `Download.Enabled: true` and `PlainTextOnly: false` on Clipboard and DragAndDrop, since the defaults skip downloads and analyze only `text/plain`, and derives `DefaultResult` and `TimeoutResult` from the fail mode (`0` deny when any in-scope policy on the device declares `closed`, `2` allow otherwise). The Firefox policy also sets `IsPerUser: false` and `PipePathName` to the core's system-wide agent name, and Chrome and Edge entries set `service_provider: local_system_agent`. Each Chrome and Edge connector entry sets `block_until_verdict: 1` and `default_action: block` under the same `closed` rule and `allow` otherwise; `OnBulkDataEntry` sets `minimum_data_size: 1` (Chrome and Edge default to 100 bytes, which would skip a 12-digit identifier); `OnFileAttached` and `OnFileDownloaded` set `block_password_protected`, and those two and `OnPrint` set `block_large_files`, to `true` under the `closed` rule; the core applies each policy's own fail mode when it answers. The browser pins the agent it connects to through Chrome's per-OS `verification` keys and Firefox's `ClientSignature`; Edge documents no pin, so the pipe and socket protections of `dlp.md` section 6.5 apply, so a process that binds the pipe while the core restarts is not answered as the agent. The browser-side timeout is the vendor's (`AgentTimeout` in Firefox, set from the warn timeout; Chrome sends `expires_at` per request) and the policy deadline (default 2 s) stays below it, so the core, not the browser, decides on a missed deadline.

Where no connector reaches the browser, the adapter declares the content-script gate and its backstop; among the first-party adapters that is Chrome without Chrome Enterprise Core, Edge on Linux and Safari. The managed extension's content script intercepts file inputs, drag and drop and paste and holds the event until the native-messaging answer. Chrome and Edge can synchronously cancel requests visible to `webRequest`, available because policy force-installs the extension. That API sees WebSocket and WebTransport handshakes but cannot mediate messages after establishment ([Chrome documentation](https://developer.chrome.com/docs/extensions/reference/api/webRequest)). Chrome without Chrome Enterprise Core on every required OS and Edge on Linux therefore remain release blockers for persistent-channel transfers until every page and worker send is mediated or a qualified restriction excludes those channels (`dlp.md` section 6.5). Safari has no blocking `webRequest`. Its `declarativeNetRequest` rules match URL and resource metadata but do not expose the request body or a transfer identity, so an allow rule cannot bind the inspected bytes to one send. The content script also has no established control over every page and worker API or each message on a WebSocket opened before the verdict. Safari upload and paste blocking therefore remain a v1.0.0 release blocker under DLP-01; no timed tab or destination allowance is installed (`dlp.md` section 6.5). Printing outside a connector uses the candidate file gate at the completed spool (Endpoint Security `AUTH_OPEN` on macOS, fanotify `FAN_OPEN_PERM` on Linux, the driver on Windows). A first read-open alone does not contain an existing descriptor or mapping; print blocking must pass the exact-byte contract of `dlp.md` section 6.4. Downloads use a connector hook where one exists; otherwise the same unresolved file gate controls local use after download and does not prevent the network transfer. The managed extension supplies tab URL and user context on every browser.

Clipboard blocking requires mediation before every read, not ownership after a copy notification. X11 sends the selection owner a `SelectionRequest` for each request. The Wayland candidate uses `ext-data-control-v1` where the compositor offers it; on GNOME the candidate extension owns the selection through Mutter's `MetaSelection` API and relays each request to the helper. These paths qualify only if the first reader, simultaneous readers and repeated consumers cannot receive bytes before the core decides; watcher-then-re-own does not prove the first-read condition. Windows delayed rendering does not meet that contract: `WM_RENDERFORMAT` is sent only while a format has no rendered handle, and the handle supplied with `SetClipboardData` is reusable by later consumers. Re-owning again after each render leaves another race and does not make retrieval per-read. No documented macOS pasteboard callback authorizes every read, and promised data may be cached by the pasteboard server. Re-owning after a change also leaves every OS exposed before ownership changes. Windows/macOS per-read mediation and Linux first-read exclusion remain v1.0.0 release blockers under DLP-01. Disabling clipboard history, cross-device clipboard and Universal Clipboard removes separate capture paths but does not close those blockers (`dlp.md` section 6.5).

Processes in the user session are untrusted input: a missing or unresponsive session helper or browser extension is an unavailable helper and is reported, and a policy may deny network connections to a browser process until its extension connects, using the network enforcement point, since the browser channels have no other one.

Ricevanta's own processes are excluded from their own checks: muted in Endpoint Security, listed by signature in the driver, held in a trusted-process map for BPF, so inspection cannot deadlock on itself.

Enforcement while the core is down (restart, update, crash) differs per OS: the Endpoint Security extension and the driver keep their installed rules; Linux BPF LSM rules survive through pinned links and maps; fanotify permission checks lapse. Content decisions during that time take the policy's declared fail mode, since the helper is unavailable.

## 4. Local IPC

- macOS: XPC Mach services with code-signing requirements. The core connects to each system extension's listener (`NSEndpointSecurityMachServiceName` and `NEMachServiceName`, both app-group-prefixed), and the Safari handler reaches the core through a Mach service registered under the app-group prefix, since sandboxed processes cannot look up arbitrary global names (verify both directions and the prefix rules).
- Linux: Unix domain sockets; the peer is checked with `SO_PEERCRED`, and with `SO_PEERPIDFD` on kernels 6.5 and later; below that the executable is verified through `/proc` with a residual PID-reuse window (verify).
- Windows: named pipes; the core opens a handle to the client process from its pipe client ID and keeps it for the connection's lifetime, then checks the process token and the signed image through that handle.
- Messages are length-prefixed and serialized with a Rust-native binary serializer (`postcard`), since both ends ship in the same release. File descriptors and handles travel with the message where the OS allows it.
- Browsers: the agent writes its generated `ricevanta-nmhost` manifest only to the exact targets in the adapter's signed browser registration (`extensions.md` section 7.2). It validates the registration generation, grant, reserved namespaces and resolved target at every write. Chrome, Edge and Firefox use the native host among the first-party adapters. Where the registration permits a policy that disables user-level manifests, the agent sets it so a user cannot register a substitute host (`NativeMessagingUserLevelHosts` in Chrome and Edge); Firefox has no such policy (verify), which `../platform-support.md` records as an OS limit. A `connectNative` port keeps the extension's service worker alive. Safari sends native messages to the extension handler inside `Ricevanta.app`. Force-install and the Safari `AlwaysOn` extension state follow DLP-01. The core also serves the `content_analysis_sdk` channel to every browser whose adapter declares a connector (section 3), pinned by the browser through Chrome's `verification` keys and Firefox's `ClientSignature`; Edge has no documented pin (`dlp.md` section 6.5).
- Inventory SQL worker: the core passes a bounded inventory snapshot to a separate on-demand query process under `../specs/rule-adapters.md` section 8.1. The worker has no writable agent state, network, credentials or ambient file access. Its native launcher, sandbox, containment and kill/reap contract remain implementation blockers; no binary name or proved native mechanism is selected.
- Extension helpers: the DLP and batch instances of `ricevanta-ext` use separate generations of the same per-OS channel and peer checks as `ricevanta-scan`, with the core as their only peer. The core brokers every interaction; helpers never talk to each other, and a response from a replaced generation is refused.
- Driver: the minifilter communication port with versioned C structs.

## 5. Local state and spool

The first Rust slice is the file-free `agent/crates/spool` library in the `agent/` workspace; [its spec](../specs/agent-spool-format.md) owns the byte contract and [its plan](../plans/agent-spool-format.md) owns implementation and CI. It does not establish native spool durability.

State lives in SQLite (`rusqlite` with bundled SQLite, pinned to a current release), chosen because the lineage graph needs path queries, which recursive SQL gives and a key-value store does not, and because it is the one candidate with SQL, a documented durability model and no server process. Two databases, both readable only by root or LocalSystem and protected by section 9:

- `state.db`: policy cache, inventory snapshot, response-action journal, helper state. WAL mode with `synchronous=FULL`; command receipt is durable before acknowledgement or execution, and running actions retain their recovery obligation after power loss. The journal row per command uid, the dispatch grant and the server-side detection of undelivered commands are defined in `../specs/policy-envelope.md` section 7. An `extension.respond` command also stores its immutable canonical plan and one row per stable step id as defined in `../specs/extension-agent-runtime.md` section 6. Each action has a tested idempotency and reconciliation contract; journal recovery never blindly repeats a side effect.
- `lineage.db`: the lineage graph (`lineage.md`). WAL mode with `synchronous=NORMAL`, writes batched into one transaction per second and a checkpoint every 10 s, so a power loss costs at most the edges since the last checkpoint; per-edge fsyncs would cost battery and disk wakeups.

Memory rules for every connection: `cache_size=-2048` (2 MiB), `mmap_size=0`, a fixed prepared-statement cache, one connection per database. Recursive queries carry an explicit depth limit, which is the cycle guard. SQLite allows one writer at a time, which fits a single core process; helpers never open the databases.

Event spool: a directory per event class in drop order (raw telemetry, context, lineage edges, findings and state (detections, DLP matches, remediation outcomes, compliance and vulnerability findings, inventory, configuration state, agent health), audit), each holding append-only segment files of length-prefixed records with a CRC32C per record. A segment holds one class only, so dropping by class is dropping whole segments. One shared byte counter enforces the cap (default 512 MB or 5 % of the volume, whichever is smaller); when full, the oldest sealed segment of the lowest class is deleted first, and the drop is itself recorded as an audit event. The record format, sealing, upload order, acknowledgement and the lookback ring are in `events.md` section 2; per-class drop counters persist in `state.db` and travel in every check-in. Sealed segments are zstd-compressed and uploaded whole. The active segment is synced on seal and every 500 ms; on start the agent follows [the spool spec's recovery and error precedence](../specs/agent-spool-format.md#4-recovery-and-error-precedence). Only a returned `TailIssue` permits the spool manager to truncate to `valid_len`, under exclusive ownership and with native durability established before resuming at `next_sequence`. Fatal errors permit no truncation. The one-class-per-segment rule is load-bearing: the surveyed shippers (Vector, Fluent Bit, Beats, osquery, the OpenTelemetry Collector) cap by bytes or count and drop oldest or newest, none by class.

[The sealed batch writer](../specs/agent-batch-writer.md) specifies the file-free conversion from a complete segment to upload bytes (AG-11); durable sealing and transport remain separate slices.

Offline: the cached policy stays in force without expiry. Certificate renewal and recovery are in `pki.md`.

## 6. Memory budget

AG-02 defines idle RAM as the sum over resident user-mode Ricevanta processes of the per-OS private footprint metric: `phys_footprint` on macOS, private working set on Windows, proportional set size on Linux, so shared framework pages are not counted once per process. The reference configuration is one login session and one browser. The 80 MB target (blueprint section 7) is a design target, not a hard limit: the allocation below is the starting point, it is re-derived from the first prototype measurement, and the budgets the self-watchdog enforces (section 7) are policy values the operator can raise:

| Process | Idle budget |
|---|---|
| `ricevanta-agent` | 44 MB |
| `ricevanta-updater` | 4 MB |
| Endpoint Security extension and Network Extension (macOS) | 16 MB together |
| `ricevanta-session` | 6 MB per session |
| `ricevanta-nmhost` or the Safari handler | 2 MB per browser |
| `ricevanta-scan` | 0 when idle (not running); capped at 256 MB when running |
| Inventory SQL worker, required contract unresolved | 0 when idle (not running); total active cap 64 MiB, including a 32 MiB SQLite heap |
| `ricevanta-ext` DLP instance | 0 when idle (not running); capped at 128 MB when active, a policy value |
| `ricevanta-ext` batch instance | 0 when idle (not running); capped at 128 MB when active, a policy value |

Reference idle total: 72 MB on macOS, 56 MB on Windows and Linux. At most one DLP and one batch instance of the same `ricevanta-ext` binary run, never one process per module. Their default aggregate active cap is 256 MB in addition to the idle total. The 128 MB DLP instance cap is reserved and batch work cannot borrow it. The self-watchdog accounts each instance and their aggregate, and stops either class after its work drains. The required SQL worker permits one active query per device and a queue of eight. The self-watchdog must include its total process footprint and its 64 MiB cap in aggregate active-helper accounting without allocating resident idle memory. Startup, snapshot transfer, preparation, functions, serialization and cleanup share the 100 ms deadline of `../specs/rule-adapters.md` section 8.1; native enforcement of those limits remains a blocker. Kernel pool and BPF map memory are reported separately.

## 7. Resource governance

No product that combines EDR and DLP publishes a footprint near 80 MB; telemetry-only agents reach tens of MB and full EDR agents sit at 200 MB and above (third-party measurements, verify). Low RAM and CPU are therefore properties the agent enforces on itself against measured budgets, not a number promised in advance.

- Self-watchdog: the `runtime` module meters CPU time per OS thread (one thread per telemetry source; helpers are metered as processes), samples rule evaluation time one event in N rather than timing every evaluation, and accounts memory by the owned data-structure size of each unit plus the per-process footprint. Budgets come from the policy bundle. When a budget is exceeded for longer than its window, the offending unit is throttled first and disabled second, the device reports the event, and the console shows the unit as degraded. The agent never grows to stay complete; osquery's watchdog applies the same rule by restarting its worker and denylisting the offending query.
- Hot-source control, telemetry only: every notification source keeps per-path and per-process event rates. A source that exceeds its rate is sampled, then muted at the enforcement point with the mute reported as an event, so a busy build directory or backup job cannot drive the agent past its budget. Authorization and permission rules are exempt (section 3); a throttled content check takes the policy fail mode and raises an alert; repeated mutes attributed to one user become a detection, since flooding a path to get it muted is an evasion.
- Footprint telemetry: each process samples its own CPU, footprint, open descriptors and event rates on a fixed interval (default 60 s) and ships them as OCSF events; the console shows the budget against the measurement per device and per group, and a fleet-wide regression is an alert.
- Extension modules: each installed `agent-module` is a unit of work, metered by fuel, memory, queue and call latency, broker requests, output, traps, timeouts and helper replacements. DLP and batch work use separate process generations, executor queues and broker-worker pools. The core throttles the offending module first and disables it second; a batch timeout cannot kill a DLP instance or consume its reserved worker capacity (`../specs/extension-agent-runtime.md` sections 1, 2 and 5).
- Incremental rule installation: a bundle update is diffed against the installed rule sets and only the changed rules are installed into the enforcement points, with the driver and BPF maps updated in place. A full reinstall per policy change is the failure that Sysmon's configuration reload showed (non-paged pool growth per reload, verify).
- Performance gate in CI: every agent build runs the footprint benchmark (idle footprint per process, idle CPU, event-path latency) and fails when a metric regresses against the last release beyond its tolerance. Footprint is gated on hosted runners for the core and helpers; CPU and latency, which are noisy on shared runners, and everything involving the Endpoint Security extension, the driver or BPF LSM are gated on the self-hosted machines in `../project.md`. The gate exists from the first agent build (`../roadmap.md`, v0.1.x).

## 8. Update

Releases publish signed packages per OS to the blob store or to the project's download URL. The core is the only process with the device identity and server connection. It fetches `GET /agent/v1/update` over mTLS, applies the server's rollout selection, downloads the named package with range requests, and streams the opaque manifest and package into the updater's root-only local inbox over authenticated IPC. Update-only mode leaves only this transport and private identity renewal open. The updater has no network client and cannot read or use the device identity key.

The updater owns the inbox, previous-package store and installed-version record. It accepts an atomic staged pair only after it verifies the release signature, manifest expiry, package digest, target OS and architecture, and OS code signature, and refuses a manifest version lower than its installed-version record. The updater treats core-supplied bytes as untrusted and rejects unsigned or older staged packages. Rollout has a local health gate: the updated core must start, load its cached policy and report healthy over local IPC within 15 minutes, or the updater restores the previous package it retained. Server reachability is reported but not required. If the core cannot fetch at all, the updater can roll back to that retained healthy package but has no independent server recovery path; an administrator repairs a device with a signed OS package when no retained package starts.

Local rollback is the only path to a lower version and needs no manifest. A release package contains the updater too; the updater replaces itself last and the service manager restarts it, and the core restores the previous updater binary if the new one fails to start. The driver and system extensions follow the same manifest but apply through OS-specific mechanisms: `OSSystemExtensionRequest` from `Ricevanta.app` on macOS, the driver package on Windows, and the core reloading pinned BPF objects on Linux. A Wasmtime version change invalidates the extension compile cache and recompiles installed modules before health reporting; a failed module is disabled and reported without failing core health (`../specs/extension-agent-runtime.md` section 3).

## 9. Tamper resistance

Prevention only where the OS provides it, reporting elsewhere. The precondition per OS:

- macOS: the MDM `SystemExtensions` payload controls approval and activation. Profile-based Device Enrollment is removable; removing enrollment also removes its managed settings. The agent therefore cannot promise non-removability against the person able to remove that profile. Detect enrollment or extension loss and flag affected protection; a lost check-in is the server's fallback signal.
- Windows: without ELAM and protected process (v2.0.0) an administrator can stop the service at boot or in safe mode, which the driver cannot report once the core is stopped and the server detects as a missed check-in.
- Linux: root can remove BPF pins, kill the core, clear immutable attributes or change the kernel command line, so BPF LSM self-protection is detection, and prevention would need a locked boot chain (Secure Boot with a signed unified kernel image and lockdown) that the agent only reports (verify).

Configuration protection and uninstall authorization: the enrollment configuration, the local state and the spool are readable and writable only by root or LocalSystem, and the core ignores any local change to its configuration that is not a signed bundle. Ricevanta-controlled uninstall and stop paths require an uninstall token: a signed command from the server for a named device, or, for an offline device, a signed uninstall object bound to the device uid and a nonce the device displays (`../specs/policy-envelope.md` section 7), which the installer's uninstall path verifies against the pinned chain and accepts once. Without the token those paths refuse and report. A release object of the same form releases an isolated host that cannot reach the server (`../specs/edr-response-actions.md` section 3.3). OS or administrator escape paths remain subject to the limits above; a token check in Ricevanta's installer cannot govern direct OS removal of a manual MDM profile. Server-initiated MDM removal requires the protected administrative authorization path and records the resulting loss of management.

## 10. Benefits, trade-offs, dependencies, limits, alternatives

Benefits: rules compiled into the enforcement points keep authorization latency off the IPC path and keep enforcing while the core restarts; one core process keeps identity, policy and the server connection single; extension code runs in a separate, capped WebAssembly helper, so it cannot reach the core's keys or enforcement points; the self-watchdog and footprint telemetry turn the 80 MB target into something measured and enforced rather than promised; a separate updater can roll back a broken core.

Trade-offs: a separate updater is one more resident process; Swift shims on macOS add a second language where Apple frameworks require it; metering by thread and by owned structure sizes is approximate; the Linux fallback to a software key weakens identity on hosts without a TPM.

Dependencies: Rust crates `tokio`, `rustls`, `rustls-cng`, `security-framework`, `rusqlite`, `aya`, `endpoint-sec`, `windows-rs`, `tss-esapi`, `cel`, `postcard`, `zstd`, `crc32c`, `blake3`, a TLSH crate, and `wasmtime` with Cranelift and `wasmtime-wasi` in `ricevanta-ext`; all with rows in `../licensing.md`.

Limits: Linux fanotify enforcement lapses during a core restart; Wayland clipboard depends on the compositor offering `ext-data-control-v1` or, on GNOME, on the GNOME Shell extension; the content-script gate (Chrome without Chrome Enterprise Core, Edge on Linux, Safari) is weaker than a connector; Firefox has no policy that disables user-level native hosts (verify); community adapters are not qualified (`extensions.md` section 7.3); extension modules have no network and add a hop to content decisions; the connector on Chrome needs Google-hosted management; manual macOS enrollment can be removed; tamper resistance and uninstall refusal against a local administrator are reporting on Windows until v2.0.0 and on Linux without a locked boot chain; clipboard mediation, exact-byte file gates and Safari and Chromium fallback transfers remain required mechanism blockers (`dlp.md` sections 6.4 and 6.5).

Alternatives considered: RocksDB for local state as osquery uses it (rejected: C++ dependency, larger binary, no SQL for the graph); pure-Rust key-value stores such as `redb` or `fjall` (rejected: no SQL, no production users listed); JSON for local IPC (rejected: event volume from the Endpoint Security extension); `cel-cxx` as the CEL runtime (rejected: C++ build chain and cross-compilation limits; `cel` ships the conformance harness); `libbpf-rs` instead of `aya` (not chosen: both are maintained; `aya` keeps the build pure Rust and `libbpf-rs` stays the fallback if CO-RE on the kernel floor misbehaves); updates applied by the core itself (rejected: a broken core cannot roll itself back); a fixed process memory cap that restarts the agent (rejected: loses enforcement and hides which unit was at fault); policy expiry offline (rejected: turns an outage into a loss of enforcement).
