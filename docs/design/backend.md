# Backend design

How `ricevanta-server` is built inside: modules, the libraries they build on, the agent-facing handler rules and cross-replica coordination, the policy and event pipelines, storage, and secrets. The domain designs `mdm.md`, `edr.md`, `dlp.md`, `radius.md`, `policy.md` and `events.md` hold the server side of their domains. Roles, listeners, key custody per role, APIs and deployment are in `../architecture.md`; certificates in `pki.md`; the extension model in `extensions.md`. Decisions: BE-01 to BE-07, EV-01 to EV-03, POL-01 to POL-03, and EXT-02, EXT-04, EXT-05 and EXT-07 for the server side of extensions, in `../decisions.md`.

## 1. Modules

```
server/internal/
├── identity     organizations, users, groups, OIDC and SAML login, sessions, SCIM, LDAP sync, API tokens, the first-start setup token
├── authz        permissions, roles, access policies and approvals (BE-02)
├── devices      device records, groups, tags, lifecycle, device-to-user links
├── mdm          agent-delivered management, Apple MDM and DDM server, APNs, Windows OMA-DM server
├── policy       envelope validation, CEL profile, compilation, signing, distribution, rule-pack registry, adapters
├── detection    server-side Sigma correlation, alerts, investigations, response-action dispatch, threat intelligence
├── dlp          classification catalogue, rule packs, matches, evidence, reports, fingerprint sets and their envelope-encrypted originals in the blob store
├── lineage      graph storage and queries
├── pki          issuing CAs, profiles, issuance, ACME, SCEP, revocation, CRL and OCSP, external CA
├── radius       RADIUS and RadSec servers, EAP-TLS, authorization, gateway profiles
├── events       ingestion, OCSF validation, PostgreSQL and raw store, retention, holds, export log and destinations, report templates, runs and schedules
├── extensions   package registry, verification, trust list, grants, browser registrations, console bindings, bundle distribution, connector registry and health
├── audit        append-only administrative audit log
├── transport    HTTP routers, long-poll registry, command dispatch, `/api/v1/changes`, the embedded console
└── platform     configuration, database, blob store, in-process bus, jobs, metrics, secrets
```

Rules:

- A module owns one PostgreSQL schema named after it and is the only code that reads or writes those tables.
- Modules call each other only through Go interfaces defined by the callee, and publish facts on the in-process bus (`platform/bus`) for the others to consume. Routine cross-replica coordination goes through PostgreSQL (`LISTEN`/`NOTIFY`, lease rows, job tables), never through the in-process bus. Authority mutations also use the independent journal of section 6.1.
- Every module exposes a change watermark per device group (BE-10) and its report sources (BE-11), described and executed, through those interfaces.
- An import-graph check in CI fails the build when a module imports another module's internal packages, so the boundaries hold without code review.
- Every module has its own package of tests that run against a real PostgreSQL in CI.

### 1.1 Identity principals and protected authority

The [permission catalogue](../specs/permission-catalogue.md) defines the machine-readable permission inventory and the proposed `authz/catalogue` library. Its metadata does not replace the committed-authority checks in this section.

An administrator is one immutable internal user uid with explicit external-principal links. OIDC defines stable subjects per issuer ([claim stability](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStability)); SAML defines persistent identifiers separately from transient identifiers ([SAML Core section 8.3](https://docs.oasis-open.org/security/saml/v2.0/saml-core-2.0-os.pdf)). OIDC links key on provider uid, exact `iss` and `sub`; SAML links key on provider uid, issuer, persistent `NameID` format and `NameID`; transient and email-based identifiers cannot create privileged principal links; SCIM links key on directory uid and SCIM resource id; LDAP links key on directory uid and `entryUUID` or `objectGUID`. Each external key links to at most one user and each provider links a user at most once. Email, display name, login name and mutable claims never identify or merge accounts. A sync collision disables the candidate link and raises an alert for an operator to resolve through a protected link operation.

Claim and directory mappings may assign ordinary roles and groups, but they cannot assign `identity.authority.approve`. That permission is assigned directly to an internal user. Changing an identity provider's trust or endpoints, principal links, claim or group mappings, directory source or filter, account recovery, break-glass credentials, or a direct authority-approver assignment is an identity-authority action. The `authz` module always sends such an action through the fixed two-account protocol in `console.md` section 3.2, or an exact offline repair when no unaffected approver exists; an access policy cannot disable or weaken it. The approver must re-authenticate through a method outside the authorities the action changes. The transaction reloads both users, their direct permission, the unaffected authentication method, the exact before and after hashes and the approval immediately before applying the change. Any difference makes the request stale.

## 2. Library choices

- Apple MDM: NanoMDM's `http`, `service` and `storage` layers with the PostgreSQL backend; the DDM engine is written in-project, since no maintained open-source DDM server exists; APNs is NanoMDM's `push/nanopush` HTTP/2 client, run in `jobs`.
- Windows MDM: Fleet's MIT-licensed MS-MDE2 and SyncML code, file by file.
- PKI: `smallstep/crypto` for X.509, KMS and PKCS#11; `micromdm/scep` for SCEP; the ACME server is written in-project on the same packages, since no standalone Go ACME server library exists.
- RADIUS: `layeh/radius` for transport; EAP-TLS written in-project, seeded from the MIT `radius-eap` state machine and interoperability-tested against `wpa_supplicant`, because no maintained Go library ships it.
- Identity: `go-oidc`, `go-ldap`, `elimity-com/scim` at a pinned commit (early-stage, no bulk operations); the SAML library is chosen after an activity check, because the common one is stale (verify).
- Data: `pgx`, `klauspost/compress` for zstd, `minio-go` for S3-compatible blob storage, `clickhouse-go` for the raw store, the OpenSearch and Elasticsearch Go clients for export destinations; `franz-go`, the OTLP protobuf and gRPC modules, `azlogs` and `azidentity` for the other destination adapters (`../specs/event-export.md`).
- CEL: `cel-go`, with the agent's `cel` crate passing the same conformance subset (POL-01).
- Rule engines: `ricevanta-rulec` (POL-05), a Rust subprocess with the agent's matcher, detectors, YARA-X, SQLite and `cel` crate, for engine-exact validation and rule tests (`policy.md` section 5.1).
- HTTP: the standard library router; the OpenAPI 3.1 document is hand-written and validated in CI, since generator support for 3.1 is partial.
- Extensions: no plugin runtime in the server (EXT-05). Manifest and index signatures use the Go standard library `crypto/ed25519` with the DSSE code the policy module already uses; manifests and adapters validate with the same JSON Schema 2020-12 validator as the policy envelope; browser registrations and console bridge bindings use explicit authorization services in this module; connector calls use the standard library HTTP client against the required OpenAPI documents under `schemas/openapi/connectors/`, which are absent and block connector clients (`../analysis.md` section 3).

Console assets are served only from a live server-issued binding's frozen, hash-verified mount. The exact route, candidate sandbox header and qualification gates are defined in `extensions.md` sections 5.1 and 5.2.

## 3. Agent-facing handler rules

Taken from the documented scaling failures of comparable servers (Fleet's per-check-in reads of shared state and commit-bound result writes, Elastic Fleet Server's per-check-in authentication):

- Routine check-ins and waiting long polls avoid fleet-wide shared-state reads; the current policy bundle version per scope is held in process memory and refreshed by `NOTIFY`. When a command is ready, `jobs` reads the protected command, frozen target and approval records before signing a dispatch grant for the device's fresh poll nonce. These authorization reads are required and cannot be replaced by the exposed handler's cached claims (`../specs/policy-envelope.md` section 7).
- The certificate-to-device lookup is cached only inside a versioned authorization snapshot. Every request, including a new HTTP/2 stream, checks the serial, certificate epoch and device state before reading a body or waiting. Each refresh reads `pki.authorization_version` and the corresponding state in one consistent database snapshot; its five-second lease starts at the monotonic time immediately before that snapshot read begins, not when a slow read finishes. A revocation transaction advances the durable version and sends `NOTIFY`. Replicas reload refused serials and close their indexed connections, streams and long polls. A separate timer closes all device connections and refuses authenticated paths at lease expiry even if a refresh query, notification listener or request handler is blocked. Polling starts before the lease expires; a missed notification never renews a lease. No new or existing stream can run past five seconds from the last successful snapshot's observation of authority, and a stalled refresh cannot extend that bound. The test must include a commit immediately after observation, a dropped notification and a refresh held past the deadline. PostgreSQL requires inspecting durable state when establishing a listener ([`LISTEN`](https://www.postgresql.org/docs/17/sql-listen.html)).
- Events are written in batches with `COPY` into the day partitions, never row by row.
- Enrollment is rate-limited per source.
- `LISTEN` needs a direct PostgreSQL connection, so the server keeps a small pool outside any transaction-pooling proxy; `NOTIFY` is used only for the low-rate commands, policy-version and issuance channels, never on the ingest path, because a `NOTIFY` inside a transaction takes a global lock at commit.
- Leader election for `jobs`: one lease row per job, taken and renewed at 80 % of its interval against database time; a replica whose renewal fails stops the job and logs it.

Reference points: Fleet runs 10 instances for 25,000 hosts; Elastic Fleet Server runs one 8 GB instance from 10,000 to 75,000 agents. The `agent` role targets 20,000 endpoints on two to three replicas, measured.

## 4. Policy and event pipelines

```
Author (console, CLI, GitOps)
  └─> policy: validate envelope and CEL profile ──> compile per domain ──> sign in api ──> store bundle versions
        └─> transport: agents fetch bundle for their scope
              └─> agent policy: verify assignment and signature ──> CEL single-event evaluation ──> compiled rule sets to enforcement points

Sensors ──> agent events: OCSF construction, telemetry profile filter ──> spool ──> batch upload
  └─> server events: validate, store detections and context, raw to the raw store if enabled
        ├─> detection: correlation rules, alerts
        ├─> lineage: edges uploaded by agents as lineage events, plus cross-device edges from content hashes
        └─> exporters: export log, per-destination cursors, retries and dead letters (events.md section 4)

Extension package (console, API, GitOps, index)
  └─> extensions: verify signature against the trust list, file hashes, interface versions ──> approval of grants ──> blob store
        ├─> policy: agent-bound components (content, adapters, modules) into the bundles of target scopes, by hash with the grant
        ├─> api: frozen assets under /ext/<id>/<version>/<package-sha256>/<component>/<asset-mount>/
        └─> jobs: connector registry, health probes, contract calls
```

Certificate and command-dispatch requests from exposed roles are untrusted. The PKI module derives issuance authority from protected records and independently verifies proof (`pki.md` section 3); the command dispatcher verifies approval and expiry against database time before signing a fresh artifact-bound grant. Request-row insertion never confers signing authority. Module interfaces provide those protected records under BE-04; roles do not bypass schema ownership.

Single-event rules evaluate on the agent, correlation on the server (EDR-01). The same policy envelope carries MDM desired state, EDR detections and DLP enforcement with domain-specific execution semantics (blueprint section 4).

Events are OCSF 1.9.0 (EV-02); the classes each domain emits and the `ricevanta` extension are in `../specs/ocsf-profile.md`.

The `extensions` module owns the trust list, installed packages, grants, their per-component monotonic generations, browser registrations, console mount bindings and connector registrations. Every grant write advances its component generation, even when the capability values match an earlier grant, and the generation is never reused. It hands agent-bound components to `policy` through a Go interface; `policy` never reads the extension tables. Browser registration changes are protected, enforce exact namespace ownership, advance the separate registration generation and invalidate affected grants before bundle recompilation (`extensions.md` section 7.2). The blob store is not a trust anchor: `policy` verifies each artifact's SHA-256 against the install record before placing it in a bundle, `api` verifies each console module asset before serving it, and a mismatch refuses the artifact and raises an audit event.

The console bridge creates an authenticated server-side binding to an immutable package digest, component, grant generation, slot and operator session. Every dispatch reloads current enabled and revocation state and operator rights, then uses a transactional generation fence shared with invalidation before it enters the named administration handler. Disable, revocation, uninstall or any grant write advances that fence, invalidates bindings and cancels queued dispatches in the same transaction; a bus notification closes frames but never carries authority. Protected requests bind the same extension origin and pass the fenced check again immediately before approved action dispatch (`extensions.md` section 5.2). Connector calls run in `jobs` and follow the exporter rules: per-connector queues, retries and an alert on repeated failure.

## 5. Storage

- PostgreSQL 17 or later is the system of record; 17 is the floor for its support window (16 leaves support in 2028, 17 in 2029, verify) and so that operators who prefer physical backups have incremental backup available. Event tables use native declarative partitioning by day with no DEFAULT partition; a `jobs` task creates partitions two days ahead and, past the configured retention (EV-01 defaults), runs `DETACH PARTITION CONCURRENTLY` and drops them, so retention never runs a row-by-row DELETE. Events carry typed columns for the keys used to filter and retain (time, class, severity, device, rule) with B-tree indexes, and one `jsonb` column for the full OCSF body under `lz4` TOAST compression, stored once and referenced by detections; no GIN index sits on the ingest path. Ingest uses `pgx` `CopyFrom` in batches of 5,000 to 10,000 rows, tuned by measurement; `synchronous_commit=off` is allowed for context events and bounded raw rows only, never for detections, lineage, audit or administrative rows, and the `agent` role acknowledges every new or duplicate batch only after a fresh synchronous WAL marker covers the observed ledger commit on the current primary (`events.md` section 3.5); a failover to a standby can still lose them (`events.md` section 1). Event partitions are by server receipt day (`metadata.logged_time`), with a unique index on event uid and partition day (`events.md` section 3.3). 10^7 events a day is about 116 rows per second, so the binding limits are disk, vacuum and query latency, not row rate; a load test on the target hardware sets the point where the raw store is required.
- Raw telemetry, when a device group is switched to the full profile, goes to the bundled ClickHouse, to an external search destination through the exporters, or, for a bounded investigation set of at most 50 devices for 7 days, into PostgreSQL partitions under the same rules (EV-01); at C9's upper rate that set is at most 5×10^6 rows a day. ClickHouse is Apache-2.0, needs no JVM, documents a single-node minimum of 8 GB (verify) and ships two LTS releases a year each supported for one year, and columnar storage with codecs stores events in a fraction of a search index's space (vendor benchmark, verify); investigation queries are structured filters plus substring matches on command lines, which it serves without a full-text index. The raw store holds bounded-retention telemetry and is excluded from backups by default. Its source tables use fenced retention jobs rather than autonomous TTL, so legal-hold capture can pin a source until its held copy verifies (`events.md` section 5). Two hedges: the `events` module writes raw telemetry through a raw-store interface with two implementations at v1.0.0, ClickHouse and none, so a later OpenSearch implementation is an adapter rather than a redesign; and the ClickHouse schema (typed OCSF base columns plus one JSON column, native JSON type or string to be measured) and the Sigma-to-SQL translator are benchmarked on real EDR telemetry in v0.4.x (`../roadmap.md`) on ingest rate, bytes per event and query latency, with the outcome "keep, or swap to OpenSearch before v0.8.x". Every deployment profile sets a per-query memory limit and a query timeout, since an unbounded aggregation can take the node's RAM.
- The blob store (`platform/blob`) has two backends, local filesystem and S3-compatible. It holds installer packages, agent release packages, rule-pack archives, extension packages with their console module assets, private exported reports, frozen S3 export-plan payloads, diagnostics bundles and triage packages, and the envelope-encrypted originals of fingerprinted documents (`dlp.md` section 4). It also holds the event export log, bounded by age and size (`events.md` section 4.1), which the `agent` role writes create-only under its own prefix and only `jobs` reads. DLP evidence snippets are stored in PostgreSQL (DLP-02) and also travel in export-log objects, as does script content, for up to the log's bound, so the blob store is encrypted at rest: every write to an S3-compatible backend carries a server-side encryption request (SSE-S3 by default, or SSE-KMS by configuration), and the local backend needs an encrypted volume, which the operator provides and the server cannot verify.
- A complete backup has four independently recoverable parts: PostgreSQL, the blob store, the external authority journal of section 6, and a signed key-custody manifest. The manifest inventories every wrapping root and non-exportable dependency: the server master key, the `jobs` wrapping key, the `agent`, `device` and `radius` role data keys, the offline recovery custodian keys and their root-signed quorum manifest, each external KMS key and replica, and each PKCS#11 token and backup token. It also inventories the software-held keys and ciphertext the wrapping roots recover, including every issuing CA, server TLS, policy and command, audit, journal signing, RADIUS sealing, APNs, escrow and connector client key. Release and platform code-signing keys are project keys outside an installation backup and are named as external dependencies rather than copied.
- `ricevanta backup verify` restores the database and blob backup into an isolated instance, resolves each wrapping root through its declared recovery method, unwraps every software key, matches public keys to their stored certificates, signs and verifies a challenge with every signing key, and opens a fixture encrypted under every data-key class. For an external KMS or HSM, the procedure verifies access to a replicated key or backup token in the recovery environment; an identifier alone does not pass. The command writes the tested backup ids, authority-journal head and per-key result into the manifest and obtains the offline custodian signatures required by section 6.1. A backup without a passing result for every required key is incomplete. Docker Compose stores the database and blob copies, the role keys and the offline recovery material on separate operator-controlled media. Helm uses the PostgreSQL operator for the database, but the same manifest, blob, journal and key checks still apply.

## 6. Secrets

Secrets at rest use envelope encryption: a server master key from the environment, a file or an external KMS wraps per-secret data keys, so rotating the master key rewraps data keys without re-encrypting the data. The master key reaches only the `api` and `jobs` roles. Issuing CA key rows and the audit checkpoint and journal signing key rows are readable only by the `jobs` database credentials, and their data keys are wrapped under a `jobs`-scoped key that the master key does not unwrap, so an `api` replica, which holds the master key, can neither read nor unwrap a CA key or sign an audit checkpoint or journal head. Each agent-facing role (`agent`, `device`, `radius`) receives its own role-scoped data key from the environment, which unwraps only its TLS key and, for `radius`, the gateway shared secrets. `api` seals each gateway shared secret and binding token to the `radius` role's X25519 public key (HPKE base mode, RFC 9180), so `api` writes secrets it cannot later read back and only `radius` replicas open them; `jobs` performs routine sealing-key rotation with trusted replicas; compromise recovery must revoke copied database and deployment credentials, terminate old connections and replace the role wrapping key before replacement private material reaches trusted replicas, then regenerate gateway secrets without an overlap (`radius.md` section 5). Recovery secrets that originate on a device (BitLocker recovery passwords, LUKS recovery keys) are encrypted on the device to the escrow certificate's public key (HPKE base mode, RFC 9180), as is the FileVault recovery key (CMS), so the `agent` and `device` roles that terminate check-ins store ciphertext and only `jobs` opens it (`mdm.md` section 12). Issuing CA keys and the `device` role's TLS key may instead live in a PKCS#11 device or the KMS.

The inventory: issuing CA keys, server TLS private keys for the `agent`, `device` and `radius` roles, the policy and command signing key, the audit checkpoint and journal signing keys, the APNs push key and certificate, escrowed device recovery secrets (FileVault personal recovery keys, BitLocker recovery passwords, LUKS recovery keys, macOS lock PINs, Recovery Lock passwords, activation lock bypass codes), the escrow certificate key, RADIUS shared secrets, SCEP challenge secrets, break-glass second-factor seeds, directory bind credentials, OIDC and SAML client credentials, Git credentials, export, mail and webhook destination credentials, the `service` client key `jobs` presents to connectors, and connector bearer tokens.

### 6.1 External authority journal and restore fence

Restore is sealed until authority has been reconciled with an independent live journal. A backup, device report or operator-selected journal head cannot establish the latest authority. The journal covers grants and denies, certificate and identity state, enrollment and recovery tokens, approvals and target consumptions, roles and principal mappings, policies and assignments, commands and signed reports, compliance statements, extension grants and registrations, CRL numbers, signing-key state and all counter floors. PostgreSQL holds a projection of that state, not the recovery authority.

The required protocol has these invariants:

1. Authenticate the live head. Each organization has one signed head binding installation uid, organization, recovery epoch, writer fence, prepare sequence and hash, resolved sequence and hash, and authority-projection digest. `jobs` holds the journal signing key under its own wrapping key. The offline root certifies that key and the recovery quorum manifest. Read the configured store's current head directly; neither a database row nor a supplied object version may select it. Reject a lower cached fence, sequence or epoch, an invalid signature, a broken chain or a projection mismatch. Only a recovery transition with the required offline signatures can change the journal signer.
2. Serialize and fence writers. A coordinator holds the organization's PostgreSQL authority row lock from validation through the database commit. It also obtains exclusive ownership of the live head and a never-reused writer fence from the journal backend. Every prepare, commit and resolution compares the exact prior head and fence atomically. Taking over a writer cannot clear an unresolved prepare. A stale writer must fail both journal publication and the database apply check; a lease row, `O_EXCL` file creation or an S3 listing alone does not provide that fence.
3. Prepare before applying. An immutable, signed prepare contains request uid, resource uids, exact before and after hashes, recoverable canonical after-images or tombstones, consumed identifiers, reserved counter floors and the previous head hash. Secret values stay encrypted; hashes alone cannot recover a required secret. Advance the live head to include the prepare before the database transaction may commit. Reservations are never reused, even after abort. Denies and consumption in a prepare take effect conservatively; grants remain inactive.
4. Commit before exposure. The transaction validates the current fence and protected authority against the journal projection, applies the exact prepared change and writes its reference with synchronous commit. `jobs` then publishes a signed commit and advances the head atomically. Until that commit is in the authenticated resolved prefix, no role may expose a grant, signed artifact, issuance result or external side effect from the database rows. Retries return the same result by request uid and after-image hash. Readers and signers compare authority with the authenticated projection; a database writer cannot promote a pending grant or revive a consumed approval by changing a status column.
5. Resolve crashes without guessing. A prepare without a commit or resolution stops later authority writes. Exact matching database and action evidence may complete its commit. Otherwise the offline recovery quorum signs an `aborted` or `tampered` resolution binding the prepare and inspected evidence. Keep the original record, denies, consumptions and reserved floors. A missing row cannot prove that an action never committed. A signed resolution never resurrects authority or authorizes another use of a token or approval.

The local backend uses one coordinator on one host, a dedicated journal volume outside database and blob backup restores, an OS exclusive lock held across the entire prepare/apply/commit cycle, create-only record files, file and directory `fsync`, and an atomically replaced, synced signed head. A replacement process must acquire the same lock before reading or advancing the head. A second host or a network filesystem needs a qualified lock and fencing protocol; a copied volume is not a second live journal. Offline copies preserve closed segments and a custodian-signed head, but cannot prove that no later entries existed. Losing the live volume without an independently current head blocks recovery. Host root or a journal-volume administrator can tamper with local evidence; the design does not promise detection when that administrator controls every independent copy.

An S3-compatible backend must provide strongly consistent current-head reads and atomic conditional updates: `If-None-Match: *` creates immutable records and `If-Match` on the current ETag replaces the signed head. Conflicts require re-reading and resolving the winning head, never an unconditional retry. Versioning and Object Lock compliance retention protect every journal object version; store-policy denies prevent delete markers, unconditional head writes and early evidence removal by serving credentials. Object Lock alone allows a new version or a delete marker and is not a writer lock ([Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html)). Amazon S3 documents the conditional operations ([conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)); another backend must pass the same concurrency and durability fixtures rather than inherit those claims from API compatibility. Journal credentials, encryption and logs are separate from ordinary blob credentials; on AWS, enable access logging, CloudTrail data events and request metrics. Per-mutation objects and retained versions add request and storage costs. No cloud service is mandatory.

Recovery starts with only a local recovery API and metrics available. Read the live head, verify the backup's recorded head is its ancestor, replay the exact journal suffix and compare the complete authority projection. Missing ciphertext, a gap, an unproved head or an ambiguous prepare leaves serving sealed. Resources with incomplete evidence remain `recovery_pending`. A recovered grant needs a new request; tokens, approvals and target pairs from an earlier epoch cannot authorize new work. Revocations, disables, retired identities and consumed identifiers stay denied.

The offline ceremony uses independent Ed25519 custodian keys rather than a reconstructed shared key. The offline root signs a manifest binding installation uid, root fingerprint, threshold and each custodian public key. The default is two distinct signatures from three custodians; a declared single-administrator installation may choose one offline custodian key, with a persistent warning that the ceremony then proves separate credential possession, not separation of people. Before opening normal APIs, first-start setup creates this manifest and stores each private key on separate offline media, then consumes the local one-time setup token to create the first administrator. The bootstrap token cannot be reused for later authority changes. Adding the first provider or a second approver follows the ordinary protected flow or the offline ceremony when no unaffected approver exists.

For recovery, custodians independently inspect the live head, backup manifest, unresolved records, proposed state changes and key inventory on an offline workstation. Each signs the same canonical request binding installation, organization, exact prior head, backup digest, new 64-bit epoch, replacement journal signer and exact authority repair hashes. The recovery API verifies the pinned manifest, threshold, distinct signatures, prior head and unused request uid, then uses the journal's fenced update to append the transition. The transition and its consumption remain outside the restored database. An authority repair without a database restore uses the same ceremony and advances the epoch. Changing the quorum manifest requires the existing quorum and an offline-root signature. If enough keys or the current head are lost, normal recovery has no bypass.

Every installation-authority signature carries `recovery_epoch`; monotonic values compare `(recovery_epoch, counter)`, with both values unsigned 64-bit integers and exhaustion failing closed. CRL numbers use `recovery_epoch * 2^64 + counter`, within RFC 5280's 20-octet bound. Extension grants and registrations carry the epoch beside their generation. Recovery requires a new authorized issuance for certificates and signing identities; an epoch never relabels restored certificates. All roles maintain an independently expiring head/projection lease of at most five seconds. The timer closes authenticated streams and blocks authority use at expiry despite a stalled journal read. Signing, mutation, consumption and external dispatch additionally require the current writer fence and committed authority, not only the read lease. `pki.md` section 4 and `../specs/policy-envelope.md` sections 6 and 7 define endpoint epoch transitions.

`../specs/authority-journal-protocol.md` proposes the head, immutable records, database apply, publication and sealed restore. The row-lock and compare-and-swap composition does not establish cross-store ordering: a submitted head update or external effect can complete after PostgreSQL releases its timed-out lock. Authority implementation is blocked first on an independent gate or recipient fence with one proved linearization point. Exact schemas, the complete audit payload and replay model, deterministic reducers and dependency closure for every authority domain, signed external-action evidence, database DDL and grants, a model-checked transition system and fault-injection fixtures also remain blockers. The candidate does not change key custody.

## 7. Benefits, trade-offs, dependencies, limits, alternatives

Benefits: per-module schemas and the import-graph check keep the monolith splittable later; PostgreSQL handles routine coordination, while the independent journal prevents a database restore from becoming the authority source; the handler rules are the fixes comparable servers had to make after shipping; extension code never enters the server process, so a faulty connector cannot reach the signing keys or the database.

Trade-offs: the journal adds synchronous storage writes, retained evidence and a sealed recovery path; writing the DDM engine, the ACME server and EAP-TLS in-project is work that a library would otherwise carry, accepted because no maintained Apache-compatible library exists for any of the three; `NOTIFY` stays off every high-rate path because its commit lock is cluster-wide and scales with the rate of notifying commits; server-side extensions are separate connector processes with network round trips, because no Go WebAssembly runtime offers WASIp2 with fuel metering without cgo (EXT-05).

Dependencies: `cel-go`, `pgx`, `klauspost/compress`, `layeh/radius`, `radius-eap`, `go-oidc`, `go-ldap`, `elimity-com/scim`, `minio-go`, `clickhouse-go`, NanoMDM, `smallstep/crypto`, `micromdm/scep`, Fleet's MS-MDE2 code, the OpenSearch and Elasticsearch clients, `franz-go`, `go.opentelemetry.io/proto/otlp`, `grpc-go`, `protobuf-go`, `azlogs`, `azidentity`, `aws-sdk-go-v2` and `maxminddb-golang`; all with rows in `../licensing.md`.

Limits: the authority-journal candidate in section 6.1 remains blocked on cross-store ordering, typed records, audit replay, the domain model and fixtures named there; legal holds also need the cross-store capture and retention recovery specification in `events.md` section 5, and S3 delivery needs the immutable plan schema and recovery fixtures in `../specs/event-export.md` section 10; fleet-wide raw telemetry needs ClickHouse or an external destination; the bounded PostgreSQL mode is for investigations, not fleets; Sigma-to-SQL translation for investigation queries is written in-project, since no SigmaHQ-maintained ClickHouse or PostgreSQL backend exists; the SCIM library lacks bulk operations; the SAML library is unsettled until its activity check; the server cannot compile or inspect WebAssembly modules, so import enforcement happens on each agent.

Alternatives considered: Redis for caches and live results as Fleet uses it (rejected: a second stateful service; in-process caches and PostgreSQL cover the scale target); PostgreSQL session advisory locks for leader election (rejected: they pin a connection and fail behind transaction pooling; a lease row does not); TimescaleDB for event tables (rejected: retention and compression sit under the Timescale License; native partitioning covers the need); `pg_partman` (rejected: an extension in every image for what a small job does); OpenSearch as the bundled raw store (rejected: a JVM with heap and shard sizing for self-hosters, and its Sigma backend matters little since single-event rules evaluate on the agent; it stays an export destination); Elasticsearch and Loki as the raw store (rejected: license); Quickwit (rejected: an object-storage log search engine now owned by Datadog, verify, without the typed-column analytics the investigations need); a generated OpenAPI document (not chosen: generator support for 3.1 is partial); MicroMDM as the MDM base (rejected: in maintenance mode, its own notes point to NanoMDM); FreeRADIUS as a separate process (rejected: GPL-2.0); in-process server plugins on `wazero`, `wasmtime-go`, Go's `plugin` package or go-plugin (rejected by EXT-05).
