# PKI design

How devices get and keep their identity: the enrollment bootstrap, renewal and recovery, certificate issuance inside the server, and the policy signing certificate. The key table and who holds what are in `../architecture.md` section 4. Decisions: PKI-01 and PKI-02 in `../decisions.md`. Complete certificate profile constraints, OCSP, CRL serving for non-agent consumers, and the external CA protocol are open (`../analysis.md` section 3) and belong in this file.

## 1. Enrollment bootstrap

1. The installer package is the company-signed package, unchanged (PF-03). Enrollment configuration (server URL, the Ricevanta root CA certificate to pin, and an enrollment token) is delivered beside it: a root-only or SYSTEM-only file written by the deployment tool on every OS, an MDM-pushed configuration profile on macOS, or, as a fallback, a hidden MSI property on Windows, which stays out of installer logs but not out of the `msiexec` command line (verify). The agent deletes the token after use. The configuration's integrity rests on the distribution channel plus the pinned CA.
2. The token is scoped to a device group and expires. For any group whose devices may receive network-access certificates or MDM management, tokens are single-use and enrollment waits for administrator approval by default; multi-use tokens without approval are allowed only for groups limited to telemetry. The one multi-use exception is the Windows imaging token, which admits OMA-DM enrollment only and leaves every enrollment `pending` until approval (`mdm.md` section 10).
3. The agent creates its identity key in the `KeyStore` (hardware-backed from v0.3.x, `../roadmap.md`), collects hardware identifiers and a platform attestation where one exists (TPM on Windows and Linux, checked against an endorsement-key allow list the administrator imports; none for a macOS daemon, verify), and posts a certificate signing request with the token to `/agent/v1/enroll` over server-authenticated TLS against the pinned CA.
4. The `agent` role writes a request row; the `jobs` role records the device as pending or active and answers through `NOTIFY`. An active record receives the device identity certificate from the device issuing CA together with the policy signing certificate, the root-signed recovery quorum manifest and current epoch proof, and the agent API endpoint; a pending record receives only a request identifier, which the agent polls on `/agent/v1/enroll` with its token until approval or token expiry, so no certificate exists before approval. Network-access certificates are issued only to approved records.
5. All later traffic uses mTLS on `/agent/v1`.

Apple MDM enrollment, Windows OMA-DM enrollment and management certificates are separate flows that reuse the device record (MDM-01).

## 2. Renewal and recovery

- Agent identity renewal uses the private `POST /agent/v1/renew` protocol, not ACME. The body carries a server nonce, request uid, current certificate fingerprint, new public-key fingerprint and PKCS#10 certificate signing request. The current device identity key signs the canonical body as JWS; the certificate signing request self-signature proves the new key. mTLS with the current certificate admits the request, and `device-attest-01` may add platform evidence where available (verify the draft's status). Neither admission nor attestation replaces the two key proofs, which `jobs` verifies itself. The `agent` listener admits an expired, unrevoked certificate only on this path and only within the 30-day grace period.
- Agent-managed network certificate renewal also uses a private request: the enrolled device identity signs a nonce-bound body naming `network_access`, the immutable `netid`, current network certificate fingerprint and new certificate signing request hash. `jobs` verifies that device identity, the active network identity binding and the certificate signing request self-signature. The request cannot change the user, identity or profile. Native payload and third-party network clients use standard ACME with an authorized account registration for the same identity instead.
- Standard ACME lives on `/acme` for service connectors, third-party clients and clients of an Apple ACME payload. Its account key is separate from every certificate key, persists across orders and changes only through RFC 8555 `keyChange`; orders use identifiers and challenges from the stored registration and issuance policy, and `jobs` rejects a finalize request whose certificate signing request uses a known account key. RFC 8555 defines account and certificate keys as separate classes and defines account rollover through `keyChange` ([sections 7.3.5 and 11.1](https://www.rfc-editor.org/rfc/rfc8555.html#section-7.3.5)). The private agent protocol shares nonce, request-row and authorization machinery with ACME but no endpoint or account semantics.
- Beyond the grace period, after re-imaging, or when the current identity key is lost, an administrator issues a new token and approves recovery. Re-enrollment takes over an existing record only with proof of the previous identity key or that administrator approval; attestation and hardware identifiers may select and support review of the record but never authorize the takeover, since hardware identifiers are not secrets.
- The cached policy stays in force throughout (`agent.md`).

## 3. Issuance inside the server

Every certificate the `device` or `agent` role is asked for (enrollment, private agent renewal, ACME, SCEP for MDM payloads and network devices) becomes a request row. A request row is untrusted input, not an authorization decision: it holds the request identifier, channel, the raw protocol message, the transport principal the listener saw, and attestation evidence. Database grants let the exposed roles insert request rows and read only their own result status; they cannot write device, token, approval, account, certificate, certificate-profile or issuance-policy rows. ACME and private-renewal nonces live in separate namespaces in two tables: minted nonces, which an exposed role inserts with a database-set expiry, and consumed nonces, which only `jobs` writes. A nonce is valid once while minted and not consumed. Values are 128-bit random and unique in their namespace; consumed rows outlive the minted row's 10-minute expiry and recovery preserves their consumption (`backend.md` section 6.1).

The `jobs` role locks a pending request and independently authorizes it in one transaction. It applies request-size limits and deduplication first, then decrypts a SCEP envelope, verifies an ACME JWS against the ACME account row, or verifies a private-renewal JWS against the current device certificate key, and consumes the channel's nonce atomically. Parsing and decryption do not authorize issuance. `jobs` then verifies the certificate signing request self-signature and the token, challenge or attestation proof the channel requires.

For private agent renewal, `jobs` loads the authoritative device and current certificate, confirms that the device is eligible and the certificate unrevoked and either valid or expired within the 30-day grace period, and verifies the JWS with that certificate's key. An identical completed retry by request uid and certificate signing request hash returns the same persisted result and never issues another certificate; another signing key, an arbitrary expired certificate, or a certificate signing request for another device is refused. The issuance transaction makes the certificate signing request's key the next device identity key and supersedes the prior certificate. Until the device's first request signed by the new key, `jobs` accepts the superseded key only to download the persisted result or repeat the identical request, so a lost response cannot strand the device. Standard ACME renewal does not change its account key at issuance; `keyChange` is the only account-key replacement path.

`jobs` then loads the organization, device, enrollment state, group, approval, certificate profile and issuance policy from authoritative rows. From those rows it derives the subject, subject alternative names, issuer, lifetime, key usages and whether the request may issue. Caller-provided identity, group, approval, profile, subject, subject alternative name, lifetime and usage claims do not grant authority: `jobs` ignores them or rejects the request when the protocol requires them to equal the derived values. Enrollment consumes the stored token use atomically and applies only its stored group. When administrator approval is required, the approval row binds the request identifier, SHA-256 of the exact certificate signing request, derived device record and certificate profile; an approval for another request or certificate signing request does not authorize issuance. Network-access issuance requires an approved device record (PKI-02), an eligible stored profile and, for first issuance of an identity, the enrollment approval; renewal of an existing `netid` requires its channel-specific proof from section 2 and a still-eligible account or device binding; renewal never creates a new identity or broadens its profile. `jobs` records the authorization inputs and decision with the issued certificate.

Only after authorization does `jobs`, the only role holding issuing CA keys, sign, write the certificate and notify the requester. The requesting role returns the result, or a SCEP `PENDING` while it waits. A compromised agent-facing replica cannot make its identity, profile or approval claims authoritative and cannot mint outside a valid proof and stored policy. `jobs` applies per-principal issuance limits and deduplicates protocol request identifiers and certificate signing request hashes before costly cryptographic work when the protocol exposes those values before decryption. Direct request-row access still lets a compromised database role consume storage and queue capacity; deployment database quotas and monitoring bound and detect that denial of service, but do not eliminate it. The issuing CA keys sit under envelope encryption or in a PKCS#11 device; the root stays offline under the custodian quorum (PKI-01); the independently verifiable recovery ceremony is defined in `backend.md` section 6.1.

An external CA completion is an untrusted result, not issuance authority. Pending requests and callback tokens bind the connector registration, immutable package and component digests, exact request uid and CSR hash, issuance-field digest, recovery epoch and both component and registration generations (`extensions.md` section 6.2).

`jobs` reloads committed authority and validates the returned certificate under the same fenced transaction before consuming the result. Disable, revocation, expiry or a grant or registration change invalidates pending authority and queued completions; an external certificate already issued requires separate reconciliation or revocation. A restored callback never gains a new epoch. Connector schemas and fault fixtures remain implementation blockers.

The `service` certificate profile is issued by the server issuing CA to two kinds of holder: service connectors as TLS servers, with the subject and SAN `jobs` derives from the connector's registration row, and `jobs` itself as a TLS client with subject `CN=io.ricevanta.jobs`, which no registration can obtain (`extensions.md` section 6.2). A connector enrolls through ACME with a registration token, as third-party clients do, and renews through ACME; certificates last 90 days and are revocable from the console. The profile's remaining details are open (`../analysis.md` section 3).

The network-access profile is issued from the network-access issuing CA to an identity row (`netid`, kind `device` or `user_device`, device, user, profile, state) that `jobs` mints with 128 random bits and never reuses. Unique constraints cover `(organization, netid)` for every identity and the canonical identity mapping `(organization, kind, device, user, profile)` for active identities, with null users treated as equal. Retired identities and their names remain as tombstones; an epoch transition may mint a new active identity for the same device and profile without reusing the retired `netid`.

A child name table maps each UPN and DNS SAN value to exactly one identity and has a unique constraint on `(organization, name_type, value)`. Certificates reference the identity and a certificate generation; certificate SAN columns are not unique, so old and new certificates for one identity may overlap during renewal.

`jobs` writes SAN `otherName` UPN `<netid>@<realm>`, SAN `dNSName` `<netid>.<realm>` and `CN=<netid>` from the name row and ignores names in the certificate signing request. Renewal keeps the identity and `netid`; the superseded certificate is revoked (`superseded`) when the agent reports the new one installed or 24 hours after issuance.

Renewal overlap does not identify which generation a gateway authenticated. Name-only RADIUS requests expose identity-level facts with unknown generation; serial, fingerprint, issuer and validity require an exact observed binding under `radius.md` sections 3 and 6. Revoking a possible generation targets name-only sessions conservatively under that design.

Lifetime 30 days and ECDSA P-256 are the defaults. The `network-gateway` profile (`clientAuth`, subject from the RADIUS gateway registration) authenticates gateways to RadSec, and the `radius` role's EAP and RadSec server certificates come from the server issuing CA. Gateways check revocation through the OCSP responder and CRL this module serves (`radius.md`). A suspended device's network-access certificates are placed on the CRL with reason `certificateHold` and released on resume (MDM-02, `mdm.md` section 1.2).

Management certificates reuse the device record (MDM-01): the Apple MDM identity is issued through the ACME payload with hardware binding where the device supports it and SCEP as the fallback, and the Windows OMA-DM management certificate through MS-WSTEP, both as request rows that `jobs` authorizes under section 3 against the enrollment token and device record (`mdm.md` sections 9 and 10). The escrow certificate is issued by the server issuing CA to `jobs`, which alone holds its private key and opens escrowed recovery secrets: macOS wraps the FileVault recovery key to it, and the agent seals BitLocker and LUKS recovery secrets to its P-256 public key with HPKE, delivered in the signed bundle (`mdm.md` section 12, `backend.md` section 6).

## 4. Policy signing certificate

The organization's policy and command signing key has its public key in a short-lived certificate (90 days) from the device issuing CA. Agents accept it only when it chains to the pinned root through that issuing CA, carries the subject `CN=io.ricevanta.policy-signing, O=<organization>`, the Ricevanta policy-signing extended key usage (an OID under the project's UUID-derived arc `2.25.<uuid>` per ITU-T X.667, which needs no registration) and an Ed25519 key, and is absent from the issuing CA's CRL, fetched from `/agent/v1/crl` outside the bundle channel the key signs; no other certificate under the root, such as a device, network-access or third-party certificate, is accepted for signing. The CRL carries `nextUpdate` (default validity 7 days, refreshed with every policy fetch) and a CRL number encoded from the recovery epoch and its counter (`backend.md` section 6.1); RFC 5280 requires that number to increase for a CRL scope and permits values up to 20 octets ([section 5.2.3](https://www.rfc-editor.org/rfc/rfc5280.html#section-5.2.3)). An agent refuses a CRL number below its cached value and installs no new bundle or command while its cached CRL is past `nextUpdate`, while cached policy stays in force.

An epoch transition follows the sealed recovery gate of `backend.md` section 6.1, whose executable journal protocol remains an implementation blocker. A transition does not revive or relabel certificates from restored rows. Every Ricevanta private certificate carries the recovery epoch in a non-critical private extension, and exposed roles refuse an older epoch after transition. Standard ACME certificates without that extension remain `recovery_pending` until a new order is authorized. Device, management and service identities recover through new approved issuance. Network identities receive a new `netid`, which makes a certificate-derived request using an old certificate fail lookup even when the gateway cannot pass its serial; the old identity stays retired. Server and issuing certificates are reissued under the offline root before serving resumes. The enrollment path can serve the quorum-signed transition chain and fresh recovery request status without accepting an old credential for other operations. An endpoint records the higher epoch and its proof durably before using replacement credentials. An offline endpoint that has not received the transition keeps cached enforcement; recovery cannot make that endpoint learn new deny facts while disconnected. A server certificate for the `agent` role is accepted only when it chains through the active server issuing CA, carries `serverAuth` and matches the configured name. Rotation is delivered in the next bundle; ordinary signing-key compromise recovery uses revocation and does not require re-enrollment.

## 5. Benefits, trade-offs, dependencies, limits, alternatives

Benefits: a stolen token cannot become a VPN credential or take over another device's record; issuance in `jobs` keeps CA keys out of every internet-facing process; the grace period lets devices that retain their current identity key recover from long outages without administrator action; revocation of the signing key is independent of the channel it protects.

Trade-offs: single-use tokens with approval add administrator work per device, accepted as the default for groups that carry network access or management; issuance through a request row adds one round trip; a hidden MSI property is still visible on the command line, so the file delivery is preferred.

Dependencies: `smallstep/crypto`, `micromdm/scep`, and on the agent `rustls`, `rustls-cng`, `security-framework`, `tss-esapi`; all with rows in `../licensing.md`.

Limits: no attestation exists for a macOS daemon (verify), so macOS enrollment rests on the token and approval; Linux hosts without a TPM enroll with a software key flagged per device. Where attestation exists, it is admission and review evidence only, not a substitute for the current-key proof in renewal or administrator-approved lost-key recovery.

Alternatives considered: enrollment configuration embedded in the installer (rejected: the company-signed package cannot be rebuilt per installation); multi-use tokens without approval as the default (rejected: a stolen token would enroll any machine); attestation-only renewal or recovery (rejected: attestation does not prove possession of the enrolled identity key or authorize record takeover); re-enrollment matched on serial numbers (rejected: not secrets); SCEP for the agent (rejected: commonly assumes RSA, Secure Enclave keys are P-256); revocation of the signing key through the bundle channel (rejected: the bundle is signed by the key being revoked).
