# PKI design

How devices get and keep their identity: the enrollment bootstrap, renewal and recovery, certificate issuance inside the server, and the policy signing certificate. The key table and who holds what are in `../architecture.md` section 4. Decisions: PKI-01 and PKI-02 in `../decisions.md`. Certificate profiles and lifetimes, OCSP, CRL serving for non-agent consumers, and the external CA protocol are open (`../analysis.md` section 3) and belong in this file.

## 1. Enrollment bootstrap

1. The installer package is the company-signed package, unchanged (PF-03). Enrollment configuration (server URL, the Ricevanta root CA certificate to pin, and an enrollment token) is delivered beside it: a root-only or SYSTEM-only file written by the deployment tool on every OS, an MDM-pushed configuration profile on macOS, or, as a fallback, a hidden MSI property on Windows, which stays out of installer logs but not out of the `msiexec` command line (verify). The agent deletes the token after use. The configuration's integrity rests on the distribution channel plus the pinned CA.
2. The token is scoped to a device group and expires. For any group whose devices may receive network-access certificates or MDM management, tokens are single-use and enrollment waits for administrator approval by default; multi-use tokens without approval are allowed only for groups limited to telemetry.
3. The agent creates its identity key in the `KeyStore` (hardware-backed from v0.3.x, `../roadmap.md`), collects hardware identifiers and a platform attestation where one exists (TPM on Windows and Linux, checked against an endorsement-key allow list the administrator imports; none for a macOS daemon, verify), and posts a certificate signing request with the token to `/agent/v1/enroll` over server-authenticated TLS against the pinned CA.
4. The `agent` role writes a request row; the `jobs` role records the device as pending or active and answers through `NOTIFY`. An active record receives the device identity certificate from the device issuing CA together with the policy signing certificate and the agent API endpoint; a pending record receives only a request identifier, which the agent polls on `/agent/v1/enroll` with its token until approval or token expiry, so no certificate exists before approval. Network-access certificates are issued only to approved records.
5. All later traffic uses mTLS on `/agent/v1`.

Apple MDM enrollment, Windows OMA-DM enrollment and management certificates are separate flows that reuse the device record (MDM-01).

## 2. Renewal and recovery

- Renewal runs through ACME on `/agent/v1/acme` (RFC 8555) with a Ricevanta pre-authorization. The ACME account key is the device identity key: every request is a JWS signed by that key over a server `Replay-Nonce`, and the finalize request carries a certificate signing request whose self-signature proves possession of the new key, so the current key authorizes the replacement and the new key is proved inside the ACME messages. The account key changes at issuance rather than through `keyChange` (section 3), a deviation from RFC 8555 that the in-project server and client share. mTLS with the current identity certificate admits the request; `device-attest-01` may add platform evidence where available (verify the draft's status). Neither admission nor attestation replaces the JWS and certificate signing request proofs, which `jobs` verifies itself (section 3). The `agent` listener verifies client certificates itself so that this path admits an expired, unrevoked certificate within the 30-day grace period.
- Beyond the grace period, after re-imaging, or when the current identity key is lost, an administrator issues a new token and approves recovery. Re-enrollment takes over an existing record only with proof of the previous identity key or that administrator approval; attestation and hardware identifiers may select and support review of the record but never authorize the takeover, since hardware identifiers are not secrets.
- The cached policy stays in force throughout (`agent.md`).

## 3. Issuance inside the server

Every certificate the `device` or `agent` role is asked for (enrollment, ACME, SCEP for MDM payloads and network devices) becomes a request row. A request row is untrusted input, not an authorization decision: it holds the request identifier, channel, the raw protocol message (the ACME JWS, the SCEP envelope, or the enrollment certificate signing request with its token), the transport principal the listener saw, and attestation evidence. Database grants let the exposed roles insert request rows and read only their own result status; they cannot write device, token, approval, certificate, certificate-profile or issuance-policy rows. ACME nonces live in two tables: minted nonces, which any role inserts with a database-set expiry, and consumed nonces, which only `jobs` writes; a nonce is valid once, while it is in the first table and absent from the second, and the scheme rests on that consumption, not on who minted the value. Nonce values are 128-bit random and unique in the minted table, consumed rows outlive the minted row's database-set expiry (10 minutes), and a replay of a renewal JWS after issuance fails in any case because the stored account key has changed.

The `jobs` role locks a pending request and independently authorizes it in one transaction. It applies request-size limits and deduplication first, then parses the protocol message: it decrypts a SCEP envelope, or verifies the ACME JWS signature against the account key stored for the device and consumes the nonce atomically, rejecting a reused or unknown one. Parsing and decryption do not authorize issuance. `jobs` then verifies the certificate signing request self-signature and the token, challenge or attestation proof the channel requires.

For renewal, `jobs` loads the authoritative device and current certificate, confirms that the device is eligible and the certificate unrevoked and either valid or expired within the 30-day grace period, and verifies that the JWS account key is that certificate's key. An identical completed retry by request uid and certificate signing request hash returns the same persisted result and never issues another certificate; a JWS by another key, an arbitrary expired certificate, or a certificate signing request for another device is refused. The issuance transaction replaces the stored account key with the certificate signing request's key and supersedes the prior certificate, so the next renewal is signed by the new key; RFC 8555 `keyChange` is not used, since the account key changes only at issuance. Until the device's first request signed by the new key, `jobs` also accepts the superseded key for the certificate download and for an identical finalize retry, so a lost response cannot strand the device.

`jobs` then loads the organization, device, enrollment state, group, approval, certificate profile and issuance policy from authoritative rows. From those rows it derives the subject, subject alternative names, issuer, lifetime, key usages and whether the request may issue. Caller-provided identity, group, approval, profile, subject, subject alternative name, lifetime and usage claims do not grant authority: `jobs` ignores them or rejects the request when the protocol requires them to equal the derived values. Enrollment consumes the stored token use atomically and applies only its stored group. When administrator approval is required, the approval row binds the request identifier, SHA-256 of the exact certificate signing request, derived device record and certificate profile; an approval for another request or certificate signing request does not authorize issuance. Network-access issuance requires that exact approval, an approved device record and an eligible stored profile. `jobs` records the authorization inputs and decision with the issued certificate.

Only after authorization does `jobs`, the only role holding issuing CA keys, sign, write the certificate and notify the requester. The requesting role returns the result, or a SCEP `PENDING` while it waits. A compromised agent-facing replica cannot make its identity, profile or approval claims authoritative and cannot mint outside a valid proof and stored policy. `jobs` applies per-principal issuance limits and deduplicates protocol request identifiers and certificate signing request hashes before costly cryptographic work when the protocol exposes those values before decryption. Direct request-row access still lets a compromised database role consume storage and queue capacity; deployment database quotas and monitoring bound and detect that denial of service, but do not eliminate it. The issuing CA keys sit under envelope encryption or in a PKCS#11 device; the root stays offline under the M-of-N quorum (PKI-01).

## 4. Policy signing certificate

The organization's policy and command signing key has its public key in a short-lived certificate (90 days) from the device issuing CA. Agents accept it only when it chains to the pinned root through that issuing CA, carries the subject `CN=io.ricevanta.policy-signing, O=<organization>`, the Ricevanta policy-signing extended key usage (an OID under the project's IANA Private Enterprise Number) and an Ed25519 key, and is absent from the issuing CA's CRL, fetched from `/agent/v1/crl` outside the bundle channel the key signs; no other certificate under the root, such as a device, network-access or third-party certificate, is accepted for signing. The CRL carries a CRL number and `nextUpdate` (default validity 7 days, refreshed with every policy fetch): an agent refuses a CRL whose number is below its cached one and installs no new bundle or command while its cached CRL is past `nextUpdate`, while cached policy stays in force. A server certificate for the `agent` role is accepted only when it chains through the server issuing CA, carries the `serverAuth` key usage and matches the configured name. Rotation is a new certificate delivered in the next bundle; a compromised key is revoked in the CRL, so recovery never requires re-enrolling devices.

## 5. Benefits, trade-offs, dependencies, limits, alternatives

Benefits: a stolen token cannot become a VPN credential or take over another device's record; issuance in `jobs` keeps CA keys out of every internet-facing process; the grace period lets devices that retain their current identity key recover from long outages without administrator action; revocation of the signing key is independent of the channel it protects.

Trade-offs: single-use tokens with approval add administrator work per device, accepted as the default for groups that carry network access or management; issuance through a request row adds one round trip; a hidden MSI property is still visible on the command line, so the file delivery is preferred.

Dependencies: `smallstep/crypto`, `micromdm/scep`, and on the agent `rustls`, `rustls-cng`, `security-framework`, `tss-esapi`; all with rows in `../licensing.md`.

Limits: no attestation exists for a macOS daemon (verify), so macOS enrollment rests on the token and approval; Linux hosts without a TPM enroll with a software key flagged per device. Where attestation exists, it is admission and review evidence only, not a substitute for the current-key proof in renewal or administrator-approved lost-key recovery.

Alternatives considered: enrollment configuration embedded in the installer (rejected: the company-signed package cannot be rebuilt per installation); multi-use tokens without approval as the default (rejected: a stolen token would enroll any machine); attestation-only renewal or recovery (rejected: attestation does not prove possession of the enrolled identity key or authorize record takeover); re-enrollment matched on serial numbers (rejected: not secrets); SCEP for the agent (rejected: commonly assumes RSA, Secure Enclave keys are P-256); revocation of the signing key through the bundle channel (rejected: the bundle is signed by the key being revoked).
