# Footprint harness and baseline

The AG-09 performance gate for the processes hosted CI can run: it measures `ricevanta-agent` on the three native GitHub-hosted runners, records an evidence document, enforces the absolute budgets of blueprint section 7 and [agent design section 6](../design/agent.md#6-memory-budget), and fails on regression against a baseline. Sensors, the driver, system extensions and everything that needs a real machine stay on the self-hosted gate of `design/agent.md` section 7; this harness never claims them.

Authorities: AG-02, AG-08, AG-09 and AG-13 in [decisions](../decisions.md), [agent design](../design/agent.md) sections 6 and 7, [platform qualification](platform-qualification.md) section 7, [release builds](release-builds.md) section 6, [CI hardening](ci-hardening.md) sections 6 and 8, [the agent runtime](agent-runtime.md) and [the implementation plan](../plans/footprint-harness.md), which is the single home of the CI job, its leaf IDs and the build command.

## 1. Boundary

The harness lives in `tests/footprint/`, runs on the Python release named in `.github/python-version` (the one validator interpreter of CI hardening section 8; [CI hardening plan](../plans/ci-hardening.md) Task 6 moves every workflow, including the three native agent hosts, to that file). `measure.py`, `check.py`, the fixture writer helper and the samplers import the standard library only; the unit test `test_measure.py` validates evidence with `jsonschema` from the validator closure of CI hardening section 8, which the `footprint-unit` job installs on each of the three native hosts with that section's hash-locked command. The harness consists of `measure.py`, `check.py`, one sampler module per OS under `samplers/`, run profiles under `profiles/`, the budget file `budgets.json`, baselines under `baselines/`, a fake agent and shared fixture writer helper for its own tests, and unit tests. It starts the agent in `run` mode with a disposable configuration, samples the agent's process externally, reads the agent's own health document for a cross-check, and writes one evidence document. It does not modify the agent, needs no privilege, loads no third-party package outside that test and never sends anything off the runner.

What it measures now: the agent core alone. Each later process (`ricevanta-updater`, `ricevanta-scan`, `ricevanta-ext`, `ricevanta-session`, `ricevanta-nmhost`) joins the evidence `processes` list with its own budget row when its slice lands; the aggregate check then sums the per-OS private metric over all listed processes, which is the AG-02 idle definition. A process that is absent from the list is not measured, and a budget row without a process fails.

Linux release measurements consume the [admitted build-root recipe](linux-build-root.md#4-building-in-the-root), including its ABI, per-executable link-map and distribution-probe evidence. Measure the resulting binary on the hosted runner, not inside a probe container; a root or probe failure blocks measurement. The candidate and baseline retain the same environment matching rules in section 6.

## 2. Metrics and samplers

Each sample is taken once per second from outside the agent and records footprint, CPU, threads and descriptors. Only `footprint_bytes` and the `footprint_metric` values take their names and units from the OCSF `process_sample` object in [the field catalogue](../../schemas/ocsf/contract-fields.md); the descriptor count and its `kind` (`fd` or `handle`) carry the meaning of the catalogue's `fd_count` and `handle_count` under the harness's own name, and threads are a harness field the catalogue does not define. Event rate, the fourth AG-09 quantity, is measured once the agent produces events, through a later profile. CPU differs from the catalogue as well: the harness records `cpu_core_pct`, `100 × Δ(cpu time) / Δ(wall time)` over the phase after warm-up, so one fully busy core is 100 and the value is independent of the runner's core count. The catalogue's `cpu_pct` divides by the logical processor count as well; it is derivable as `cpu_core_pct / cpu_count` from the recorded `cpu_count`, and the budgets in section 4 are stated per core, which is stricter than the normalized figure on every runner.

| Quantity | Linux x64 | macOS ARM64 | Windows x64 |
|---|---|---|---|
| `footprint_bytes` | `Pss` from `/proc/<pid>/smaps_rollup`, the sum over all mappings of the proportional share ([kernel proc documentation](https://www.kernel.org/doc/html/latest/filesystems/proc.html)); metric `pss` | `ri_phys_footprint` from `proc_pid_rusage(pid, RUSAGE_INFO_V4)` through `ctypes` on `/usr/lib/libproc.dylib`, with `rusage_info_v4` declared as 16 bytes of `ri_uuid` plus 35 `uint64_t` fields, 296 bytes, from [resource.h](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/bsd/sys/resource.h) and the signature from [libproc.h](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/libsyscall/wrappers/libproc/libproc.h); metric `phys_footprint` | `PrivateWorkingSetSize` from `GetProcessMemoryInfo` with `PROCESS_MEMORY_COUNTERS_EX2` through `ctypes.WinDLL("kernel32", use_last_error=True)` (`K32GetProcessMemoryInfo`), process handle opened with `PROCESS_QUERY_LIMITED_INFORMATION` ([GetProcessMemoryInfo](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-getprocessmemoryinfo), [PROCESS_MEMORY_COUNTERS_EX2](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2)); a value of 0 is a failed sample; metric `private_working_set` |
| `cpu_core_pct` | `utime + stime` from `/proc/<pid>/stat` fields 14 and 15 in `USER_HZ` ticks, parsed after the last `)` ([proc_pid_stat](https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html)); `USER_HZ` is the kernel's fixed user-interface tick rate of 100 ([uapi param.h](https://raw.githubusercontent.com/torvalds/linux/master/include/uapi/asm-generic/param.h)), and the harness records `os.sysconf("SC_CLK_TCK")` beside it and fails if the two differ | `ri_user_time + ri_system_time`, Mach absolute time converted to nanoseconds with `mach_timebase_info` from `/usr/lib/libSystem.B.dylib`; the harness records `numer` and `denom` in the evidence | `GetProcessTimes` kernel plus user time in 100 ns units ([GetProcessTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes)) |

`ctypes` loads `libproc.dylib` and `libSystem.B.dylib` by their absolute `/usr/lib` paths, never by a bare leaf name that the loader would search along the environment and working directory first; `kernel32` is a known system DLL. Structures are declared with `_fields_` and sizes are asserted before any call ([ctypes](https://docs.python.org/3/library/ctypes.html)). A failed call records a failed sample; the phase fails when more than 1 % of its samples failed or when the footprint summary is 0. The harness and the agent run as the same unprivileged runner user on every OS; no `sudo` is used and none is needed.

Environment record: `runner_os` and `runner_arch` from `RUNNER_OS` and `RUNNER_ARCH`, `run_id` and `run_attempt` from `GITHUB_RUN_ID` and `GITHUB_RUN_ATTEMPT` ([GitHub variables](https://docs.github.com/en/actions/reference/workflows-and-actions/variables)); `runner_label` from the workflow matrix (`ubuntu-26.04`, `windows-2025`, `macos-26`, the [release agent runners](release-builds.md#3-required-outputs-and-native-jobs), with Linux using the admitted platform identity `linux-x64-ubuntu26.04`); `os_version` is the per-OS comparison key of section 6, with the full vendor string in `os_release`; `cpu_count` from `os.cpu_count()`; `memory_bytes` from `os.sysconf("SC_PHYS_PAGES") * os.sysconf("SC_PAGESIZE")` on Linux and macOS ([sysconf](https://man7.org/linux/man-pages/man3/sysconf.3.html); Apple's `unistd.h` defines `_SC_PHYS_PAGES` and `_SC_PAGESIZE` ([Libc unistd.h](https://github.com/apple-oss-distributions/Libc/blob/main/include/unistd.h)), and CPython maps `SC_PHYS_PAGES` whenever the platform header defines it ([posixmodule.c](https://github.com/python/cpython/blob/v3.14.0/Modules/posixmodule.c))) and from `GlobalMemoryStatusEx().ullTotalPhys` on Windows ([GlobalMemoryStatusEx](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-globalmemorystatusex)); `clk_tck` on Linux and `mach_timebase` on macOS as above. Hosted runners for public repositories provide 4 vCPU and 16 GB on Linux and Windows and 3 CPU and 7 GB on macOS ARM64 ([GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)); the evidence records the observed values rather than assuming them.

## 3. Phases, profiles and identity

A phase is one complete agent run under one profile, in a fresh temporary directory tree (state, runtime, logs) that the harness deletes afterwards. Before any phase the harness hashes the binary and records the binary's own `ricevanta-agent version --json` output as `binary.reported_identity`; `--identity PATH` names the release identity file whose four fields become `identity`, and `check.py` fails the run with `identity_mismatch` when the two differ, so evidence can never claim an identity the measured binary does not report. Without `--identity` the evidence is marked `smoke: true` with `identity: null` and can be neither a gate result nor a baseline. The harness then copies the phase's profile into the temporary tree as `agent.json` with mode `0600` (on Unix the agent refuses a configuration file that grants group or others any access, [agent runtime section 3.1](agent-runtime.md#31-file-protection)) and starts `ricevanta-agent run --config <copy> --state-dir ... --runtime-dir ... --log-dir ... --log file`, polls the health document until `state` is `ready` (at most 30 s; otherwise `measure.py` stops the agent, prints `not_ready` with the phase name and exits 1 without writing evidence, because a phase without samples has nothing to judge), discards a warm-up of 10 s, samples for the phase duration, then sends the stop request (`SIGTERM` on Unix, `CTRL_BREAK_EVENT` through `GenerateConsoleCtrlEvent` on Windows, where the agent is started in its own process group) and records the shutdown duration and exit code, which must be 0 within `shutdown.timeout_ms` plus 5 s.

| Phase | Profile | Duration | What it exercises |
|---|---|---|---|
| `idle` | `profiles/idle.json`: `health.interval_ms` 60000, `log.level` `info` | 120 s | The resting runtime: executor, signal listeners, sampler every minute, log file open |
| `load` | `profiles/health-burst.json`: `health.interval_ms` 100, `log.level` `debug`, `log.max_file_bytes` 65536 | 60 s | The sampler and health writer at 10 Hz, one bounded `sample_completed` debug event per successful tick and at least one observed log rotation during measurement |

Profiles are complete `agent.json` documents validated against [the agent configuration schema](../../schemas/agent/config/v1/config.schema.json); the evidence records each profile's SHA-256 so a changed profile is visible. Later slices add profiles for the spool writer, policy compilation and event upload against a local fake, each with its own budget row; a profile is never removed, only superseded with a documented reason in the plan.

Per phase and metric the harness records `min`, `max`, `mean`, `p50` and `p95` by nearest rank over all samples after warm-up, the sample count, and the agent's own last health sample captured before sending the stop request. The runtime's sampled timestamps identify the sample, not the later health write. The one-second observations and p95 budget measure sustained footprint; they cannot bound a transient peak between observations. The sampler allocation proof belongs to [runtime section 7](agent-runtime.md#7-health-and-the-self-sampler). `--duration-scale F` below 1 shortens phases for a local smoke check and marks the evidence `smoke: true`.

### 3.1 Workload evidence

Record phase `started_unix_ms` and `finished_unix_ms` around the measured window, excluding warm-up and shutdown; `duration_ms` is the elapsed monotonic time. Poll health at both boundaries and with every one-second external observation. On Windows, harness health and log reads use `CreateFileW` through `ctypes` with `FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE`, close promptly and then parse the copied bytes, so the observer permits the replacement and rotation it measures ([CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)). In `health_progress`, record the launched child's `pid` and retain `start` and `end` snapshots, `observations`, `invalid_observations`, `counter_regressions`, `max_write_age_ms`, `max_sample_age_ms` and `max_observation_gap_ms`. Each snapshot records its read time as `observed_unix_ms` and `observed_elapsed_ms` (monotonic milliseconds since measured-window start), then contains `pid`, `state`, `interval_ms`, `written_unix_ms`, `uptime_ms`, the sample's `sampled_unix_ms` and `sampled_uptime_ms`, and counters `samples`, `sample_failures`, `log_errors`, `health_write_failures`, `log_rotations`. A missing, malformed or null-process read is a null snapshot and increments `invalid_observations`; never reuse a successful read to hide it. Also count as invalid a wrong child pid, non-ready state, interval differing from the committed profile, timestamp ordering violation, counter advancement without advancing sample timestamps, or any write/sample timestamp in the future. A counter decrease increments `counter_regressions`. These aggregates summarize every read, including intervening ones, not just the endpoints.

For each read, age is the larger of wall-clock age (`read_unix_ms` minus the sample/write wall timestamp) and elapsed monotonic time since the first observation minus the corresponding uptime advancement from that observation, clamped at zero. This prevents a health writer that rewrites old samples from refreshing their age. Wall-clock reversal or a wall/monotonic elapsed discrepancy greater than 2,000 ms fails freshness; record it in `invalid_observations`. Require both maximum ages at most `H + 2,000 ms`, where `H` is the interval from the committed profile, not the agent. Require `max_observation_gap_ms <= 2,000`, at least `floor(D / 1,000)` observations plus the two boundary reads, and boundary reads inside the window and within 1,000 ms of its edges, where `D` is the measured duration. `observations` counts reads, including failed reads. `check.py` rechecks endpoint identity, state, interval, timestamp ordering, boundary placement and age directly, and refuses summaries whose maxima are smaller than an endpoint age; it does not trust a zero invalid count to excuse a bad endpoint. All times and counters are bounded by the evidence schema; overflows fail measurement.

For full gate runs let `N = floor(D / H)` and require the successful-sample delta from `start` to `end` between `max(1, N - floor(N / 100))` and `ceil(D / H) + 1`, inclusive. The lower bound allows at most 1 % missed calls, the upper bound allows boundary rounding but refuses catch-up bursts. Use the monotonic distance between the endpoint reads for this delta calculation when a boundary read is delayed; use the full window duration for the phase-duration gate. Both endpoints must be valid, no counter may regress, and `sample_failures` and `health_write_failures` must not increase. The final sample must originate inside this phase's measured window. Full runs must retain the section 3 profile durations; a shortened phase is smoke evidence. For smoke windows shorter than `H`, record progress without claiming the gate; freshness still applies. Health remains local diagnostic evidence, not an attestation against a compromised binary or host.

`self_sample` is the final pre-stop process projection, with its sampled timestamps and health write timestamp; those timestamps must equal `health_progress.end`. `self_sample_external` records `unix_ms`, `footprint_bytes` and `footprint_metric` of the nearest successful external sample to `sampled_unix_ms`, using the earlier observation on a tie. Keep the external observations in memory until selecting this pair. The pair must lie inside the measured window, within 2,000 ms of the self-sample, and use the same metric. `check.py` derives agreement from this pair, never from an existing `results` verdict or a difference measured against the health write time. For a smoke window shorter than `H`, a fresh non-null self-sample taken before the window yields `recorded` agreement, not a gate pass; missing or stale health still fails.

During `load`, read the bounded active log and rotations every second and at both boundaries, accepting only complete valid JSON lines under the runtime's limits. Deduplicate `sample_completed` by `sample` and `log_rotated` by `rotation`, with bounded sets sized to the phase's maximum expected events. Count events only when their sequence is above the start snapshot and at most the end snapshot, and `sampled_uptime_ms` for a debug event is in the measured window. A rotation marker must be the first line of its new file. Record `log_activity` with `sample_events`, `rotations_observed` and `invalid_lines`; no log text enters evidence. Require at least the progress lower bound of distinct debug events, at least one observed rotation, a matching increase in `log_rotations`, no invalid lines and no increase in `log_errors`. Re-reading a retained file or seeing a warm-up rotation cannot pass the load check. At `idle`, record log activity without requiring rotation. A shortened smoke load records log activity without requiring rotation; it cannot establish this workload gate. All full runs use the same gate on every OS.

### 3.2 Atomic replacement by Python fixture writers

The fake agent and fixture writers share `tests/footprint/windows_io.py` for health publication and log renames. On Linux and macOS it calls `os.replace` once. On Windows it performs one handle-based extended rename with replacement and POSIX semantics; it never tries a legacy rename first. This gives the fixture the open-target replacement capability of the pinned [Rust standard library](https://github.com/rust-lang/rust/blob/1.99.0/library/std/src/sys/fs/windows.rs), which the Windows agent adapter calls. [CPython 3.14.8](https://github.com/python/cpython/blob/v3.14.8/Modules/posixmodule.c) implements `os.replace` using `MoveFileExW` with `MOVEFILE_REPLACE_EXISTING` alone. Matching the required capability does not require copying Rust's fallback sequence or changing agent code.

The helper is used only for fixture-owned ordinary files in the same real parent directory within the caller's fresh temporary tree. The caller finishes and closes the source write before replacement; the source exists and the destination may be absent or an ordinary file. On Windows, require distinct absolute paths with the same normalized parent, no embedded NUL, directory, stream syntax, device/UNC namespace, symlink or reparse-point input; reject these before opening the source. The caller owns the parent and its ancestors for the operation, so this is not a general path-confinement or hostile-local-process primitive. Same-directory use supplies the same-volume requirement; an OS volume or access error remains a failure. Do not copy, unlink the target, alter attributes/ACLs, create parents, retry or sleep. The helper changes only the rename operation, not writing, flushing, log order, reader sharing or durability claims.

Windows bindings use the standard library's [`ctypes.WinDLL('kernel32', use_last_error=True)`](https://docs.python.org/3.14/library/ctypes.html), with explicit `argtypes` and `restype` for every call and pointer-width handles. Bind lazily, so import and injected-API tests require no Windows DLL on other hosts. The operation is:

1. Validate paths and construct the complete bounded rename buffer before acquiring a handle. Encode the absolute destination as strict UTF-16LE; count encoded bytes, not Python characters, and exclude the terminating two zero bytes from `FileNameLength`. Reject an unpaired surrogate and more than 32,766 UTF-16 code units before the terminator. This fixture bound is not a promise that every such path is accepted by the filesystem.
2. Open the source once with [`CreateFileW`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew): `DELETE` access (`0x00010000`), `FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE` (`7`), null security attributes, `OPEN_EXISTING` (`3`), `FILE_FLAG_OPEN_REPARSE_POINT` (`0x00200000`) and null template. Do not open the destination, grant extra access or make the handle inheritable. Treat `INVALID_HANDLE_VALUE` as failure and never close it.
3. Call [`SetFileInformationByHandle`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle) once on that handle, using [`FileRenameInfoEx`](https://learn.microsoft.com/en-us/windows/win32/api/minwinbase/ne-minwinbase-file_info_by_handle_class) (`22`). Set `Flags` to exactly `FILE_RENAME_FLAG_REPLACE_IF_EXISTS | FILE_RENAME_FLAG_POSIX_SEMANTICS` (`3`) and `RootDirectory` to null. The [documented POSIX semantics](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information) let existing destination handles retain their old object while subsequent opens see the renamed source. Do not request ignore-readonly or any storage/pin-state flag.
4. Capture the last-error code immediately on a false API return, before another call overwrites it. Close every acquired source handle exactly once in `finally` using [`CloseHandle`](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-closehandle), including rename or injected binding exceptions. Propagate the original operation error with its Windows code; if close also fails, retain it as secondary error detail without replacing the original. A close-only failure fails the helper. Never retry close or claim an unsuccessful rename succeeded. A successful rename followed by close failure may already have changed the name; the fixture fails and does not attempt rollback.

The buffer follows the conditional union in Microsoft's [SDK `FILE_RENAME_INFO` declaration](https://github.com/microsoft/win32metadata/blob/1bfb76db1c360653bdcb56512af0fdf987aceab8/generation/WinSDK/RecompiledIdlHeaders/um/WinBase.h), not a second sequential `ReplaceIfExists` field in the rendered API page. Use fixed-width 32-bit flags/length, an 8-bit Boolean union member, a native pointer and 16-bit code units; host `c_wchar` width is not the wire width. Under the [Windows x64 ABI](https://learn.microsoft.com/en-us/cpp/build/x64-software-conventions#x64-type-and-storage-layout), assert offsets `Flags=0`, `RootDirectory=8`, `FileNameLength=16`, `FileName=20`, structure alignment 8 and one-code-unit structure size 24 before calling Windows. Allocate zeroed, 8-byte-aligned storage for the header, encoded name and two-byte terminator, rounded up to alignment, and pass that exact allocation length as `dwBufferSize`; the bound above caps it at 65,560 bytes. No packing override, undersized header, unchecked arithmetic or truncated DWORD is accepted. A different native ABI requires its own reviewed layout and proof; the pure buffer tests use this explicit x64 layout on every current harness host.

The extended flags are defined from the SDK's Windows 10 RS1 contract, within the Windows 11 endpoint eligibility and the Windows Server hosted test environment. API availability alone is insufficient: the native Windows unit leaf must prove replacement on its actual temporary filesystem while the destination remains open. Unsupported API/filesystem behavior, sharing denial or permission failure fails the test with the real error; there is no fallback or skip on Windows. This fixture-only mechanism establishes neither crash durability nor agent runtime/platform qualification.

Preserve the existing native observer test's 500 cycles, each with source write, atomic replacement, rotation and active-file recreation, and the unchanged concurrent reader loop and empty-error assertion. Add a deterministic prelude in the same test: hold a delete-sharing read handle to an existing destination, replace it while that handle stays open, require that handle to read the old bytes and a new `read_shared` call to read the new bytes, and require the source name to be absent. Close the retained handle even on assertion failure, then execute every concurrent cycle. The fake agent uses the same helper for every health and rotation rename, as does the sequential collected-workload fixture. Keep all readiness, phase duration, resource, progress and failure-mode assertions unchanged.

Benefits: fixture writes exercise the capability of the actual Windows writer without suppressing a measured failure. Costs: a small test-only foreign-function boundary and explicit layout/error tests. Dependencies remain the admitted Python standard library and Windows APIs. Reject changing the reader, serializing it with the writer, accepting access-denied errors, retrying until a favorable schedule, reducing operations, replacing rename with copy/delete, or changing Rust; each either weakens the proof or changes a component without an established defect. Section 8's seven attacker outcomes remain unchanged: only fixture-owned bytes and temporary names enter this helper, no runtime credential or authority does, and a compromised runner can already forge local test behavior.

| `regression_footprint_p95` | each | `fail` when `p95` exceeds the baseline's by more than `footprint_ratio` (10 %) and more than `footprint_bytes` (2 MiB) | AG-09 |
| `regression_threads_max` | each | `fail` when the maximum exceeds the baseline's by more than `threads` (2); tokio spawns blocking threads on demand, so small variation is timing, not code | AG-09 |
| `regression_descriptors_max` | each | `fail` when the maximum exceeds the baseline's by more than `descriptors_fd` (4) or `descriptors_handle` (16) | AG-09 |
| `regression_cpu_mean`, `regression_shutdown_ms` | each | `recorded`; hosted CPU and timing are noisy | Section 2 |

A `fail` on any check fails the job. A `recorded` check appears in the evidence with its observed value and no verdict. A metric below its baseline is recorded as an improvement and never fails. Raising a budget or a tolerance is a reviewed change to `budgets.json` with the reason in the pull request; resource limits and regression tolerances come only from this file; protocol cadence and freshness rules are fixed by section 3.1, and `check.py` defines no extra limit or tolerance and never reads one from the agent, the environment or the baseline.

## 5. Evidence document

`measure.py` writes one JSON document validated by [`schemas/agent/footprint/v1/evidence.schema.json`](../../schemas/agent/footprint/v1/evidence.schema.json); [`example.json`](../../schemas/agent/footprint/v1/example.json) is a complete synthetic record and [`schema-cases.json`](../../schemas/agent/footprint/v1/schema-cases.json) holds positive and negative shapes. The document carries `schema`, the build `identity` (the four release-build fields, or `null` on a smoke run), `smoke`, `target`, `environment` (section 2), `binary` (`name`, `size`, `sha256`, `reported_identity`), `processes`, `phases` with their profiles, sample counts and summaries, `budgets`, `results`, `baseline` (`kind` `none`, `initial` or `release`, the baseline's identity and whether the environment matched), `outcome` and timestamps. The phase also carries the workload evidence of section 3.1. Schema cases cover shape errors; the `expected_checks` cases in [`schema-cases.json`](../../schemas/agent/footprint/v1/schema-cases.json) contain schema-valid instances with expected semantic check outcomes, consumed by the plan's checker tests. Evidence never contains the agent's logs, paths outside the temporary tree, or environment values other than the named ones.

## 6. Baseline and regression

AG-09 fails a build on regression against the last release, and [release builds section 6](release-builds.md#6-workflow-trust-and-required-checks) forbids passing a missing baseline as zero regression. The protocol must also land under [the workflow](../../instructions/workflow.md): a required check is never red by design, and a baseline is never chosen by a pull request.

1. `tests/footprint/baselines/<target>.json` is an evidence document with `outcome: pass`, `smoke: false` and `identity.channel` equal to `master` or `prerelease`. `check.py` rejects any other file as `baseline_invalid`: a `pr` identity, a smoke record or a failed run can never become the floor.
2. `check.py --out` writes the completed evidence document. For every passing, non-smoke run whose `identity.channel` is `master` or `prerelease`, it also writes `baseline-candidate.json` beside it, byte-identical to the `--out` document, whether or not a baseline file exists; a `pr` run never writes a candidate. Both files are uploaded as job evidence.
3. While no baseline file exists for the target and the run's channel is `pr` or `master`, `check.py` records `baseline_present` as `recorded` with observed `none` and enforces every absolute budget of section 4; the run passes on the absolute budgets alone. When the channel is `prerelease` (a tag build), a missing baseline is `fail`, so the release gate of release builds section 6 holds.
4. The initial baseline comes from the first `master` run after the harness lands: a follow-up pull request copies that run's three `baseline-candidate.json` files into `baselines/` byte for byte and cites the run URLs. Because the reviewer may run without Git or network access ([workflow, Reviews](../../instructions/workflow.md#reviews)), the coordinator downloads each cited artifact, records the run URL, the run's head SHA with proof that it is on `master`, the artifact ID and the SHA-256 of each downloaded `baseline-candidate.json`, and hands those files and records to the independent reviewer. The reviewer requires each committed file's SHA-256 to equal the downloaded file's and rejects a file that differs or comes from another run, then approves the files like any contract fixture. From then on every run compares.
5. After each `release-ready` tag run, the same procedure replaces the three files with that run's `baseline-candidate.json`, so the baseline is the last release's measurement and its identity names the release; until that pull request lands, comparisons use the previous baseline.
6. The baseline must match the run on `target`, `runner_os`, `runner_arch`, `runner_label` and `os_version`; a mismatch is `fail` with `baseline_environment`, never a skip. `os_version` is the comparison key per OS: the macOS major from `platform.mac_ver()[0]`, the Windows version string `platform.win32_ver()[1]` (for example `10.0.26100`, where the build number is what changes between images), and the Linux `VERSION_ID` from `platform.freedesktop_os_release()` ([platform](https://docs.python.org/3/library/platform.html)). A pull request that changes the measured environment, such as a new `runner_label`, also deletes the affected `baselines/<target>.json`, which reviewers treat as a baseline edit; its own run then passes under step 3, and step 4 re-establishes the file from the first `master` run after it lands. When the hosted image changes `os_version` without a workflow change, runs fail with `baseline_environment` until such a deletion lands; that red state is a real environment change awaiting review, not a state the protocol creates.
7. Regression verdicts follow the section 4 table. Every verdict names the check, phase, observed value, limit or baseline value and the baseline identity, so a failing log needs no second lookup.

Baseline promotion uses repository development/release authority, not a Ricevanta console permission. Copying, replacing or deleting baseline files requires the section 6 artifact provenance and independent repository review; no console permission authorizes weakening a budget or selecting a pull-request floor. The permission coverage refresh records this procedure under `qualification` and adds this spec and `agent-runtime.md` to its source inventory through [permission catalogue section 7](permission-catalogue.md#7-fixtures-and-required-tests).

## 7. Commands

Local, repository root, after `cargo build --locked -p ricevanta-core --bin ricevanta-agent` in `agent/`:

```sh
python -B -m unittest discover -s tests/footprint -p 'test_*.py' -v
python -B tests/footprint/measure.py --binary agent/target/debug/ricevanta-agent --target linux-x64 --phases idle,load --duration-scale 0.1 --out /tmp/footprint/evidence.json
python -B tests/footprint/check.py --evidence /tmp/footprint/evidence.json --budgets tests/footprint/budgets.json --baseline tests/footprint/baselines/linux-x64.json
```

The local run has no identity file and is a smoke run; `check.py` reports its absolute budgets and refuses to treat it as a gate result or a baseline. CI runs the full durations with `--identity` on each native target through the job the plan defines. `measure.py` exits 0 after writing evidence, 1 on `not_ready` or a sampler preflight failure such as a missing `smaps_rollup`, and 2 on usage error. `check.py` exits 0 on `pass`, 1 on `fail`, 2 on usage or schema error, and prints every result line. Evidence and the baseline candidate are uploaded as job evidence for 30 days; a failed check keeps its evidence.

## 8. Trust and attacker outcomes

The harness is a test; it holds no key, opens no listener and reads only the binary, its profiles and its own temporary tree. Its trust boundary is the pull request: `budgets.json`, `baselines/` and `profiles/` are reviewed files, and the plan names them as review focus because a change there can hide a regression. The harness consumes the binary built in the same job and verifies its identity against the release identity file, never a downloaded one. Of the project's attacker list, none gains anything from the harness: a stolen enrollment token, a compromised agent host, a compromised console session, a rogue extension publisher, a network position, a database writer and a restored server all touch runtime systems the harness never contacts. A pull request author can weaken a budget or baseline only through a reviewed diff, cannot make a `pr` run a baseline, cannot substitute a hand-made baseline file because the reviewer matches each file to the artifact the coordinator downloaded from the cited `master` run (section 6 step 4), and the CI policy checker rejects a workflow that skips the footprint IDs on an agent change.

## 9. Benefits, trade-offs, dependencies, limits, alternatives

Benefits: the first agent build is measured on all three targets with the metric the design defines, not an RSS proxy; evidence is machine-readable and self-describing; the baseline protocol is explicit about the no-release case and landable; the agent's self-sampler is cross-checked by an independent sampler, and freshness, counter progress and observed log rotation prove that the intended workload ran.

Trade-offs: retaining boundary snapshots and polling summaries adds evidence fields and can fail a heavily stalled runner; the explicit cadence tolerance preserves the workload instead of passing a lighter run. `ctypes` on macOS and Windows is foreign-function code in a test tool, accepted because the alternatives are a third-party package or trusting the agent's own numbers; hosted runners make CPU a recorded value, accepted because the design already gates CPU on self-hosted machines; two full phases add about three and a half minutes per target to every agent build; a per-core CPU figure differs from the catalogue's normalized one, accepted because it is stricter and the normalized value is derivable.

Dependencies: the Python release of `.github/python-version` with its standard library (`ctypes`, `subprocess`, `json`, `hashlib`, `statistics`, `platform`) for the harness itself and the CI hardening validator closure for its schema test, the agent runtime's health document and `run` mode, and the release identity file from `scripts/release/version.py`.

Limits: sampling and percentiles do not establish transient peak memory; the runtime allocation review and growth tests own the sampler proof. `smaps_rollup` needs `CONFIG_PROC_PAGE_MONITOR`, present on the hosted Ubuntu kernels and recorded as a preflight check; the Windows private working set needs the 2023 servicing baseline, which `windows-2025` meets; a hosted result proves nothing about kernel memory, BPF maps, the driver or the system extensions; the GitHub runner image version is not exposed as a documented variable, so environment matching uses the OS version key and label.

Alternatives considered: accepting only the final self-sample, rejected because a stopped sampler or a health-only writer can pass; inferring log rotation from `debug` configuration, rejected because no bytes may have been written; treating one-second p95 as a peak bound, rejected because observations miss shorter allocations. `psutil`, rejected as a new dependency with its own native build and license row when the standard library reaches the same APIs; measuring resident set size, rejected because AG-02 defines the metric as the per-OS private footprint and RSS counts shared pages; trusting the agent's self-sample alone, rejected because the sampler under test would grade itself; a Rust harness in the agent workspace, rejected because it would inherit the agent's unsafe-code rules and build time for a test-only tool; `/usr/bin/time -v`, rejected because it reports only the peak at exit; an initial baseline taken from a pull-request head, rejected because the author would choose the floor and the required check would be red until it landed.
