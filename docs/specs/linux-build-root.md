# Linux build root

This contract requires every Linux release ELF that links the C library to build inside a container root pinned by digest, with the glibc 2.34 ABI floor required by the [eligible Linux distributions](../platform-support.md#os-eligibility-and-qualification). An independent symbol-version check refuses any binary that needs a newer GNU C library, GCC runtime or C++ runtime, and distribution probes start every Linux release binary on each eligible distribution family before a release. The Go server builds without cgo and links no C library, so it needs no root. Runner images therefore never set the Linux ABI floor.

Authorities: PF-01, PF-02, PF-04 and AG-12 in [decisions](../decisions.md), [release builds](release-builds.md) sections 3 and 4, [CI hardening](ci-hardening.md) section 8, [platform support](../platform-support.md) and [licensing](../licensing.md). [Release plan Task 4A](../plans/release-builds.md#task-4a-linux-build-root-abi-check-and-distribution-probes) implements this contract. The scripts and production pin file are implementation interfaces, not existing admission results. Native evidence and publication gates in section 10 remain open. The machine-readable pin file follows [the build-root schema](../../schemas/build/root/v1/build-root.schema.json).

| Debian | 12, 13 | 2.36, 2.41 | [bookworm](https://packages.debian.org/bookworm/libc6), [trixie](https://packages.debian.org/trixie/libc6) `libc6` |
| RHEL family | RHEL 9 with AlmaLinux 9 and Rocky Linux 9; RHEL 10 with its rebuilds | 2.34; 2.39 | [RHEL 9.0 release notes](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/9/html-single/9.0_release_notes/index) list glibc 2.34; [AlmaLinux 9](https://repo.almalinux.org/almalinux/9/BaseOS/x86_64/os/Packages/) and [Rocky Linux 9](https://dl.rockylinux.org/pub/rocky/9/BaseOS/x86_64/os/Packages/g/) ship `glibc-2.34-283.el9_8`; [AlmaLinux 10](https://repo.almalinux.org/almalinux/10/BaseOS/x86_64/os/Packages/) and [Rocky Linux 10](https://dl.rockylinux.org/pub/rocky/10/BaseOS/x86_64/os/Packages/g/) ship 2.39 (RHEL 10 itself: verify) |
| Fedora | 43, 44 ([supported releases](https://docs.fedoraproject.org/en-US/releases/)) | 2.42, 2.43 | [Fedora glibc packages](https://packages.fedoraproject.org/pkgs/glibc/glibc/) |
| openSUSE Leap | 16.0 ([current release](https://get.opensuse.org/leap/)) | 2.40 | [16.0 repository](https://download.opensuse.org/distribution/leap/16.0/repo/oss/x86_64/); the unreleased [16.1 repository](https://download.opensuse.org/distribution/leap/16.1/repo/oss/x86_64/) also carries 2.40 |

The floor is glibc 2.34 from RHEL 9 and its rebuilds, which keep that version for the whole major release. It rises only when platform support removes RHEL 9; the root then moves to the next oldest eligible family through a reviewed change. A runner upgrade never changes it.

The other version ceilings below are candidate bounds from the candidate root inventory, not proof that every permitted symbol exists on every distribution. Task 4A verifies each bound against the exact runtime libraries on both architectures, retains their version-definition tables, and proves the actual imports with section 6 probes before admission. A missing symbol fails even when its version number is below the ceiling.

| Namespace | Library | x86_64 ceiling | aarch64 ceiling |
|---|---|---|---|
| `GLIBC_` | `libc.so.6`, `libm.so.6`, the program interpreter | 2.34 | 2.34 |
| `GCC_` | `libgcc_s.so.1` | 7.0.0 | 11.0 |
| `GLIBCXX_` | `libstdc++.so.6` | 3.4.29 | 3.4.29 |
| `CXXABI_` | `libstdc++.so.6` | 1.3.13 | 1.3.13 |

Vendor backports can expose symbol versions above a package's base version. Task 4A inspects the pinned glibc version definitions and imports; package metadata alone never proves the floor. Section 5 refuses `GLIBC_2.35`. A feature that needs a newer interface must provide a reviewed, qualified path on every eligible distribution, such as a direct system call where the supported kernel supplies it. Runtime lookup cannot silently drop the feature.

CPU baseline: x86_64 artifacts keep the baseline x86-64 level of the [x86-64 psABI](https://gitlab.com/x86-psABIs/x86-64-ABI) (CMOV, CX8, FPU, FXSR, MMX, OSFXSR, SCE, SSE, SSE2), as a Ricevanta artifact baseline; individual distributions may require newer CPUs. RHEL 9 requires x86-64-v2 and builds its packages for it ([RHEL 9.0 release notes](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/9/html-single/9.0_release_notes/index), [Red Hat's x86-64-v2 article](https://developers.redhat.com/blog/2021/01/05/building-red-hat-enterprise-linux-9-for-the-x86-64-v2-microarchitecture-level)); the recipe must not inherit the vendor compiler's default target. The recipe therefore passes `-march=x86-64 -mtune=generic` to C compilation, and section 5 checks the vendor objects the linker takes from the root. aarch64 artifacts target `-march=armv8-a`, the ARMv8.0-A minimum RHEL 9 states.

Benefits: the compiler, headers, start files and runtime libraries arrive as one content-addressed input; no build job installs a package; both architectures share one recipe; the image's purpose matches the requirement, since [PEP 600](https://peps.python.org/pep-0600/) defines `manylinux_2_34` as binaries that run on glibc 2.34 or later. Trade-offs: an image of about 590 MB per architecture with content the recipe never runs; upstream marks `manylinux_2_34` ALPHA because RHEL 9 packages target x86-64-v2, which section 1 and section 5 handle; PyPA rebuilds images on upstream commits, so a newer toolchain or security update arrives only through a reviewed pin change. Dependencies: PyPA's image publication, `quay.io` availability and the runner's Docker Engine. An older root such as `manylinux_2_28` (AlmaLinux 8, glibc 2.28) also meets the floor, but AlmaLinux 8 is not eligible, so it would forbid glibc 2.34 interfaces every eligible distribution has without widening support. Compiling on the runner host was rejected because Ubuntu 22.04's glibc 2.35 already exceeds the floor and newer runners raise it further.

## 3. Pins and admission

Commands in sections 3 to 6 are CI interfaces run from the repository root after implementation; they are not commands executed by this design task.

`scripts/release/build-root.json` holds the floor table of section 1, the two roots and the probe images, validated by [the schema](../../schemas/build/root/v1/build-root.schema.json); [its example](../../schemas/build/root/v1/example.json) is synthetic, and [the schema cases](../../schemas/build/root/v1/schema-cases.json) list rejected shapes. The floor gives, per architecture, the program interpreter, the allowed sonames with the version namespaces each owns, the four ceilings, the C flags and the root objects that may enter a binary. Each root, keyed by architecture, names its runner label, lock platform, repository, informational tag, manifest digest, config digest, vendor key fingerprint, exact package versions and absolute compiler and archiver paths. Each probe names its family, release and, for both architectures, a repository with manifest and config digests. The file contains no tag-only reference. `build_root.py` refuses a root whose architecture, runner label and lock platform disagree, duplicate probe identifiers or family/release pairs, a missing architecture, and any image reference that is not in the file. Semantic validation requires the exact section 1 floor, architecture-specific interpreter, namespace ownership, CPU flags and startup-object set; it rejects a wider ceiling or added object unless this contract and the pins change together through review. Synthetic schema examples never supply production image or package authority.

`python -B scripts/release/build_root.py admit --pins scripts/release/build-root.json --arch ARCH --evidence DIR` runs in every job that uses a root or probe image, with network access only for the pull:

1. `docker pull --platform <platform> <repository>@<manifest digest>` for the root and every probe image of that architecture. The fixed mapping is `x86_64` to `linux/amd64` and `aarch64` to `linux/arm64/v8`; repository architecture names are not Docker platform names. The [OCI distribution specification](https://github.com/opencontainers/distribution-spec/blob/main/spec.md) addresses manifests and blobs by digest and tells clients to verify them; Docker documents a digest pull as [pinning](https://docs.docker.com/reference/cli/docker/image/pull/).
2. Independently of Docker's pull checks, [save the selected platform](https://docs.docker.com/reference/cli/docker/image/save/) by immutable image ID and parse the archive with bounded streaming in project code. Require exactly one selected image, a config SHA-256 equal to the pin, config OS/architecture equal to the fixed mapping, and every layer's uncompressed SHA-256 equal to the config's ordered `rootfs.diff_ids` ([OCI configuration](https://github.com/opencontainers/image-spec/blob/main/config.md)). Support only explicitly tested Docker-save or OCI-layout encodings; unknown formats fail. Never extract archive paths onto the host. Reject duplicate or escaping outer member names, linked outer members, missing or extra referenced layers, duplicate JSON keys, unsupported compression, truncated streams and trailing compressed data. Bound outer members to 4,096, config/manifest JSON to 4 MiB each, streamed layer bytes to 16 GiB total and operation time to 300 seconds; inner filesystem entries stay opaque hashed bytes, so ordinary image symlinks are not mistaken for unsafe outer links. The admitted Python must pass gzip and optional [zstd](https://docs.python.org/3.14/library/compression.zstd.html) import/decompression controls before admission; an absent module fails, with no external fallback. Retain the exact config and ordered DiffID evidence.
3. In a container of the root with no network, query each locked package's exact version, architecture, signing-key metadata and owned files, run `rpm -V` on those packages, and record `gcc --version`, `ld --version` and `gcc -Q --help=target` with the recipe's C flags, which must report `-march=x86-64` on x86_64.

All containers, including package inspection and probes, override the entry point, clear the environment and use section 4's isolation flags. Inspect and run only the admitted immutable image ID, never a local tag. Refuse image-declared volumes and image configuration that conflicts with the fixed mounts. Any mismatch stops the job before the root runs a build. Evidence records the runner image version, Docker version, both digests, every package version and the tool output. `rpm -V` and signature metadata use the image's own package database. They detect drift and accidental changes, not an image built to lie or an independent cryptographic verification of vendor RPM payloads (section 8).

## 4. Building in the root

The host prepares inputs; the root only compiles and links. On the host, the bootstrap of [CI hardening section 8](ci-hardening.md#toolchain-lock-and-bootstrap-step) installs the locked Rust components for the runner's lock platform, and the admitted `cargo fetch --locked` fills a fresh job-owned `CARGO_HOME`, verifying every crate against `Cargo.lock`. Rust documents glibc 2.17 for the two [GNU/Linux host targets](https://doc.rust-lang.org/rustc/platform-support.html). Task 4A must still run the exact admitted Rust distribution inside each root; a target-support table alone does not qualify the compiler payload or its shared libraries.

`build_root.py build --pins PATH --arch ARCH --unit agent|workspace-tests --rust-env PATH --cargo-home DIR --target-dir DIR --out DIR --evidence DIR` starts the root with a fixed argument array, never a shell string:

- `docker run --rm --pull never --network none --read-only --tmpfs /tmp --workdir /work/src/agent --user <runner uid>:<gid> --cap-drop ALL --security-opt no-new-privileges --entrypoint /usr/bin/env` with the [documented options](https://docs.docker.com/reference/cli/docker/container/run/); [`--network none`](https://docs.docker.com/engine/network/drivers/none/) leaves only loopback.
- Mounts: the checkout read-only at `/work/src`, the admitted Rust prefix read-only at `/opt/ricevanta/rust`, and the job-owned `/work/cargo-home`, `/work/target` (fresh per pass) and `/work/out`. No other host path enters the container.
- The command is `env -i` followed by a closed environment, so no image or runner variable survives: `PATH=/opt/ricevanta/rust/bin:/opt/rh/gcc-toolset-14/root/usr/bin:/usr/bin:/bin`, `HOME=/tmp`, `CARGO_HOME=/work/cargo-home`, `CARGO_TARGET_DIR=/work/target`, `CARGO_NET_OFFLINE=true`, `CARGO_INCREMENTAL=0`, `LC_ALL=C`, `TZ=UTC`, the four `rust-env.json` values, `CC_<target>` and `AR_<target>` with the absolute toolset paths, and `CFLAGS_<target>` with the section 1 flags plus `-ffile-prefix-map` entries matching the Rust path remapping.
- Cargo runs `build --locked --offline --release --target <triple> --bin ricevanta-agent` for `agent`, or `test --locked --offline --release --target <triple> --workspace --no-run` for `workspace-tests`, with `--config` arguments that set `target.<triple>.linker` to the fixed linker wrapper below and explicit Rust `-C target-cpu=x86-64` on x86_64 or `-C target-cpu=generic` on aarch64, and the path remapping of [release builds section 4](release-builds.md#4-reproducibility-and-toolchain-admission). Every dynamic executable, including each workspace test executable, requires its own complete link map. A project-owned linker wrapper passes an argument array to the absolute toolset `gcc`, derives a unique map path from the linker output path, refuses duplicate outputs, and records the output path, argument array and map digest. It is mounted read-only with the checkout, uses the root's recorded shell, and never evaluates arguments. A single shared `-Map` path is forbidden because parallel links overwrite it. Cargo JSON artifact messages enumerate the expected executables; the harness requires exactly one map per executable and binds both SHA-256 values after linking. The linker wrapper fixes the toolset subprocess search path, records the actual linker and start-file paths, and rejects a different linker or any path outside the admitted mounts. The native run proves which startup objects and runtime libraries the exact compiler selects.

These names reach only the container process, never workflow `env`, `GITHUB_ENV` or Cargo configuration files, as [CI hardening section 6](ci-hardening.md#6-execution-proof-ci-01-and-ci-08) requires. Two passes use identical container paths in fresh directories, so the [release comparison](release-builds.md#4-reproducibility-and-toolchain-admission) still applies. The source mount contains only verified build inputs: no `.git`, workflow credentials or unrelated ignored files. `CARGO_HOME` is a fresh project-created offline tree with no credentials, Git credentials or Cargo configuration. Check all mounts for symlink escape and disjoint writable paths before starting; the Docker socket, host home and admitted credentials never enter the container. Evidence records the root digests, the closed environment, the cargo arguments, every link map and the output SHA-256 values.

The Go server builds on the host with the admitted Go and `CGO_ENABLED=0` in the child environment of the [server recipe](release-builds.md#4-reproducibility-and-toolchain-admission). [cgo is enabled by default for native builds](https://pkg.go.dev/cmd/cgo) when a C compiler is on `PATH`, as on the hosted runners, and with cgo the [`net` package](https://pkg.go.dev/net) can select the native resolver; disabling cgo yields a binary with no program interpreter and no dynamic dependency. Rust executables that later ship in the server image, such as `ricevanta-rulec` and `ricevanta-scan`, build in the root for each image architecture.

## 5. ABI check

`python -B scripts/release/elf_abi.py --pins scripts/release/build-root.json --arch ARCH --kind dynamic|static [--link-map PATH --root-objects DIR] --out PATH FILE...` runs on the host with the admitted Python and the standard library only, so the root's own tools never judge the root's output. It parses ELF64 little-endian files under the [ELF format](https://man7.org/linux/man-pages/man5/elf.5.html) and the [symbol versioning sections](https://refspecs.linuxfoundation.org/LSB_5.0.0/LSB-Core-generic/LSB-Core-generic/symversion.html), using program headers and `PT_DYNAMIC`, including when section headers are stripped. Cross-check present section metadata against dynamic metadata. Bound file size to 1 GiB, tables to 1,000,000 entries each and cumulative decoded strings to 16 MiB; reject cycles, invalid indices, contradictory table overlaps and out-of-file ranges; legitimate segment containment is allowed. It refuses with the file, field and value:

- A machine other than `EM_X86_64` or `EM_AARCH64` for the architecture, a 32-bit or big-endian file, or a truncated or inconsistent header or table.
- For `dynamic`: a program interpreter other than `/lib64/ld-linux-x86-64.so.2` or `/lib/ld-linux-aarch64.so.1`; a `DT_NEEDED` entry outside the floor's soname list (`libc.so.6`, `libm.so.6`, `libgcc_s.so.1` and the interpreter) or containing `/`; any `DT_RPATH` or `DT_RUNPATH`; a missing `BIND_NOW` (`DF_BIND_NOW` in `DT_FLAGS` or `DF_1_NOW` in `DT_FLAGS_1`), which Rust sets by default ([rustc exploit mitigations](https://doc.rust-lang.org/rustc/exploit-mitigations.html)).
- Any version need above the section 1 ceiling, compared numerically per component; `GLIBC_PRIVATE`; a namespace the needed library does not own (`GLIBC_` for `libc.so.6`, `libm.so.6` and the interpreter, `GCC_` for `libgcc_s.so.1`, `GLIBCXX_` and `CXXABI_` for `libstdc++.so.6`); and any other version name.
- An undefined, non-weak dynamic symbol without a version. Weak undefined symbols such as `__gmon_start__` may stay unversioned.
- For `static`: a program interpreter, a `DT_NEEDED` entry or a version-needs section.
- For `dynamic`, `--link-map` is mandatory and exactly one FILE is accepted; `--root-objects` is also mandatory on x86_64. For `static`, both are refused. Reject a missing, truncated, unrecognized or mismatched map and any object file or archive member the map shows was taken from the root (`/lib`, `/lib64`, `/usr/lib64` or `/opt/rh/gcc-toolset-14`, normalized inside the root) that is not on the floor's `rootObjects` list for the architecture. The list holds the five candidate startup objects admitted by this recipe: `Scrt1.o`, `crti.o` and `crtn.o` from `glibc-devel`, and `crtbeginS.o` and `crtendS.o` from GCC Toolset 14. A new entry needs a reviewed license position (section 9) and, on x86_64, the baseline check below. Shared libraries in the map are dynamic dependencies and fall under the soname rule instead.
- On x86_64, with `--root-objects`: any listed root object whose disassembly, produced in the root with no network and copied into that directory, contains an instruction from the x86-64-v2 or later feature sets of the psABI (CMPXCHG16B, LAHF and SAHF, POPCNT, SSE3, SSSE3, SSE4.1, SSE4.2, AVX and later). This disassembly filter is a regression check, not proof of instruction-set compatibility: instruction aliases, embedded data and runtime dispatch prevent a mnemonic blacklist from proving the baseline. Task 4A retains object hashes and disassembly for review; full release qualification must execute the exact artifact on the declared CPU baseline and exercise runtime-dispatched paths. No `libgcc.a` member is admitted by the current object list. Rust and zstd retain explicit baseline compile flags; their dispatch behavior also needs that native qualification.

A new library dependency, such as `libstdc++.so.6` for a C++ component, enters the soname list with its ceilings through a reviewed change to the pin file. The output is a JSON report with each file's SHA-256, interpreter, needed libraries, highest version per namespace and linked root objects. Task 4A records measured imports and linked objects for every workspace test executable on both architectures. Those measurements are unresolved evidence, not claims established by this document. Fixtures prove each refusal with byte-level mutations and an above-floor symbol fixture; if a real `epoll_pwait2` link exposes `GLIBC_2.35` in this pin, retain it as an additional end-to-end negative control.

## 6. Distribution probes

`python -B scripts/release/probe.py --pins scripts/release/build-root.json --arch ARCH --kind agent|server|test --binary PATH --expected-identity PATH --evidence DIR` starts each Linux release binary in every probe image of its architecture. Probes run on hosted runners: `ubuntu-26.04` for x86_64 (agent, server and workspace test executables) and `ubuntu-26.04-arm` for aarch64 (server and test executables). Each probe is `docker run --rm --pull never --network none --read-only --tmpfs /tmp --user 65534:65534 --cap-drop ALL --security-opt no-new-privileges` with the binary mounted read-only, `/usr/bin/env` as the entry point and arguments `-i PATH=/usr/bin:/bin LC_ALL=C /work/binary <probe arguments>`, a 60-second limit and an image admitted by section 3. The agent and server run `version --json` and must exit 0 with an identity equal to the job-owned expected identity; a test executable runs `--list` and must match the nonempty test-name/type inventory captured from that executable in the root. `--expected-identity` is required for agent/server and forbidden for tests. Each probe caps combined output at 1 MiB and records binary SHA-256, immutable image ID, manifest/config digests, command, exit status and output hash. A timeout, cap breach, empty inventory or missing result fails. The verifier requires exact equality of expected binary-by-probe pairs, not just one successful row per family.

| Family | Probe repositories, one row per eligible release |
|---|---|
| Ubuntu | `docker.io/library/ubuntu` 22.04, 24.04, 26.04 |
| Debian | `docker.io/library/debian` 12, 13 |
| RHEL family | `ghcr.io/almalinux/almalinux` 9, 10; `quay.io/rockylinux/rockylinux` 9, 10 |
| Fedora | `registry.fedoraproject.org/fedora` 43, 44 |
| openSUSE Leap | `registry.opensuse.org/opensuse/leap` 16.0 |

The set holds every eligible release that publishes an official container image. A reviewed change updates it when platform support's lifecycle rules add or remove a release; the release owner confirms it against the frozen [required-unit manifest](platform-qualification.md) before a tag. RHEL itself remains required. AlmaLinux and Rocky probes test compatible rebuilds; they do not prove RHEL support. The release required-unit manifest must also contain the exact artifact's RHEL startup, import and full native qualification evidence. No RHEL container or other payload needing unapproved terms is admitted by this slice.

What a probe proves: that distribution's program interpreter, `libc.so.6`, `libm.so.6` and `libgcc_s.so.1` load the exact release bytes, resolve every needed version and, because of `BIND_NOW`, every imported symbol, and run start-up and the identity path. What it does not prove: kernel behaviour, because containers share the runner's kernel; eBPF, BPF LSM, fanotify, systemd and package installation; libraries the binary loads with `dlopen` on paths the version command does not reach; CPU baseline compatibility, because the hosted CPU supports later levels; and performance. Those remain with [platform qualification](platform-qualification.md) on real machines.

Ubuntu 26.04 and its Arm64 image are [generally available](https://github.com/actions/runner-images/issues/14747) as free [standard runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), and both images list Docker Engine ([x64](https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2604-Readme.md), [Arm64](https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2604-Arm64-Readme.md)). Linux x64 release jobs share CI's `linux-x64-ubuntu26.04` identity. Arm64 release jobs require the release-only `linux-arm64-ubuntu26.04` identity. Its seven candidate payloads remain in the [licensing inventory](../licensing.md#release-arm64-payload-staging), outside the production lock until release Task 2 atomically adds those rows, bootstrap support, policy mappings and native qualification. This design does not establish bootstrap support. Task 2 must require `VERSION_ID` 26.04 on an `aarch64` host and qualify relocation of the Arm64 Python build's `DT_RUNPATH` from `/opt/hostedtoolcache/Python/3.14.8/arm64/lib`. No release job uses `ubuntu-22.04` or `ubuntu-22.04-arm`, and the Ubuntu 22.04 lock identities no longer exist.

`footprint-linux-x64` measures the agent that `build_root.py build --unit agent` produces on `ubuntu-26.04`, so the measured bytes are the release recipe's bytes and the measurement host is the release runner. A runner change deletes the affected baseline under [the harness rule](footprint-harness.md#6-baseline-and-regression).

## 8. Security trace

The trust path is: reviewed pin file and lock → admitted host toolchain → digest pull over TLS → project-code check of config and layer digests → vendor package and signature query → isolated build with no network, a read-only root and a closed environment → host-side ABI check → probes in admitted images → the [release record, snapshot and verification](release-builds.md#5-build-records-checksums-and-sbom) chain. The root holds no credential, enrollment material or signing key, and nothing it produces is trusted without the host-side checks.

| Threat | Outcome |
|---|---|
| Substituted image under the same tag | The pull names the manifest digest, so a moved tag has no effect; different bytes fail the config and DiffID comparison and stop the job |
| Compromised registry | Can withhold or corrupt the image, which stops the release; cannot supply different accepted content without a SHA-256 collision. Recovery is a reviewed pin change, never a fallback tag |
| Network attacker during a pull | TLS protects transport and the digest checks protect content; blocking the pull only delays the release |
| Malicious image published before review | A reviewed digest of malicious bytes passes admission. The compiler could insert code. This is the accepted [approved-payload residual](ci-hardening.md#11-security-trace-benefits-and-alternatives); the vendor signature query, no network, host-side checks and reproducible second pass limit but do not remove it |
| Stolen enrollment token | Gains nothing here; the root takes no enrollment input and builds no enrollment state |
| Compromised agent host | Can tamper with its own installed binary, not with release bytes, pins or CI results; the root never receives endpoint data |
| Compromised console session | Has no path to repository content, CI or pins; console state cannot select a root or probe |
| Rogue extension publisher | Cannot add pins; a pull request that changes them runs as untrusted code with read-only tokens and needs independent review, and tag builds use only `master`'s reviewed pins |
| Network position between agent and server | Unrelated to the build; signed updates under AG-07 protect delivered code |
| Database writer without signing keys | Has no route to pins, CI or release assets |
| Server restored from backup | Restores no CI state; old pins live only in old commits, and a rebuild uses the tagged commit's pins |

Limits: no second, independently built root compares outputs, so reproducibility proves stable inputs, not an honest compiler. A compromised runner image or Docker Engine stays inside the [bootstrap trust boundary](release-builds.md#4-reproducibility-and-toolchain-admission). Docker Hub limits unauthenticated pulls to [100 per six hours per IPv4 address](https://docs.docker.com/docker-hub/usage/pulls/), and whether hosted runners share that budget is a verify item; a refused pull fails the job rather than skipping a probe. Anonymous access is not proof that a registry imposes no additional terms. Registry eligibility remains the section 10 gate; this design neither accepts terms nor creates accounts.

## 9. Licensing position

[Licensing](../licensing.md) holds the rows. The image and its compilers are build tools that run and never ship; the only root code that enters a binary is the five start objects of section 5.

- GCC and binutils are GPL-3.0-or-later programs. `crtbeginS.o` and `crtendS.o` fall under the [GCC Runtime Library Exception 3.1](https://raw.githubusercontent.com/gcc-mirror/gcc/releases/gcc-14.2.0/COPYING.RUNTIME), under which a compilation process is eligible when it uses GCC alone or with other GPL-compatible software, or uses no work based on GCC; the zstd objects come from GCC and the Rust objects from `rustc`, which is MIT OR Apache-2.0.
- glibc uses LGPL-2.1-or-later. The [glibc copying guidance](https://sourceware.org/glibc/manual/latest/html_node/Copying.html) and the library's [COPYING.LIB](https://raw.githubusercontent.com/bminor/glibc/glibc-2.34/COPYING.LIB) distinguish a suitable shared-library mechanism from linked library code. System `libc.so.6` stays dynamically loaded. Startup code needs separate accounting: [`csu/init.c`](https://raw.githubusercontent.com/bminor/glibc/glibc-2.34/csu/init.c) has no additional linking permission, and [`csu/Makefile`](https://raw.githubusercontent.com/bminor/glibc/glibc-2.34/csu/Makefile) includes it in startup objects. The [aarch64 entry source](https://raw.githubusercontent.com/bminor/glibc/glibc-2.34/sysdeps/aarch64/start.S) also has LGPL terms without that permission. Upstream files do not establish the contents or licensing of AlmaLinux's patched objects. Task 4A maps every linked startup object to the exact vendor source package and patches for both architectures; Task 5 verifies notices and a complete relinking path. The proposed compliance path is LGPL section 6(a), with equivalent access under 6(d): offer the complete corresponding library sources and changes, all Ricevanta source or object inputs needed to relink, build/install scripts and required data beside the binary. Include library notices and license texts, permit modification and reverse engineering as the license requires, and demonstrate a relink using a modified startup object without relying on an expiring root image. A source-package URL and root digest alone do not prove the required materials are complete. This interpretation and the exact vendor source analysis remain verify items and block publication of glibc-linked artifacts on both architectures until independently resolved under section 10.
- Kernel UAPI headers are `GPL-2.0 WITH Linux-syscall-note` ([kernel license rules](https://www.kernel.org/doc/html/latest/process/license-rules.html)) and only compile.

No GPL code is linked into any release binary.

## 10. Evidence and publication gates

Task 4A may implement the isolated qualification harness after independent design approval. It cannot qualify a root without the native evidence below. Task 5 cannot publish any affected binary until the licensing and registry gates are resolved; owner approval of the pinned-root choice does not itself supply these results. No feature, distribution or architecture is removed to close a gate.

- Do native runs on both architectures verify the candidate image digests, full tool/package closure, compiler execution, exact imports, complete link maps and every distribution probe? Task 4A records the results and source-package provenance before production pin admission.
- Does independent examination of the exact vendor startup sources and a demonstrated relink establish LGPL compliance for every glibc-linked archive on both architectures? Task 5 needs the complete section 9 source/materials and notices inventory in its artifact contract before publication. A plain LGPL source is not reclassified as permissive merely because its output is small.
- Can every selected registry and image be consumed under project policy without a new registration, account or acceptance of additional third-party terms? Task 4A records first-party evidence before enabling pulls in authoritative CI. If any registry fails, a designer must select and review a policy-compatible distribution path; no job accepts terms or silently substitutes a tag.
- Does real-machine qualification exercise the exact release binaries on the declared x86-64 and ARMv8-A baselines and on RHEL itself? PF-04 owns that release evidence; hosted probes and disassembly do not replace it.
