# Platform qualification

The release gate that proves Ricevanta works as one product on every v1.0.0 target. Exact operating-system versions, editions, distributions, kernel prerequisites, capability mechanisms and documented OS limits come from `../platform-support.md`; this specification does not repeat them. Every feature in `../blueprint.md` remains required. The workflows below exercise integration risks and do not reduce that scope.

## 1. Required units and state

A qualification unit is one release candidate on one declared configuration profile. Before release freeze, the release owner creates a finite required-unit manifest from the live eligibility and browser windows in `../platform-support.md`.

The manifest must contain:

- One entry for every eligible macOS release; every eligible Windows release, edition and servicing channel; and every eligible Linux distribution release. Each Linux entry pins a tested running kernel and a filesystem and graphical-session profile.
- The four first-party browser adapters (EXT-06): Chrome, Edge and Firefox on every OS entry, plus Safari on every macOS entry. Each entry records the adapter, browser and extension version. A declared browser family cannot become inapplicable on one OS. Community adapters are not required units; a release does not qualify them, and a community adapter enters the manifest only when the project adds it with evidence.
- Candidate and server release, OS and security configuration, CPU architecture, package format and immutable package and image digests, signing identities, filesystem, session, browser, extension, driver and deployment profile, enabled stores, test-suite revision, feature and case coverage, owner and state.
- Representative or pairwise coverage assignments for hardware, firmware, deployment shape, optional store, installation path and other unbounded dimensions. Mandatory interaction cases cover hardware key and identity lifecycle, Windows security policy and driver, Linux kernel and filesystem enforcement, session and clipboard enforcement, browser and native host enforcement, and deployment or store failure and recovery.

An automated omission check compares the manifest with the frozen eligibility and browser inputs and the complete blueprint feature list. Any absent eligible release, Windows edition or channel, Linux profile, browser family, blueprint feature, required interaction or coverage assignment blocks release. Applicability may select a documented OS mechanism or explicit OS limit; it cannot remove an eligible unit or blueprint feature.

Each unit has one state:

| State | Meaning | Transition |
|---|---|---|
| Candidate | An eligible required unit is under evaluation, including while preflight, evidence or remediation is pending or failed | Entered when the manifest is frozen, for every new candidate, or after a material change |
| Qualified | Every applicable requirement and blueprint traceability item passes with acceptance evidence; no open blocker or unexplained retry remains | Candidate to qualified only after the evidence manifest is complete and independently approved |
| Unsupported | The configuration is outside eligibility in `../platform-support.md`, or the tested capability has an explicit documented OS limit | Recorded with the exact eligibility rule or limit; never used for failed preflight, pending remediation or a missing required mechanism |

These states belong to release candidates in the lab. A device in the field reports its preflight result and per-capability support (`../platform-support.md`) and has no qualification state.

A product release qualifies only when every required unit is qualified. A later security finding, invalid artifact, revoked signing identity or reproducible regression returns affected units to candidate. Observation-only results never preserve qualified state.

A change to an OS release, running kernel, browser, extension, driver, security policy, filesystem, session type or declared configuration profile is material. Affected profiles enter candidate before preflight and every requirement selected by impact analysis reruns; signing or package changes also rerun integrity, install, update, rollback and tamper cases. The evidence records the change, impact analysis and retest set.

An unresolved, missing or failing mechanism on a required v1 target is a release blocker, not an unsupported result. This includes a browser gate that does not hold the upload, paste or print until the core decides, and a clipboard helper that answers a consumer before the decision. Notification, audit and clearing content after access do not prove blocking.

## 2. Preflight

Preflight must establish before functional testing:

- The environment matches a target and all prerequisites in `../platform-support.md`. Linux checks the named distribution, kernel capabilities, BTF, BPF LSM, bpffs, fanotify privilege, service manager, package manager and graphical-session protocol. Windows checks the supported edition, Secure Boot, HVCI state, TPM state and acceptance of the WHCP-signed driver. macOS checks architecture, MDM enrollment where required, APNs reachability, granted entitlements, notarization and activation of system extensions.
- Host time, DNS, server trust, storage headroom and required network paths are usable. The test records proxy, firewall and TLS-passthrough configuration.
- Server roles, PostgreSQL, blob storage and each enabled optional store are healthy. The environment records Docker Compose or Helm topology, replica count and migration level.
- Production qualification uses release-signed packages and the production signing chain. Development signatures can produce diagnostic evidence but cannot qualify a unit.
- Every browser family required by the manifest, its adapter, its managed extension and its native-messaging host are installed at the locations the adapter declares; where a connector applies, the connector or `ContentAnalysis` policy names and pins the core, and Chrome Enterprise Core enrollment is recorded. The adapter's device-side bypass self-test proves one verdict binds the exact bytes to one transfer on every required upload, paste and print path. A missing or failed browser prerequisite, including Safari's unresolved exact-transfer gate, leaves the unit in candidate and blocks qualification.
- EDR: Linux checks the cgroup v2 unified hierarchy and attaches the isolation programs at its root; Windows checks the audit-policy baseline, ETW session creation for every base provider and the provider manifests' keywords; macOS checks Endpoint Security subscription to every base event type and Network Extension filter activation.

Preflight failure stops dependent tests. The report keeps the failure rather than converting later cases to passes.

## 3. Identity and lifecycle gates

Each platform proves the following flows through the public API, console and endpoint state where each surface applies:

1. Enroll with an approved, scoped, expiring single-use token. Verify the pinned root, locally created identity key, certificate chain, device record, group assignment, inventory, atomic token-use consumption and retained audit record. Reject concurrent or later reuse, an expired, wrong-scope or unapproved token and a takeover authorized only by hardware identifiers.
2. Prove hardware-backed key use where the platform provides it. Linux without a TPM must show the flagged root-only software-key fallback defined by the agent design.
3. Renew agent identity before expiry and during the grace period through the private nonce-bound protocol of `../design/pki.md` section 2. Verify current-key JWS and new certificate signing request proof, nonce consumption and an identical completed retry returning the same result. Reject reused or unknown nonces, another signing key, a revoked or ineligible certificate and another device. Test a lost response followed by result retrieval through the superseded credential without permitting a new issuance. Separately run an unmodified standard ACME client with a persistent account key and changing certificate keys through two renewals, then explicit `keyChange`; replacing a certificate key must not replace the account key. Renew a network identity during the overlap, prove both certificate generations map to the same unique identity names and reject another identity claiming those names. Beyond grace or after re-imaging, require a new token and prior-key proof or approval.
4. Suspend and retire a device. Verify command refusal or access loss, certificate status, retained audit evidence and cleanup of local management state. Complete native unenrollment before agent command download, and agent uninstall before native removal, in separate cases. The other channel must retain removal access until its own completion; browser-policy cleanup is required for agent completion. Delay one channel past 24 hours and require revoked credentials with removal still incomplete and usable local cleanup evidence, never a completed retirement claim. Revoke a device while it holds an HTTP/2 connection, a body upload and a long poll; new streams must fail and existing streams must close within five seconds. Drop `NOTIFY`, disconnect the listener and hold the snapshot refresh query beyond its deadline in separate cases. The independent lease timer must close streams without waiting for refresh completion (`../design/backend.md` section 3).
5. Treat every exposed-role certificate request row as untrusted input under `../design/pki.md` section 3. Attempt to substitute the asserted identity, group, certificate profile, certificate signing request and approval. Verify that `jobs` verifies the JWS, nonce and certificate signing request itself, derives authority from stored state, accepts only an approval bound to the exact request, certificate signing request, device and profile, and records the authorization inputs and decision.
6. Provision an Apple MDM Push Certificate for each self-hosted MDM service through the project's signing service and identity.apple.com. Renew the existing certificate with the same Apple ID while preserving its push topic and prove enrolled devices continue without re-enrollment. Verify the exact first-party behavior for expiry, revocation and topic mismatch, and require degraded state, operator warning and recovery evidence rather than assuming continuity.

## 4. Policy gates

- Publish a valid policy, exception, baseline and rule pack through the console, API and GitOps. Verify identical validation, compiled content, signature chain, per-device assignment, monotonic sequence, scope resolution, installed enforcement rules and OCSF policy references.
- Move a device between groups and prove the next higher-sequence assignment changes policy. A rollback republishes the prior content as a new signed bundle and higher assignment sequence. It never installs an older assignment.
- Exercise a protected weakening change and verify approval is required on every write surface. Verify dry-run and audit output before apply.
- Publish a new check-only baseline that cannot weaken an existing required set without approval. Publish an apply-capable baseline and require approval bound to its canonical revision hash and `allowedGroups`; substitute content, a referenced resource revision or groups after approval and require refusal. Apply to frozen device uids through a separately approved policy revision. Change or delete an item, remove an applying policy, widen its scope, rename or replace a group, or add a device by manual membership, a dynamic-group rule or inventory update; each state change or added target must remain pending until separately approved. Verify the compiler and native-channel writer refuse every unapproved revision and target while existing approved targets keep their approved state. Include a `linux.systemd` drop-in that selects an executable, a `linux.polkit` rule, a `linux.pam` change and an executable-mode `linux.file`; the first three require approval and the last is rejected even when approved.
- Compliance weakening: deploy a required failing read-only check and an unchanged RADIUS policy that rejects noncompliance. Change `expect` to `true`, make the item optional, remove or replace it, lengthen grace, widen an exception, narrow or disable its enforcing report policy, and remove its target through labels, group rules or inventory. Every weakening stays pending on all write surfaces until approval bound to exact before and after required revisions and frozen devices. Substituted content or an added device fails; no unapproved change may yield a RADIUS accept.
- Revision-bound evidence: approve a stricter item revision with the same item id. The old pass and an otherwise fresh signed report from the older assignment cannot satisfy the new revision; state stays `unknown` until exact bound evidence arrives. Substitute a baseline uid, settings hash, assignment, declaration identifier or server token, query/session identity and required-set hash separately. Grace cases cover fail, temporary pass, fail again before the original deadline, pass at deadline, fail after closure, zero grace, missing evidence, restart and restore; no duplicate or stale result resets a deadline.
- Apple native evidence: accept a verified failure, then inject both a previously consumed signed pass and a previously unseen withheld signed pass. Neither may raise compliance or refresh its evidence. Verify one-use current `CommandUUID`, request-generation ordering, duplicate idempotency and foreign, expired or superseded query refusal. Test correct declaration tokens with stale same-token status and `FullReport`; origin and revision alone must not count as freshness. Required native status remains a release blocker until the reviewed freshness mechanism and adversarial fixtures pass on every eligible macOS release.
- Reject malformed YAML and JSON, schema violations, an out-of-profile or over-cost CEL expression, missing and untranslatable rule references as specified, an invalid DSSE signature, foreign-device assignment, hash mismatch, replayed or lower sequence, expired or replayed command, archive traversal, links and decompression beyond the bundle limit. The active bundle must remain unchanged and the refusal must produce the specified health or audit event.
- Exercise the signed command, dispatch-grant and action-journal protocol in `policy-envelope.md` section 7. Verify that a protected-action approval binds its immutable request, exact fields and frozen device and command uid pairs and authorizes each pair once; an identical creation retry returns the original signed command; reused approval, changed fields, a substituted uid or an added target creates no command. Verify refusal of a grant after `valid_for_ms`, a grant or command substituted across device, poll nonce, hash or command, and a grant for a command with a verified result. Verify that a command replayed on a later poll is answered from its journal row without execution, that an undo command waits for its predecessor and runs when `open_seqs` voids it, that an unsigned or forged journal report or result is refused by `jobs`, that a crash between the journal write and execution resumes through the command type's reconciliation without repeating a side effect, and that the server marks a command the device never journaled as undelivered after its expiry.
- Prove equal-priority conflict resolution, exclusions, monitor and disabled modes, deadline fail mode and unsupported-channel reporting. Mix a priority-500 point block with a priority-900 core allow, a point allow with a higher-priority core block, equal-priority point/core decisions and a detector-free core condition. A point may finalize only when unresolved core outcomes cannot change the global decision or actions. Test content-dependent exceptions against fresh, cached, incomplete and failed classification; an exception error never grants an exemption.
- Exception time: keep the endpoint offline, move its wall clock backward and forward, suspend through expiry and crash around the durable expired-marker write. Expired revisions must not reactivate after clock changes, new bundles or anchors. Reboot or lose monotonic continuity and prove expiring exceptions stay inactive until a fresh signed nonce-bound anchor; non-expiring policy remains active. Reject delayed, replayed, foreign-device and wrong-epoch anchors. A point must not retain an unchecked expiring allowance while the core is down.
- Rule identity and regex: place the same rule key from two pack versions in one bundle and match only one. Correlation tags, references, findings and late uploads must retain the exact version and manifest digest. Compare Go and translated Rust match spans and capture groups for vertical tab, form feed, Unicode digits and spaces, negated classes, boundaries, bracket escapes and allow lists (`rule-adapters.md` section 7).
- Inventory SQL: exercise pack discovery, scheduled queries and baseline queries under every bound in `rule-adapters.md` section 8.1. Refuse `length(hex(zeroblob(100000000)))` before oversized allocation; terminate a long function even when no progress callback runs. Force heap, process, row, byte, queue and deadline caps. The core must keep enforcing within budget, baseline errors must stay `unknown`, and scheduled failures must retain the previous differential snapshot.
- Extensions (`../design/extensions.md`): refuse a package with a bad signature, an untrusted publisher, an id outside the key's prefixes, a file hash mismatch or an unsupported interface, and record the refusal. Refuse overlapping publisher ownership without a protected id assignment and different bytes or publishers under an accepted id/version, including after uninstall; an identical retry must return the same record. Prove that protected changes require approval, only the stored grant reaches runtimes, and revocation removes agent components at the next compile. Every grant write must advance the component generation in the signed bundle and in later extension-origin events. Each origin also binds the recovery epoch; a new epoch with an equal numeric generation cannot authorize old handles, bindings, callback tokens, commands, pending steps or fresh collector inventory/compliance. Apply grant A, grant B and values equal to A again; handles, responder commands, pending steps and console bindings from the first A generation must remain stale. A module importing outside its grant must fail to instantiate.
- Collector cases must prove that an allowed ancestor cannot expose a denied descendant, resolved links, reparse points and aliases cannot escape, multiply-linked and special files are refused, a singly linked root-only approved regular file remains readable, and every enumeration, request, input and output bound holds (`extension-agent-runtime.md` section 4). Standard user-level tests must swap paths and create or remove hard links during broker opens and reads, including removal after the first open and before the second open or a read fence. Require the call-scoped identity pin, canonical-path reopen fence, stable handle identity, regular-file type, link count one and current path and identity deny checks before and after each accepted read. A stale watch snapshot alone must not authorize a current protected alias; the fence must resolve the identity synchronously or reject the read. Put classified user content in an approved root-only file and home subtree. The broker must refuse or redact content in the frozen snapshot before guest input, including query and list metadata; base64, hex and split-field output must not recover restricted bytes. Arbitrary guest logs from every class must remain local, with only core-generated reasons and counts exported. An unsupported format or scanner failure must disclose no raw bytes. A normal new or atomically replaced approved file must be readable through its permitted disclosure profile in a later call under the same grant. An unenforceable platform or filesystem must refuse the grant.
- Browser registration cases must refuse broad ancestors, reserved OS and Ricevanta namespaces, unregistered policy names, ownership collisions, target aliases and a request to write Windows Firewall `EnableFirewall`. Prove that server and agent independently intersect registration, adapter and grant, runtime resolution stays at the exact target, shared native-host output is agent-generated and byte-identical, and the qualified first-party registrations match their recorded vendor locations. A new documented community browser must register and self-test as data without a core change.
- Console module cases must prove opaque-origin and external-egress isolation in Chromium, Firefox and WebKit under exact production headers. Observe external sinks and packets for hard-coded WebRTC peers, ICE, STUN/TURN credentials, data channels, DNS/resource hints, self-navigation, redirects, workers, forms, beacons, WebSockets and encoded asset URLs; a missing or ignored control fails qualification and refuses every module mount. Prove the initial entry and every asset match the server binding's frozen package and component digests, stale cached code and replacement cannot acquire a new binding, and module-supplied identity or digest cannot select authority. Then keep an existing `MessagePort` open across disable, revocation, any grant write and operator-role loss. Every later API dispatch must fail at the server even when the close notification is dropped. Verify binding substitution fails, queued requests cancel, the frame unmounts when notified, an already admitted action is audited rather than reported as undone, and a protected approval cannot dispatch after its bound extension state or operator rights change. Attempt token creation, approval decisions, credential/escrow reads, bridge binding creation, identity/RBAC, grant and trust administration through the bridge; refuse them even with those permissions in the operator and manifest. Allowed domain operations must still work under scoped and filtered catalogue entries.
- Responder fixtures must refuse parent signing without every allowed child permission and require protected approval for a single-device parent allowed to restore, un-isolate or unban, even when the returned plan omits that action. Bind the complete fleet scope and parameter envelopes before parent signing; refuse any returned step outside them. Responder signature and replay fixtures must substitute each bound package, component, artifact, grant, action and entity field and require refusal. Validate the whole returned plan before side effects, then crash before and after plan persistence and at step start, side effect and terminal write. Prove recovery uses the stored plan, never reruns the module or a completed step, refuses unstarted work after revocation, reconciles running work, handles cancellation and partial failure, and halts an unsafe unknown result. Malformed later steps and nondeterministic module output must not create a partial or changed plan.
- Connector cases must substitute callback package/component digests, request uid, CSR hash, issuance-field digest, epoch and component/registration generations. Expired or revoked tokens and callbacks after disable, uninstall, revocation, grant write or registration change must fail. Invalidate between API admission and `jobs` consumption and refuse the queued candidate; accept an exact completed retry once without another issuance, and refuse changed output. Reconcile an externally issued certificate separately without reviving stale callback authority. Prove that `jobs` refuses a connector with a revoked `service` certificate. Prove that an adapter whose self-test fails shows the capability as failing on the device and in the console.
- Identity authority: attempt provider, principal-link, claim/group mapping, directory, recovery, break-glass and direct approver-permission changes through console, API, GitOps and an extension bridge. Configurable approval-policy disable must not bypass protection. Reject self-approval, a directory-derived authority-approver permission, approval through an affected authentication method and a changed before/after hash. Verify one-use bootstrap, the first-provider and second-approver path, the declared single-custodian warning and an exact offline repair when no unaffected approver exists.
- Audit log: server credentials must fail `UPDATE`, `DELETE` and `TRUNCATE` and cannot remove the audit trigger. With database superuser access, alter an uncheckpointed record, rehash its suffix, delete only that suffix and rewrite a verification result. Each case must disagree with the independent authenticated tail, alert and prevent a later checkpoint from accepting altered history. Crash before prepare, after prepare, after database commit and before commit publication; exact retries must preserve the original sequence and hashes. A missing database row must not become an unsigned abort. Refuse forged resolutions, replayed older heads, omitted prepare objects and a head inconsistent with its chain. Run local-volume and qualified S3-compatible-store cases, including a delete marker over a locked version; report the journal-administrator boundary rather than promise detection without a trusted independent head (`../design/events.md` section 6). Creating, enabling, disabling or deleting an export destination, changing its filter, projection, endpoint or credentials, shortening audit retention and releasing a hold each require approval.
- Durable consumption: hold the earlier export or correlation transaction open while a later producer tries to allocate, then commit and roll back the earlier transaction in separate cases. Consumers must neither skip a late commit nor wait for an abandoned counter. Crash after destination acknowledgement and before cursor persistence, test pruning across a stalled cursor and verify the recorded duplicate or loss boundary. Exposed-role credentials must fail direct commit-head updates and caller-selected index sequences; narrow allocation functions must preserve the lock order (`../design/events.md` section 4.1).
- Report access: run a report, then revoke one source permission or narrow the runner's scope. The runner and every other affected reader must fail metadata listing, rows, downloads, range retries and cached dashboard reads. Move a covered entity out of scope, change group membership, disable the schedule owner and follow an old notification link. No storage URL may bypass the current footprint check (`report-template.md` section 4).
- Ingest acknowledgement: lose the original response after an asynchronous ledger commit while WAL flush is blocked. Retry on another replica; no `200 duplicate` may precede the new primary fence. Crash before the fence flush, promote a standby and repeat the ledger read and marker on the promoted primary. An absent ledger or failed marker must not acknowledge. After a successful fence, primary crash must preserve the batch; record the configured asynchronous-failover and `remote_write` operating-system-crash limits (`../design/events.md` section 3.5).
- Hold capture: pause an event, raw or lineage producer after fence acquisition and before commit while activating a hold and running retention. Every matching committed source must appear in the durable boundary or later capture tasks. Crash before and after ClickHouse copy, task completion and external partition drop; pending tasks must keep source pins, ambiguous results must block activation and retention, and missing evidence must produce `capture_failed`. Prove no autonomous TTL, other writer or lineage prune can bypass the fence. Release and narrow with overlapping holds and interrupted cleanup (`../design/events.md` section 5).
- S3 plans: pre-create the planned key with different bytes, including the right size and wrong digest, then force `412`; the destination must pause without advancing its cursor or publishing a complete manifest. Retry after a lost successful write and verify exact stored bytes. Crash after upload and before receipt persistence, change compression binaries and revoke read-back permission. Resume only from the frozen plan and staged bytes. Rewind with a changed projection and verify a new replay namespace and a manifest matching every actual output object (`event-export.md` section 10).
- EDR response: run the acceptance cases of `edr-response-actions.md` section 4 on every OS entry. Pause termination after identity validation, exit the target, force PID reuse and prove the replacement survives in normal, automatic, recovery and descendant sub-steps. Windows must prove successful creation-time validation with terminate and query rights, query failure refusal, mismatch refusal and protected-process refusal. Script timeout and cancellation must contain descendants that fork, call `setsid`, fork again and outlive the interpreter, including after a core crash; no surviving or unowned descendant permits terminal cancellation. Isolation must hold across a core crash, a reboot and removal of one filter, rule or map, and the reconcile loop must report the removal. An intel delta with a lower sequence, a foreign organization or a bad signature is refused and the installed set stays.
- RADIUS negative cases: refuse and record an Access-Request without `Message-Authenticator` over UDP, a forged or wrong-secret response path, a source outside the gateway prefixes, `Proxy-State`, a RadSec client certificate not pinned to a registration; a certificate-derived request with a wrong binding token, a password-login probe using a valid `netid` on the same FortiGate, a FortiGate login with an empty `mfa-password` and one with a typed password on the same server object (both `request_shape`), an ASA request that is not Authorize-Only or names a tunnel group outside the list; a name with no issued certificate, of a retired identity, a certificate from a foreign CA that carries an issued `netid` presented to a gateway configured as `radius-gateway-profiles.md` sections 4.3 and 5.2 require (it must fail at the gateway), of a superseded certificate past the overlap; EAP-TLS with a device-identity or server certificate, an expired or held certificate, TLS 1.0 or 1.1, TLS 1.2 without extended master secret, a resumption attempt (a full handshake must follow), oversized and excess fragments, conversation-cap exhaustion; kill a replica mid-conversation and prove the supplicant restarts cleanly. Stop PostgreSQL and prove every request is rejected and accounting is unanswered; stop `jobs` past the heartbeat bound and prove `authority_stale` rejects; prove the `jobs` accept audit alerts on an injected accept without a committed decision.
- RADIUS certificate evidence: during renewal overlap, authenticate separately with generations A and B of one `netid`. EAP-TLS and a qualified exact-binding gateway expose only the observed generation. Name-only requests expose `binding = identity_only`, omit serial, fingerprint, issuer and validity, and record unknown generation. Reject serial-specific policy publication or gateway admission without exact evidence; prove guarded access, dynamic-key refusal and runtime evidence-loss rejection. Another eligible generation must never fill the missing fields. Revocation of a possible name-only generation must target its sessions conservatively.
- RADIUS accounting: lose Start and three interim updates, then revoke while the gateway still carries traffic. Awaiting-Start and `accounting_stale` records must remain possibly active and targeted until proved termination or original enforced expiry. Deliver Accounting-On and Accounting-Off after newer Starts, duplicate them with changed delay and packet identifiers, reorder Start and Stop, reuse session ids across boots, skew the NAS clock and fail over servers. No delayed event may close a newer generation or reopen a stopped one; ambiguous linkage or timing must preserve possible activity. Verify retention does not delete possible sessions.
- RADIUS session order: publish two rapid narrowing revisions while parallel replicas claim work. Delay the first packet and replies, lose ACKs, duplicate packets, crash before and after transmission, expire a sender fence and resume the old sender. Every send and retry must use the current desired version; obsolete or unresolved CoA must block later CoA until stale application is excluded or Disconnect proves termination. A late ACK cannot complete current work or regress applied state. Require fresh authentication and a new session uid after Disconnect, and prove selectors cannot target a reused newer session id. These cases remain blocked until the exact dispatch protocol and gateway proofs exist.
- RADIUS attribute transitions: remove `Filter-Id`, remove a vendor group, change VLAN tunnel sets and timeout fields, and switch between profiles with different attribute sets, including a same-name profile revision. Inspect gateway state, not only ACK. CoA must use qualified explicit clearing and combined transition semantics; an unsupported removal or unknown applied set must select Disconnect. Delayed old packets cannot restore old permissions after current state is proved. A missing termination or timeout proof blocks the required gateway unit.
- RADIUS compromise recovery: copy the replica's role wrapping and sealing keys, TLS keys, database and deployment credentials, KMS grants and stored ciphertext into an adversarial fixture. Isolate it, terminate retained connections, revoke copied and shared credentials, and provision a new wrapping root and custody generation only to trusted replacements. The copied material must fail reads, watches, decryptions, secret-update submission and access to the replacement key. Generate and install fresh gateway secrets and binding tokens without overlap; an incomplete gateway cutover must stay disabled. A new sealing key wrapped under the copied role key must fail this case.
- Rule compilation: a rule `ricevanta-rulec` accepts compiles on each supported agent minor release, or is reported unsupported on that device (POL-05).

## 5. Whole-product workflows

The evidence manifest maps every blueprint feature to at least one passing case on every required unit through its documented platform mechanism or limit. The omission check reconciles this matrix with the required-unit manifest. These representative workflows must also pass end to end:

| Domain | Required workflow and observable result |
|---|---|
| MDM | Enroll, collect hardware, OS, software, user and disk inventory, apply and remove configuration, install, update and remove software, manage an OS update, assess compliance, run remote actions, and exercise lock and wipe by the platform mechanism. State, result, failure and audit records must agree. |
| MDM lock and recovery | On Windows add an alternate numerical recovery protector and external recovery key. On Linux add FIDO2, PKCS#11, password and second recovery slots. Lock must retain exactly one fresh acknowledged route and every alternate key must fail after restart. Interrupt before and after enrollment, escrow commit, acknowledgement and each deletion; inject an inventory change, lost acknowledgement, wrong volume, route, ciphertext hash, epoch or challenge, and replay an acknowledgement after restore. Prior recovery stays usable until valid durable acknowledgement; unknown state stops deletion. Verify authorized unlock and re-enrollment, suppressed route recreation while locked, and FileVault rotation's durable escrow and failure path. |
| EDR | Generate process-tree, file, network, DNS, registry (Windows), persistence, logon and script activity from every base source of `../design/edr.md` section 1.2 and the rule-demanded sources a test pack names; match a supported Sigma rule on the agent while offline and a correlation of each type on the server, including a late upload; raise each behavioral analytic and a YARA-X match; create an alert and investigation with ATT&CK and intelligence context, including an indicator delivered as a signed delta; exercise every command type of `edr-response-actions.md` with its undo, including isolation that passes only the allow list on IPv4 and IPv6, and a FIM change made while the core was down. Validate history, coverage gaps and remediation events. |
| DLP | Detect renamed content by format, inspect a file and archive, classify representative source code, API key, customer, Vietnamese identifier and financial samples, then exercise allow, monitor, warn and block across every file, clipboard, removable-media, browser, cloud and network channel, including a decision that uses an extension `parser` and `classifier` module. ## 6. Tamper, offline, recovery and update gates

- On macOS, remove a profile-based enrollment manually and verify prompt detection of enrollment, managed-setting and extension loss, degraded protection, operator warning and the server's missed-check-in fallback. On Windows as administrator and Linux as root, exercise direct service, driver or BPF removal and verify the reporting and missed-check-in limits in `../design/agent.md` section 9 without claiming prevention.
- For Ricevanta-controlled online uninstall and stop, require a valid token bound to the device. Reject a missing, invalid, replayed or foreign-device token and retain audit evidence. For offline removal, reject expired, reused and foreign-device release objects, and objects whose nonce is not the one the device currently displays.
- Disconnect an enrolled endpoint long enough to cross event retries and a certificate expiry. ## 8. Evidence and artifacts

Acceptance evidence is a machine-readable assertion tied to a case ID, requirement ID, unit identity, candidate digest and raw artifacts. An automated case supplies command output, structured results and relevant logs. A manual case supplies numbered steps, expected and observed results, operator identity, timestamps and screenshots or protocol captures. Security-sensitive failures also preserve server, endpoint and enforcement-point evidence with secrets and raw sensitive content removed.

An observation records context such as noisy timing, vendor behavior or a non-required environment. It cannot satisfy a requirement, waive a failure or change unsupported behavior into support. Flaky, skipped, retried without explanation, missing-artifact and expected-failure results block qualification. A justified environmental retry keeps both attempts and the reason.

The signed evidence manifest contains the frozen required-unit manifest and omission-check result, requirement-to-case matrix, exact lab inventory, preflight report, result files, benchmark data, schema and signature validation, logs, screenshots or captures, known OS limits, blocker list and reviewer decision. Artifacts use immutable hashes, access controls and the product's configured retention and data-minimization rules. Test data uses synthetic sensitive content and nonproduction keys.

## 9. Design assessment

Benefits: one state model prevents partial platform claims; blueprint traceability keeps representative workflows from narrowing scope; immutable evidence makes a release decision reproducible.

Trade-offs: the matrix requires substantial hardware, gateway and browser coverage; manual MDM, wipe, recovery and vendor-integration cases remain costly even when most assertions are automated.

Dependencies: release-signed platform packages, vendor entitlements and signing programs, supported test hardware, FortiGate and Cisco ASA and ASAv gateways, hostapd with one managed switch and one access point model, identity providers, directory services, external CA fixtures, every export destination, controlled performance hosts and an independent reviewer.

Limits: support applies to the declared qualified configuration profiles. Representative and pairwise assignments bound uncountable hardware, firmware, deployment and store combinations; qualification does not claim every combination. OS-imposed limits and the two capabilities deferred in `../platform-support.md` remain explicit and cannot be generalized to supported channels.

Alternatives considered: one smoke suite per OS was rejected because it cannot prove full feature scope; capability-only tests were rejected because they miss cross-domain identity, policy and event failures; field observation was rejected as release evidence because it is not controlled or reproducible.
