# Agent runtime entry point

`ricevanta-agent` becomes a real executable: a process that the native service manager starts, that reports readiness and health, that stops within a bound, and that refuses bad configuration. This specification fixes that lifecycle and nothing else. Enrollment, identity, transport, policy, sensors, local IPC, the spool manager and upload arrive with their own reviewed slices and are named in section 9 as blocked.

Authorities: AG-03, AG-08, AG-09, AG-12 and AG-13 in [decisions](../decisions.md), [architecture](../architecture.md) sections 1, 2 and 7, [agent design](../design/agent.md) sections 1, 6, 7 and 9, [release builds](release-builds.md) section 2, [platform support](../platform-support.md) and [the implementation plan](../plans/agent-runtime.md). [The footprint harness](footprint-harness.md) measures what this runtime produces.

## 1. Boundary and crates

|---|---|---|---|

| `agent/crates/json` | `ricevanta-json` | Strict bounded JSON reader and canonical writer for the configuration file and the health document (section 3) | Forbidden |
| `agent/crates/config` | `ricevanta-config` | Typed agent configuration, defaults, validation and per-OS default paths | Forbidden |

| `agent/crates/os-macos` | `ricevanta-os-macos` | `proc_pid_rusage`, `proc_pidinfo` and `mach_timebase_info` sampler through `libc`, descriptor-based file checks | Allowed only as section 1.1 states |
| `agent/crates/os-windows` | `ricevanta-os-windows` | Service Control Manager dispatcher and status, known-folder resolution, security-descriptor checks, the event log writer of section 6, `psapi`, `processthreadsapi` and `tlhelp32` sampler through `windows-sys` | Allowed only as section 1.1 states |

`ricevanta-core` depends on `ricevanta-json`, `ricevanta-config`, `ricevanta-os` and, by target, exactly one OS crate. It does not depend on `ricevanta-spool` or `ricevanta-batch`; those stay libraries until the spool manager slice wires durable segments, and the batch spec's measured-memory gate uses [the harness](footprint-harness.md). `ricevanta-json` serves the configuration file and the health document only; the agent's general JSON stack for OCSF events, policy bundles and the server protocol is decided by the transport and policy slices, so a second JSON implementation there is a conscious decision, not an accident. The executor is `tokio` 1.53.3 with features `rt-multi-thread`, `signal`, `sync` and `time` only: no `net`, `fs`, `process`, `macros` or `parking_lot`. The runtime is built explicitly with two worker threads named `rv-worker-<n>`, a blocking pool capped at four threads, and no `#[tokio::main]`. The release profile keeps `panic = "unwind"`, Cargo's default, so the task boundary of section 4 can catch a panic ([Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html#panic)); [release builds](release-builds.md) section 4 preserves that choice. [Dependency rows](../licensing.md) exist for the closure before code uses it, and the licensing row is the single home of the resolved `windows-sys` feature union.

### 1.1 Native crate boundary

The workspace lint `unsafe_code = "forbid"` stays and every portable crate inherits it. `os-macos` and `os-windows` do not inherit `[lints] workspace = true`; each declares `[lints.rust] unsafe_code = "deny"` and `missing_docs = "deny"`. Every `unsafe` block lives in a private function carrying `#[expect(unsafe_code, reason = "<API>: <invariant>")]` and a `// SAFETY:` comment naming the pointer, length and lifetime invariants it relies on. The Rust reference defines `forbid` as not overridable and `expect` as an expectation that warns when unfulfilled ([lint check attributes](https://doc.rust-lang.org/reference/attributes/diagnostics.html#lint-check-attributes)), so a stray `expect` without an unsafe block fails Clippy with `-D warnings`. Every foreign declaration comes from the locked `libc` or `windows-sys` crate; numeric constants and byte layouts those crates lack, or carry only under a feature outside the locked union (the Windows ACE type values and xnu's `kauth_filesec` layout of section 3.1), are crate-private constants that cite their header and declare no foreign item; no OS crate writes its own `extern` block, and none exposes a raw handle, pointer or `extern` item publicly; each exposes the `ricevanta-os` traits. Each OS crate has its own independent code review and an adversarial pass, and its tests run only on its native target.

## 2. Command line and modes

```
ricevanta-agent --version
ricevanta-agent version [--json]
ricevanta-agent run [--config PATH] [--state-dir PATH] [--runtime-dir PATH] [--log-dir PATH] [--log stderr|file]
ricevanta-agent service [--config PATH]
ricevanta-agent check-config [--config PATH]
ricevanta-agent health [--config PATH] [--max-age-ms N]
```

| Command | Behaviour |
|---|---|
| `--version` | One line `ricevanta-agent <version> <commit> <channel>` and exit 0, before any file or directory is touched |
| `version --json` | The four identity fields of [release builds section 2](release-builds.md#2-one-product-version) as a sorted-key JSON object, exit 0 |
| `run` | Foreground mode for development and the footprint harness: logs to stderr by default, handles `SIGINT` and `SIGTERM` on Unix and Ctrl+C, Ctrl+Break and console close on Windows, writes the health document, exits with the codes below |
| `service` | Service-manager mode: on Windows it calls `StartServiceCtrlDispatcherW` and runs the lifecycle inside `ServiceMain`; on Linux and macOS it is `run` with `--log file` and service-manager notifications enabled. Mode is chosen by the command only, never by detecting a console or an environment variable |
| `check-config` | Loads and validates configuration, prints the effective configuration as sorted-key JSON, exits 0 or 2 |
| `health` | Reads the health document, requires `state` to be `ready` and `written_unix_ms` within `max-age-ms` (default two intervals plus 5,000 ms), exits 0 when healthy, 1 otherwise |

Identity comes from the build environment variables `RICEVANTA_VERSION`, `RICEVANTA_COMMIT`, `RICEVANTA_CHANNEL` and `SOURCE_DATE_EPOCH` read with `option_env!`, which the release recipe sets from `rust-env.json`. A build without them reports version `0.0.0-local`, commit `unknown`, channel `local` and source epoch `0`; that identity can never match a build record. Exit codes: `0` success, `1` failure after the process was ready (a task panic, or a stop that missed its deadline), `2` command line or configuration error, `3` startup failure (directories, ownership, access control, health document, service manager). Section 5.1 maps every end to one restart rule on all three service managers; on Windows a code reaches the SCM's status only for a stop the SCM requested (section 5.4). Unknown commands, unknown flags and repeated flags exit 2 with a usage line on stderr; no output is ever written to stdout except `--version`, `version` and `check-config`.

## 3. Configuration

One file, `agent.json`, at a fixed per-OS path, or the path given by `--config`. It is the agent's operational file: logging, paths and intervals. It never carries a policy, identity, server, trust or token value, and [`config.schema.json`](../../schemas/agent/config/v1/config.schema.json) admits a security-relevant key only through a decision in `decisions.md`; the enrollment configuration (`design/pki.md`) and server-delivered signed policy are the other two local inputs the agent will read, each with its own slice. That is what `agent.md` section 9 means by rejecting unsigned local changes: policy, identity and trust come only signed, while this file sets how the service logs and where it writes.

Environment: no variable configures the agent. The agent reads exactly these variables and nothing else, in `service` mode on Linux only: `NOTIFY_SOCKET`, `WATCHDOG_USEC` and `WATCHDOG_PID` for the notification protocol, and `INVOCATION_ID`, which becomes the log field `invocation_id`. No build of the binary, test builds included, reads any other variable or carries a test hook; the plan tests the shutdown deadline and sampler failures in-process through the lifecycle's injected traits. The Windows data root comes from `SHGetKnownFolderPath(FOLDERID_ProgramData)`, not from `%ProgramData%`, so an environment value cannot redirect the service; the returned string is freed with `CoTaskMemFree` "whether SHGetKnownFolderPath succeeds or not" ([SHGetKnownFolderPath](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shgetknownfolderpath), [KNOWNFOLDERID](https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid)); a failed lookup is a startup failure.

| OS | Configuration | State | Runtime (health document) | Logs |
|---|---|---|---|---|
| macOS | `/Library/Application Support/Ricevanta/agent.json` | `/Library/Application Support/Ricevanta/state` | `/Library/Application Support/Ricevanta/run` | `/Library/Logs/Ricevanta` |
| Windows | `<ProgramData>\Ricevanta\agent.json` | `<ProgramData>\Ricevanta\state` | `<ProgramData>\Ricevanta\run` | `<ProgramData>\Ricevanta\logs` |
| Linux | `/etc/ricevanta/agent.json` | `/var/lib/ricevanta` | `/run/ricevanta` | `/var/log/ricevanta` |

Apple's local domain `/Library` is for "resources ... shared among all users" and `Application Support` holds app data under a vendor subdirectory ([File System Programming Guide](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html)); the Linux paths are the bases of `ConfigurationDirectory=`, `StateDirectory=`, `RuntimeDirectory=` and `LogsDirectory=` ([systemd.exec](https://man7.org/linux/man-pages/man5/systemd.exec.5.html)). The spool location in [events design section 2.6](../design/events.md#26-footprint-and-per-os-behaviour) sits under the same state root. On Windows `run` mode has no default paths: `--state-dir`, `--runtime-dir` and `--log-dir` are required (exit 2 without them), and a configuration file is read only when `--config` names one, so a development run never reads or creates anything under `<ProgramData>\Ricevanta`, a tree that only the installer creates (section 3.1).

| Key | Default | Bounds |
|---|---|---|
| `schema` | `ricevanta-agent-config-v1` | Exact |
| `log.level` | `info` | `error`, `warn`, `info`, `debug` |
| `log.sink` | `file` in `service`, `stderr` in `run` | `file`, `stderr`; `--log` overrides |
| `log.max_file_bytes` | 8388608 | 65536 to 268435456 |
| `log.max_files` | 4 | 1 to 16 |
| `health.interval_ms` | 60000 | 100 to 3600000; under a systemd watchdog at most `WATCHDOG_USEC / 2000`, section 5.2 |
| `shutdown.timeout_ms` | 10000 | 1000 to 60000; at most 15000 on macOS, section 5.3 |
| `paths.state_dir`, `paths.runtime_dir`, `paths.log_dir` | The OS row above | Absolute paths; `--state-dir`, `--runtime-dir`, `--log-dir` override |

[The example](../../schemas/agent/config/v1/example.json) is the complete default on Linux. Precedence, highest first: command-line flags, the file, built-in defaults. A missing file is allowed and logged as `config_default`; a present file must parse completely. `ricevanta-json` accepts the [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259.html) grammar with the project's strict profile: UTF-8 without a byte-order mark, at most 65,536 bytes, nesting depth at most 8, objects with unique keys, integers within `i64` and no fraction or exponent, no `NaN` or `Infinity`, no trailing bytes after the value, strings without unpaired surrogates. Unknown keys, wrong types and out-of-bounds values are errors that name the JSON pointer of the offending member. Any configuration error exits 2 before a directory, log file or health document is created. The reader is a portable library with its own vectors in [`schemas/agent/json/v1/`](../../schemas/agent/json/v1/vectors.json) and no `serde` dependency: six keys do not justify the `serde` closure, `serde_json::Value` and map decoding keep the last duplicate key where this profile must reject it, and the canonical sorted-key writer the health document needs is not something `serde_json` provides.

### 3.1 File protection

Every check runs on an open descriptor or handle, never on a path, so the file that is checked is the file that is read. On Unix the configuration file is opened read-only with `O_NOFOLLOW | O_CLOEXEC | O_NONBLOCK` through `OpenOptionsExt::custom_flags`. A symbolic link fails with `ELOOP`, and `O_NONBLOCK` makes the open of a FIFO "return without delay" instead of waiting for a writer, so the type check rejects it rather than hanging startup; the flag changes nothing for a regular file ([open(2)](https://man7.org/linux/man-pages/man2/open.2.html), [POSIX open](https://pubs.opengroup.org/onlinepubs/9799919799/functions/open.html), [fifo(7)](https://man7.org/linux/man-pages/man7/fifo.7.html), [OpenOptionsExt](https://doc.rust-lang.org/std/os/unix/fs/trait.OpenOptionsExt.html)). `File::metadata` on that descriptor must show a regular file, mode bits that grant nothing to group or others (`0600` or `0400`, as [agent design section 9](../design/agent.md#9-tamper-resistance) requires), and an owner that is the effective user or root; in `service` mode as root the owner must be root. Directories are opened with `O_DIRECTORY | O_NOFOLLOW | O_CLOEXEC | O_NONBLOCK` and checked the same way: owned by the effective user (root in `service` mode), mode exactly `0700` for state and logs and `0755` for the runtime directory, whose health document other local users may read on Unix.

Every object is reached through the descriptor of its checked parent. Every configured path, from `--config`, `--state-dir`, `--runtime-dir`, `--log-dir` or `paths.*`, must be absolute and in normal form: no empty segment (`//`), no `.` or `..` segment anywhere, no trailing separator, and on Windows a drive-letter root with `\` separators, no UNC or `\\?\` prefix, and segments that contain none of `<`, `>`, `:`, `"`, `/`, `|`, `?`, `*` or the characters 0 to 31, do not end in a period or a space, and are not a device name: a segment's text before its first period, with trailing spaces removed and compared case-insensitively, is none of `CON`, `PRN`, `AUX`, `NUL`, `COM1` to `COM9`, `LPT1` to `LPT9`, the superscript forms `COM¹`, `COM²`, `COM³`, `LPT¹`, `LPT²`, `LPT³` ([Naming Files, Paths, and Namespaces](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)), or the console names `CONIN$` and `CONOUT$` ([CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)), so `CON.txt`, `CON .txt` and `conout$.log` are all refused. The schema admits both forms because one schema validates documents for every OS, but the loader accepts only the running OS's form: a Windows path on Unix or a Unix path on Windows is an error. Any other spelling is a configuration error with exit 2, enforced by the schema pattern and repeated by the loader, because `O_NOFOLLOW` covers only the last component, a trailing `/` or `/.` would follow a link before it, and a `..` segment would make the checked parent differ from the lexical one. Each such path then splits into a parent and a final plain name. The parent is opened by path with the directory flags above and checked, and the child is opened or created relative to that descriptor. Inside a checked directory, `health.json.tmp`, `health.json`, `agent.log` and its rotations are created, renamed and deleted relative to the directory's descriptor, never by resolving the directory's path again. On Linux `ricevanta-os-linux` does this with the standard library alone by addressing `/proc/self/fd/<descriptor>/<name>`, where each entry is "a symbolic link to the actual file" ([proc_pid_fd](https://man7.org/linux/man-pages/man5/proc_pid_fd.5.html)) and, as a magic link, is "not resolved through pathname-expansion" but acts as a "direct reference to the kernel's own representation of a file handle" ([symlink(7)](https://man7.org/linux/man-pages/man7/symlink.7.html)), so the name is looked up in the open directory itself; on macOS `ricevanta-os-macos` calls `openat`, `mkdirat`, `renameat` and `unlinkat` from the locked `libc` under section 1.1. The `Platform` trait therefore takes a checked directory and a name, never a path, for everything below the parent.

The configuration file's parent must be owned by root or the effective user (root in `service` mode) and writable by neither group nor others, so no other user can rename or replace the file between starts. The parents of the state and runtime directories follow the same rule, writable by neither group nor others, because a group writer could swap in an older state directory or plant a health document. The parent of the log directory alone must be owned the same way and not writable by others, with write by its group accepted, because distribution layouts grant it to system groups on log roots, for example `/var/log` on Ubuntu and `/Library/Logs` on macOS (verify); the plan's CI records the observed owner and mode of every default parent. Ancestors above the parent are not checked: the default ancestors are root-owned system directories, and a configured path is chosen by root in a root-only file, so a path under a writable ancestor is a configuration error the operator owns, recorded in section 8. A missing directory is created relative to its parent's descriptor with `DirBuilderExt::mode`, opened relative to the same descriptor and checked for ownership; only when this call created it and it is still empty is it set to its exact mode with `File::set_permissions` on the open descriptor, which is `fchmod` on Unix, because `mkdir` applies the process umask, which launchd or a shell may set narrower ([mkdir(2)](https://man7.org/linux/man-pages/man2/mkdir.2.html), [File::set_permissions](https://doc.rust-lang.org/std/fs/struct.File.html#method.set_permissions)). Every file the agent creates, the health document and the log files, is set to its mode the same way; an existing file is opened without truncation, checked on its descriptor, and only then truncated. A directory that already existed is never re-moded: a wrong mode fails. On macOS the data root `/Library/Application Support/Ricevanta`, parent of `agent.json`, `state` and `run`, is root-owned with mode `0755` and is created or verified first by the same rule; on Linux systemd creates the four directories (section 5.2). Any failure is `startup_failed` with the step name and exit 3, never a fall back to defaults or a weaker mode.

On macOS the mode bits are not the whole answer: xnu evaluates an object's extended ACL before its mode bits, and an allow entry grants rights the mode denies ("if we have an ACL, evaluate it", "ALLOWED - all rights granted by ACL", `vnode_authorize_simple` in [vfs_subr.c](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/vfs/vfs_subr.c)). Every object the agent checks or creates on macOS (`agent.json`, its parent, the state, runtime and log directories, their parents, and each file it creates) is therefore also checked for an extended ACL on its open descriptor. `ricevanta-os-macos` calls `fgetattrlist` from the locked `libc` with an `attrlist` whose `bitmapcount` is `ATTR_BIT_MAP_COUNT` and whose only set bit is `commonattr = ATTR_CMN_EXTENDED_SECURITY`, options 0 and a 3,128-byte buffer: a `u_int32_t` total length, one 8-byte `attrreference_t` whose `attr_dataoffset` is relative to the reference itself, and room for a 44-byte `kauth_filesec` header plus `KAUTH_ACL_MAX_ENTRIES` (128) entries of 24 bytes. Because `ATTR_CMN_RETURNED_ATTRS` is not requested, the reference is always present. The agent decodes the returned `kauth_filesec` with bounds checks, using the layout and constants of xnu's [kauth.h](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/kauth.h) (`KAUTH_FILESEC_MAGIC`, `KAUTH_FILESEC_NOACL`, 24-byte `kauth_ace` entries, `KAUTH_ACE_KINDMASK`); the kernel packs the in-memory ACL in host byte order behind a header it fills itself, and, for this request, returns an empty attribute when the object has no ACL ([vfs_attrlist.c](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/vfs/vfs_attrlist.c)). An empty attribute or an entry count of `KAUTH_FILESEC_NOACL` means no ACL. A failed call, a total length above the bytes returned, or an offset or attribute length that reaches outside them fails closed as `insecure_acl` with exit 3. An object passes only when every entry is of kind `KAUTH_ACE_DENY`, which can only take rights away; an allow (`KAUTH_ACE_PERMIT`), audit, alarm or unknown entry, a bad magic or a length that is not a whole number of entries fails as `insecure_acl` with exit 3, whoever the entry names. The log directory's parent gets no ACL allowance beyond its group-write bit. Because no checked parent carries an allow entry, a created object can inherit only deny entries, and the agent checks it again after creation. On Linux a POSIX ACL's named entries are limited by the mask, and "the group permissions correspond to the permissions of the ACL_MASK entry" ([acl(5)](https://man7.org/linux/man-pages/man5/acl.5.html)), so the exact-mode rules already bound them; on the log directory's parent, whose group write is accepted, that mask can also admit named users, which widens the log-rename residual of section 8 to them.

On Windows the same rule holds in `service` mode, with security descriptors as the evidence. `ricevanta-os-windows` opens `agent.json`, its parent directory and the three directories with `FILE_FLAG_OPEN_REPARSE_POINT` and, for directories, `FILE_FLAG_BACKUP_SEMANTICS` through `OpenOptionsExt::custom_flags` and `access_mode(READ_CONTROL | FILE_READ_ATTRIBUTES | FILE_READ_DATA)` ([CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [OpenOptionsExt](https://doc.rust-lang.org/std/os/windows/fs/trait.OpenOptionsExt.html)), rejects a handle whose attributes include `FILE_ATTRIBUTE_REPARSE_POINT`, and calls `GetSecurityInfo(handle, SE_FILE_OBJECT, OWNER_SECURITY_INFORMATION | DACL_SECURITY_INFORMATION)`, which needs `READ_CONTROL` on the handle and returns a descriptor freed with `LocalFree` ([GetSecurityInfo](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-getsecurityinfo)). Accepted owners are exactly `S-1-5-18` (Local System) and `S-1-5-32-544` (Administrators) ([well-known SIDs](https://learn.microsoft.com/en-us/windows/win32/secauthz/well-known-sids)). The DACL must be present and not null. Every entry is read with `GetAce`, including inherit-only entries, because those decide the rights of the log and health files the agent creates later. On every checked object an `ACCESS_ALLOWED_ACE_TYPE` entry whose trustee is neither of those two SIDs fails when its access mask is nonzero, whatever the bits, so no read, execute, synchronize or attribute right is granted to anyone else either; an `ACCESS_DENIED_ACE_TYPE` entry is accepted; any other entry type (object, callback or compound entries) fails closed, since a plain file DACL written by the installer contains none ([ACE_HEADER](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-ace_header)). `CREATOR OWNER` (`S-1-3-0`) counts as another principal. No other principal can therefore open the health document, or any other checked object, for read, write, delete or a change of its security descriptor on Windows: a process that opens a file without `FILE_SHARE_DELETE` keeps others from opening it for delete access ([CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)), which the replacing rename of section 7 needs (verify), so a reader outside `SYSTEM` and Administrators could stall health updates or startup. The DACL does not stop an open that requests no access: with a desired access of zero "the application can query certain metadata such as file, directory, or device attributes without accessing that file or device, even if GENERIC_READ access would have been denied" (same page). Microsoft does not state whether such a handle blocks the rename (verify); the plan's Windows service test records it. The parent of each of the three directories, which is `<ProgramData>\Ricevanta` in the default layout and a directory the operator prepares the same way for a configured path, passes the same rule. The checked objects on Windows are therefore exactly `agent.json`, its parent, which is the data root `<ProgramData>\Ricevanta` in the default layout and the directory of the `--config` path otherwise, the state, runtime and log directories, and each directory's parent. `<ProgramData>` itself is never checked, and the data root is verified only as a parent of those objects: the default `<ProgramData>` DACL lets `Users` create folders (verify), which the rule would refuse on every installation. Renaming or deleting the data root needs `DELETE` on it, which its own checked DACL grants no one else, or `FILE_DELETE_CHILD` on `<ProgramData>`, which its default DACL does not grant to `Users` (verify); the plan's CI records the observed `<ProgramData>` DACL. Renaming or deleting an object needs "either delete permission on the file or delete child permission in the parent directory" ([MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw)), and the rule leaves no other principal any right on these objects, so on Windows files inside a checked directory are created by path: no principal outside `SYSTEM` and Administrators can redirect that path, and each created file is opened with `FILE_FLAG_OPEN_REPARSE_POINT` and refused when it is a reparse point. A failing object is `startup_failed` with `insecure_acl`, the object and the offending SID, and exit 3. The agent never creates these objects in `service` mode: the installer under [AG-12](../decisions.md#ag-12-native-packages-and-development-archives) creates `<ProgramData>\Ricevanta` with inheritance removed and grants exactly `SYSTEM:(OI)(CI)F` and `Administrators:(OI)(CI)F` ([icacls](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/icacls)), which is also how the plan's CI service test prepares the tree. When `<ProgramData>\Ricevanta` already exists, the installer sets its owner to Administrators and replaces the DACL of the whole tree before it writes any file, or fails the installation visibly; a tree that another user pre-created would otherwise refuse every start. In `run` mode on Windows nothing is checked: the developer names the three directories (section 3), the agent creates missing ones with inherited permissions and logs `dev_directories_created`; that mode is a development path, not an installation.

## 4. Lifecycle

```
starting ──> ready ──> stopping ──> stopped
   │                       ▲
   └── failed (exit 2 or 3) └── stop request: signal, service control, console event
```

Startup, in order: parse the command line; load and validate configuration; create or verify the directories (section 3.1); open the log sink; build the executor; start the health sampler; register stop sources; write the health document with `state: starting` then `ready`; notify the service manager ready (`READY=1`, `SERVICE_RUNNING`). Lines emitted before the file sink opens go to standard error, or to the event log in the Windows service (section 6). Any failure before `ready` logs `startup_failed` with the step name and exits 2 or 3; a health document that cannot be written during startup is step `health_write` and exit 3. No partial service stays running. Readiness is reported only after the health document is written, so a consumer that sees `ready` can also read health.

Stop: the first stop request moves the state to `stopping`, is logged as `stop_requested` with its source, writes the health document with `state: stopping`, notifies the service manager (`STOPPING=1` with `STATUS=stopping`; on Windows, only for a stop the SCM requested, `SERVICE_STOP_PENDING` with `dwWaitHint` equal to the effective deadline plus 5,000 ms and an incremented `dwCheckPoint` every 2,000 ms), cancels the sampler and every task, and joins them under the deadline. Repeated stop requests are counted and ignored; the Windows service receives none (section 5.4). On completion the agent writes `state: stopped`, logs `shutdown_complete` with the elapsed milliseconds, flushes and closes the log, reports the end to the service manager with code 0 (section 5), and exits 0. If the deadline passes the agent logs `shutdown_timeout`, naming the tasks still running, writes `state: stopped`, reports the end with code 1, and exits 1; process exit ends any remaining thread.

The effective deadline is `shutdown.timeout_ms`, except: on `SERVICE_CONTROL_SHUTDOWN` it is the smaller of that value and 15,000 ms, because the SCM gives a service about 20 seconds at system shutdown ([service control handler](https://learn.microsoft.com/en-us/windows/win32/services/service-control-handler-function)); on `ctrl_close` it is the smaller of that value and 4,000 ms, because the console gives a closing process 5,000 ms ([HandlerRoutine](https://learn.microsoft.com/en-us/windows/console/handlerroutine)). systemd sends `SIGTERM` and, after `TimeoutStopSec=`, `SIGKILL` ([systemd.service](https://man7.org/linux/man-pages/man5/systemd.service.5.html), [systemd.kill](https://man7.org/linux/man-pages/man5/systemd.kill.5.html)); launchd sends `SIGTERM` at shutdown ([Creating Launch Daemons and Agents](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html)). The unit and plist in section 5 set their stop bounds above the agent's maximum. There is no configuration reload: `SIGHUP` is logged as `signal_ignored` and a changed file takes effect at the next start.

Stop sources per mode: Unix `run` and `service` take `SIGTERM` and `SIGINT` through `tokio::signal::unix` (`SignalKind::terminate`, `SignalKind::interrupt`); registering a listener replaces the default disposition for the process lifetime and coalesces repeated signals, which the design tolerates because a stop is idempotent ([tokio Signal](https://docs.rs/tokio/1.53.3/tokio/signal/unix/struct.Signal.html)). Windows `run` takes `ctrl_c`, `ctrl_break` and `ctrl_close` through `tokio::signal::windows`, which uses `SetConsoleCtrlHandler`. Windows `service` takes `SERVICE_CONTROL_STOP` and `SERVICE_CONTROL_SHUTDOWN` through the `HandlerEx` function registered with `RegisterServiceCtrlHandlerExW`; the handler only records the request on a channel and returns, because "the control handler must return within 30 seconds"; `SERVICE_CONTROL_INTERROGATE` is answered by the current status, `SERVICE_ACCEPT_PRESHUTDOWN` is not requested, and controls are accepted only after `SERVICE_RUNNING` is reported, as [Writing a ServiceMain Function](https://learn.microsoft.com/en-us/windows/win32/services/writing-a-servicemain-function) recommends. A panic in any task is caught at the task boundary, logged as `task_panicked` with the task name, and treated as a stop request with exit code 1; the process never continues with a dead task. In the Windows service such an internal stop reports nothing to the SCM: the status stays `SERVICE_RUNNING` until the process ends (section 5.4).

## 5. Service-manager integration

Installation of these files and settings belongs to the AG-12 lifecycle slice, which owns binary locations, package transactions and uninstall authorization. `<bindir>` stands for that slice's install directory. This section fixes their contents so the lifecycle slice and the tests agree.

### 5.1 One restart policy

The service manager, never the agent, restarts the agent, and one rule holds on all three managers: a stop through the manager ends the service; a stop signal sent from outside the manager ends it only when the stop completes within its deadline; every other end restarts it. Exit codes 2 and 3 restart too, so the agent returns without an administrator once a corrected file, directory or permission lets it start; launchd and the SCM cannot tell one nonzero code from another, so excluding them on systemd alone would make the managers disagree. Each manager bounds a failure loop to about one start every 10 seconds and never stops retrying.

| End | Exit | systemd | launchd | SCM |
|---|---|---|---|---|
| Stop through the manager: `systemctl stop`, `launchctl bootout`, `SERVICE_CONTROL_STOP`, system shutdown | 0, or 1 when the deadline passed | Not restarted: `systemctl stop` is exempt from `Restart=` | Not restarted: `bootout` unloads the job | Not restarted: `SERVICE_STOPPED` is reported and non-crash failure actions are off |
| `SIGTERM` or `SIGINT` from outside the manager (`kill`, `systemctl kill`, `launchctl kill`), completed | 0 | Not restarted: clean exit | Not restarted: `SuccessfulExit` false restarts only a nonzero exit | No signals |
| The same, deadline passed | 1 | Restarted | Restarted | No signals |
| Task panic after `ready` | 1 | Restarted | Restarted | Restarted: the process ends without reporting `SERVICE_STOPPED` |
| Configuration error | 2 | Restarted | Restarted | Restarted, as above |
| Startup failure | 3 | Restarted | Restarted | Restarted, as above |
| Killed: `SIGKILL`, watchdog `SIGABRT`, crash | Signal or abnormal end | Restarted | Restarted (`Crashed`; `SIGKILL` verify on `macos-15`, fallback in section 5.3) | Restarted |

systemd's `Restart=on-failure` restarts on a nonzero exit code, an unclean signal, a timeout and a watchdog failure, treats exit 0 and `SIGHUP`, `SIGINT`, `SIGTERM` and `SIGPIPE` as clean, and skips the restart when the service "is stopped with systemctl stop or an equivalent operation"; restarts stay subject to the start rate limit, and a unit that reaches it is "not attempted to be restarted anymore", so the unit sets `StartLimitIntervalSec=0`, which disables the limit ([systemd.service](https://man7.org/linux/man-pages/man5/systemd.service.5.html), [systemd.unit](https://man7.org/linux/man-pages/man5/systemd.unit.5.html)). launchd and the SCM are described in sections 5.3 and 5.4.

### 5.2 Linux

`ricevanta-agent.service`:

```ini
[Unit]
Description=Ricevanta endpoint agent
StartLimitIntervalSec=0
[Service]
Type=notify
NotifyAccess=main
ExecStart=<bindir>/ricevanta-agent service
Restart=on-failure
RestartSec=10s
TimeoutStopSec=75s
WatchdogSec=180s
KillMode=control-group
ConfigurationDirectory=ricevanta
StateDirectory=ricevanta
RuntimeDirectory=ricevanta
RuntimeDirectoryPreserve=yes
LogsDirectory=ricevanta
StateDirectoryMode=0700
LogsDirectoryMode=0700
RuntimeDirectoryMode=0755
UMask=0077
NoNewPrivileges=yes
[Install]
WantedBy=multi-user.target
```

No network ordering appears because this slice opens no connection; the transport slice adds `Wants=network-online.target` together with `After=`, the pairing [systemd.special](https://man7.org/linux/man-pages/man7/systemd.special.7.html) requires for units that need a configured network. `Type=notify` keeps the unit in `starting` until `READY=1` arrives, and `WatchdogSec=` requires `WATCHDOG=1` within the interval or the service is marked failed and killed ([systemd.service](https://man7.org/linux/man-pages/man5/systemd.service.5.html)). `RuntimeDirectoryPreserve=yes` keeps `/run/ricevanta` and its final health document after a stop; the default removes the directory when the service stops ([systemd.exec](https://man7.org/linux/man-pages/man5/systemd.exec.5.html)). `UMask=0077` does not narrow the health document, whose mode the agent sets on the open file (section 3.1). The agent implements the notification protocol itself: one datagram per message to the `NOTIFY_SOCKET` address, a filesystem path when it starts with `/` or a Linux abstract name when it starts with `@`, which the manual states may be reimplemented without `libsystemd` ([sd_notify](https://man7.org/linux/man-pages/man3/sd_notify.3.html)). The implementation uses `UnixDatagram::unbound` and `send_to_addr` with `SocketAddrExt::from_abstract_name` for the abstract form ([UnixDatagram](https://doc.rust-lang.org/std/os/unix/net/struct.UnixDatagram.html), [SocketAddrExt](https://doc.rust-lang.org/std/os/linux/net/trait.SocketAddrExt.html)), so no LGPL library is linked (`licensing.md` lists libsystemd for journal reading only).

Messages: `READY=1` once, `STATUS=<state>` on every state change, `STOPPING=1` at stop, and `WATCHDOG=1` at the end of every sampler tick, whether the tick produced a sample or a typed `SampleError`, only when `WATCHDOG_PID` is unset or equals the own pid ([sd_watchdog_enabled](https://man7.org/linux/man-pages/man3/sd_watchdog_enabled.3.html)). The tick is the only ping cadence, so a metric failure stays a health-document condition and only a hung or dead sampler task stops the pings. A tick interval that cannot keep two pings inside one watchdog period is refused: when `health.interval_ms × 1000` exceeds `WATCHDOG_USEC / 2`, startup fails with `watchdog_interval_conflict` and exit 2. Under `WatchdogSec=180s` the default 60,000 ms interval and anything up to 90,000 ms pass; a drop-in `WatchdogSec=60s` caps the interval at 30,000 ms.

`NoNewPrivileges=yes` holds for this slice, which starts no child process. The bit "is inherited across fork, clone, and execve", and "LSMs will not relax constraints after execve" ([no_new_privs](https://www.kernel.org/doc/html/latest/userspace-api/no_new_privs.html)), so a package manager the core runs under MDM-05 could be refused an SELinux domain transition (verify on an SELinux distribution). The MDM slice therefore revisits this setting, and qualifies its choice on an SELinux distribution, before the core executes any package manager.

### 5.3 macOS

`/Library/LaunchDaemons/io.ricevanta.agent.plist`, owned by root with mode `0600`: Apple requires that globally installed daemons "must be owned by the root user" and "must not be group writable or world writable", naming modes `600` or `400` ([Creating Launch Daemons and Agents](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html)):

```xml
<key>Label</key><string>io.ricevanta.agent</string>
<key>ProgramArguments</key><array><string><bindir>/ricevanta-agent</string><string>service</string></array>
<key>RunAtLoad</key><true/>
<key>KeepAlive</key><dict><key>SuccessfulExit</key><false/><key>Crashed</key><true/></dict>
<key>ThrottleInterval</key><integer>10</integer>
<key>ExitTimeOut</key><integer>75</integer>
<key>StandardErrorPath</key><string>/Library/Logs/Ricevanta/launchd.err.log</string>
```

The `launchd.plist` manual page shipped with macOS, which Apple does not publish online, defines these keys (verify on the qualified release): with `SuccessfulExit` false the job is restarted "in the inverse condition" of an exit with status zero; `Crashed` true restarts a job that exited "due to a signal which is typically associated with a crash"; "If multiple keys are provided, launchd ORs them"; `ThrottleInterval` sets the minimum seconds between spawns, by default jobs "will not be spawned more than once every 10 seconds", which the plist states explicitly; `ExitTimeOut` is the wait between `SIGTERM` and `SIGKILL`, whose "default value is system-defined", so the plist sets it to match `TimeoutStopSec=`. Apple also warns that a daemon which "shuts down too quickly after being launched" may be "suspended and not launched again" and advises "do not shut down for at least 10 seconds after launch". Neither key's text settles a `SIGKILL`, which is also how macOS ends processes under memory pressure (verify), and the plan's `macos-15` run records whether launchd respawns the job after one. If it does not, the plist uses `<key>KeepAlive</key><true/>` instead, which the manual page describes as "unconditionally keep the job alive"; the only change to section 5.1 is then that a completed `SIGTERM` from outside launchd (`kill`, `launchctl kill`) also restarts the agent on macOS, while `bootout` still ends it. In `service` mode on macOS the agent holds a nonzero exit until 10 seconds after process start, idle and with its sampler stopped, and ends at once with the same code if `SIGTERM` arrives during the hold. The configuration loader caps `shutdown.timeout_ms` at 15,000 on macOS, which keeps the agent's stop well inside any bound launchd applies at system shutdown, a bound Apple does not document; launchd sends `SIGTERM` at shutdown (section 4), and the plan's `macos-15` run records the observed stop timing. `StandardErrorPath` captures what the agent writes before its log opens; Apple documents the key and advises against pointing output at `/dev/null`. Apple's daemon rules apply: no window-server connection, no per-user state, daemon-safe frameworks only ([TN2083](https://developer.apple.com/library/archive/technotes/tn2083/_index.html)); this runtime links no framework.

### 5.4 Windows

Service `RicevantaAgent`, display name `Ricevanta Agent`, own process, automatic start, `LocalSystem`, one restart action after 10 seconds with a one-day reset period, non-crash failure actions off:

```
sc.exe create RicevantaAgent binpath= "<bindir>\ricevanta-agent.exe service" type= own start= auto obj= LocalSystem displayname= "Ricevanta Agent"
```

`sc.exe create` takes exactly these parameters, with a space after each `=` ([sc.exe create](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/sc-create)). The AG-12 installer sets recovery through `ChangeServiceConfig2W`, never by running `sc.exe`: `SERVICE_CONFIG_FAILURE_ACTIONS` with `dwResetPeriod` 86,400, `lpRebootMsg` and `lpCommand` null, and one `SC_ACTION` of type `SC_ACTION_RESTART` with a 10,000 ms delay, on a handle with `SERVICE_CHANGE_CONFIG` and the `SERVICE_START` right the restart action requires; then `SERVICE_CONFIG_FAILURE_ACTIONS_FLAG` with `fFailureActionsOnNonCrashFailures` false ([ChangeServiceConfig2W](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nf-winsvc-changeserviceconfig2w)). When a service fails more often than it has actions, "the service controller repeats the last action in the array", and the count resets after `dwResetPeriod` seconds without failure ([SERVICE_FAILURE_ACTIONSW](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/ns-winsvc-service_failure_actionsw)). For CI and verification only, the same settings are `sc.exe failure RicevantaAgent reset= 86400 actions= restart/10000` and `sc.exe failureflag RicevantaAgent 0`, read back with `sc.exe qfailure` and `sc.exe qfailureflag`; that syntax comes from an archived Microsoft page (verify on the runner).

The SCM counts a service as failed "when it terminates without reporting a status of SERVICE_STOPPED" (SERVICE_FAILURE_ACTIONSW). With `fFailureActionsOnNonCrashFailures` true it would also queue failure actions after `SERVICE_STOPPED` with a nonzero `dwWin32ExitCode`, but that change "takes effect the next time the system is started" ([SERVICE_FAILURE_ACTIONS_FLAG](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/ns-winsvc-service_failure_actions_flag)), which would leave the first boot after installation without restarts, and it would restart a requested stop that missed its deadline, while "a queued restart action cannot be canceled" (ChangeServiceConfig2W). The flag therefore stays false and the agent reports by intent: for an end the SCM requested (`SERVICE_CONTROL_STOP` or `SERVICE_CONTROL_SHUTDOWN`) it calls `SetServiceStatus` with `SERVICE_STOPPED` once, last, with `NO_ERROR` when the deadline was met and with `dwWin32ExitCode = ERROR_SERVICE_SPECIFIC_ERROR` and `dwServiceSpecificExitCode` 1 when it passed, and the SCM does not restart it ([SetServiceStatus](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nf-winsvc-setservicestatus)). For every other end (a task panic, a configuration error or a startup failure inside `ServiceMain`) it writes the final health document when it can, logs the reason to the log file or, before the log opens, to the event log (section 6), and ends the process with its exit code without reporting `SERVICE_STOP_PENDING` or `SERVICE_STOPPED`, so the SCM sees the process end from `SERVICE_START_PENDING` or `SERVICE_RUNNING`, the same transition as a crash, and runs the restart action. No Microsoft page states how the SCM treats a process that ends after it reported `SERVICE_STOP_PENDING` itself, so the agent never reports that state on its own initiative.

`LocalSystem` carries extensive privileges and acts as the computer on the network ([LocalSystem account](https://learn.microsoft.com/en-us/windows/win32/services/localsystem-account)); the architecture requires it for the sensors and the driver port, and this slice uses none of those privileges. The main thread calls `StartServiceCtrlDispatcherW` within 30 seconds of process start and `ERROR_FAILED_SERVICE_CONTROLLER_CONNECT` is reported as exit 3 with the hint to use `run` ([StartServiceCtrlDispatcherW](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nf-winsvc-startservicectrldispatcherw)). `ServiceMain` registers the handler first, reports `SERVICE_START_PENDING` with a 10,000 ms wait hint and `dwControlsAccepted = 0`, runs the section 4 startup, then reports `SERVICE_RUNNING` with `SERVICE_ACCEPT_STOP | SERVICE_ACCEPT_SHUTDOWN` ([SERVICE_STATUS](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/ns-winsvc-service_status), [RegisterServiceCtrlHandlerExW](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nf-winsvc-registerservicectrlhandlerexw)).

During a requested stop the agent reports `SERVICE_STOP_PENDING` with `dwControlsAccepted = 0`. Accepting `SERVICE_ACCEPT_SHUTDOWN` there would change nothing: after the SCM sends `SERVICE_CONTROL_STOP`, "it will not send other control codes" ([service control handler](https://learn.microsoft.com/en-us/windows/win32/services/service-control-handler-function)), and `ControlService` refuses any control to a service in `SERVICE_STOP_PENDING` with `ERROR_SERVICE_CANNOT_ACCEPT_CTRL` ([ControlService](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nf-winsvc-controlservice)). The 15,000 ms cap of section 4 therefore applies only to a `SERVICE_CONTROL_SHUTDOWN` that arrives while the service is `SERVICE_RUNNING`. A system shutdown that begins during a requested stop does not shorten that stop's deadline; Windows waits for services only up to its own limit, `WaitToKillServiceTimeout` when rebooting (same page), and then proceeds, so a stop still running then can lose its final health document and last log lines, and the next start is unaffected. Once `SERVICE_STOP_PENDING` has been reported, every end of that stop, a task panic during it included, reports `SERVICE_STOPPED` once, last, with code 1 unless the stop completed cleanly, because the stop was requested. As the SCM delivers at most one stop control, the `stop_requests` counter of the Windows service is 0 or 1; on Unix and in Windows `run` mode it counts every stop signal or console event, of which only the first acts.

## 6. Logging

One format for every sink: one JSON object per line, encoded by `ricevanta-json` with sorted keys and no embedded newlines. Fixed fields: `ts` (UTC, RFC 3339 with milliseconds), `level` (`error`, `warn`, `info`, `debug`), `event` (a closed `snake_case` token from the catalogue in the plan), `pid`, `invocation_id` when systemd supplies one, and typed fields per event; an optional `detail` string is truncated at 2,048 bytes and a whole line is capped at 8,192 bytes. Logs carry identifiers, counts, durations and error variants, never file contents, user data, environment values or configuration bytes. Tests match `event` tokens and typed fields; display strings are not a contract.

The `file` sink writes `agent.log` in the log directory with mode `0600`, rotates by renaming to `agent.log.1` through `agent.log.<max_files - 1>` when the active file would exceed `log.max_file_bytes`, deletes the oldest, and logs `log_rotated` as the first line of the new file. A write failure is counted, retried on the next line and reported in the health document as `log_errors` with the token `log_write_failed`; it never stops the agent. The `stderr` sink writes the same lines to standard error. In `service` mode on Linux the service manager owns standard output and error ([systemd.exec](https://man7.org/linux/man-pages/man5/systemd.exec.5.html) defaults them to the journal), and the agent writes there only the lines emitted before the file sink opens and the final `startup_failed` line; the same holds for launchd's `StandardErrorPath`. The Windows service has no console, so it writes those same lines to the Application event log instead: `RegisterEventSourceW` with the source name `RicevantaAgent`, then one `ReportEventW` per line with `EVENTLOG_ERROR_TYPE` for `startup_failed` and `EVENTLOG_INFORMATION_TYPE` otherwise, the JSON line as the single insertion string with every `%` written as the JSON escape `\u0025` because Event Viewer treats `%n` as an insertion, and `DeregisterEventSource` before exit ([RegisterEventSourceW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-registereventsourcew), [ReportEventW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-reporteventw)). The AG-12 installer registers the source; without that registration "the event logging service uses the Application log" and shows the line without a description, which keeps the record. After the file sink opens, the Windows log is the file alone. These event log lines are unauthenticated diagnostics, never evidence of agent state: the Application log's default access grants `INTERACTIVE` and `SERVICES` logons read and write, and `RegisterEventSource` needs only write access ([Eventlog Key](https://learn.microsoft.com/en-us/windows/win32/eventlog/eventlog-key), [Event Logging Security](https://learn.microsoft.com/en-us/windows/win32/eventlog/event-logging-security)), so any interactive user can read the lines and write entries under the source name `RicevantaAgent`. The lines carry only what this section allows in any log (event tokens, identifiers, paths and error variants, never secrets or configuration bytes); the authoritative records are the agent's log file and health document, which only `SYSTEM` and Administrators can open, and the SCM's own state.

## 7. Health and the self-sampler

Every `health.interval_ms` the sampler task takes one `ProcessSample` of its own process through the `ProcessSampler` trait, then writes `health.json` in the runtime directory atomically: write `health.json.tmp` (mode `0644` on Unix, set on the open file), flush, rename over `health.json`. A failed write while running increments `health_write_failures`, adds `health_write_failed` to `errors` from then on, logs `health_write_failed` at `warn` and never stops the agent; the tick still ends with its watchdog ping. A failed write during startup is `startup_failed` at step `health_write` with exit 3 (section 4). A failed final `stopped` write is logged and leaves the exit code unchanged; a consumer then sees a stale document, which `health` reports as unhealthy by age. The document is validated by [`schemas/agent/health/v1/health.schema.json`](../../schemas/agent/health/v1/health.schema.json) and carries: `schema`, `pid`, `state`, `version`, `commit`, `channel`, `mode` (`run` or `service`), `written_unix_ms`, `uptime_ms`, `interval_ms`, `process` (the sample or `null`), `counters` (`samples`, `sample_failures`, `log_errors`, `health_write_failures`, `stop_requests`) and `errors`, a set drawn from exactly five tokens: `sampler_failed` (the last tick produced no sample), `log_write_failed` (a log write failed since start), `health_write_failed` (a health write failed since start), `watchdog_notify_failed` (a `WATCHDOG=1` datagram could not be sent), `shutdown_timeout` (set on the final document when the deadline passed). Every counter is bounded at `i64::MAX`, the reader's integer range, and the schema says so. The sample carries `footprint_bytes` with `footprint_metric` fixed per OS, `cpu_user_ms`, `cpu_system_ms`, `threads`, and `fd_count` on macOS and Linux or `handle_count` on Windows. Only `footprint_bytes`, `footprint_metric`, `fd_count` and `handle_count` take their names and units from the OCSF `process_sample` object in [the field catalogue](../../schemas/ocsf/contract-fields.md); the CPU times and the thread count are fields of this document that the catalogue does not define, and the later `agent_health_activity` conversion derives the catalogue's `cpu_pct` from the CPU times, the interval and the processor count. Event rate, the fourth AG-09 quantity, is sampled once the agent produces events. A sampler error sets `process` to `null`, adds `sampler_failed`, increments `sample_failures` and logs at `warn`; the agent keeps running and the watchdog ping is still sent (section 5.2). When enrollment exists, the same sample becomes the `agent_health_activity` event of AG-09; before enrollment no event is produced because the class requires a device uid.

| OS | Footprint | CPU | Threads | Descriptors |
|---|---|---|---|---|
| macOS | `libc::proc_pid_rusage(pid, RUSAGE_INFO_V4)` field `ri_phys_footprint` of `libc::rusage_info_v4`, 296 bytes ([resource.h](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/bsd/sys/resource.h), [libproc.h](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/libsyscall/wrappers/libproc/libproc.h)); Apple defines the footprint as dirty plus compressed memory ([WWDC 2018 session 416](https://developer.apple.com/videos/play/wwdc2018/416/)) | `ri_user_time` and `ri_system_time` are Mach absolute time, converted to nanoseconds with `libc::mach_timebase_info` | `libc::proc_pidinfo(PROC_PIDTASKINFO)` field `pti_threadnum` ([proc_info.h](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/bsd/sys/proc_info.h)) | `libc::proc_pidinfo(PROC_PIDLISTFDS)` buffer length divided by `PROC_PIDLISTFD_SIZE` |

Every declaration above comes from the locked `libc` or `windows-sys`. Sampling the own process needs no privilege on any OS. A sample must complete within 50 ms, and its memory is bounded by construction, which code review checks: every reader uses fixed buffers of at most 4 KiB, keeps no collection that grows with the number of mappings, descriptors or threads, and holds at most one directory enumeration open at a time, whose buffer the C library allocates and frees within the call. A test proves that sampling does not grow: in a dedicated test process, 10,000 consecutive samples after 1,000 warm-up samples raise the process's private memory by at most 64 KiB, read as `Anonymous` from `/proc/self/smaps_rollup` on Linux (the `status` and `statm` RSS fields are "inaccurate", and smaps_rollup gives "accurate, detailed information", [proc_pid_statm](https://man7.org/linux/man-pages/man5/proc_pid_statm.5.html)), `ri_phys_footprint` on macOS and `PrivateUsage`, the commit charge, on Windows ([PROCESS_MEMORY_COUNTERS_EX2](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2)). Together these bound the sampler's steady state; neither measures the transient peak inside one call, which only the footprint harness bounds, as part of the whole process. The Linux reader parses `smaps_rollup` and `stat` with bounded buffers and locates `utime` after the last `)` so a `comm` containing spaces or parentheses cannot shift fields.

## 8. Protocol trace and attacker outcomes

The path is: service manager starts the binary as root or `LocalSystem` → command selects the mode → configuration file opened and checked through its descriptor or handle → directories opened and checked → log opened → sampler started → health document written → readiness notified → stop request → bounded shutdown → final health and exit code. Nothing in this slice listens on a socket, opens a network connection, holds a key or accepts input from another process; the only inputs are the command line, the configuration file and the service manager's signals and environment.

| Attacker | What the attacker gets and what remains |
|---|---|
| Stolen enrollment token | Nothing here: no enrollment path exists and the configuration file never holds a token. The token's own protections are the PKI slice's |
| Compromised agent host | Root, `LocalSystem` or an administrator can stop, replace or reconfigure the agent and change or remove its restart settings; this slice adds no protection against that beyond refusing weak ownership and permissions, which is the reporting-only limit `design/agent.md` section 9 records for Windows and Linux. The configuration carries no security-relevant value, so tampering changes logging, paths and intervals within bounds |
| Compromised console session | No console, server or API connection exists in this slice |
| Rogue extension publisher | No extension loading exists; the agent reads no package |
| Network position between agent and server | No network traffic is produced or consumed |
| Database writer without signing keys | No server state reaches the agent |
| Server restored from backup | No server state reaches the agent; the health document and logs are local and carry no authority |
| Local unprivileged user on the endpoint | On Unix can read the health document (pid, version, counters, own-process metrics) and nothing else; on Windows cannot open any of the agent's objects for read, write, delete or a security-descriptor change, so cannot hold the health document open for read to stall its replacement; an open that requests no access, which the DACL does not prevent, can query attributes, and whether it can block the replacement is recorded by the plan's Windows test (section 3.1), but as an interactive user can read the pre-log lines in the Application event log and write misleading entries under the source name `RicevantaAgent`, which section 6 treats as unauthenticated diagnostics. Cannot pre-create or replace the configuration file, the state, runtime or log directories, because the service refuses to start on any object not owned by root, `SYSTEM` or `Administrators` or open to another principal (section 3.1). Where the log directory's parent grants write to a system group (section 3.1), a member of that group, or on Linux a named user that the parent's POSIX ACL admits within the same mask, can rename the checked log directory while the agent runs: the agent keeps writing into the directory it checked, through its descriptor, a reader of the log path can be shown planted log files, and the next start refuses any planted directory that is not root-owned with the exact mode. The state and runtime parents admit no group writer, so the state and the health document cannot be swapped this way. A configured path under an ancestor that other users can write is an operator error the agent does not detect. A `<ProgramData>\Ricevanta` tree that user pre-created before installation is reset by the AG-12 installer, or the installation fails visibly; a tree the installer did not reset is refused, not adopted. On macOS an ACL allow entry naming that user, set by root, an administrator or an MDM profile, or inherited from a parent, makes the agent refuse to start rather than run on an object the user can change. Can send `SIGTERM` only to processes it owns, so cannot stop the root service; a crash or failure the user provokes is restarted under section 5.1 |

## 9. Explicitly not in this slice

Each item below is blocked on the gate named and refuses, rather than fakes, its function: enrollment and device identity (analysis section 3.1 row 3, BE-12, PKI-02); server transport, mTLS and `/agent/v1` (same row); policy bundles, CEL and compiled rules (SH-02, POL-02); telemetry sources and enforcement points (EDR-02, platform qualification); local IPC listeners and helpers (AG-03); the durable spool manager, segment files and upload (AG-10, AG-11, EV-04); the updater and its local health gate (AG-07); `ricevanta-spool` and `ricevanta-batch` as dependencies of the binary; installation of the unit, plist and Windows recovery settings, installer-owned directory creation, the reset of a pre-existing `<ProgramData>\Ricevanta` tree and its access control lists, and event source registration on Windows (AG-12); configuration reload. The binary accepts no flag that pretends any of these exists.

## 10. Benefits, trade-offs, dependencies, limits, alternatives

Benefits: one explicit lifecycle on three service managers with readiness and watchdog on systemd, status on the SCM, bounded stop on all three and one restart rule for every exit code; a configuration file that cannot be weakened by environment or remote input and whose ownership is verified on the object that is read; a health document and self-sample that the footprint harness, the updater and the later OCSF health event all consume; native code confined to two crates with per-function expectations.

Trade-offs: `tokio` and its closure arrive before any network code needs them, accepted because the design names it as the executor and its signal handling is reviewed upstream code; a strict in-project JSON reader is more code to review than `serde_json`, accepted for the one-crate closure, the duplicate-key profile and the canonical writer; Windows directories come from the installer, so `run` on Windows is a development path only; restarting after configuration and startup errors repeats a failing start about every 10 seconds, each logged, accepted so a corrected installation recovers without an administrator; on Windows the SCM shows such an end as an unexpected termination, and the exit code lives in the agent's log or the event log; the Windows health document is readable only by `SYSTEM` and Administrators.

Dependencies: `tokio` 1.53.3 with its resolved closure, `libc` in `os-linux` (constants only) and `os-macos`, `windows-sys` 0.61.2 in `os-windows`; the exact feature union and every row are in [licensing](../licensing.md).

Limits: no privilege separation yet, since every later component is absent; the sampler's transient peak inside one call is bounded by review, not measured (section 7); ancestors above a directory's parent are not checked, and a group allowed to write the log root can show readers of the log path planted log files while the agent runs (section 3.1); the Windows private working set metric needs the 2023 servicing baseline; the `launchd.plist` key semantics, launchd's restart after a non-crash signal and the `sc.exe` recovery syntax carry verify markers that the plan's CI runs settle; a Windows restart already queued cannot be canceled, so an administrator who wants the agent to stay down after a failure disables the service before stopping it; `NoNewPrivileges=yes` is qualified for this slice only (section 5.2); `SIGHUP` reload is not offered.

Alternatives considered: `windows-service` crate, rejected because it adds a second binding layer over the same `windows-sys` family and its own unsafe code to review; `libsystemd` linking, rejected (LGPL and an unnecessary dependency when the protocol is documented for reimplementation); `serde_json` or `toml`, rejected for closure size, last-wins duplicates in `Value` and map decoding, and the missing canonical writer; mode detection through `ERROR_FAILED_SERVICE_CONTROLLER_CONNECT` or the absence of a terminal, rejected because an explicit command cannot be confused by a stolen console; environment-variable configuration, rejected because a root service must not take settings from whoever controls its launcher's environment; a health socket, rejected until the IPC slice fixes peer checks, since a file with atomic replacement answers the readiness question without a listener; path-based permission checks, including `GetNamedSecurityInfoW` on Windows, rejected for the check-then-open window that descriptor and handle checks (`GetSecurityInfo` on the opened handle) close; a counting global allocator as the sampler's memory proof, rejected because it needs `unsafe impl GlobalAlloc`, which the workspace lint forbids in every target, and because it sees no allocation the C library makes, such as the directory buffer; Valgrind DHAT, which would also measure the per-call peak, rejected because it runs on Linux only, adds a pinned GPL tool to CI and leaves macOS and Windows without an equivalent; checking every ancestor up to `/`, rejected because default log roots are group-writable on supported distributions and the parent check plus descriptor-relative creation already confine every write to the checked directory; group write on the state and runtime parents, rejected because it would let a group writer restore an older state directory or plant a health document; no restart after exit codes 2 and 3 (`RestartPreventExitStatus=2 3`), rejected because launchd and the SCM restart on any nonzero code, so the managers would disagree, and a corrected file would need a manual start; `fFailureActionsOnNonCrashFailures` true with every failure reported through `SERVICE_STOPPED`, rejected because the flag takes effect only at the next system start and would restart a late requested stop that cannot be canceled (section 5.4); `RestartSteps=` backoff on systemd, rejected because it needs systemd 254 and the supported distributions' systemd releases must be checked one by one (verify); read access to the Windows health document for `Users`, rejected because a reader holding the file can stall its replacement (section 3.1); a dedicated event log with a `CustomSD` that limits write to `SYSTEM`, rejected because it adds installer registry state for lines that carry no secret and decide nothing, while the authoritative records already sit in the restricted log file.
