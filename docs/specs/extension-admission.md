# Extension package admission

Admission decides whether a package the [loader](extension-loader.md) verified may be installed, which grants and targets it receives, whether a grant or target write on an installed version may commit, and what each commit writes. The decision is a pure, deterministic Go function over typed inputs. The production coordinator that supplies those inputs from committed authority and commits the result under the BE-12 fence remains blocked. EXT-09 records the decision; [the contracts](extension-admission-contracts.md) own the exact Go API, schemas and fixtures; [the plan](../plans/extension-admission.md) requires independent approval before code.

## 1. Boundary

The loader proves bytes: a signature by one caller-selected key over the exact manifest, a decoded document that passes [the manifest contract](extension-manifest.md), and files whose sizes and digests match. It proves no authority. Admission adds the stateful facts: which keys the operator trusts now, who owns an id, which `(id, version)` pairs are fixed forever, what is installed with which grants, targets, enabled state and install generation, which browser registrations exist and what they are bound to, which interfaces and release this server runs, whether approval policies are disabled, whether first-start setup is still open, and the current recovery epoch.

Admission is split in two:

| Part | What it is | State |
|---|---|---|
| Decision function `admission.Decide` | Pure Go: verified evidence, a typed decision-scoped authority snapshot, a typed request and component verdicts in; admit, approval required, identical retry or reject with stage-ordered reasons out. On admit it also returns the exact prepare intent. No clock, I/O, database, network, randomness or global state | Implementable now as `server/internal/extensions/admission` |
| Coordinator | Derives the request's source and requester from the authenticated call path, builds the snapshot from the journal projection under the writer fence, runs the function, stores the request content and creates the approval request or records a single-administrator exemption, or commits the intent, allocates grant generations, writes registration bindings, targets and the enabled state, publishes blobs and hands components to `policy` | Blocked on the executable journal protocol (BE-12, `authority-journal-protocol.md` section 10) |

The function never reads PostgreSQL rows. A snapshot built from rows alone is not admission authority; the coordinator derives it from the authenticated journal projection ([backend design section 6.1](../design/backend.md#61-external-authority-journal-and-restore-fence)). This keeps a database writer without signing keys out of every decision, and makes every decision reproducible from a fixture.

Out of scope here, with their homes: the browser-registration schema and canonical OS targets ([extension design section 7.2](../design/extensions.md#72-agent-use), `analysis.md` section 3), the browser-adapter file schema (section 7.1 there), component content validators (each format's owner), the console bridge catalogue, connector contracts and the agent runtime. Admission consumes their results as typed verdicts; it does not reimplement them.

## 2. Inputs and their authority

| Input | Content | Source of authority |
|---|---|---|
| Evidence | Id, version, publisher fingerprint, the three exact digests (package, manifest, envelope), `spec.requires`, and every component with its name, kind, interface and requested capabilities | `admission.FromPackage(loader.Package, manifest.Options)` over the loader's result; for a grant update, the stored package blob loaded again |
| Snapshot | Recovery epoch; the approval-policy setting and its generation; whether first-start setup is open; the running release version, present only when a release manifest verified at start (section 6); the fingerprint of the project key compiled into the binary; the trust list with each entry's generation; the id's revocations and revocation generation, ownership record, tombstones and install with its enabled state, install generation, targets and grant records; the referenced browser registrations with their bindings; reviewed disclosure-profile ids; the requested device-group uids that exist; whether the presented approval uid is consumed; served interfaces | Journal projection for every authority item (trust list, revocations, ownership, tombstones, installs, grants, targets, enabled state, install generations, bindings, consumed approvals, the approval-policy setting, the first-start marker and every generation); the running binary for served interfaces, the reviewed disclosure-profile list and the compiled project key; the start-up release-manifest check for the release version; the `devices` module interface for device-group existence, which is not journaled (section 8) |
| Request | Source (`upload`, `api`, `gitops`, `index`, `server-image`), requester uid, whether it is a grant update, one proposed grant per component, targets, and either nothing, an operator approval, a single-administrator exemption or a release-fixed approval | The coordinator, which takes source and requester from the authenticated principal and route, never from request content; stored by request digest between the two runs (section 6) |
| Verdicts | `ok` or `failed` per component | Each kind's validator |

The snapshot is scoped to the decision: it carries the records the stages read for this id, this version, this approval and these registrations, filtered by the coordinator under the fence. Permanent sets (tombstones, consumed approvals) are therefore looked up by key, never copied whole, and nothing in the design caps how many an installation accumulates. The one unscoped collection is the trust list. Trust import refuses a 1,025th entry, counting retired and revoked entries, so the list always fits the snapshot. The cap is not a lifetime limit: a protected trust change may purge a purgeable entry, which frees its slot. A purgeable entry is retired, not revoked, and named by no ownership record (as owner or prior owner) and no tombstone. The journal keeps a purged entry's fingerprint with its last generation as a floor, so a re-import continues the generation and an approval bound to the old entry stays stale. Junk imports therefore cost an operator a purge, not the installation's capacity; only entries that admitted packages reference stay, and admitting a package needs an approval or, on a single-administrator installation, that administrator's exemption.

A trust entry that a record names is never deleted. Removing a key sets `retired`; the entry stays on the list so ownership records and tombstones that name it keep resolving, and it authorizes no new admission until an operator re-imports it (which clears `retired` on the same entry, because the fingerprint identifies the raw key). Retirement is not revocation: installs the key signed keep their grants, bindings and targets until an operator uninstalls or revokes them. Every write to an entry (import, retirement, re-import, revocation, removal of a revocation) advances its `generation`, and every write to an install (install, upgrade, reinstall, grant update, enable, disable, the move to `recovery_pending`) advances the install's `generation`. Loading the compiled project-key default at start creates the entry only when neither an entry nor a journaled purge floor has that fingerprint, so a retired or purged project key comes back only through a protected re-import; loading never clears `retired` or `revoked`. The `project_publisher` flag is not stored: the coordinator derives it when it builds the snapshot, setting it exactly on the entry whose fingerprint is the running binary's compiled project key, so an operator import never sets it, and snapshot rule 11 checks it. When an installation moves between a development build and a tag build, the compiled key changes: the new key's entry is created at start (unless a purge floor holds its fingerprint), the old key's entry stays on the list as an ordinary entry without the flag, and nothing seals. The old key then fails `namespace.reserved` for every reserved id, including grant updates of its installs, and the first-party ids it owns admit the new key's packages only after a protected ownership transfer (`extensions.ownership.transfer`) to the new key; until then server-image proposals for those ids fail `ownership.owner`. Tag builds compile the production project extension publisher key. Master and pull-request builds compile a separate development project key, which signs only development-labelled first-party packages and which no tag build carries, so a development package never verifies as first-party on an installation running a tag build. Maintainers hold both private keys offline; CI holds neither, and a CI-held development key needs its own reviewed change under the conditions in [release builds section 8](release-builds.md#8-signing-and-installation-boundary). Every entry carries its raw 32-byte public key, and the function calls the shared [Ed25519 key admission](ed25519-key-admission.md) predicate on the verifying entry on every decision; a stored validation flag is never consulted. Fingerprints are `sha256:` plus lowercase SHA-256 of those 32 bytes, as the loader binds them. The DSSE `keyid` hint never enters the snapshot. A trust entry's display name carries no C0 or C1 control character and no DEL (U+0000 to U+001F, U+007F to U+009F).

Unsigned 64-bit values (`recovery_epoch`, generations) are decimal strings, as in the journal protocol. Identifiers (`requester`, approver, exemption principal, approval and device-group uids) are UUIDv7 under [core primitives](core-primitives.md). The fixed system principal `00000000-0000-7000-8000-000000000000` is the requester of every `server-image` request and of nothing else, and it never approves or holds an exemption.

## 3. Decision stages

Stages run in this order. A stage with at least one reason stops the decision and reports every reason found in that stage, sorted by code then subject, each `(code, subject)` once; later stages do not run. The outcomes `identical_retry`, `approval_required` and `admit` leave the stage sequence at the points named below. [The contracts](extension-admission-contracts.md#4-reason-codes) list every reason code and its subject.

| Stage | Checks | Reasons |
|---|---|---|
| `input` | Evidence is well formed (section 2 of the contracts); the snapshot and request rules below | `input.evidence`, `input.snapshot`, `input.request` |
| `key` | The publisher fingerprint names a trust entry; the entry's raw key passes key admission; the entry is not revoked, and it is not retired unless the request is a grant update. A grant update reloads bytes that were admitted earlier, so a key retired since then still serves it, and the `targets` and `grant` stages then let it only narrow | `key.unknown`, `key.invalid`, `key.revoked`, `key.retired` |
| `namespace` | `io.ricevanta` and its descendants require an entry flagged `project_publisher`; the id equals one of the entry's prefixes or lies under one at a label boundary (`io.ricevantaevil.rules` is not under `io.ricevanta`) | `namespace.reserved`, `namespace.prefix` |
| `revocation` | No id revocation; no version revocation for `(id, version)` | `revocation.id`, `revocation.version` |
| `tombstone` | If a tombstone exists for `(id, version)`, its publisher, manifest digest and package digest all equal the evidence. A grant update requires an `active` install of this version. Otherwise, if the id is installed at this version in state `active`: equal proposed grants and targets give `identical_retry`, and a difference is rejected and points the caller to a grant update | `tombstone.manifest`, `tombstone.package`, `tombstone.publisher`, `tombstone.grants`, `tombstone.targets`, `tombstone.not_installed` |
| `ownership` | With an ownership record: the verifying key is the owner, or a tombstone for `(id, version)` names the verifying key and that key is a recorded prior owner. Without a record: exactly one non-retired trust entry covers the id, counting revoked entries, and the intent creates ownership for it; two or more require a prior protected assignment | `ownership.owner`, `ownership.assignment_required` |
| `interface` | Every interface in `spec.requires` is served | `interface.unserved` |
| `component` | Every component has a verdict and it is `ok`. A browser adapter names a stored registration; each OS it declares exists in the registration; its policy names are a subset of the registration's names for that OS; `native_host` only where the registration has a native-host target; the registration is not bound to an `active` holder of another id (a binding this id holds never blocks, because the intent's binding set replaces the id's bindings, so a renamed adapter keeps its registration across an upgrade); no earlier adapter of the same package, in component-name order, names the same registration, whether or not that registration is stored, so a shared unknown registration gives the later adapter both `component.registration_duplicate` and `component.registration_unknown` | `component.verdict_missing`, `component.verdict_failed`, `component.registration_unknown`, `component.registration_os`, `component.registration_names`, `component.registration_native_host`, `component.registration_bound`, `component.registration_duplicate` |
| `targets` | For a package with a `content`, `browser-adapter` or `agent-module` component, exactly one of `device_groups` (nonempty) or `all_devices`; for a package without one, neither. `all_devices` only on a `server-image` request, or on a grant update whose active install already targets all devices, which keeps the target and never introduces it. Under a retired key, a grant update may not reach beyond the install's targets: an install that targets all devices may keep them or move to any existing device groups, and an install that targets device groups may keep or drop some of them. `console` is true exactly when a `console-module` exists; `jobs` exactly when a `service-connector` exists; every group uid exists | `targets.device_groups_required`, `targets.device_groups_forbidden`, `targets.all_devices`, `targets.console`, `targets.jobs`, `targets.unknown_group`, `targets.retired_key` |
| `grant` | Exactly one grant per component, none for an unknown component; kind and interface match the component; a browser-adapter grant names the component's registration; values stay within the request (section 4); a collector grant names a reviewed disclosure profile and at most `max_roots` roots. When those checks pass under a retired key, no component is widened against the current grant (the section 6 definition) | `grant.missing`, `grant.extra`, `grant.kind`, `grant.registration`, `grant.exceeds`, `grant.profile`, `grant.roots`, `grant.retired_key` |
| `approval` | No approval: `approval_required` with the frozen request digest. Release-fixed: the preconditions and the cases of section 6, else reject or `approval_required` with the reasons that name what needs an operator. Operator or single-administrator: approval epoch equals the snapshot epoch; its request digest equals the recomputed digest; the uid is not consumed; for operator the approver differs from the requester; for single-administrator the snapshot says approval policies are disabled and the principal is the requester. Then `admit` | `approval.release_fixed`, `approval.release_operation`, `approval.widened`, `approval.targets_changed`, `approval.epoch`, `approval.digest`, `approval.separation`, `approval.exempt_unavailable`, `approval.exempt_principal`, `approval.consumed` |

Snapshot rules (`input.snapshot`); one vector covers each part and trips that rule alone:

1. Fingerprints are unique.
2. Each fingerprint is the SHA-256 of its entry's raw key.
3. Every revocation names the id under decision, and a version revocation names the version under decision.
4. The ownership record names the id.
5. Every tombstone names the id, at most one per version.
6. The install names the id, and its version has a tombstone with the same package digest.
7. The install's grant records name distinct components, and each carries the install's id, version and package digest.
8. No grant record carries an epoch above the snapshot's, and every grant record of an `active` install carries the snapshot's epoch.
9. At most one registration record per registration id.
10. The owner, every prior owner and every tombstone publisher are entries on the list (active, revoked or retired).
11. An entry carries `project_publisher` exactly when its fingerprint is the snapshot's compiled project key.
12. An install or a tombstone exists only beside the id's ownership record, because the first admitted commit of an id writes both in one transaction; without the record a sole covering key would otherwise claim ownership of an id with history.

Request rules (`input.request`): each component is named at most once; the source is `server-image` exactly when the requester is the system principal; no approver or exemption principal is the system principal; a `server-image` request is never a grant update.

After the `component` stage the function fixes the operation, in this precedence: `grant_update` when the request is a grant update; otherwise, with no install, `reinstall` when a tombstone exists for the version and `install` when none does; with an install of this version (which is `recovery_pending`, because an `active` one left at the `tombstone` stage), `reinstall`; with an install of another version, `upgrade`. A rollback to an earlier accepted version is therefore an `upgrade` whose tombstone must match. Versions compare by exact string, never by SemVer precedence.

Verdict order does not affect results. Map iteration order does not affect results: reasons are sorted, components are processed by name, and digests use canonical encoding.

## 4. Grants and bounded values

The stored grant, never the request, reaches bundles, the bridge and `jobs` ([extension design section 2.3](../design/extensions.md#23-capabilities-and-grants)). The requester proposes the exact grant per component, bounded by the manifest request; the approver approves or rejects exactly that proposal. An approver who wants less asks for a new proposal, which is a new request from a requester with a new digest. The approver never edits values, so one digest covers what was proposed, what was approved and what commits, and the separation rule has one meaning.

| Kind | Grant values | Bound |
|---|---|---|
| `content` | None (an empty object) | The component itself is what the approver grants |
| `browser-adapter` | Registration id and, per OS, policy names and `native_host` | The component's registration; each OS present in the request; names a subset of the requested names, which the `component` stage already intersected with the registration; `native_host` only if requested |
| `agent-module` | `memory_pages`, `fuel_per_call`, `deadline_ms`; parser `mime_types`; collector limits plus `roots` and `disclosure_profile`; responder `actions` and plan limits | Each number at most the requested number; each set a subset of the requested set; roots count at most the granted `max_roots`; the profile id is on the snapshot's reviewed list |
| `console-module` | Operations per slot | Slots a subset of the declared slots; each slot's operations a subset of the requested operations |
| `service-connector` | Outbound destinations | A subset of the requested destinations |

Set-valued grant arrays (policy names per OS, MIME types, responder actions, collector roots, slot operations and outbound destinations) are sets: identical retry compares them as sets, both digests encode them in canonical order (strings bytewise, objects by their JCS bytes) and the coordinator stores that order. Device groups follow the same rule. No other grant array exists. A proposal may be narrower than the manifest request, including an empty operation list for a slot. A grant can never exceed the manifest request, and the manifest request can never exceed the schema ceilings, so the product ceilings in [the manifest contract](extension-manifest.md#5-components-and-requested-capabilities) bound every stored grant.

Collector roots are canonical absolute paths: a POSIX path for `macos` and `linux`, a drive-rooted backslash path for `windows`, segments never `.` or `..`, interior spaces allowed on every OS (macOS root-only inventory lives under paths such as `/Library/Application Support`), no leading or trailing space in a segment. A Windows segment also never ends in a period: Windows path normalization removes a trailing period from a segment and trailing periods and spaces from the last one, and Microsoft tells applications not to end a file or directory name with a space or a period ([File path formats on Windows systems](https://learn.microsoft.com/en-us/dotnet/standard/io/file-path-formats), Trim characters; [Naming Files, Paths, and Namespaces](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)). With that rule every accepted Windows root is its own normalized form, so the string the approver reads names the directory the broker opens. Comparisons are exact strings on every OS. Windows compares names case-insensitively (same Microsoft pages), so `C:\Data` and `C:\DATA` name one directory but compare as different roots: against a current grant a case change counts as widened, which errs toward asking. A reserved device name such as `CON` is a valid segment string; the broker opens only regular files, so such a root yields no rows. The agent applies the broker's containment, identity and privacy rules on every read ([agent runtime section 4](extension-agent-runtime.md#4-collector-filesystem-broker)). A disclosure profile id names a server-reviewed profile compiled into the binary; that catalogue is absent, so no collector grant can be admitted until it exists, and admission rejects an unknown profile rather than passing it through.

Generations: the function never allocates `grant_generation`. The coordinator assigns, in its commit transaction, the next unused generation per component within the current epoch, including for a grant whose values equal an earlier grant ([extension design section 2.3](../design/extensions.md#23-capabilities-and-grants)). Every grant write, including a reduction and a target-only grant update, is a new generation for every component the intent names; an upgrade writes a new generation for every component of the new version.

## 5. Identity, ownership, tombstones and bindings

One id namespace spans all publishers. Trust-list prefixes authorize publication under them; they do not partition the namespace. The first accepted install of an id creates its ownership record when exactly one non-retired trust entry covers the id. A revoked entry still counts: revocation is immediate and never held for approval, so counting it keeps an unprotected revocation from deciding who owns a new id. A retired entry does not count: retirement is a protected trust change, and after a key rotation the remaining key owns new ids under the shared prefix without a per-id assignment. When two or more entries cover an id, an operator must first make a protected assignment (`extensions.ownership.assign`), which the snapshot carries as an ownership record; admission never picks an owner from overlapping prefixes.

A publisher-key transfer (`extensions.ownership.transfer`) replaces the owner and adds the previous owner to `prior_owners`, a set of trust-list fingerprints that therefore holds at most 1,023 entries. After a transfer, only the new owner publishes new versions. The prior-owner exception covers every operation on a version whose tombstone names the verifying key: reinstall, a rollback `upgrade` over the new owner's version, and a grant update, each with an operator approval. It never covers a version without such a tombstone, so a prior owner can neither publish new versions nor change old bytes. Tombstones are never rewritten by a transfer.

A tombstone fixes `(id, version)` to one publisher fingerprint, one manifest digest and one package digest. It is created by the first admitted commit of the pair and is permanent: uninstall, revocation, transfer and epoch transition never remove it. Recompressing the same manifest produces a different package digest and is refused as different bytes; publishers release a new version instead. An identical retry of an active install with the same grants and targets returns that install without a new approval. A reinstall of an uninstalled pair needs identical bytes and a new approval.

Registration bindings: one browser registration is bound to at most one adapter component across the installation, and within one package at most one adapter names a given registration (`component.registration_duplicate`). The binding `(registration, id, component)` is written at install commit from the intent, so two installed adapters never contend at enable time; a grant update rewrites the same binding. The intent's `registration_bind` is the id's complete binding set after commit: the coordinator writes every binding it names and, in the same transaction, releases every binding the id holds that it does not name, so an upgrade that drops an adapter or moves it to another registration frees the old registration. It is cleared by uninstall and by revocation of the component, the version, the id or the publisher key, and it follows the install into `recovery_pending` at an epoch transition, where it no longer blocks and a new admitted install of the same or another id rebinds the registration.

Revocation of a publisher key, an id or a version is a separate authority write ([extension design section 2.5](../design/extensions.md#25-revocation)); admission only reads its result. Every id or version revocation write, and every removal, advances the id's `revocation_generation`. Removing a revocation is protected and makes later admission possible again; it never revives the install, grants, bindings, targets or approvals the revocation ended.

## 6. Approval binding

The function freezes the request into a canonical object and hashes it (JCS, RFC 8785, then SHA-256; exact fields in [the contracts](extension-admission-contracts.md#3-digests)). The frozen request includes the operation and the dependency-closure digest: the recovery epoch, the approval-policy setting and its generation, for a `server-image` request only the first-start state and the release version, the verifying trust entry with its generation, the covering entries, the id's revocations and revocation generation, ownership record and tombstone, the current install with its enabled state, install generation, targets and every grant record's epoch, generation and values, every referenced registration with its generation and binding, the required interfaces, the referenced disclosure profiles and the target groups. An approval binds the request digest and the recovery epoch.

The coordinator stores the request content (grant-update flag, grants, targets, source, requester) under the request digest when it creates the approval request, shows the approver exactly that content, and feeds the same content to the second run. The function recomputes the digest from what it is given, so stored content that was altered fails `approval.digest`. The coordinator refuses an approval past its expiry (the access policy's, 72 hours by default, [console design section 3.2](../design/console.md#32-approval-queue)) before it calls the function, which has no clock.

Consequences:

- The approver decides on exactly the bytes, grants, targets and operation that will commit; any change to the request produces a new digest and a new approval request.
- Any change to the closure after approval (a revocation, a transfer, a registration change, a new grant on the installed version, an enable or disable, an interface withdrawn, a trust-entry write, disabling or enabling approval policies) makes the approval stale (`approval.digest`). The approval-policy setting, trust entries, the id's revocations, the install, ownership and registrations carry generations, so reverting one of them does not restore the old closure: an approval never revives after a revocation is lifted, a key is unrevoked, the setting is toggled back or the install is disabled and enabled again. The covering entries enter the closure by fingerprint only: importing a covering entry and retiring it again restores the closure, which is harmless because the intermediate state only rejects (`ownership.assignment_required`) and the restored state yields the decision that was approved. A registration's binding carries no generation of its own; when another id takes the registration and releases it, the closure returns to the binding state the approver saw, and the `component` stage still enforces exclusivity, so the approval binds exactly what was approved.
- An approval from an earlier epoch never authorizes work in a later one (`approval.epoch`), and a consumed approval never authorizes a second commit (`approval.consumed`). Consumption is an irreversible journal effect.
- Operator approvals need a different principal (`approval.separation`), the BE-02 rule. API tokens can request but never approve (BE-09); that rule is the coordinator's, applied before an approval reaches the function.

Single-administrator exemptions carry BE-02's setting into the function without an approval decision by anyone. While the committed setting has configurable approval policies disabled, a protected action creates no approval request ([console design section 3.2](../design/console.md#32-approval-queue)). The coordinator then runs the function once without an approval, records an exemption for the requester bound to the returned request digest and epoch inside the same fenced guard, and runs the function again with it. The function accepts the exemption only while the snapshot's `approval_policy_disabled` is true and only when its principal is the requester. The exemption is journaled, consumed and audited like an approval, and the intent names it so the audit event states that the exemption was used. Enabling or disabling approval policies is a protected authority write that advances the setting's generation, and both are in the closure, so an exemption or approval bound under one setting is stale under any later one. The exemption never covers a `server-image` request, whose requester is the system principal, and never covers identity-authority actions, which are outside admission and keep their fixed two-account protocol.

Release-fixed approvals are how the server image installs and maintains the first-party components it ships ([extension design section 8.1](../design/extensions.md#81-channels)). Their authority is the running binary: the release manifest fixes each component's grant per release, the binary is signed under the project's release keys, and nothing restored from a database or backup can supply or alter a release-fixed approval, which is what BE-12 requires of an approval that bypasses stored authority. Preconditions, else `approval.release_fixed`: the project publisher key, a reserved id, source `server-image`, and a `release_version` equal to both the snapshot's running release and the package version (SH-04 gives first-party components the product version). The running release is a fact the server establishes at start: the deployment supplies the AG-07 release manifest beside the image, and the server verifies its signature under the release root or successor key compiled into its binary and requires it to list the SHA-256 of the running server executable for this target; the manifest's version is then the running release. The server applies AG-07's rotation rule with journaled state: once a successor-signed manifest verifies, the journal records the root as retired, and a root-signed manifest no longer establishes a release. Expiry is not checked: it bounds how long an update offer is acceptable, and says nothing about which bytes run. An air-gapped installation therefore keeps its release with the manifest delivered once beside the image, with no refresh. The AG-07 release spec must list each server executable's SHA-256 per target. The release payload schema is the blocking AG-07 release spec ([release builds section 8](release-builds.md#8-signing-and-installation-boundary)). A self-builder's binary compiles the self-builder's own release keys (AG-07) and reports the release its own manifest verifies. Every build without a verifying manifest, development, pull-request and unsigned tagged pre-release alike ([release builds section 2](release-builds.md#2-one-product-version)), has none, so no release-fixed approval is accepted there. On such a build, setup closes the first-start marker without first-party installs, and the server image proposes its first-party components afterwards without a release-fixed approval; each waits for an operator like the other `approval_required` cases below. Extension versions exclude build metadata, so a development build labels its first-party packages `<core>-dev.0.g<FULL_SHA>` (release builds section 2) and two development builds never claim one `(id, version)`. When they hold, release-fixed admits without an operator in exactly three cases:

| Operation | Admitted without an operator when | Otherwise `approval_required` with |
|---|---|---|
| `install` | First-start setup is open (`first_start`): a journaled one-use marker that setup creates with the journal and closes as its last authority write before normal APIs open: on a build with a running release once every first-party install has been decided, admitted and committed or rejected, and at once on a build without one. A rejected first-start install raises a critical audit event naming its reasons and does not block setup; after setup the server image proposes it again, which after first start needs an operator approval, and an operator-rejected proposal is not proposed again for the same digest ([backend design section 6.1](../design/backend.md#61-external-authority-journal-and-restore-fence)); a setup that stops earlier resumes at the next start with the marker open, and installs already committed return `identical_retry` | `approval.release_operation` |
| `upgrade` | No component is widened and the targets equal the current install's, whether that install is `active` or `recovery_pending` (a recovery that meets a new release) | `approval.widened` per widened component, `approval.targets_changed` |
| `reinstall` of a `recovery_pending` install of the same version | No component is widened against that install's pre-transition grants and the targets equal its targets | the same two reasons |

Every other release-fixed case returns `approval_required`: a `reinstall` of a pair the operator uninstalled, an `install` of an id the operator uninstalled at a new version, and the first install of a first-party id that ships in a later release all carry `approval.release_operation`. Widened means: a component that the current install does not have, a kind or interface that changed, or values not bounded by the current grant under the section 4 rules, where a changed `disclosure_profile`, a root outside the current roots or any other value that is neither equal nor narrower counts as widened. Comparing against the stored grant and targets is what preserves operator choices: a grant the operator narrowed through a grant update, which keeps all devices on a fleet-wide install, makes the release grant widened, and targets the operator narrowed to device groups differ from `all_devices`. The coordinator builds a release request from the current install's targets, so an equal-grant release keeps an operator's narrowing without asking. An upgrade or reinstall never changes the enabled state: the intent carries the install's current `enabled`, so a component the operator disabled stays disabled. The first-start install is the one admission outcome that turns a component on; every other enable is the separate protected action. The release-fixed precondition is checked first; only when it holds is the operation case evaluated, so a decision never carries `approval.release_fixed` with another approval reason.

An `approval_required` server-image request goes to the approval queue like any other, with the system principal as requester. An operator approves or rejects exactly that proposal; the approver always differs from the requester, also on a single-administrator installation, where the one administrator approves it as an operator. Because the request's source is `server-image`, an approved request keeps `all_devices`; that target is valid on no other source, so an upload, API, GitOps or index request that names it is rejected at `targets` rather than queued for an approval nothing could satisfy. An operator-approved `install` commits disabled, like any operator install; enabling is the separate protected action.

## 7. Recovery fence

The coordinator follows the BE-12 publication barrier ([backend design section 6.1](../design/backend.md#61-external-authority-journal-and-restore-fence)); the journal protocol is a research candidate whose cross-store gate is unproved, so this section states obligations, not an implementation.

| Admission fact | Journal role | Why |
|---|---|---|
| Tombstone creation, approval or exemption consumption | Irreversible effect in the prepare record | A rollback or abort must never free the pair for other bytes or let the approval authorize again |
| Install record with its targets and enabled state, ownership creation, grant records with their generations, registration bindings | After-images named by the intent, pending until commit, exposed only after publication | A pending grant, target or binding must not reach a bundle, a bridge binding or `jobs`, and must not block another admission |
| Revocations, transfers, assignments, registration writes, trust import, retirement and re-import, approval-policy changes, closing the first-start marker | Separate authority operations with their own prepare and commit, each advancing its generation; admission reads their committed projection | Admission never writes trust or policy, and a reverted fact never restores an old closure |
| Snapshot | Built from the authenticated projection at the current head, under the writer fence, inside the same guard that commits | A database row cannot promote a grant, delete a tombstone or reopen first start |

The coordinator runs `Decide` twice for an operator-approved request: once to create the approval request (outcome `approval_required`; the request row stores the digest and the request content) and once at commit with the approval (outcome `admit`). For a single-administrator exemption both runs happen inside one guard. Every run reads a fresh snapshot under the fence, so a state change between them fails the second run instead of committing against stale facts. The commit transaction compares the function's `Intent` with the prepare record field by field, including targets, enabled state and registration bindings; a mismatch seals the operation for resolution.

Epoch transition: every grant record carries `recovery_epoch`. After a transition the coordinator marks installs whose grants belong to an earlier epoch `recovery_pending`, together with their registration bindings; such an install does not satisfy `identical_retry`, and the same bytes return `approval_required` with operation `reinstall` (or admit under a fresh release-fixed approval for first-party components, bounded by the pre-transition grants and targets). Nothing is relabelled to the new epoch: a new request, a new approval and new generations are the only way back to `active`. Tombstones, revocations, consumed approvals and the closed first-start marker persist across the transition.

Restore: a restored PostgreSQL that lacks tombstones, ownership records, bindings or revocations present in the live journal is a projection mismatch, and serving stays sealed until replay rebuilds the rows. A restored server never admits against its restored rows. If the live journal is lost, admission has no snapshot and stays sealed; there is no bypass.

Agents are unaffected by any of this except through the signed bundle: they receive components with `(recovery_epoch, grant_generation)` and never see trust-list, ownership or tombstone state (EXT-02).

## 8. Attacker paths

The protocol end to end: upload or fetch, `loader.Load` under one caller-selected current key, `FromPackage`, snapshot from the fenced projection, `Decide`, approval request with stored content (or an exemption in the same guard), second `Decide` with the approval, prepare with irreversible effects, database apply, commit, publication, blob verification by `policy` and `api` against the install record, bundle compilation. A grant update follows the same path from the stored package.

| Attacker | What they get | Boundary |
|---|---|---|
| Stolen enrollment token | Nothing here. Enrollment never reaches admission; an enrolled device receives bundles compiled from committed installs | PKI-02 token rules; agents never install packages |
| Compromised agent host | Can falsify local execution and read its own bundle. Cannot submit a package, mint a grant or learn trust state | Admission runs only on the server from console, API, GitOps or index input; bundles are organization-signed |
| Compromised console session | Can upload packages, submit install, upgrade and grant-update requests within the session's permissions, and add a publisher-key revocation at once. Cannot approve its own request. With `authz.approvals.approve` and fresh authentication it can approve requests from other principals, server-image proposals included, as any eligible approver can. On an installation whose committed setting disables approval policies, its own requests proceed under a recorded exemption, as every protected action there does, and the audit event names the exemption. Cannot claim the server-image source or the system principal, give an imported key the project-publisher flag, target all devices, forge an approval digest, revive a stale approval by reverting a change, bypass tombstones or ownership, retire or re-import a key or remove a revocation without approval | `approval.separation`, `input.request`, snapshot rule 11, `targets.all_devices`, closure generations, fresh-authentication rules of BE-09, protected actions of BE-02; immediate revocation is an accepted denial-of-service surface that an audit event records |
| Rogue extension publisher | Can sign well-formed malicious packages under its prefixes and request any capability the schema allows. Cannot publish under `io.ricevanta` or another publisher's id, replace the bytes of an accepted pair, select a key through a hint or fingerprint, exceed a registration, bind a registration another active adapter holds, or obtain a grant without an operator's approval of the exact values (or, under the single-administrator setting, the administrator's own exempted request) | `namespace`, `ownership`, `tombstone`, `component` and `grant` stages; component validators; runtime isolation (EXT-03, EXT-04, EXT-05) |
| Network position between agent and server | Can replay or drop a signed package reaching the server. Replay of an admitted pair is an identical retry; replay of a changed archive fails the loader or the tombstone | TLS plus loader digests; agents verify bundles, not publishers |
| Database writer without signing keys | Can edit rows: delete a tombstone, flip an install to active or enabled, purge a trust entry, insert a grant with a higher generation, add a trust entry, flip the approval-policy flag or the first-start marker, lower a generation. None of it enters a decision: the snapshot comes from the journal projection and raw keys are revalidated; a row that disagrees with the projection seals serving. Can insert a device-group row, which admission reads through the `devices` interface rather than the journal: a target then names a group the writer created, and which devices it reaches is the `devices` module's membership, which the compiler reads for every group-targeted resource ([policy design section 3.1](../design/policy.md#31-scope-resolution)), not an admission fact. Section 10 keeps journaling group existence open | BE-12 projection comparison; `key.invalid`; publication only after commit |
| Server restored from backup | Gets rows as they were. Tombstones, ownership, bindings, revocations and the closed first-start marker missing from the rows but present in the journal keep serving sealed; grants from the old epoch become `recovery_pending`; an old approval fails `approval.epoch` | Sealed restore, epoch transition, no relabelling |

What no stage prevents: a trusted publisher whose private key is stolen can publish under its own prefixes until the operator revokes the key, which is why key revocation is never held for approval. A compromised coordinator process holding the journal signer is outside this boundary ([authority journal protocol section 1](authority-journal-protocol.md#1-target-guarantee-and-boundary)).

## 9. Benefits, trade-offs, dependencies, limits, alternatives

Benefits: every admission decision is a fixture; the same vectors drive the Go tests and any later reimplementation. Authority facts enter through one typed snapshot, so review can see exactly which facts a decision depends on. Approvals bind exact bytes, grants, targets, the operation and the dependency closure with its generations, so an approver never approves a moving target and no approval revives. Grant updates pass the same stages as installs, so the all-devices and widening rules have no side door. Release automation keeps first-party coverage current without overriding an operator's uninstall, narrowing or disable. Irreversible effects are named, which gives the journal reducers their first concrete domain.

Trade-offs: a closure-bound approval goes stale on unrelated changes to the same id (for example a revocation of another version), which costs the approver a second look. Narrowing a grant is a second request rather than an approver edit. Reinstalling the same bytes after uninstall needs a new approval. Recompression is a new version. A widened first-party release, a release after an operator narrowing that the release cannot keep, and every first-party id new in a later release wait for an operator. A grant update writes a new generation for every component, which invalidates console bindings even for a target-only change. The trust list holds at most 1,024 entries at a time; entries that packages reference are never purged. Every server-image proposal pending at a release goes stale with it, because its closure binds the release; operator requests do not, because their closure omits release and first-start state. Unsigned builds install first-party components only through an operator. On a single-administrator installation with approval policies disabled, a request from an API token or GitOps proceeds under the exemption without a second step, as every protected action there does. The coordinator filters the snapshot per decision under a lock.

Dependencies: `loader`, `manifest`, `ed25519key` and the Go standard library. No new module and no new licensing row. The coordinator depends on BE-12.

Limits: `Decide` does not check permissions, authenticate principals, verify fresh authentication, check approval expiry, allocate generations, write anything or compile bundles. It cannot validate component content; it consumes verdicts. Device-group existence is a `devices` module fact, not journaled authority. The disclosure-profile catalogue, browser-registration schema, console bridge catalogue and connector contracts are absent, so collector, console-module and connector components can be admitted by the function but their consumers remain blocked, and the first-party browser adapters cannot be enabled until the registration slice ships.

Alternatives considered:

- Admission inside the loader or an HTTP handler reading PostgreSQL: rejected; it couples authority to replaceable rows and cannot be fixture-tested.
- Selecting the verifying key from the DSSE hint or the manifest fingerprint, then checking trust: rejected by the loader and DSSE contracts; the caller selects a current key and the fingerprint is a binding check.
- Per-publisher id namespaces: rejected by EXT-02; two packages with one id would reach agents under one identity.
- SemVer precedence for identity or "latest" resolution: rejected by the manifest contract; identity is the exact string.
- Approval bound to id and version only: rejected; it would let grants, targets or trust change between request and commit.
- A closure of plain values without generations: rejected; reverting a revocation or the approval-policy setting would revive an old approval.
- An approver who edits granted values, hashed into the approval: rejected; it makes the approver a second author of the request and needs a second separation rule, while a resubmitted proposal costs one round trip.
- A single-administrator approval recorded by the requesting account: rejected; it is an approval by the requester, which the console refuses in every case and the approval permission excludes. The exemption is a coordinator record of the committed setting instead.
- Extension admission declared non-exemptible from BE-02's single-administrator setting: rejected; it would leave a declared single-administrator installation unable to install any package, contradicting BE-02 without a security gain over a journaled, audited exemption.
- Release-fixed authority for every server-image request: rejected; the next start or release would undo an operator's uninstall, narrowing or disable.
- Release-fixed installs of first-party ids that first ship in a later release: rejected; a server upgrade would silently add fleet-wide components that no operator saw.
- Grant and target writes outside the function: rejected; they would bypass the manifest bound, the all-devices rule and the closure-bound approval.
- Deleting a referenced trust entry on removal: rejected; ownership records and tombstones that name the key would stop resolving and every later decision would fail.
- Retired entries counting as covering: rejected; every new id under a rotated prefix would need a protected assignment forever.
- A lifetime cap on trust imports without a purge: rejected; repeated imports without a second person would exhaust it permanently.
- Release-fixed authority for unsigned development builds: rejected; the authority rests on the release signature those builds lack.
- Development first-party packages signed with the production project key: rejected; every tag build trusts that key for `io.ricevanta`, so a development package would become installable in production, and the key would vouch for arbitrary commits instead of releases.
- A `project_publisher` flag set by an operator import: rejected; it would let a protected trust change mint a key for the reserved namespace and for release-fixed approvals.
- A per-decision copy of all tombstones and consumed approvals: rejected; the sets grow forever and the stages read only the id's records.
- Admission that picks an owner among overlapping prefixes by first install: rejected; a race between publishers would decide ownership.
- A single `install` permission for every operation: rejected; BE-02 and the catalogue separate install, upgrade, enable and grant.

## 10. Review focus and unresolved questions

Review focus:

- Can any stage be skipped by input shape, map order or a verdict list order? Can two reasons for one defect appear, or one defect hide behind another within a stage?
- Does the closure include every fact the decision read, with a generation for every fact that can be reverted? A fact read but not in the closure lets an approval survive a change to it.
- Can a prior owner publish a new version or change bytes after a transfer? Can a transfer, retirement or revocation drop a tombstone or a binding?
- Is the release-fixed path reachable from any source other than the server image, for any non-reserved id, at another release, or in a way that undoes an operator's uninstall, narrowing or disable? Is `all_devices` reachable from any other source?
- Is the single-administrator exemption reachable while approval policies are enabled, for a principal other than the requester, or for a server-image request?
- Does the identical-retry outcome require an `active` install with equal grants and targets, and does every grant or target write pass through the function? Can a grant update under a retired key widen anything, or any grant update introduce all devices?

Unresolved questions, each with the default this specification selects until independent review changes it:

- Should an approval survive closure changes that cannot weaken the decision, such as a revocation of an unrelated version? Default: no; any closure change is stale.
- Should recompression of an accepted manifest be accepted as the same pair when the manifest digest and files match? Default: no; the package digest is part of the pair identity.
- Should per-device-group exclusivity replace installation-wide exclusivity of one adapter per browser registration? Default: installation-wide, because device-group overlap needs membership closure the function does not have.
- Which executable journal gate will the coordinator use, and does its prepare record carry the `Intent` fields verbatim? Default: the coordinator waits for BE-12; no interim database-only coordinator.
- Who reviews and publishes disclosure profiles, and in which schema? Default: collector grants stay unadmittable until that catalogue exists.
- Should device-group existence become journaled authority so that a database writer cannot shape targets? Default: it stays a `devices` module fact, read through that module's interface as every group-targeted resource reads it.
- Should a protected action under the single-administrator exemption require the requester's recent interactive authentication, which would exclude API tokens and GitOps polling? Default: no; the operation's own permission and session rules apply, as for every exempted protected action.
