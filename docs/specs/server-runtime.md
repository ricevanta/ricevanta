# Server runtime entry point

`ricevanta-server` becomes a real executable: one binary that runs the roles it is told to run, reports health and readiness, serves the embedded console with the production headers, logs in one format and stops within a bound. This specification fixes that contract. Database access, identity, the administration API, enrollment, the native device protocols, RADIUS and jobs arrive with their own reviewed slices and refuse to start until then (section 8).

Authorities: BE-03, BE-04, BE-08, BE-13 and BE-15 in [decisions](../decisions.md), [architecture](../architecture.md) sections 3 and 5, [backend design](../design/backend.md) section 1, [console design](../design/console.md) sections 6.1 and 10, [console foundation](console-foundation.md) sections 3 and 4, [release builds](release-builds.md) section 2 and [the implementation plan](../plans/server-runtime.md).

## 2. Build identity and the version command

The package `server/internal/buildinfo` selects its identity with the build tag `ricevanta_release`, so it consumes the constants-only file that `scripts/release/version.py` writes, unchanged:

| File | Tracked | Build constraint | Content |
|---|---|---|---|
| `buildinfo.go` | Yes | None | `type Identity struct { Version, Commit, Channel string; SourceEpoch int64 }` and `func Current() Identity`, which returns `Identity{Version, Commit, Channel, SourceEpoch}` built from the package constants |
| `development.go` | Yes | `//go:build !ricevanta_release` | `const Version = "0.0.0-local"`, `const Commit = "unknown"`, `const Channel = "local"`, `const SourceEpoch int64 = 0` |
| `generated.go` | No, gitignored | None | Exactly the text of [release builds section 2](release-builds.md#2-one-product-version), which the release recipe copies in |

A release build passes `-tags ricevanta_release` together with any other tag, for example `-tags ricevanta_console,ricevanta_release` ([build constraints](https://pkg.go.dev/cmd/go#hdr-Build_constraints)); `development.go` then drops out and `generated.go` supplies the four constants. Every wrong combination fails to compile instead of reporting a wrong identity: the tag without `generated.go` leaves `Version` undefined, and `generated.go` without the tag declares each constant twice. A tracked file therefore never changes during a release build, a development build is unmistakably non-release, and the release tooling checks that the generated file's constants and the `--version` output agree with `identity.json`.

```
ricevanta-server --version            ricevanta-server <version> (commit <commit>, channel <channel>)
ricevanta-server version --json       {"channel":...,"commit":...,"sourceEpoch":...,"version":...}
ricevanta-server serve --config PATH
ricevanta-server check-config --config PATH
ricevanta-server console-manifest     the embedded console manifest (section 6) as JSON on stdout
```

Exit codes: `0` success, including a completed stop before readiness; `1` failure after readiness or a stop timeout at any startup or serving stage; `2` command line or configuration error, including a role this build does not admit (`role_blocked`, section 8), which `check-config` reports the same way; `3` startup failure (console verification, TLS material, listener bind). Section 4 defines stop/error precedence. `migrate` and every role beyond `api` are not subcommands or values yet; naming them exits 2 with the gate from section 8.

## 3. Configuration

One YAML file, default `/etc/ricevanta/server.yaml`, selected by `--config` or, when the flag is absent, by `RICEVANTA_SERVER_CONFIG`, plus a closed list of environment overrides. Precedence, highest first: environment variables, the file, built-in defaults; for the file path alone the flag wins over the variable, because the flag is the operator's explicit action on this invocation. The file is at most 65,536 bytes, UTF-8, and exactly one YAML document whose root is a mapping. It is decoded with `yaml.v3` `Decoder.KnownFields(true)` into closed structs, so an unknown key is an error ([yaml.v3](https://pkg.go.dev/go.yaml.in/yaml/v3)); duplicate mapping keys are errors on their own, because v3.0.4 constructs its decoder with `uniqueKeys: true` and reports `mapping key %#v already defined at line %d` and, for structs, `field %s already set in type %s` ([decode.go](https://github.com/yaml/go-yaml/blob/v3.0.4/decode.go)). A `yaml.Node` pre-pass rejects every node with `Kind == AliasNode`, a nonempty `Anchor`, or `Style & TaggedStyle != 0` (an explicit tag), so no alias expansion or type coercion through tags reaches the struct. The JSON projection of the effective configuration, after environment overrides, validates against [`schemas/server/config/v1/config.schema.json`](../../schemas/server/config/v1/config.schema.json), whose [example](../../schemas/server/config/v1/example.json) is a complete minimal configuration; the Go validator repeats the same bounds with the standard library so design CI and the binary agree on the same fixtures.

| Key | Default | Rule |
|---|---|---|
| `schema` | required | `ricevanta-server-config-v1` |
| `roles` | required | Non-empty list from `api`, `agent`, `device`, `radius`, `jobs`, no duplicates; only `api` is admissible in this build, see section 8 |
| `listen.api.address` | required when `api` is listed | `host:port`; host is an IPv4 or bracketed IPv6 literal or empty for all interfaces; port 1 to 65535 |
| `listen.api.tls.mode` | required whenever `listen.api` is present, from the file or `RICEVANTA_SERVER_LISTEN_API_TLS_MODE` | `file` or `none`; `none` only when the host is a loopback address, else exit 2 `plaintext_requires_loopback` |
| `listen.api.tls.certificate_file`, `listen.api.tls.key_file` | required for `file` | Absolute paths to PEM files; the key file is opened once, following symbolic links, and the checks apply to `fstat` of the opened file, which must be a regular file owned by root or the effective user, with no permission bits for others and write permission at most for the owner, and readable by group only when the file's group is the effective group or a supplementary group of the process (`0400`, `0600`, `0440` or `0640`) |
| `console.enabled` | `true` | Serve the embedded console on the `api` listener |
| `log.level` | `info` | `error`, `warn`, `info`, `debug` |
| `http.read_header_timeout_ms` | 10000 | 1000 to 60000 |
| `http.idle_timeout_ms` | 60000 | 1000 to 600000 |
| `http.max_header_bytes` | 65536 | 4096 to 1048576 |
| `shutdown.timeout_ms` | 20000 | 1000 to 120000 |

The key-file rule fits the deployment shapes. The kubelet keeps Secret data in a `tmpfs` ([Kubernetes Secrets](https://kubernetes.io/docs/concepts/configuration/secret/)) and projects each key as a symbolic link into a hidden timestamped directory that it swaps atomically ([atomic_writer.go](https://github.com/kubernetes/kubernetes/blob/master/pkg/volume/util/atomic_writer.go)), which is why the open follows links and the checks judge the opened file. A Secret volume's `defaultMode` "Defaults to 0644" and "might be in conflict with other options that affect the file mode, like fsGroup" ([core/v1 types.go](https://github.com/kubernetes/api/blob/master/core/v1/types.go), `SecretVolumeSource`), and `fsGroup` makes the volume's files group-owned by that ID and adds it to the container processes' supplementary groups ([pod security context](https://kubernetes.io/docs/tasks/configure-pod-container/security-context/)). The deployment slice therefore mounts the key with `defaultMode: 0440` and the server's `fsGroup`, which this rule accepts, records the mode that results on its qualified cluster, and never relaxes the rule: a world-readable `0644` key is refused. Compose cannot set those modes for a file secret: "support for `uid`, `gid`, and `mode` attributes are only implemented in Docker Compose when the source of the secret is `environment`", and for a `file` source "Compose uses a bind-mount" and "these attributes are silently ignored" ([Compose services reference](https://docs.docker.com/reference/compose-file/services/#secrets)), while an environment secret defaults to the world-readable mode `0444` that this rule refuses. Under Compose the host file's own owner and mode therefore reach the container, and the deployment slice prepares the host key owned by the container user with mode `0400`, or owned by root with the container's group and mode `0440`. Environment overrides are exactly `RICEVANTA_SERVER_CONFIG`, `RICEVANTA_SERVER_ROLES` (comma separated), `RICEVANTA_SERVER_LISTEN_API_ADDRESS`, `RICEVANTA_SERVER_LISTEN_API_TLS_MODE`, `RICEVANTA_SERVER_LISTEN_API_TLS_CERTIFICATE_FILE`, `RICEVANTA_SERVER_LISTEN_API_TLS_KEY_FILE`, `RICEVANTA_SERVER_CONSOLE_ENABLED` and `RICEVANTA_SERVER_LOG_LEVEL`. Any other variable with the prefix `RICEVANTA_SERVER_` is an error naming it, so a misspelled override cannot silently fall back. Values pass the same validation as file values. No secret exists in this slice; the later secrets slice adds `_FILE` references and never inline values (`design/backend.md` section 6). `check-config` prints the effective configuration as sorted-key JSON with key-file paths but no file contents.

## 4. Lifecycle

```
starting ──> ready ──> stopping ──> stopped
   ├─────────────────────> stopping
   └── failed (exit 2 or 3)
stopping ──> timeout (exit 1)
```

Startup, in order: parse the command line; create the `slog` JSON logger on standard error at level `info`; register the stop sources and independent stop controller below before any log write or startup I/O; load and validate configuration; publish the validated stop budget; set the logger to the configured level through its `slog.LevelVar`; resolve the role table and refuse blocked roles; verify the embedded console (section 6.1) when enabled; load TLS material; bind the `api` listener; start serving; mark `api` ready; log `ready`. Readiness is per role and the process is ready when every configured role is ready. A failure committed before a stop logs `startup_failed` with the step and exits 2 or 3. Once stop is latched, cancellation errors and late startup results follow the stop outcome instead, and readiness can never become `ready`.

Stop sources: `SIGTERM` or `SIGINT` through `signal.NotifyContext` on Unix, and `os.Interrupt` plus the `syscall.SIGTERM` that Go delivers for console close, logoff and shutdown events on Windows ([os/signal](https://pkg.go.dev/os/signal)); cancellation of the runtime's parent context is also a stop. The first stop request latches monotonic time `t0` and a single process deadline `D = t0 + B`, independently of startup work and logging. `B` is 20,000 ms until the complete configuration has validated and its timeout has been published to the controller; thereafter it is `shutdown.timeout_ms`. Budget publication and stop latching are serialized without I/O under their lock. A stop that wins this race freezes the default even if configuration finishes later. Repeated requests are counted but never reset or shorten `D`. A listener failure after readiness initiates the same bounded cleanup with exit 1.

Reserve the final 100 ms of `B` for terminal logging and forced cleanup: the graceful cutoff is `C = D - 100 ms`. On stop, the controller cancels startup, flips existing readiness to `stopping`, and requests `stop_requested` logging without waiting for the log sink. The startup worker checks cancellation before each operation and before handing off any result. Configuration reads, embedded verification, TLS reads and binding run in one serial worker, separate from the controller; use context-aware operations where available, but do not claim cancellation interrupts ordinary file I/O. Go documents that ordinary files generally do not support deadlines ([os.File.SetDeadline](https://pkg.go.dev/os#File.SetDeadline); local source evidence below). A blocked operation may therefore remain running until process exit. Start no replacement worker. Never hold the controller lock across an operation, close, join or log write.

Resource handoff and readiness publication share the stop fence. Results arriving after stop cannot start serving or publish readiness; their worker closes newly acquired resources instead. The controller schedules one cleanup worker to close startup resources already handed off and, when a server exists, call `http.Server.Shutdown` with the absolute deadline `C`. The controller observes worker and serving completion only until `C`; it never performs blocking cleanup itself. `Shutdown` closes idle connections and waits for active ones ([net/http Server.Shutdown](https://pkg.go.dev/net/http#Server.Shutdown)). If all work and cleanup finish before `C`, emit `shutdown_complete` and exit before `D` with 0 for a requested stop, or the earlier committed failure code when cleanup follows a failure. Otherwise, commit exit 1 at `C`, emit `shutdown_timeout`, and attempt `Close` on remaining connections without extending `D`; a late completion cannot change that result. A stop during a blocked startup operation is thus exit 1, not a successful stop at an unreachable step boundary.

An independent watchdog owned by the executable calls `os.Exit(1)` at `D` if the process has not exited. It does not wait for the worker, cleanup, log writes, deferred functions or a runtime result. The library exposes a testable controller; only the executable installs the process-exit callback. Go specifies immediate termination without deferred functions ([os.Exit](https://pkg.go.dev/os#Exit); local source evidence below). The 100 ms reserve permits terminal JSON records on a responsive stderr; a blocked sink can lose those records, but cannot delay exit. Keep a bounded terminal-record slot and one terminal writer, not a new writer per repeated stop. If completion logging itself blocks past `D`, the watchdog exits 1. Tests must prove actual subprocess exit as well as the library's outcome. The default budget fits the deployment's 30 s termination grace; deployment settings must exceed any configured `B`. A panic in a handler is recovered by `net/http` per connection; a panic outside a handler exits 1, with logging subject to the same bound once stop is latched.

The HTTP server sets `ReadHeaderTimeout`, `IdleTimeout` and `MaxHeaderBytes` from configuration and `DisableGeneralOptionsHandler`, so an `OPTIONS *` request reaches the handler instead of Go's built-in `200` without the header set. It leaves the server-wide `ReadTimeout` and `WriteTimeout` at zero, because later roles hold requests open for long polls and the change stream; every handler family bounds its own reads and writes through `http.ResponseController` instead ([net/http Server](https://pkg.go.dev/net/http#Server), [ResponseController](https://pkg.go.dev/net/http#ResponseController)). `ReadHeaderTimeout` also bounds the TLS handshake, for which `net/http` uses the smallest positive value of `ReadHeaderTimeout`, `ReadTimeout` and `WriteTimeout` ([server.go](https://github.com/golang/go/blob/go1.27.1/src/net/http/server.go), `tlsHandshakeTimeout`).

The console and health handlers accept no request content. A request that declares any, by a nonzero `Content-Length` or a chunked body that Go reports as length -1, is answered `413` with a problem body and `Connection: close` before its method or path is examined, and the handler never reads the content. Before writing that response the handler calls `http.NewResponseController(w).SetReadDeadline(time.Now())`. The header alone is not enough: it makes Go skip the discard in `WriteHeader`, but `finishRequest` still closes the request body "regardless of w.closeAfterReply", and that close reads up to 256 KiB plus one byte of a declared or chunked body under no deadline while `ReadTimeout` is zero ([server.go](https://github.com/golang/go/blob/go1.27.1/src/net/http/server.go), `finishRequest`; [transfer.go](https://github.com/golang/go/blob/go1.27.1/src/net/http/transfer.go), `body.Close`). With the deadline already passed, that read fails at once and Go marks the body closed early. On HTTP/1.1 Go then closes the connection after its 500 ms `rstAvoidanceDelay`, so a client that declares content and trickles it holds the connection for about half a second and delays `Shutdown` by no more. On HTTP/2 the same header makes Go send `GOAWAY`, a stream whose content was not read is reset when the handler returns, and the connection closes `goAwayTimeout`, 1 s, after its last open stream completes ([internal/http2/server.go](https://github.com/golang/go/blob/go1.27.1/src/net/http/internal/http2/server.go)).

Writes are bounded by progress: before its first write the handler sets a write deadline 10 s ahead and moves it 10 s ahead each time another 16 KiB has been written, so a client that stops reading loses its connection within 10 s instead of holding it until the shutdown deadline; the final flush after the handler returns still runs under the last deadline, and `net/http` clears the deadline before it reads the next request on the connection (server.go, after `finishRequest`). On HTTP/2 the same 10 s bound is also set as `http.Server.HTTP2 = &http.HTTP2Config{WriteByteTimeout: 10 s}`, the timeout "after which a connection will be closed if no data can be written to it", extended "whenever any bytes are written" ([net/http HTTP2Config](https://pkg.go.dev/net/http#HTTP2Config)). A stream's write deadline alone is not enough there: all streams share one frame writer, so when a client stops reading, the deadline only queues a stream reset behind the blocked writer, and `Shutdown` would wait until its own deadline; the connection-level timeout closes the connection instead.

`WriteByteTimeout` bounds gaps in successful server writes, not total response duration. Reading a few bytes periodically does not necessarily free enough socket capacity for the server writer to make progress. A client that drains enough to sustain that progress can still keep the HTTP/2 writer occupied and delay a queued stream reset until shutdown forces `Close`, producing `shutdown_timeout` and exit 1 under the stop budget above. The [repository test comment](../../server/cmd/ricevanta-server/serve_test.go) records approximately 10.4-second closure for 4, 64 and 256 KiB bursts every five seconds on Linux loopback, while 1 MiB bursts reached the shutdown deadline; the test uses 2 MiB for margin. These are observations from one Linux configuration, not portable thresholds. The first-party writer loop extends its deadline after successful partial writes ([internal/http2/http2.go](https://github.com/golang/go/blob/go1.27.2/src/net/http/internal/http2/http2.go), `writeWithByteTimeout`; local source evidence below). HTTP/2 is negotiated on TLS listeners by Go's default; plaintext listeners speak HTTP/1.1.

## 5. Health and readiness

| Path | Method | Response |
|---|---|---|
| `/healthz` | GET, HEAD | `200` with body `{"status":"ok"}` while the process is serving; it is liveness, not readiness |
| `/readyz` | GET, HEAD | `200` with `{"status":"ready","roles":{"api":"ready"}}` when every configured role is ready; `503` with `status` `starting` or `stopping` and the per-role states otherwise |

Both carry `Content-Type: application/json`, `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`, and never a version, hostname, build identity, address or configuration value; [`schemas/server/health/v1/readiness.schema.json`](../../schemas/server/health/v1/readiness.schema.json) validates the bodies. Other methods receive `405` with `Allow: GET, HEAD`. The endpoints live on the `api` listener so the container probe and the load balancer reach them without a second port; what they disclose is bounded to the states above, which is why they are safe on a public listener. `/metrics` answers `404` until the Prometheus client slice adds it with its own exposure rules.

## 6. Console serving

The `transport/console` package embeds the console build with `//go:embed all:dist` and `manifest.json` under a build constraint `ricevanta_console`; without the tag the package embeds nothing, `console.enabled: true` fails startup with `console_missing`, and tests use a fixture tree. Go embeds a directory recursively and excludes dot and underscore names unless `all:` is used ([embed](https://pkg.go.dev/embed)); `all:` is required because Vite writes `.vite/manifest.json`. The release recipe (release plan Task 4) copies the console job's tree to `server/internal/transport/console/dist/` and its `manifest.json` beside it, and builds with `-tags ricevanta_console,ricevanta_release`; both paths are gitignored. `manifest.json` follows [`schemas/server/console-manifest/v1/manifest.schema.json`](../../schemas/server/console-manifest/v1/manifest.schema.json): an object with `schema` `ricevanta-console-manifest-v1` and `files`, an array of `{path, size, sha256}` sorted by `path` with unique paths. `path` follows the member-path rules of [release builds section 5.1](release-builds.md#51-inventory-v1-and-strict-parsing), including its one exact exception for `.vite/manifest.json`; the schema pattern carries that grammar and the server repeats the device-name check. The manifest has one producer: `scripts/release/console_manifest.py` of release plan Task 3 writes it for the built console tree as canonical JSON (UTF-8, keys sorted, no insignificant whitespace, one final LF), the console job uploads it beside the tree, and every embedding job copies that file unchanged next to the copied tree. `console-manifest` prints the embedded bytes unchanged, so the release verifier requires byte equality with the console job's manifest. The identity inside the tree, `dist/build-info.json`, is produced by `scripts/release/version.py` through the console recipe of release plan Task 3; a tree without it, or a server built without `generated.go` from the same identity, fails verification as `console_identity_mismatch`, so the embedding job must run both halves of release plan Tasks 1 and 3.

### 6.1 Startup verification

Before the listener binds, the server parses `manifest.json` with the strict JSON rules of release builds section 5.1 and its schema; malformed JSON, a schema violation, unsorted entries or a duplicate path is `console_manifest_invalid` and exit 3. It then reads every embedded file, computes SHA-256 and compares path, size and digest with the manifest; a missing, extra or changed file is `console_mismatch` and exit 3. It then parses `dist/build-info.json` and requires `version`, `commit`, `channel` and `sourceEpoch` to equal `buildinfo.Current()`; a missing file or a mismatch is `console_identity_mismatch` and exit 3, which is the "one architecture embeds a different console version" failure the release plan names. It parses `dist/.vite/manifest.json` with the strict JSON rules of release builds section 5.1 and records the set of emitted files, chunks and assets; a missing or malformed Vite manifest is `console_vite_manifest_invalid` and exit 3, because serving every asset `no-cache` is the Node test harness's fallback, not a production state. The CSP is a Go string constant in the package equal to `console/security/csp.txt` without its final LF; the package test reads that repository file and requires equality, so the console file stays the single home and the constant cannot drift from it. All verified bytes stay in memory in an immutable map; the handler never touches the filesystem.

### 6.2 Response contract

Every console response, including `404` and `405`, carries the foundation header set from [console foundation section 4](console-foundation.md#4-production-header-and-trust-boundary): `Content-Security-Policy` with the exact `csp.txt` value, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Permissions-Policy: camera=(), microphone=(), geolocation=(), usb=(), payment=()`, and on TLS listeners `Strict-Transport-Security: max-age=31536000`. Only a reviewed consumer widens a directive; this slice ships the foundation profile, not the wider header of console design section 6.1.

| Request | Response |
|---|---|
| Any request that declares content | `413` with `Connection: close` and an expired read deadline, before every other row (section 4) |
| Method other than GET or HEAD on a console path | `405`, `Allow: GET, HEAD`, body `application/problem+json` with `status` 405 and `type` `about:blank`, per [RFC 9110 section 15.5.6](https://www.rfc-editor.org/rfc/rfc9110.html#name-405-method-not-allowed) and [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html) |
| Path longer than 1,024 bytes, containing NUL, a backslash, an empty or `.` or `..` segment, or a percent-encoded slash | `404` problem body; the escaped path is checked, decoded exactly once and matched against the manifest, never against a filesystem |
| GET or HEAD with a decoded path ending in `.br` or `.gz` | `404` problem body before asset lookup or SPA fallback; sidecars are negotiated representations only |
| `/assets/<file>` present in the manifest | `200`; `Content-Type` from the closed map below; `ETag: "<sha256>"`; `Cache-Control: public, max-age=31536000, immutable` when `.vite/manifest.json` lists the file as an emitted file, chunk or asset, otherwise `no-cache`; `Vary: Accept-Encoding`; `Content-Length` |
| Same with `If-None-Match` matching the ETag | `304` with the same headers and no body |
| Same with an acceptable `br` coding and `<file>.br` embedded | The `.br` sibling's bytes with `Content-Encoding: br`; else `gzip` and `.gz` the same way; else identity. `Accept-Encoding` is parsed per [RFC 9110 section 12.5.3](https://www.rfc-editor.org/rfc/rfc9110.html#name-accept-encoding): a coding is acceptable when listed with a nonzero weight, or matched by `*` with a nonzero weight when not listed; `q=0` means not acceptable, so `br;q=0` never selects the Brotli sidecar; among acceptable codings the highest weight wins, with `br` preferred on a tie; the uncoded bytes are sent when no coding is acceptable. Sidecars are never addressable by their own names |
| `/brand/<file>` present | As assets with `Cache-Control: public, max-age=86400` |
| `/healthz`, `/readyz` | Section 5 |
| Any other GET or HEAD whose `Accept` is absent or includes `text/html` or `*/*`, and whose path is not under a reserved prefix; an absent field means the sender "has no preference on that dimension of negotiation" ([RFC 9110 section 12.4.1](https://www.rfc-editor.org/rfc/rfc9110.html#name-absence)) | `index.html`, `200`, `Cache-Control: no-cache`, `ETag` of `index.html`, `Content-Type: text/html; charset=utf-8` |
| Any other GET or HEAD whose `Accept` is present and excludes both | `404` problem body; a client that does not accept HTML gets no document |
| A path under a reserved prefix that no handler serves | `404` problem body; the reserved prefixes are the list in [console design section 10](../design/console.md#10-build-and-delivery), which never fall back to `index.html` |

The `api` listener's handler is one root handler: it reads the escaped request path, applies the rows above, and dispatches health, console and reserved prefixes itself. No `http.ServeMux` sits in front, because a ServeMux redirects "any request containing . or .. segments or repeated slashes to an equivalent, cleaner URL" ([ServeMux](https://pkg.go.dev/net/http#ServeMux)), which would answer `301` where this contract requires `404`; the handler never answers with a `3xx` status.

This specification owns the closed MIME map used by the runtime and console foundation harness: `.html` `text/html; charset=utf-8`, `.js` `text/javascript; charset=utf-8`, `.css` `text/css; charset=utf-8`, `.json` `application/json; charset=utf-8`, `.webmanifest` `application/manifest+json; charset=utf-8`, `.svg` `image/svg+xml; charset=utf-8`, `.png` `image/png`, `.ico` `image/x-icon`, `.woff2` `font/woff2`, `.txt` `text/plain; charset=utf-8`.

During section 6.1 verification, an entry outside this map is admitted only as a `.br` or `.gz` sidecar: strip exactly one final suffix and require that exact original path to exist in the same verified manifest and embedded tree with an extension in the map. Both original and sidecar pass the path, size and SHA-256 checks. Derive `Content-Type` from the original; the suffix selects only `Content-Encoding`. An orphan, a nested sidecar such as `app.js.gz.br`, or a sidecar of an unknown type fails as `console_unknown_type`; other unknown extensions fail the same way. A missing or changed manifest-listed file remains `console_mismatch`. Sidecars are representations attached to the original, never independent route entries; direct GET or HEAD requests ending in `.br` or `.gz` receive `404`, including outside `/assets/` and `/brand/`, before SPA fallback. New original types require review. No directory listing, no redirect from `/index.html`, no range requests, no `Last-Modified`.

## 7. Logging

`log/slog` with `JSONHandler` on standard error, one object per line with `time`, `level`, `msg` ([log/slog](https://pkg.go.dev/log/slog)); `msg` is a closed `snake_case` event token (`starting`, `config_loaded`, `console_verified`, `listening`, `ready`, `request`, `stop_requested`, `shutdown_complete`, `shutdown_timeout`, `startup_failed`) and the plan's catalogue is the contract tests match. `request` records `method`, `path` without query, `status`, `bytes`, `duration_ms` and `remote` as the TCP peer; proxy headers are not trusted or logged in this slice. No header, cookie, body, query string, environment value or file content is logged at any level. Level comes from configuration; `debug` adds per-asset cache decisions and nothing sensitive.

## 8. Roles and what is blocked

`roles` is required and parsed against the full BE-03 list so configuration written for a later build validates, but this build starts only `api`, and `api` serves only sections 5 and 6. Naming `agent`, `device`, `radius` or `jobs` exits 2 with `role_blocked` and the gate: `agent` and `device` wait for the authority journal, enrollment and mTLS contracts (analysis section 3.1 row 3, BE-12, PKI-02); `radius` waits for RAD-02 to RAD-06 contracts; `jobs` waits for the database and journal slices. There is no default role set in any build: a process runs exactly the roles its configuration lists and fails closed without the list, and the deployment slice names the roles explicitly in Compose and Helm (`architecture.md` section 3.1). `/api/v1/*` answers `404` because no operation exists, not `501`, since the OpenAPI document that would define one is itself absent (analysis section 3). There is no database connection, migration, session, CSRF token, API token, blob store, metrics endpoint or change stream in this slice; each refuses rather than stubs.

## 9. Protocol trace and attacker outcomes

Path: operator writes the YAML file and TLS files → container starts the binary as its unprivileged user → configuration and environment validated → console tree verified against its embedded manifest and build identity → TLS loaded → listener bound → requests answered from memory with fixed headers → first stop request latches the deadline independently of startup → readiness drops and startup cancels → cleanup and connections drain within the same budget → clean exit or watchdog exit 1. A stop can enter this path during any startup operation; late results cannot publish readiness. Inputs are the configuration, the environment prefix, the embedded bytes and HTTP requests; outputs are static bytes, health states and logs.

| Attacker | What the attacker gets and what remains |
|---|---|
| Stolen enrollment token | Nothing: no enrollment handler exists; `/agent/v1/*` is a `404` |
| Compromised agent host | Can request static assets and health states but has no agent-specific path. Section 4 bounds header waits, unread request content and gaps in successful server writes. Reading small amounts is not itself write progress. A client that drains enough to sustain HTTP/2 server writes can keep the shared writer occupied and delay a stream reset until forced `Close`, causing `shutdown_timeout` and exit 1; it cannot extend the process stop deadline. No total response-duration or aggregate connection-count bound is established by these progress timeouts |
| Compromised console session | No session exists; a browser that loads the console can only fetch the same static files, and the CSP forbids inline script, so an injected page cannot widen what the served document does. CSP is not authorization and later slices still need sessions and CSRF defence |
| Rogue extension publisher | `/ext/` answers `404`; no module mount, binding or asset serving exists (EXT-04) |
| Network position between agent and server | With `tls.mode: file` the position sees TLS; the console origin's integrity rests on the operator's certificate. Plaintext is loopback only, so the position would have to be on the host. HSTS is sent only on TLS listeners |
| Database writer without signing keys | No database is opened; nothing the server serves comes from a store |
| Server restored from backup | The binary serves the same embedded bytes regardless of restore; no authority state exists here |
| Operator with write access to the configuration or image | Can point the listener elsewhere, disable the console or supply a certificate; cannot change headers, the CSP or the console bytes without rebuilding, since they are embedded and verified. Readiness and health disclose only states |

## 10. Benefits, trade-offs, dependencies, limits, alternatives

Benefits: the console's production header boundary is enforced by the binary that will serve it, with the same fixtures the foundation already runs; the embedded tree is verified against its manifest and build identity before a byte is served; role admission is explicit, so a build cannot pretend to run a role whose contracts are blocked; one configuration path with strict decoding and a closed environment list; one stop budget across startup and drain, with process termination independent of blocked startup I/O.

Trade-offs: the stop watchdog preserves the process bound at the cost of abandoning blocked work, deferred cleanup and possibly terminal logs; reserving 100 ms for finalization shortens graceful work by that amount. The default budget is frozen if stop precedes validated configuration, so a timeout in an unread file cannot control that stop. Sidecar admission preserves deterministic precompression without opening the MIME map; it trusts the reviewed build to produce valid compressed bytes and does not decompress during startup. Requiring `roles` with no default makes every configuration name its roles, accepted over a default that silently runs a subset; a build tag for the embedded console keeps `go test ./...` independent of a console build, at the cost of one more recipe flag that the release plan records; `yaml.v3` is a dependency for a six-key file, accepted because the architecture fixes YAML for the server and the loader slice already admits this exact version.

Dependencies: Go 1.27.1 standard library and `go.yaml.in/yaml/v3` v3.0.4, both with rows in [licensing](../licensing.md); the console build under [console foundation](console-foundation.md); the release identity tooling of release plan Tasks 1 and 3 for any embedding job.

Limits: no API, identity or database; a request that `net/http` rejects before any handler runs, such as a malformed request line or a header block above `max_header_bytes`, receives Go's plain-text error with `Connection: close` and without the console header set, which carries no HTML; TLS material reloads only by restart; proxy headers are untrusted so logged peers are the load balancer's when one exists; `/metrics` absent; the Go binary on macOS or Windows is a test convenience, not a supported deployment.

Alternatives considered: boundary-only cancellation or deadlines on ordinary files do not bound blocked I/O; waiting for configuration to choose a timeout or starting a fresh timer at drain can extend a stop indefinitely; returning from a library while its worker lives does not prove process exit. Reject those choices in favor of the independent watchdog. A helper subprocess for startup adds IPC and process custody to a static, read-only slice without removing the need for a final executable stop bound. Reject treating `.br` and `.gz` as independent MIME types because it admits orphan representations and direct sidecar routes; rejecting all sidecars contradicts the build contract. `http.FileServer` and `http.ServeFileFS`, rejected because they list directories, redirect `index.html`, derive `Content-Type` by sniffing and set `Last-Modified`, each contradicting the contract; serving from a directory on disk, rejected because the deployment then depends on a writable path and a copied tree that nothing verifies; a `--dev` flag that relaxes headers, rejected because every test must run under the production header; a separate administrative port for health, rejected for this slice since the endpoints disclose only states and the container probe reaches one port; `501 Not Implemented` for `/api/v1`, rejected because it would advertise an API surface that no contract defines; a default of all roles, rejected because it would silently run the implemented subset; a server-wide `ReadTimeout` or `WriteTimeout`, rejected because it would cut the later long polls and change stream, which bound their own reads and writes per handler; `http.MaxBytesHandler` for the console, rejected because it limits how much Go reads but not how slowly: the close after the handler would still wait on a trickled body, while an expired read deadline ends that read at once.
