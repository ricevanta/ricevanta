# Server runtime entry point

`ricevanta-server` becomes a real executable: one binary that runs the roles it is told to run, reports health and readiness, serves the embedded console with the production headers, logs in one format and stops within a bound. This specification fixes that contract. Database access, identity, the administration API, enrollment, the native device protocols, RADIUS and jobs arrive with their own reviewed slices and refuse to start until then (section 8).

Authorities: BE-03, BE-04, BE-08, BE-13 and BE-15 in [decisions](../decisions.md), [architecture](../architecture.md) sections 3 and 5, [backend design](../design/backend.md) section 1, [console design](../design/console.md) sections 6.1 and 10, [console foundation](console-foundation.md) sections 3 and 4, [release builds](release-builds.md) section 2 and [the implementation plan](../plans/server-runtime.md).

## 1. Boundary and packages

| Path | Purpose | Dependencies |
|---|---|---|
| `server/cmd/ricevanta-server/main.go` | Command line, exit codes; calls the runtime and nothing else | Standard library |
| `server/internal/buildinfo/` | Build identity: tracked development default and the generated release constants | Standard library |
| `server/internal/platform/config/` | YAML file and environment loading, closed struct, validation | `go.yaml.in/yaml/v3` v3.0.4 |
| `server/internal/platform/runtime/` | Lifecycle state machine, role table, listeners, graceful shutdown, signal handling | Standard library |
| `server/internal/platform/health/` | `/healthz` and `/readyz` handlers and the readiness registry | Standard library |
| `server/internal/transport/console/` | Embedded console tree, startup verification, asset handler, headers | Standard library |

The supported runtime target is the Linux container image of [architecture section 5](../architecture.md#5-deployment) on amd64 and arm64; the binary also compiles on the developer's macOS and Windows hosts for tests, and those builds are not release artifacts. The console foundation's Node harness stays the console's own test server; this package replaces it in deployment and must pass the same header fixtures against the real binary.

## 2. Build identity and the version command

`server/internal/buildinfo/buildinfo.go` is tracked and defines `type Identity struct { Version, Commit, Channel string; SourceEpoch int64 }`, `func Current() Identity`, and the package-level development default `Version "0.0.0-local"`, `Commit "unknown"`, `Channel "local"`, `SourceEpoch 0`. The release recipe copies [`generated.go`](release-builds.md#2-one-product-version) into the package: a gitignored file with the string constants `Version`, `Commit`, `Channel`, the `SourceEpoch int64` constant and an `init` function that assigns them to the package default. A tracked file therefore never changes during a release build, and a development build is unmistakably non-release. The release tooling checks that the generated file's constants and the `--version` output agree with `identity.json`.

```
ricevanta-server --version            ricevanta-server <version> (commit <commit>, channel <channel>)
ricevanta-server version --json       {"channel":...,"commit":...,"sourceEpoch":...,"version":...}
ricevanta-server serve --config PATH
ricevanta-server check-config --config PATH
ricevanta-server console-manifest     the embedded console manifest (section 6) as JSON on stdout
```

Exit codes: `0` success; `1` failure after the server was ready, including a shutdown that missed its deadline; `2` command line or configuration error; `3` startup failure (console verification, TLS material, listener bind, blocked role). `migrate` and every role beyond `api` are not subcommands or values yet; naming them exits 2 with the gate from section 8.

## 3. Configuration

One YAML file, default `/etc/ricevanta/server.yaml`, selected by `--config` or, when the flag is absent, by `RICEVANTA_SERVER_CONFIG`, plus a closed list of environment overrides. Precedence, highest first: environment variables, the file, built-in defaults; for the file path alone the flag wins over the variable, because the flag is the operator's explicit action on this invocation. The file is at most 65,536 bytes, UTF-8, and exactly one YAML document whose root is a mapping. It is decoded with `yaml.v3` `Decoder.KnownFields(true)` into closed structs, so an unknown key is an error ([yaml.v3](https://pkg.go.dev/go.yaml.in/yaml/v3)); duplicate mapping keys are errors on their own, because v3.0.4 constructs its decoder with `uniqueKeys: true` and reports `mapping key %#v already defined at line %d` and, for structs, `field %s already set in type %s` ([decode.go](https://github.com/yaml/go-yaml/blob/v3.0.4/decode.go)). A `yaml.Node` pre-pass rejects every node with `Kind == AliasNode`, a nonempty `Anchor`, or `Style & TaggedStyle != 0` (an explicit tag), so no alias expansion or type coercion through tags reaches the struct. The JSON projection of the decoded document validates against [`schemas/server/config/v1/config.schema.json`](../../schemas/server/config/v1/config.schema.json), whose [example](../../schemas/server/config/v1/example.json) is a complete minimal configuration; the Go validator repeats the same bounds with the standard library so design CI and the binary agree on the same fixtures.

| Key | Default | Rule |
|---|---|---|
| `schema` | required | `ricevanta-server-config-v1` |
| `roles` | required | Non-empty list from `api`, `agent`, `device`, `radius`, `jobs`, no duplicates; only `api` is admissible in this build, see section 8 |
| `listen.api.address` | required when `api` is listed | `host:port`; host is an IPv4 or bracketed IPv6 literal or empty for all interfaces; port 1 to 65535 |
| `listen.api.tls.mode` | `file` | `file` or `none`; `none` only when the host is a loopback address, else exit 2 `plaintext_requires_loopback` |
| `listen.api.tls.certificate_file`, `listen.api.tls.key_file` | required for `file` | Absolute paths to PEM files; the key file is opened once, following symbolic links, and the checks apply to `fstat` of the opened file, which must be a regular file owned by root or the effective user, with no permission bits for others and write permission at most for the owner, and readable by group only when the file's group is the effective group or a supplementary group of the process (`0400`, `0600`, `0440` or `0640`) |
| `console.enabled` | `true` | Serve the embedded console on the `api` listener |
| `log.level` | `info` | `error`, `warn`, `info`, `debug` |
| `http.read_header_timeout_ms` | 10000 | 1000 to 60000 |
| `http.idle_timeout_ms` | 60000 | 1000 to 600000 |
| `http.max_header_bytes` | 65536 | 4096 to 1048576 |
| `shutdown.timeout_ms` | 20000 | 1000 to 120000 |

The key-file rule fits the deployment shapes. The kubelet keeps Secret data in a `tmpfs` ([Kubernetes Secrets](https://kubernetes.io/docs/concepts/configuration/secret/)) and projects each key as a symbolic link into a hidden timestamped directory that it swaps atomically ([atomic_writer.go](https://github.com/kubernetes/kubernetes/blob/master/pkg/volume/util/atomic_writer.go)), which is why the open follows links and the checks judge the opened file. A Secret volume's `defaultMode` "Defaults to 0644" and "might be in conflict with other options that affect the file mode, like fsGroup" ([core/v1 types.go](https://github.com/kubernetes/api/blob/master/core/v1/types.go), `SecretVolumeSource`), and `fsGroup` makes the volume's files group-owned by that ID and adds it to the container processes' supplementary groups ([pod security context](https://kubernetes.io/docs/tasks/configure-pod-container/security-context/)). The deployment slice therefore mounts the key with `defaultMode: 0440` and the server's `fsGroup`, which this rule accepts, records the mode that results on its qualified cluster, and never relaxes the rule: a world-readable `0644` key is refused. Compose cannot set those modes for a file secret: "support for `uid`, `gid`, and `mode` attributes are only implemented in Docker Compose when the source of the secret is `environment`", and for a `file` source "Compose uses a bind-mount" and "these attributes are silently ignored" ([Compose services reference](https://docs.docker.com/reference/compose-file/services/#secrets)), while an environment secret defaults to the world-readable mode `0444` that this rule refuses. Under Compose the host file's own owner and mode therefore reach the container, and the deployment slice prepares the host key owned by the container user with mode `0400`, or owned by root with the container's group and mode `0440`. Environment overrides are exactly `RICEVANTA_SERVER_CONFIG`, `RICEVANTA_SERVER_ROLES` (comma separated), `RICEVANTA_SERVER_LISTEN_API_ADDRESS`, `RICEVANTA_SERVER_LISTEN_API_TLS_MODE`, `RICEVANTA_SERVER_LISTEN_API_TLS_CERTIFICATE_FILE`, `RICEVANTA_SERVER_LISTEN_API_TLS_KEY_FILE`, `RICEVANTA_SERVER_CONSOLE_ENABLED` and `RICEVANTA_SERVER_LOG_LEVEL`. Any other variable with the prefix `RICEVANTA_SERVER_` is an error naming it, so a misspelled override cannot silently fall back. Values pass the same validation as file values. No secret exists in this slice; the later secrets slice adds `_FILE` references and never inline values (`design/backend.md` section 6). `check-config` prints the effective configuration as sorted-key JSON with key-file paths but no file contents.

## 4. Lifecycle

```
starting ──> ready ──> stopping ──> stopped
   └── failed (exit 2 or 3)
```

Startup, in order: parse the command line; load and validate configuration; create the `slog` JSON logger on standard error; resolve the role table and refuse blocked roles; verify the embedded console (section 6.1) when enabled; load TLS material; bind the `api` listener; start serving; mark `api` ready; log `ready`. Readiness is per role and the process is ready when every configured role is ready. Any failure before `ready` logs `startup_failed` with the step and exits 2 or 3.

Stop: `SIGTERM` or `SIGINT` through `signal.NotifyContext` on Unix, and `os.Interrupt` plus the `syscall.SIGTERM` that Go delivers for console close, logoff and shutdown events on Windows ([os/signal](https://pkg.go.dev/os/signal)). On the first stop request the server logs `stop_requested`, flips readiness so `/readyz` answers `503` with `stopping`, calls `http.Server.Shutdown` with a context deadline of `shutdown.timeout_ms`, which closes idle connections and waits for active ones ([net/http Server.Shutdown](https://pkg.go.dev/net/http#Server.Shutdown)), then calls `Close` on whatever remains. Completion within the deadline exits 0 after `shutdown_complete`; a deadline miss logs `shutdown_timeout`, closes and exits 1. The default of 20 s stays below Kubernetes' default 30 s termination grace period, and Compose's `stop_grace_period` is set to 30 s by the deployment slice. Repeated stop requests are counted and ignored. A panic in a handler is recovered by `net/http` per connection; a panic outside a handler ends the process with exit 1 after the logger flushes.

The HTTP server sets `ReadHeaderTimeout`, `IdleTimeout` and `MaxHeaderBytes` from configuration and `DisableGeneralOptionsHandler`, so an `OPTIONS *` request reaches the handler instead of Go's built-in `200` without the header set. It leaves the server-wide `ReadTimeout` and `WriteTimeout` at zero, because later roles hold requests open for long polls and the change stream; every handler family bounds its own reads and writes through `http.ResponseController` instead ([net/http Server](https://pkg.go.dev/net/http#Server), [ResponseController](https://pkg.go.dev/net/http#ResponseController)). `ReadHeaderTimeout` also bounds the TLS handshake, for which `net/http` uses the smallest positive value of `ReadHeaderTimeout`, `ReadTimeout` and `WriteTimeout` ([server.go](https://github.com/golang/go/blob/go1.27.1/src/net/http/server.go), `tlsHandshakeTimeout`).

The console and health handlers accept no request content. A request that declares any, by a nonzero `Content-Length` or a chunked body that Go reports as length -1, is answered `413` with a problem body and `Connection: close` before its method or path is examined, and the handler never reads the content. Before writing that response the handler calls `http.NewResponseController(w).SetReadDeadline(time.Now())`. The header alone is not enough: it makes Go skip the discard in `WriteHeader`, but `finishRequest` still closes the request body "regardless of w.closeAfterReply", and that close reads up to 256 KiB plus one byte of a declared or chunked body under no deadline while `ReadTimeout` is zero ([server.go](https://github.com/golang/go/blob/go1.27.1/src/net/http/server.go), `finishRequest`; [transfer.go](https://github.com/golang/go/blob/go1.27.1/src/net/http/transfer.go), `body.Close`). With the deadline already passed, that read fails at once and Go marks the body closed early. On HTTP/1.1 Go then closes the connection after its 500 ms `rstAvoidanceDelay`, so a client that declares content and trickles it holds the connection for about half a second and delays `Shutdown` by no more. On HTTP/2 the same header makes Go send `GOAWAY`, a stream whose content was not read is reset when the handler returns, and the connection closes `goAwayTimeout`, 1 s, after its last open stream completes ([internal/http2/server.go](https://github.com/golang/go/blob/go1.27.1/src/net/http/internal/http2/server.go)). Writes are bounded by progress: before its first write the handler sets a write deadline 10 s ahead and moves it 10 s ahead each time another 16 KiB has been written, so a client that stops reading loses its connection within 10 s instead of holding it until the shutdown deadline; the final flush after the handler returns still runs under the last deadline, and `net/http` clears the deadline before it reads the next request on the connection (server.go, after `finishRequest`). HTTP/2 is negotiated on TLS listeners by Go's default; plaintext listeners speak HTTP/1.1.

## 5. Health and readiness

| Path | Method | Response |
|---|---|---|
| `/healthz` | GET, HEAD | `200` with body `{"status":"ok"}` while the process is serving; it is liveness, not readiness |
| `/readyz` | GET, HEAD | `200` with `{"status":"ready","roles":{"api":"ready"}}` when every configured role is ready; `503` with `status` `starting` or `stopping` and the per-role states otherwise |

Both carry `Content-Type: application/json`, `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`, and never a version, hostname, build identity, address or configuration value; [`schemas/server/health/v1/readiness.schema.json`](../../schemas/server/health/v1/readiness.schema.json) validates the bodies. Other methods receive `405` with `Allow: GET, HEAD`. The endpoints live on the `api` listener so the container probe and the load balancer reach them without a second port; what they disclose is bounded to the states above, which is why they are safe on a public listener. `/metrics` answers `404` until the Prometheus client slice adds it with its own exposure rules.

## 6. Console serving

The `transport/console` package embeds the console build with `//go:embed all:dist` and `manifest.json` under a build constraint `ricevanta_console`; without the tag the package embeds nothing, `console.enabled: true` fails startup with `console_missing`, and tests use a fixture tree. Go embeds a directory recursively and excludes dot and underscore names unless `all:` is used ([embed](https://pkg.go.dev/embed)); `all:` is required because Vite writes `.vite/manifest.json`. The release recipe (release plan Task 4) copies the console job's tree to `server/internal/transport/console/dist/` and its `manifest.json` beside it, and builds with `-tags ricevanta_console`; both paths are gitignored. `manifest.json` follows [`schemas/server/console-manifest/v1/manifest.schema.json`](../../schemas/server/console-manifest/v1/manifest.schema.json): an object with `schema` `ricevanta-console-manifest-v1` and `files`, an array of `{path, size, sha256}` sorted by `path` with unique paths. `path` follows the member-path rules of [release builds section 5.1](release-builds.md#51-inventory-v1-and-strict-parsing), including its one exact exception for `.vite/manifest.json`; the schema pattern carries that grammar and the server repeats the device-name check. The manifest has one producer: `scripts/release/console_manifest.py` of release plan Task 3 writes it for the built console tree as canonical JSON (UTF-8, keys sorted, no insignificant whitespace, one final LF), the console job uploads it beside the tree, and every embedding job copies that file unchanged next to the copied tree. `console-manifest` prints the embedded bytes unchanged, so the release verifier requires byte equality with the console job's manifest. The identity inside the tree, `dist/build-info.json`, is produced by `scripts/release/version.py` through the console recipe of release plan Task 3; a tree without it, or a server built without `generated.go` from the same identity, fails verification as `console_identity_mismatch`, so the embedding job must run both halves of release plan Tasks 1 and 3.

### 6.1 Startup verification

Before the listener binds, the server reads every embedded file, computes SHA-256 and compares path, size and digest with `manifest.json`; a missing, extra or changed file is `console_mismatch` and exit 3. It then parses `dist/build-info.json` and requires `version`, `commit`, `channel` and `sourceEpoch` to equal `buildinfo.Current()`; a missing file or a mismatch is `console_identity_mismatch` and exit 3, which is the "one architecture embeds a different console version" failure the release plan names. It parses `dist/.vite/manifest.json` with the strict JSON rules of release builds section 5.1 and records the set of emitted files, chunks and assets; a missing or malformed Vite manifest is `console_vite_manifest_invalid` and exit 3, because serving every asset `no-cache` is the Node test harness's fallback, not a production state. The CSP is a Go string constant in the package equal to `console/security/csp.txt` without its final LF; the package test reads that repository file and requires equality, so the console file stays the single home and the constant cannot drift from it. All verified bytes stay in memory in an immutable map; the handler never touches the filesystem.

### 6.2 Response contract

Every console response, including `404` and `405`, carries the foundation header set from [console foundation section 4](console-foundation.md#4-production-header-and-trust-boundary): `Content-Security-Policy` with the exact `csp.txt` value, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Permissions-Policy: camera=(), microphone=(), geolocation=(), usb=(), payment=()`, and on TLS listeners `Strict-Transport-Security: max-age=31536000`. Only a reviewed consumer widens a directive; this slice ships the foundation profile, not the wider header of console design section 6.1.

| Request | Response |
|---|---|
| Any request that declares content | `413` with `Connection: close` and an expired read deadline, before every other row (section 4) |
| Method other than GET or HEAD on a console path | `405`, `Allow: GET, HEAD`, body `application/problem+json` with `status` 405 and `type` `about:blank`, per [RFC 9110 section 15.5.6](https://www.rfc-editor.org/rfc/rfc9110.html#name-405-method-not-allowed) and [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html) |
| Path longer than 1,024 bytes, containing NUL, a backslash, an empty or `.` or `..` segment, or a percent-encoded slash | `404` problem body; the escaped path is checked, decoded exactly once and matched against the manifest, never against a filesystem |
| `/assets/<file>` present in the manifest | `200`; `Content-Type` from the closed map below; `ETag: "<sha256>"`; `Cache-Control: public, max-age=31536000, immutable` when `.vite/manifest.json` lists the file as an emitted file, chunk or asset, otherwise `no-cache`; `Vary: Accept-Encoding`; `Content-Length` |
| Same with `If-None-Match` matching the ETag | `304` with the same headers and no body |
| Same with an acceptable `br` coding and `<file>.br` embedded | The `.br` sibling's bytes with `Content-Encoding: br`; else `gzip` and `.gz` the same way; else identity. `Accept-Encoding` is parsed per [RFC 9110 section 12.5.3](https://www.rfc-editor.org/rfc/rfc9110.html#name-accept-encoding): a coding is acceptable when listed with a nonzero weight, or matched by `*` with a nonzero weight when not listed; `q=0` means not acceptable, so `br;q=0` never selects the Brotli sidecar; among acceptable codings the highest weight wins, with `br` preferred on a tie; the uncoded bytes are sent when no coding is acceptable. Sidecars are never addressable by their own names |
| `/brand/<file>` present | As assets with `Cache-Control: public, max-age=86400` |
| `/healthz`, `/readyz` | Section 5 |
| Any other GET or HEAD whose `Accept` includes `text/html` or `*/*` and whose path is not under a reserved prefix | `index.html`, `200`, `Cache-Control: no-cache`, `ETag` of `index.html`, `Content-Type: text/html; charset=utf-8` |
| Any other GET or HEAD whose `Accept` excludes both | `404` problem body; a client that does not accept HTML gets no document |
| A path under a reserved prefix that no handler serves | `404` problem body; the reserved prefixes are the list in [console design section 10](../design/console.md#10-build-and-delivery), which never fall back to `index.html` |

The `api` listener's handler is one root handler: it reads the escaped request path, applies the rows above, and dispatches health, console and reserved prefixes itself. No `http.ServeMux` sits in front, because a ServeMux redirects "any request containing . or .. segments or repeated slashes to an equivalent, cleaner URL" ([ServeMux](https://pkg.go.dev/net/http#ServeMux)), which would answer `301` where this contract requires `404`; the handler never answers with a `3xx` status.

Closed MIME map, from console foundation section 3: `.html` `text/html; charset=utf-8`, `.js` `text/javascript; charset=utf-8`, `.css` `text/css; charset=utf-8`, `.json` `application/json; charset=utf-8`, `.webmanifest` `application/manifest+json; charset=utf-8`, `.svg` `image/svg+xml; charset=utf-8`, `.png` `image/png`, `.ico` `image/x-icon`, `.woff2` `font/woff2`, `.txt` `text/plain; charset=utf-8`. A manifest entry with another extension fails startup verification as `console_unknown_type`, so a new asset type is a reviewed change. No directory listing, no redirect from `/index.html`, no range requests, no `Last-Modified`.

## 7. Logging

`log/slog` with `JSONHandler` on standard error, one object per line with `time`, `level`, `msg` ([log/slog](https://pkg.go.dev/log/slog)); `msg` is a closed `snake_case` event token (`starting`, `config_loaded`, `console_verified`, `listening`, `ready`, `request`, `stop_requested`, `shutdown_complete`, `shutdown_timeout`, `startup_failed`) and the plan's catalogue is the contract tests match. `request` records `method`, `path` without query, `status`, `bytes`, `duration_ms` and `remote` as the TCP peer; proxy headers are not trusted or logged in this slice. No header, cookie, body, query string, environment value or file content is logged at any level. Level comes from configuration; `debug` adds per-asset cache decisions and nothing sensitive.

## 8. Roles and what is blocked

`roles` is required and parsed against the full BE-03 list so configuration written for a later build validates, but this build starts only `api`, and `api` serves only sections 5 and 6. Naming `agent`, `device`, `radius` or `jobs` exits 2 with `role_blocked` and the gate: `agent` and `device` wait for the authority journal, enrollment and mTLS contracts (analysis section 3.1 row 3, BE-12, PKI-02); `radius` waits for RAD-02 to RAD-06 contracts; `jobs` waits for the database and journal slices. There is no default role set in any build: a process runs exactly the roles its configuration lists and fails closed without the list, and the deployment slice names the roles explicitly in Compose and Helm (`architecture.md` section 3.1). `/api/v1/*` answers `404` because no operation exists, not `501`, since the OpenAPI document that would define one is itself absent (analysis section 3). There is no database connection, migration, session, CSRF token, API token, blob store, metrics endpoint or change stream in this slice; each refuses rather than stubs.

## 9. Protocol trace and attacker outcomes

Path: operator writes the YAML file and TLS files → container starts the binary as its unprivileged user → configuration and environment validated → console tree verified against its embedded manifest and build identity → TLS loaded → listener bound → requests answered from memory with fixed headers → `SIGTERM` → readiness drops → connections drain under the deadline → exit. Inputs are the configuration, the environment prefix, the embedded bytes and HTTP requests; outputs are static bytes, health states and logs.

| Attacker | What the attacker gets and what remains |
|---|---|
| Stolen enrollment token | Nothing: no enrollment handler exists; `/agent/v1/*` is a `404` |
| Compromised agent host | Can send requests like any client and receives static assets and health states; no agent-specific path exists. A slow or stalled client is cut off by the header timeout, the refusal of request content under an expired read deadline (the connection closes about 500 ms after the `413` on HTTP/1.1 and about 1 s after its last open stream on HTTP/2) and the write-progress deadline of section 4, so it holds a connection no longer than those bounds and delays shutdown by no more |
| Compromised console session | No session exists; a browser that loads the console can only fetch the same static files, and the CSP forbids inline script, so an injected page cannot widen what the served document does. CSP is not authorization and later slices still need sessions and CSRF defence |
| Rogue extension publisher | `/ext/` answers `404`; no module mount, binding or asset serving exists (EXT-04) |
| Network position between agent and server | With `tls.mode: file` the position sees TLS; the console origin's integrity rests on the operator's certificate. Plaintext is loopback only, so the position would have to be on the host. HSTS is sent only on TLS listeners |
| Database writer without signing keys | No database is opened; nothing the server serves comes from a store |
| Server restored from backup | The binary serves the same embedded bytes regardless of restore; no authority state exists here |
| Operator with write access to the configuration or image | Can point the listener elsewhere, disable the console or supply a certificate; cannot change headers, the CSP or the console bytes without rebuilding, since they are embedded and verified. Readiness and health disclose only states |

## 10. Benefits, trade-offs, dependencies, limits, alternatives

Benefits: the console's production header boundary is enforced by the binary that will serve it, with the same fixtures the foundation already runs; the embedded tree is verified against its manifest and build identity before a byte is served; role admission is explicit, so a build cannot pretend to run a role whose contracts are blocked; one configuration path with strict decoding and a closed environment list; graceful shutdown with a bound that fits the deployment shapes.

Trade-offs: requiring `roles` with no default makes every configuration name its roles, accepted over a default that silently runs a subset; a build tag for the embedded console keeps `go test ./...` independent of a console build, at the cost of one more recipe flag that the release plan records; `yaml.v3` is a dependency for a six-key file, accepted because the architecture fixes YAML for the server and the loader slice already admits this exact version.

Dependencies: Go 1.27.1 standard library and `go.yaml.in/yaml/v3` v3.0.4, both with rows in [licensing](../licensing.md); the console build under [console foundation](console-foundation.md); the release identity tooling of release plan Tasks 1 and 3 for any embedding job.

Limits: no API, identity or database; a request that `net/http` rejects before any handler runs, such as a malformed request line or a header block above `max_header_bytes`, receives Go's plain-text error with `Connection: close` and without the console header set, which carries no HTML; TLS material reloads only by restart; proxy headers are untrusted so logged peers are the load balancer's when one exists; `/metrics` absent; the Go binary on macOS or Windows is a test convenience, not a supported deployment.

Alternatives considered: `http.FileServer` and `http.ServeFileFS`, rejected because they list directories, redirect `index.html`, derive `Content-Type` by sniffing and set `Last-Modified`, each contradicting the contract; serving from a directory on disk, rejected because the deployment then depends on a writable path and a copied tree that nothing verifies; a `--dev` flag that relaxes headers, rejected because every test must run under the production header; a separate administrative port for health, rejected for this slice since the endpoints disclose only states and the container probe reaches one port; `501 Not Implemented` for `/api/v1`, rejected because it would advertise an API surface that no contract defines; a default of all roles, rejected because it would silently run the implemented subset; a server-wide `ReadTimeout` or `WriteTimeout`, rejected because it would cut the later long polls and change stream, which bound their own reads and writes per handler; `http.MaxBytesHandler` for the console, rejected because it limits how much Go reads but not how slowly: the close after the handler would still wait on a trickled body, while an expired read deadline ends that read at once.
