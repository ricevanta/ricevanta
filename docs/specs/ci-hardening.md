# CI hardening

GitHub CI must prove that required work ran against the tested source, using admitted tools and fresh compiler output. A green process exit without execution evidence is insufficient. This specification owns CI routing, evidence and tool admission; [the plan](../plans/ci-hardening.md) implements them in separate PRs. The independent CI audit's CI-01 through CI-08 findings define the defect coverage.

Authorities: SH-04, PF-01, PF-04, AG-09, BE-13 and BE-14 in [decisions](../decisions.md), [workflow](../../instructions/workflow.md), [testing](../../instructions/testing.md), [permission catalogue](permission-catalogue.md), [console foundation](console-foundation.md) and [release builds](release-builds.md). Both this specification and its plan require an eligible independent `design_reviewer` approval before implementation. This design is not that approval.

## 1. Scope and limits

The slice owns `.github/workflows/ci.yml`, shared component workflows, `scripts/ci/` helpers, test-harness proof, validator dependencies and CI instructions. It introduces no runtime API, permission or signing key. Owner settings are separate in section 10. The core hardening mechanisms require no additional account or vendor program. [CI security scanning](ci-security-scanning.md) separately defines the owner-authorized Semgrep analysis service and its sole step-scoped credential exception; no package registry publishing credential is required. The Chrome for Testing builds in section 8 are under Google's proprietary terms, which the owner accepts for CI use in [project facts](../project.md#ci-browser-builds).

Keep the native macOS ARM64, Windows x64 and Linux x64 checks. Hosted Windows Server runners do not qualify Windows 11, and hosted codec tests do not qualify sensors. [Platform support](../platform-support.md) and its release gates remain authoritative. Every blueprint feature remains required at v1.0.0 except its two listed v2.0.0 capabilities.

This is a reviewed implementation contract. Helpers and workflow paths specified below are deliverables, not claims that they exist. [CI contract schema](../../schemas/ci/v1/contracts.schema.json) and its [examples](../../schemas/ci/v1/examples.json) exist for design validation. Examples use synthetic identities and tool bytes; they authorize no download or CI success.

## 2. Entry workflow and cancellation

`.github/workflows/ci.yml`, named `CI`, owns `pull_request` targeting `master` and `push` with `branches: [master]`. It has no workflow-level path filter. Include PR activities `opened`, `synchronize`, `reopened`, `ready_for_review` and `edited`; a base-branch change needs fresh routing. Draft PRs still run. No normal workflow pushes on `wip/**`.

Convert `design.yml`, `server.yml`, `agent.yml` and `console.yml` to `workflow_call` consumers of this entry. Remove their push, PR and dispatch triggers and their concurrency blocks. Each takes required string input `route` containing the route object in section 3. Use same-commit local calls, not a branch reference or `workflow_run` fan-in. Do not grant inherited secrets. `ci.yml` has no manual dispatch path claiming the required result.

The entry's concurrency group is `ci-${{ github.event_name }}-${{ github.event.pull_request.number || github.run_id }}` and `cancel-in-progress` is `${{ github.event_name == 'pull_request' }}`. PR runs supersede runs for that PR only. Unique master-push groups avoid cancellation of queued pushes as well as running pushes. Reusable workflows never cancel their caller. [GitHub workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax) defines these controls.

A temporary `.github/workflows/diagnose-<slice>.yml` may run on push to one exact `wip/<slice>` branch. It uses distinct job names, read-only permissions, no secrets and no required-check claim. Delete it before landing; the policy checker rejects a diagnosis workflow in a PR to `master`. A draft diagnosis branch can exist without a landing PR. [Workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch) explains why dispatch cannot bootstrap a workflow absent from the default branch.

Use `contents: read`, full-SHA third-party actions and `persist-credentials: false` on every checkout. Do not introduce `pull_request_target`, privileged follow-up workflows, write tokens, OIDC grants or self-hosted production runners. `copilot-code-review.yml` remains an optional review environment with its product-required job name; its runs and reviews are outside the required CI result.

### Action pins

Every `uses:` of a third-party action names the full commit of the action's latest release tag, followed on the same line by that tag as a comment, for example `actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1`. `check_policy.py` admits exactly these commits and checks the comment on the raw workflow line, because a YAML parser drops comments:

| Action | Tag | Commit | `runs.using` in that commit's `action.yml` |
|---|---|---|---|
| [`actions/checkout`](https://github.com/actions/checkout/blob/3d3c42e5aac5ba805825da76410c181273ba90b1/action.yml) | `v7.0.1` | `3d3c42e5aac5ba805825da76410c181273ba90b1` | `node24` |
| [`actions/upload-artifact`](https://github.com/actions/upload-artifact/blob/cf430e030ddbb5b0abf93d22962f4752f3646cd9/action.yml) | `v7.0.2` | `cf430e030ddbb5b0abf93d22962f4752f3646cd9` | `node24` |
| [`actions/download-artifact`](https://github.com/actions/download-artifact/blob/9000827ccba6bdab643e8b6fd33ac0654aef8333/action.yml) | `v8.0.2` | `9000827ccba6bdab643e8b6fd33ac0654aef8333` | `node24` |
| [`actions/cache`](https://github.com/actions/cache/blob/55cc8345863c7cc4c66a329aec7e433d2d1c52a9/action.yml) | `v6.1.0` | `55cc8345863c7cc4c66a329aec7e433d2d1c52a9` | `node24` |

A pin change resolves the tag with `gh api repos/actions/<name>/git/ref/tags/<tag>`, follows an annotated tag object to its commit, reads `runs.using` from that commit's `action.yml`, records here the input and behavior changes that the release notes name, and rewrites the action's [licensing](../licensing.md) row in the same change. The policy checker cannot read a remote `action.yml`, so the pin review owns the runtime check; a `node24` runtime keeps every job free of Node.js 20 deprecation annotations. Release-note changes the workflows handle:

- [upload-artifact v7.0.0](https://github.com/actions/upload-artifact/releases/tag/v7.0.0) adds `archive`; `archive: false` uploads one unzipped file under the file's own name and ignores `name`, which would break the receipt and `console-dist` names. The policy refuses `archive` on every upload. Hidden files remain excluded by default, so the `console-dist` upload keeps `include-hidden-files: true`.
- [download-artifact v8.0.0](https://github.com/actions/download-artifact/releases/tag/v8.0.0) fails on a digest mismatch by default and skips extraction of artifacts that are not zipped or that set `skip-decompress`. The policy refuses `digest-mismatch` and `skip-decompress`, so a mismatch fails and every downloaded artifact is extracted. [v5.0.0](https://github.com/actions/download-artifact/releases/tag/v5.0.0) changed the path of a single artifact downloaded by ID; the aggregate downloads by `pattern` with `merge-multiple: false` and the WebKit leaf by `name`, so neither path changes.
- The upload-artifact v6 and download-artifact v7 releases moved both actions to Node.js 24 and require runner 2.327.1 or later, which GitHub-hosted runners meet. `checkout` and `cache` are already at their latest releases.

## 3. Changed paths, identities and expected work

`scripts/ci/route.py --event-name EVENT --event PATH --root PATH --out PATH` accepts PR and master-push events only. It reads event data as data, validates full lowercase commit IDs, fetches missing objects from the configured origin without credentials persisted in Git, and verifies checkout identity. No event value is interpolated into shell code.

For PRs, record `baseSha` from `pull_request.base.sha`, `headSha` from `pull_request.head.sha`, and `testedSha` from the checked-out integration commit equal to `GITHUB_SHA`. Verify its parents bind that base and head. The changed-path set is the union of merge-base-to-head and base-to-tested diffs. For master pushes use `before`, `after` and checkout `after`; a missing/zero base or non-ancestor base is an error for this established repository. Fetch failure is failure, never an empty diff. Rebase and rerun when master moves before landing.

Diff with `git diff --name-only --no-renames -z BASE HEAD --`; deletion and rename source paths therefore remain inputs. Read the full local Git diff, not a truncated API or workflow path filter. Treat undecodable or unknown paths conservatively by selecting every group. Empty valid diffs still select `design` and `ci-contracts`.

The route object has `kind: route`, `version: 1`, `event`, `baseSha`, `headSha`, `testedSha`, decimal-string `runId` and `runAttempt`, sorted unique `groups` and sorted unique `units`. `groups` names selected consumers. `units` enumerates every expected leaf, including matrix rows, before jobs run. Never derive expected work from uploaded results. `scripts/ci/inventory.py` owns group expansion and consumer inputs; `scripts/ci/targets.toml` owns exact test/fuzz selectors. The policy checker requires workflow matrices and their `needs` edges to match those inventories. The route job exposes the compact JSON as output `route`; callers receive that string and the aggregate writes it from `needs.route.outputs.route` to its input file.

### Loader qualification inventory

Extension-loader Task 5 retains all 20 main fuzz package/name pairs and adds `FuzzLoad`, `FuzzVerifiedYAML` and `FuzzTar`, each in `./internal/extensions/loader`, for 23 unique pairs in `targets.toml` and its matrix. Each new Linux fuzz leaf is `server-fuzz:./internal/extensions/loader:<target>` with sole check `go-fuzz:./internal/extensions/loader:<target>`, using the existing 60-second/two-worker command and [Go testing flags](https://pkg.go.dev/cmd/go#hdr-Testing_flags). Keep `FuzzParserQualification` separate under `[loader]`; it remains required on every native Gate A host and does not count among the 23.

| Workflow job ID | Display name | Receipt unit for each native host | Exact checks |
|---|---|---|---|
| `loader-gate-a` | `loader Gate A (${{ matrix.os }})` | `loader:<host>` | `loader-extended`, `loader-repeat`, `loader-fuzz` |
| `loader-gate-b` | `loader Gate B (${{ matrix.os }})` | `loader-gate-b:<host>` | `loader-gate-b-extended` |

Both jobs use `contains(fromJSON(inputs.route).groups, 'loader')`, independent matrices over the existing three runner labels, `fail-fast: false`, no job `needs`, and native host assertion before tests. Gate A keeps its repetition count and measurement method. Gate B uses a 20-minute job timeout. Each check runs through section 6's wrapper under its ID; `targets.toml` pins Gate B's command, `go test -json -count=1 ./internal/extensions/loader -run '^(TestLoaderBudgetExtended)$' -args -loader-budget-extended` from `server/`. The extended test owns all complete-loader and combined-conversion measurements in [the loader spec](extension-loader.md#gate-b-complete-loader-qualification-after-task-4). Both jobs retain the tested-SHA checkout, admitted tools, fresh Go caches, verified modules, explicit Bash shell and read-only permissions. The existing `server-race` leaf uses [section 5's command and deadline](#5-fresh-go-compilation-and-dependency-caches-ci-03), covering the loader without a duplicate race job.

The route expands `loader` to all six native leaves before execution. No new route group, caller, `ci-required` dependency, receipt field, schema version or skipped-check allowance is needed. `inventory.py` and `check_policy.py` must admit the exact Gate B unit/check, job, command, route condition, matrix and proof steps together. Existing `required.py` set equality accepts the additional inventory entries; retain its SHA/run/attempt binding and receipt-only artifact directories. A successful Gate A receipt cannot satisfy Gate B. Each gate receipt requires the wrapper's verified record for every check it lists. Verified execution is not a measurement review: Task 5's qualification review still inspects the retained native measurements and fuzz logs before approving Gate B.

Use separate diagnostic artifacts for verbose Gate A and Gate B logs, named `loader-measurements-<runId>-<runAttempt>-gate-a-<runner>` and `loader-measurements-<runId>-<runAttempt>-gate-b-<runner>`, with 30-day retention. Capture each measurement step's combined wrapper output with Bash `set -euo pipefail` and `tee`; preserve the command's failure. Upload logs with `if: always()` before the normal success-gated proof step (no explicit `if`) and final receipt upload; absent expected logs fail upload. Retain all samples, including failures, with toolchain/host, recipe/mode, allocation/object/stack/heap/resident-memory/time data and full serial/two-call results. Keep failing fuzz corpora for the three new targets and Gate A through the existing failure-upload paths; missing corpus is allowed only because a non-fuzz failure may produce none. Diagnostic names must not match `ci-proof-*`, so the aggregate never consumes logs as receipts. The pinned [upload-artifact contract](https://github.com/actions/upload-artifact/blob/cf430e030ddbb5b0abf93d22962f4752f3646cd9/README.md) defines retention, distinct matrix names and missing-file behavior; [workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idstepsshell) defines Bash pipeline failure behavior.

This integration adds three native jobs and three fuzz leaves, with their compilation and artifact costs. Separate Gate B receipts expose a missing host without changing Gate A identity. Combining both gates under one receipt would obscure their separate qualification evidence. The trust path and all seven attacker outcomes in section 11 apply unchanged: runtime credentials or data grant no CI authority, and candidate-controlled receipts still require independent review.

## 4. One required result

The entry has caller jobs `design`, `server`, `agent`, `console`, `bootstrap`, its own `route` and `ci-contracts`, the direct `gitleaks` and `semgrep` jobs defined by the security scanning contract, and one terminal job with both ID and display name `ci-required`. Its `needs` lists these seven predecessors and both direct security scanner jobs literally; it uses `if: ${{ always() }}`. Caller jobs use route group membership. Component leaf jobs use the same route; matrix `fail-fast` is false and required jobs never use `continue-on-error`.

Each successful leaf emits exactly one receipt after all checks pass and uploads it as `ci-proof-<runId>-<runAttempt>-<safe-unit-id>`, with 30-day retention and missing-file upload treated as failure. The receipt has `kind: receipt`, `version: 1`, the route's run binding and tested SHA, its exact `unit`, `result: success`, and a nonempty list of executed check IDs in `checks`. Encode artifact unit names with a collision-free hex encoding of UTF-8 bytes. Upload raw logs and measurements as separate diagnostic artifacts, never inside the receipt-only proof directories or as executable artifacts that the aggregate will run.

The aggregate downloads only this run/attempt's proof artifacts into separate directories, without merging filenames. It validates the schema, exact receipt set, unique unit IDs, identity binding and required check IDs from the inventory. `scripts/ci/required.py --route PATH --needs PATH --receipts DIR` exits zero only when:

1. `route` and `ci-contracts` succeeded and route decoding/identity checks succeeded.
2. Every selected caller has `needs.result == success`; every unselected caller is `skipped` and routing explicitly proves it unaffected.
3. Every expected leaf supplied one valid success receipt. Missing, extra, duplicated, stale or malformed receipts fail. A removed matrix entry therefore fails even when the remaining matrix succeeds.
4. No required result is failure, cancellation, skipped, neutral, absent or unknown. No `continue-on-error` success wrapper may hide one.

`NEEDS_JSON: ${{ toJSON(needs) }}` goes through an environment variable to a file, not through a shell expression. The aggregate recomputes routing from checkout/event and compares it with the supplied route before accepting results. No API search for the latest green run and no cross-run artifact reuse is permitted. Component failures do not prevent this job from reporting failure. Whole-run cancellation or platform outage can prevent any final job from running; a cancelled or absent `ci-required` blocks landing rather than becoming success.

[GitHub required-check behavior](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks) accepts some skipped/neutral checks and ignores dispatch-run checks for PR requirements. Consequently `ci-required` runs only under the PR/master entry, has no conditional success path, and cannot be replaced by a manual dispatch. [Reusable calls](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows) retain their caller's event. Merge queues are not enabled by this slice; adding one requires its own `merge_group` integration.

Receipts catch missing execution and accidental routing defects. Candidate source controls tests and workflow code, so receipts cannot defeat a malicious author who rewrites both the gate and its evidence. Independent review of CI changes, read-only jobs and owner rules are part of the boundary, not something a self-test proves.

## 5. Fresh Go compilation and dependency caches (CI-03)

Server `race` runs wrapper ID `server-race`, separately from `validate`; both are selected by `server` and have 20-minute job timeouts. `targets.toml` pins its discovery command `go test -race -list '.*' ./...` and its run command `go test -json -race -count=1 -timeout=15m ./...`, both from `server/`; section 6 owns the evidence rules, and `-json` changes only the output framing. Preserve ordinary tests (`server-unit`, the same run without `-race` and `-timeout=15m`), formatting, vet and the key-admission benchmark in `validate`, plus dedicated fuzz, loader, OCSF and interop jobs. [Go's test flags](https://pkg.go.dev/cmd/go#hdr-Testing_flags) define `-timeout` per test binary, with a 10-minute default and zero disabling the alarm. The explicit 15-minute package budget leaves a nominal five-minute difference for setup, fresh compilation, other package work and receipt upload under the job watchdog. Package scheduling and runner load can consume that difference; it is not a guaranteed reserve.

The [native diagnosis run](https://github.com/ricevanta/ricevanta/actions/runs/38344954678/job/115124085215) measures the loader's 248 serial fresh race-binary children at 365.76 seconds: 251.79 seconds at process boundaries, 61.68 seconds in child test bodies and 52.29 seconds in parent preparation/oracle work. Completed top-level tests total 588.94 seconds; five following maximum-manifest branches pass in 1.87 to 2.47 seconds each, then branch 5 has run for 0.441 seconds when the package alarm fires at 600.029 seconds. No race warning appears. The unfinished package still includes branch 6, later tests and all four fuzz seed corpora. For workload context, the agreement test takes 91.96 seconds over the larger extended `parserCorpus(true)`; `FuzzParserQualification` seeds use the ordinary `parserCorpus(false)` subset plus additional seeds. Their remaining execution time and the later-test tail are unmeasured. The extended-corpus timing supplies neither an estimate nor an upper bound for package completion; 15 minutes is a finite execution budget requiring CI confirmation.

The deadline accommodates cumulative required work while keeping failure bounded. Preserve all packages, `-race`, `-count=1`, complete test/seed corpora, serial cold children, fresh caches, default `GORACE`, resource ceilings and success-gated same-run receipts. [Go's race detector](https://go.dev/doc/articles/race_detector) documents the default 1,000-millisecond exit wait; do not shorten it to fit the package deadline. Reject disabled or further enlarged timeouts without reviewed evidence, retries, skipped work, reduced corpora and parallel measurement children. These alternatives either hide failure, weaken coverage or change measurement isolation. A genuine hang can consume more time before failure; final-head PR CI must prove all packages terminate successfully within both deadlines. A timeout increase alone proves neither termination nor race freedom. No runtime authority or new dependency changes; section 11's end-to-end trust path and seven attacker outcomes apply unchanged.

Every Go consumer, including nested children, interop, native qualification and future release builds, sets `GOTOOLCHAIN=local`, `GOFLAGS=-mod=readonly`, `GOENV=off`, `GOCACHEPROG` to the empty string, and a newly created empty absolute `GOCACHE` under `RUNNER_TEMP`. `fresh_go.py --root PATH --env-out PATH` creates a unique directory, rejects symlinks/reuse/nonempty roots, records its path and initial entry count zero, and emits environment assignments. All subprocesses inherit that cache. Compilation may reuse objects within the job only.

`fresh_go.py` emits `GOCACHEPROG=` and every subsequent Go child inherits it. Bootstrap version probes before cache setup explicitly clear it in their subprocess environment and set `GOENV=off`. The selected-run wrapper refuses a nonempty inherited value before discovery and explicitly passes an empty value to all Go children. Policy refuses workflow overrides at every scope and in raw `run`/`shell` text, including unset and `env -u` forms; only the pinned fresh-cache writer may emit it.

[Go cache documentation](https://pkg.go.dev/cmd/go#hdr-Build_and_test_caching) describes the external cache hook; local Go 1.27.2 sources confirm helper selection ([command documentation](/usr/local/go/src/cmd/go/alldocs.go:2404), [cache selection](/usr/local/go/src/cmd/go/internal/cache/default.go:57)). Verify the same behavior on pinned Go 1.27.1 with a helper that records invocation and offers prior compiled output: the unsafe control invokes it, while admitted probes, direct Go steps, wrapper discovery/run and nested children never do. No setup action runs (section 8), so no Go cache artifact restore and no fallback to a home cache exist. Run `go mod download` and `go mod verify` in a fresh per-job module directory.

`-count=1` disables test-result reuse, not compiled-object reuse; [Go's command reference](https://pkg.go.dev/cmd/go#hdr-Build_and_test_caching) distinguishes them. A two-run control populates a real prior Go build cache with a marker-producing fixture, then places that cache at the restore location and proves the next job starts empty and never reads that location or executes its marker. First prove the unsafe restore fixture exposes the cache, so an inert marker cannot make the negative control pass. Check actual environment and workflow restore paths as well as unit behavior.

Cargo keeps dependency-download caching only, never `target/`. Cache registry index and `.crate` archives, discard restored extracted `registry/src`, verify archive SHA-256 against Cargo.lock, and extract into a fresh source root. Set a fresh `CARGO_TARGET_DIR`. A modified archive must fail before compilation. [Cargo fetch](https://doc.rust-lang.org/cargo/commands/cargo-fetch.html) defines locked fetch behavior. Console keeps frozen dependency resolution but restores no `node_modules` or build output. Tag builds restore and save no cache of any kind.

## 6. Execution proof (CI-01 and CI-08)

`scripts/ci/run_selected.py --id ID --evidence DIR` owns command execution, discovery and result verification. Workflows run it as `python -B scripts/ci/run_selected.py --id ID --evidence "$RUNNER_TEMP/evidence"` with the admitted Python. IDs resolve through `targets.toml`; no command string is accepted. It streams stdout/stderr into CI logs, retains raw output and inventories under a new hex-named directory per ID, refuses an existing one, uses argument arrays and returns nonzero for child failure or incomplete evidence. A verified run writes `verified.json` with the ID, mode, directory, commands, exit status, summary and the `GITHUB_RUN_ID`, `GITHUB_RUN_ATTEMPT` and `GITHUB_SHA` values. A receipt lists a selected check ID only when that record exists and its run ID, attempt and SHA equal the route's `runId`, `runAttempt` and `testedSha`. `--list` prints every ID with its discovery and run commands, and every skip allowance with its reason and proof.

Fixed IDs are `server-unit`, `server-race`, `key-admission-bench`, `go-fuzz:<package>:<target>`, `loader-extended`, `loader-repeat`, `loader-fuzz`, `loader-gate-b-extended`, `ocsf-native`, `agent-unit`, `spool-extended`, `batch-extended`, `interop-unit`, `interop-race`, `console-unit`, `console-component`, `console-csp`, `console-csp-webkit` and `console-fuzz`. Other leaf checks (format, schema, license, build and bootstrap) have explicit IDs in `inventory.py`; each leaf has a closed required check set. The inventory changes with any added check.

`targets.toml` holds each ID's mode, working directory, packages or Cargo arguments, flags and expected names. `check_policy.py` pins, for every non-fuzz ID, the exact discovery and run command strings, the `(working directory, mode)` pair and the proof fields: benchmark operations, Rust seed and case count, loader marker and sample count, and the interop tests, helpers, subtests and child records. Fuzz IDs always run in `server` in `go-fuzz` mode. `run_selected.py` refuses a working directory that is not one top-level path component; the policy refuses a row it does not pin. Build scripts compile zstd's C sources through the `cc` crate, which reads compiler, archiver and flag variables in four forms: `<var>_<target>`, `<var>_<target_with_underscores>`, `HOST_<var>` or `TARGET_<var>`, and `<var>` ([cc documentation](https://docs.rs/cc/latest/cc/)). This is a partial tripwire, not a closed gap: a byte computed at run time, an integer literal such as `0x16` or `22`, data from `testdata` or embedded files, and assembly sources pass it. Section 11 accepts that residual. Legitimate protocol vectors that contain the TLS handshake or DER IA5String value use byte-slice integer literals.

The parent checks exact key equality, uniqueness, finite numeric counters, existing bounds, the call count each mode implies and successful named subtest events. Preserve cold-child isolation and the existing measurement accounting; this slice changes proof, not resource limits.

Every parser has positive outputs captured from the pinned runner or reporter, including multi-package Go modules with a test-free package, examples and sub-benchmarks, and negative controls for zero matches, rename, skip, truncation, duplicate result, failing child and missing measurements. [Platform support](../platform-support.md) qualifies macOS 27 and 26, and macOS 15 is outside that window. `macos-26` is the newest generally available Apple silicon image; macOS 27 runs only under the [`xcode-27` label](https://github.com/actions/runner-images/blob/main/images/macos/xcode-27-arm64-Readme.md), a public preview ([runner images](https://github.com/actions/runner-images#available-images)), and required leaves use generally available images, which GitHub's [image definitions](https://github.com/actions/runner-images#ga) cover with its service-level agreement. The macOS payloads do not change: the Python build wraps the python.org `macos11` package, the Go, Rust, Node and pnpm archives target `darwin-arm64`, and WebKit keeps the build in [Payloads and browser hosts](#payloads-and-browser-hosts).
- `windows-2025` serves the [Windows Server 2025 with Visual Studio 2026 image](https://github.com/actions/runner-images/issues/14017), the same image as `windows-2025-vs2026`, so the label and payloads stay.
- No job uses `ubuntu-22.04` or `ubuntu-22.04-arm`, which GitHub [is retiring](https://github.com/actions/runner-images/issues/14254). Linux release binaries take their ABI floor from the digest-pinned [Linux build root](linux-build-root.md), never from a runner image. No job uses `xcode-27` or another macOS preview image; add macOS 27 only when GitHub ships a generally available image, through a reviewed label, lock mapping, major-version check and native evidence change.

Benefits: every job whose tools exist runs on the newest image, and the macOS jobs run on a release inside the qualification window. Trade-offs: two Linux x64 identities until the Playwright upgrade, which cost one more `bootstrap` leaf and nine rows whose payloads repeat `linux-x64` digests. Dependencies: GitHub's image lifecycle, which retires each image after announced brownouts, and Playwright's supported hosts. Limits: labels name mutable images, so the bootstrap logs the image version ([release builds section 4](release-builds.md#4-reproducibility-and-toolchain-admission)), and no hosted Windows Server or macOS image qualifies an endpoint configuration. Alternatives rejected: every Linux job on Ubuntu 24.04 until the Playwright upgrade, which ties the image move to an unrelated dependency; the console leaf on Ubuntu 26.04 with the browser builds made for Ubuntu 24.04, which Playwright does not support on that host; `windows-2025-vs2026`, the same image under a second name.

### Toolchain lock and bootstrap step

`scripts/ci/toolchains.lock.json` is the reviewed download authority, validated by the CI schema's `toolchains` branch. Each entry has unique `id`, `tool`, exact `version`, `platform`, HTTPS `url`, positive `size` and lowercase SHA-256, and its digest appears in that payload's licensing row. The lock contains no secrets and cannot be updated automatically during CI.

`platform` names a runner identity from the table above, not only an OS and architecture, because [actions/python-versions](https://github.com/actions/python-versions/blob/main/versions-manifest.json) and Playwright publish separate builds per Ubuntu release. On Linux the bootstrap reads `VERSION_ID` from `/etc/os-release` and refuses a platform whose Ubuntu release differs: `linux-x64` requires 24.04, and `linux-x64-ubuntu26.04` and the release-only `linux-arm64-ubuntu26.04` require 26.04 on `x86_64` and `aarch64` respectively. On macOS it reads the major release from `sw_vers -productVersion` and refuses `macos-arm64` on a major other than 26, so a stale label cannot claim the identity. A payload that is identical across releases, such as the Go, Rust, Node and pnpm archives, appears once per platform with the same digest.

`scripts/ci/bootstrap.py --lock PATH --platform PLATFORM --tools TOOL[,TOOL...] --dest DIR --cache-mode sources|none --env-out PATH` rejects duplicate selections, missing lock rows and unknown platforms. `--tools` names single tools or two groups: `rust`, all five components, of which a partial selection is refused; and `playwright`, every browser row the lock holds for that platform, refused when there is none. `pnpm` requires `node`. `check_policy.py` pins each job's and matrix row's literal `CI_TOOLS`, and every `bootstrap.yml` row selects every lock tool for its host.

The initial [GitHub-hosted runner](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) OS, shell, Git, TLS roots, hashing tools and preinstalled `python3`, used only to run the standard-library bootstrap, are trusted inputs; log their paths/versions and the runner image version. The step uses `python3` because it names the preinstalled interpreter on all three hosts: Ubuntu provides it, Apple [removed Python 2.7 from macOS 12.3](https://developer.apple.com/documentation/macos-release-notes/macos-12_3-release-notes) and the [macOS 26 image](https://github.com/actions/runner-images/blob/main/images/macos/macos-26-arm64-Readme.md) lists only Python3, and [actions/python-versions' Windows setup](https://github.com/actions/python-versions/blob/main/installers/win-setup-template.ps1) links `python3.exe`. On macOS, when that interpreter lives in the Python framework the admitted Python replaces, the bootstrap re-executes under Apple's `/usr/bin/python3` after proving it imports `hashlib`, `ssl`, `tarfile`, `zipfile`, `zlib` and `urllib.request`. That interpreter may lack `lzma`, so every macOS payload is `.tar.gz` or `.zip` and the lock check rejects macOS `.xz`.

Each consuming job runs, first after checkout, the step named `Bootstrap admitted toolchains` with the admission shell, `working-directory: .` and only literal `CI_PLATFORM` and `CI_TOOLS` env taken from the fixed runner matrix:

```sh
python3 -B scripts/ci/bootstrap.py --lock scripts/ci/toolchains.lock.json --platform "$CI_PLATFORM" --tools "$CI_TOOLS" --dest "$RUNNER_TEMP/admitted" --cache-mode none --env-out "$RUNNER_TEMP/tools.env"
```

The next step is exactly `cat "$RUNNER_TEMP/tools.env" >> "$GITHUB_ENV"`, followed by `python3 -B scripts/ci/bootstrap/controls.py evidence` with the same inputs. No other step writes or reads `tools.env` or writes `GITHUB_PATH`, except the validator venv step. Through `env` or `GITHUB_ENV`, no other step sets `PATH`, `GOROOT`, a Cargo or Rust name outside the workflow row of section 6's allowlist, `PLAYWRIGHT_*`, `pnpm_config_*`, `npm_config_*`, `CI_ADMITTED_ROOT`, `RUNNER_*`, loader variables or section 6's C toolchain names.

The env file holds `KEY=VALUE` lines without CR, LF or NUL, and only these names, each written only when its tool is selected:

| Name | Value |
|---|---|
| `PATH` | Admitted directories, then the inherited PATH without Git Bash's own leading entries on Windows |
| `GOROOT` | The admitted Go root, checked against `go env GOROOT` |
| `CARGO_HOME`, `RUSTUP_HOME` | Fresh admitted homes without `bin` or configuration |
| `RUSTUP_AUTO_INSTALL` | `0` |
| `PLAYWRIGHT_BROWSERS_PATH` | The admitted browser registry |
| `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD` | `1` |
| `pnpm_config_pm_on_fail` | `error`, so pnpm refuses a project-pinned version switch |
| `pnpm_config_update_notifier` | `false` |
| `CI_ADMITTED_ROOT` | The destination |

The bootstrap exports no `RUSTC` or `RUSTDOC`: PATH order selects the admitted `rustc` and `rustdoc`, and the evidence step proves it. After this step `python` and `python3` both name the admitted Python. The evidence step proves each tool resolves inside the admitted root through that PATH, and `cargo fmt` and `cargo clippy` through the admitted Cargo home.

`--cache-mode sources` uses the absolute directory `CI_TOOLCHAIN_SOURCES`, holding payload copies named by SHA-256. A present copy is hashed while it is copied from one descriptor into the private download directory; a copy that fails size or digest is an error, never a reason to download. A missing copy is downloaded and verified like any payload, then stored in the directory through a temporary name and an atomic rename. Two users exist: local repetition, and the `bootstrap` leaf's corruption controls (`controls.py corrupt`), which fill a private sources directory, then present truncated, appended and one-byte-changed copies through this mode and require refusal before extraction. Workflow bootstrap steps use `none`, which the policy pins; tag builds never use `sources`.

### Payload admission

Downloads use HTTPS with at most five HTTPS redirects and stop one byte past the recorded size. Only interrupted or short transfers are retried, at most three attempts, each into a fresh file; a complete download with the wrong digest is never retried. All selected payloads are verified for size and digest, then all are inspected, before any extraction, installer or tool runs. Inspection rejects traversal, absolute paths, device and FIFO members, and name collisions after NFD normalization and case folding on every host. It resolves symbolic-link chains virtually (at most 40 hops) so no member is written through a link outside staging. Hard links may name only earlier regular members, and setuid and setgid bits are dropped. Links copied while installing Rust components are rechecked. Use an empty destination; any refusal empties it, with no partial-install fallback. Installed tools run once to prove version and host. Runner tool caches are never consulted.

The Linux Python build names the runner tool cache in each ELF `DT_RUNPATH`, and that cache holds the same version. The bootstrap rewrites each RUNPATH to an `$ORIGIN`-relative path inside the admitted root and proves the interpreter maps the admitted `libpython` with no loader variable. It refuses a rewrite when another dynamic string overlaps the rewritten bytes in either direction, and a malformed ELF file is a typed refusal.

Two Python installs change the host outside the destination; both run only when `RUNNER_ENVIRONMENT` is `github-hosted`, where each job gets a fresh virtual machine, and any other value is a refusal. Workflow `env` cannot set `RUNNER_*`. On Windows the payload wraps the python.org installer, and the image already registers the same release per machine. The bootstrap removes the image's `Python 3.14.*(64-bit)` registrations from the HKCU and HKLM uninstall keys, the `S-1-5-18` UserData products and `HKCR\Installer\Products`, as the payload's own `setup.ps1` does. It refuses when any registration survives or a per-user 3.14 registration exists, then installs per user into the destination with fixed arguments. Registry errors are typed refusals. On macOS the payload wraps the python.org package; the bootstrap removes the image's `Python.framework/Versions/3.14` and installs the package with `sudo -n`. This guard prevents damage to a persistent machine; it is not a defence against a candidate, which already runs code in the job.

The `bootstrap` leaves cold-install every lock payload for their host after one-byte corruption controls prove refusal before any extraction or execution, including installer side-effect sentinels. Tests distinguish bad size, bad digest and unsupported host, and run under every platform identity. Release Task 2 atomically adds its seven `linux-arm64-ubuntu26.04` rows with bootstrap support, policy mappings and native cold-install/corruption proof on `ubuntu-26.04-arm`, using this same interface with `--cache-mode none` for tag jobs. Until then, [licensing](../licensing.md#release-arm64-payload-staging) retains those candidates and the production lock excludes them; schema acceptance alone grants no bootstrap support. SBOM and native SDK additions extend this lock only after their licensing rows exist.

### Payloads and browser hosts

The lock covers Go 1.27.1, Python 3.14.8 and the Rust 1.99.0 distribution components (rustc, cargo, std, rustfmt, clippy) on every lock platform, Node 24.21.0 and pnpm 11.18.0 on both Linux x64 platforms and macOS ARM64, and the Playwright 1.59.1 browser builds where section 6 runs them. No setup action runs; besides same-commit reusable workflows, the policy admits only the checkout, upload-artifact, download-artifact and cache actions at full SHAs. Rust installs from verified components without rustup, and pnpm's tarball runs on the admitted Node through an admitted shim. Use public first-party distribution inputs: [Go download metadata](https://go.dev/dl/?mode=json&include=all), [Python runner builds](https://github.com/actions/python-versions), [Rust distribution code](https://github.com/rust-lang/rustup), [Node release verification](https://github.com/nodejs/node#verifying-binaries), the npm registry's `dist.integrity`, and [Playwright browser distributions](https://playwright.dev/docs/browsers). An upstream checksum fetched during the same install is evidence for lock review, not the runtime authority; the reviewed repository digest is authoritative. No sample hash from the schema examples is an approved payload.

No CI job downloads or installs an operating-system package; the policy rejects `apt`, `apt-get`, `dpkg`, `brew`, `choco` and `winget` installs and `playwright install`. A browser engine therefore runs only on a host whose recorded runner image supplies its libraries, and the bootstrap names any missing library before the engine runs:

- Linux x64 (`ubuntu-24.04`) runs the Chrome for Testing headless shell (Playwright's `chromium-headless-shell`, revision 1217, Chromium 147.0.7727.15) and Firefox 148.0.2 (revision 1511). Every Playwright and Vitest launch is headless, so the full Chrome for Testing bundle is not admitted. The bootstrap checks their `ldd` dependencies against the image before use. That image does not supply WebKit's libraries: [run 38754347093](https://github.com/ricevanta/ricevanta/actions/runs/38754347093) refused `webkit-2272-linux-x64` for missing `libGLESv2.so.2`, `libavif.so.16`, `libevent-2.1.so.7`, `libflite.so.1` and `libflite_cmu_grapheme_lang.so.1`, and Playwright 1.59.1 has no Ubuntu 26.04 build, so the lock holds no Linux WebKit row.
- macOS ARM64 (`macos-26`) runs WebKit 26.4 from Playwright's `webkit-mac-15-arm64.zip`, the same revision 2272 that Linux would use: Playwright 1.59.1 [caps the macOS host at 15](https://github.com/microsoft/playwright/blob/v1.59.1/packages/playwright-core/src/server/utils/hostPlatform.ts), so macOS 26 (Darwin 25) on Apple silicon maps to `mac15-arm64`, and Playwright's own [1.59.1 CI](https://github.com/microsoft/playwright/blob/v1.59.1/.github/workflows/tests_secondary.yml) runs WebKit on `macos-26-xlarge`; its [`browsers.json`](https://github.com/microsoft/playwright/blob/v1.59.1/packages/playwright-core/browsers.json) overrides the revision only for older hosts, and its [registry](https://github.com/microsoft/playwright/blob/v1.59.1/packages/playwright-core/src/server/registry/index.ts) validates host libraries only on Linux and Windows. Every Mach-O file in that build loads only `/System/Library` frameworks, `/usr/lib` libraries and its own bundled dylibs, and the bootstrap rejects any other load command. Playwright's [browser guide](https://playwright.dev/docs/browsers) recommends WebKit on macOS for the closest match to Safari, and Safari on macOS ARM64 is the only WebKit product in the [console browser window](../platform-support.md#browser-coverage).

The Linux `console` leaf (`console.yml` job `validate`) builds `dist/` and checks reproducibility. `python -B scripts/ci/tree_digest.py --root console/dist` then computes the tree digest, which the job exposes as output `dist-digest`, before `console-csp` runs Chromium and Firefox. After the CSP run the job recomputes the digest and fails on any difference, uploads the tree, and only then writes its receipt. The `console-webkit:macos-arm64` leaf (job `webkit`) `needs` that job. It bootstraps `python,node,pnpm,playwright`, runs the [console foundation install finalization](console-foundation.md#21-frozen-install-finalization) and `audit:deps`, downloads the artifact into a fresh `console/dist`, verifies the digest, and runs `console-csp-webkit` against those bytes. All three engines therefore test identical production assets. On tag runs the leaf builds with the tag's build identity, which it derives independently under [release builds section 2](release-builds.md); release Task 3 owns that step in `console.yml`, and other runs use the development identity. This same-run hand-off carries the bytes under test from the job that built them; it is not a compiled-output cache and is never restored across runs. The WebKit leaf builds nothing.

The tree digest is a standard-library computation with a fixed serialization:

- Walk the tree without following links. Every entry must be a directory or a regular file; a symbolic link, special file or path component outside printable ASCII without `\` fails. Dot entries such as `.vite/manifest.json` are included. Directories contribute nothing, so empty directories, which artifacts cannot carry, do not change the digest.
- For each regular file, emit the record `<relative path with / separators>` NUL `<64 lowercase hex SHA-256 of the contents>` LF, encoding the path as ASCII bytes.
- Sort records bytewise by path and print `sha256:` plus the 64 lowercase hex SHA-256 of their concatenation.

The upload uses the pinned [`actions/upload-artifact` v7.0.2](https://github.com/actions/upload-artifact/blob/cf430e030ddbb5b0abf93d22962f4752f3646cd9/action.yml) with name `console-dist-<runId>-<runAttempt>`, `path: console/dist`, `include-hidden-files: true` (its default excludes hidden files), `if-no-files-found: error`, `overwrite: false` and `retention-days: 1`, all pinned in `check_policy.py`. The macOS job derives the same name from its own run ID and attempt, so re-running only that job fails closed, as same-attempt receipts already require. It receives the digest only through step `env` (`EXPECTED_DIST_DIGEST: ${{ needs.validate.outputs.dist-digest }}`), never through `${{ }}` in `run`. `tree_digest.py --root console/dist --expect-env EXPECTED_DIST_DIGEST` requires the value to match `^sha256:[0-9a-f]{64}$` and equal the recomputed digest before any server or browser starts. Both console leaves upload Playwright and Vitest reports, traces and screenshots with `if: always()` as `console-reports-<runId>-<runAttempt>-linux-x64` and `console-reports-<runId>-<runAttempt>-macos-arm64`, with 30-day retention and `include-hidden-files: false`. These names never match `ci-proof-*`.

Both console leaves require `console-install` to run `pnpm install --frozen-lockfile` then `node scripts/finalize-install.ts` in one fail-fast step. `console-audit` runs immediately afterward, before any dependency consumer. The [console foundation contract](console-foundation.md#21-frozen-install-finalization) owns physical installed evidence and preserves full-lockfile OSV on each leaf; its Task 1A qualification gate precedes workflow wiring. The WebKit checks remain `console-install`, `console-audit`, `console-dist` and `console-csp-webkit`; the Linux check set also stays unchanged. `check_policy.py` pins both commands, their order and audit-before-consumer placement, with no conditional step or ignored failure.

Benefits: no operating-system package enters the trust base, WebKit runs where its only console target ships, and the digest binds all engines to one build. Trade-offs: one more macOS job, serialized after the Linux leaf, and Node, pnpm and the WebKit build in the macOS lock. A full route with the footprint unit leaves runs seven macOS jobs: loader Gate A, loader Gate B, OCSF, agent, footprint unit, bootstrap and console WebKit. [GitHub's limits](https://docs.github.com/en/actions/reference/limits) cap a Free plan at 5 concurrent macOS jobs and 20 concurrent jobs in total. A full route already exceeds the total cap, so jobs wait for slots in every full run. Because the WebKit job starts only after the Linux console leaf, it usually finds a macOS slot freed by an earlier leaf; otherwise it adds up to one macOS job's duration, and concurrent PRs compound the wait. The owner accepts this cost. That queued jobs wait rather than fail, and the repository's plan, are verify items: the limits page states only the caps. Limits: hosted runners do not qualify Safari, and the [console foundation](console-foundation.md#production-browser-gate) keeps release browser qualification separate.

Alternatives rejected:

- All three engines on the macOS leaf. Playwright publishes macOS builds of the headless shell and Firefox, but moving them puts every console gate's browser time on the five-slot macOS pool and discards the existing Linux evidence, for no gain in host libraries, which Linux already supplies for those two engines.
- Rebuilding `dist/` on macOS and requiring an equal digest. That needs no artifact transfer but runs native build tools, including `lightningcss-darwin-arm64`, on scarce macOS slots, and a cross-host reproducibility difference would block every console change on a CSP gate. [Release Task 4](../plans/release-builds.md) owns cross-host reproducibility evidence separately.
- Digest-locked Ubuntu packages, because Playwright 1.59.1's [`nativeDeps`](https://github.com/microsoft/playwright/blob/v1.59.1/packages/playwright-core/src/server/registry/nativeDeps.ts) names 51 distinct WebKit packages for Ubuntu 24.04 before their dependencies, including GStreamer plugins and `libx264-164`, which [VideoLAN releases under the GNU GPL](https://www.videolan.org/developers/x264.html), and installing them needs root `dpkg` changes whose version constraints must track every runner image update. [apt-secure(8)](https://manpages.ubuntu.com/manpages/noble/man8/apt-secure.8.html) authenticates archive indexes, not individual `.deb` files, so the lock would still carry every digest and licensing row.
- A digest-pinned Playwright container image, because its full Ubuntu package set and its own Node and browsers would need the same inventory and duplicate admitted payloads.

The Chrome for Testing headless shell's `ABOUT` names Google Chrome and the Terms of Service at `chrome://terms`: the [Google Terms of Service](https://policies.google.com/terms) and the [Google Chrome and ChromeOS Additional Terms of Service](https://www.google.com/chrome/terms/), which apply to the executable code version of Chrome. The console job on `master` installs engines with `playwright install --with-deps chromium firefox webkit`, and in Playwright 1.59.1 the `chromium` name installs both the full Chrome for Testing bundle and the headless shell. The owner accepts both sets of terms for this repository's CI use of both bundles; [project facts](../project.md#ci-browser-builds) record the authorization beside the Semgrep one, and [licensing](../licensing.md) records the terms. The admitted lock admits only the headless shell, so the full bundle and its Widevine module leave CI when this design's bootstrap replaces the `master` install.

## 11. Security trace, benefits and alternatives

The trust path is GitHub event and reviewed base, full Git diff, expected unit inventory, read-only job checkout, admitted tools, fresh compilation, verified test output, same-run receipts, aggregate check, then independent review and owner-enforced landing. No CI job receives enrollment material, organization data, production signing keys or database credentials. CI logs use synthetic fixtures only; endpoint raw sensitive content remains on device except policy-permitted redacted snippets.

| Attacker | Result across routing, compatibility, tool admission, evidence and landing |
|---|---|
| Stolen enrollment token | Gains no repository or CI credential and cannot change a base, digest or receipt. Enrollment authorization remains PKI-02's runtime boundary. |
| Compromised agent host | Can forge local telemetry, not GitHub job outcomes. The host receives no CI key. Runtime attestation/enforcement remains outside these library tests. |
| Compromised console session | Gains only runtime session rights, no CI or repository rights. Exported console data cannot enter workflow commands or expected work. |
| Rogue extension publisher | Cannot change the tool lock or CI inventory through a published extension. If contributing a PR, gets untrusted read-only execution; workflow/test edits still need independent review. No publisher package is executed by the aggregate. |
| Network position between agent and server | Has no authority over CI. On CI download paths, substituted bytes fail pinned digests; blocking downloads causes failure. TLS or matching hashes alone cannot make an unreviewed digest trustworthy. |
| Database writer without signing keys | Cannot rewrite Git objects, Actions receipts or owner rules through runtime rows. Forged runtime authorization remains subject to its separate authority protocol. |
| Server restored from backup | Restores no CI credentials, result authority or signing keys from this slice. Old artifacts/receipts cannot satisfy a different SHA/run/attempt. This does not implement runtime rollback or recovery fences. |

The runner images and action pins of sections 2 and 8, the browser host split, the same-run `dist` hand-off, the universal startup/PATH restrictions, the empty external Go cache hook, the harness-substitution refusals and the host-mutating install guard add no credential or authority, so these seven outcomes apply to them unchanged. The hand-off digest protects the bytes between two jobs of one run; it is not authenticity against the candidate, which builds those bytes itself.

A compromised GitHub administrator, runner image, reviewed action or approved tool payload can defeat this CI boundary. Hash admission prevents replacement after review, not malicious bytes approved in the lock. A malicious PR can falsify its own tests; independent adversarial code review covers CI and harness mutations. Restricting the token limits damage but does not prove source honesty.

The in-job checks detect divergence and accidental bypasses. These deliberate in-job changes remain accepted residuals, because each needs evidently malicious code in the candidate diff and no check running inside a job can stop a step that rewrites what the check reads:

- Execution: a framing byte computed at run time or read from data; a test or step that rewrites `scripts/ci/`, `targets.toml` or the evidence directory before a later step; Cargo configuration or a C toolchain variable written by a step after the wrapper's checks, for example by a build script for a later invocation.
- Validator: a RECORD or venv marker rewritten together with the files it describes; a replaced interpreter or `bash` in any PATH directory; shell indirection (`bash scripts/x.sh`), escaped tokens such as `pi\p`, third-party actions and environment set through them; edits to the base interpreter's own library files after admission.
- Toolchains: disguised downloads and environment writes that the spelling rules miss, such as variable-built names; a PR that changes the lock with matching licensing rows, or the bootstrap itself.

Benefits: one required result covers every PR, evidence exposes omitted work, fresh compilers remove cross-run object reuse, compatibility uses reviewed history, and one Python closure removes divergent validators. Costs: more cold compilation/download time, maintained result parsers, matrix receipts and digest updates. Bound resource use with existing fuzz/property budgets and per-job timeouts; never lower required budgets to hide a timeout.

Alternatives rejected: workflow-level path filters can leave required checks absent; API polling across independent runs admits stale results; always-success wrappers hide skipped jobs; dispatch cannot satisfy the PR gate; revision-only catalogue checks miss changed semantics; setup-action pins alone leave payload bytes unpinned; compiled caches retain the audit's reuse threat. A dedicated external attestation service adds accounts and is unnecessary for this slice.

## 12. Release-build handoff

Their CLIs and the exact bootstrap, apply and admission steps are fixed above. `scripts/ci/check_policy.py --root PATH` checks workflow safety, input coverage, matrices, allowed caches and bootstrap coverage, and exits nonzero with each offending path. It exposes `check(root: pathlib.Path) -> list[str]` for fixture-based release tests.

Release jobs call these helpers and reusable workflows with the same route contract, add their explicit units to inventory, and select full mode for tag builds. `release-ready` is a separate tag aggregate using the same verifier, not an alternate branch status named `ci-required`. Ordinary CI proof is a prerequisite, never permission to publish or sign. Any interface change requires this spec and the release consumer plan to change together.
