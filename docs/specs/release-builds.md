# Release builds

CI builds reviewable development artifacts from one source revision and one product version. A tag rebuild publishes a GitHub pre-release only when its complete required artifact set and checks pass. The [first-install gap list](../analysis.md#31-first-installable-build) owns missing runtime work; this specification does not turn libraries into services or qualify endpoint support.

Authorities: SH-04, AG-07, AG-09 and PF-04 in [decisions](../decisions.md), [architecture](../architecture.md) sections 1, 4 and 5, [platform qualification](platform-qualification.md), and [implementation plan](../plans/release-builds.md). All blueprint features remain required at v1.0.0 except the two capabilities listed for v2.0.0 in [platform support](../platform-support.md).

## 1. Boundary and prerequisites

This slice owns build identity, native build orchestration, unsigned archives, checksums, a local software bill of materials (SBOM), evidence retention and tag publication. It consumes reviewed executable entry points, console serving, package lifecycle and footprint contracts. It does not define enrollment APIs, authority recovery, the updater's signed manifest or native sensor mechanisms.

The console foundation exists. Agent and server entry points, deployment and native packages do not. Contract and console CI tasks can land first. Native release jobs remain unready until their prerequisites exist; neither a successful library build nor an executable that only prints a version satisfies the artifact contract. A missing required executable, test, package recipe or benchmark fails its job. Do not use path-existence conditions to turn missing work into a successful release.

Initial build artifacts are portable archives for developer inspection and foreground runtime tests once the runtime exists. The first installed, enrolling test build additionally needs the package and enrollment gaps in the analysis. Native package publication is enabled only after its separate lifecycle design and plan pass review. Unsigned alpha artifacts are not AG-07 update inputs or a completed v0.1.x milestone.

## 2. One product version

A root `VERSION` file contains the next planned stable core, initially `0.1.0`, with one trailing newline. It is a build input, not an independently released component version. A release tag is the authority for released identity. Accept only `v<core>-alpha.<N>`, `v<core>-beta.<N>` or `v<core>-rc.<N>` in this slice, with a positive decimal N, no leading zeroes, no build metadata and core equal to `VERSION`. Reject stable tags in the pre-release workflow. [SemVer](https://semver.org/spec/v2.0.0.html) owns precedence; a separate future release-manifest counter owns AG-07 downgrade prevention.

| Source | Product version | Publication |
|---|---|---|
| Tag `v0.1.0-alpha.1` | `0.1.0-alpha.1` | GitHub pre-release, explicitly unsigned development |
| Untagged master commit | `0.1.0-dev.0+g<FULL_SHA>` | Actions artifact only |
| Pull request integration commit | `0.1.0-dev.0+g<FULL_SHA>` | Actions artifact only; channel `pr` |
| Dirty local checkout | Rejected by release-build tooling | Manual local builds are outside this build-record contract |

`FULL_SHA` is the full lowercase 40-character commit object ID of the checkout, never a branch name. Build metadata does not affect SemVer precedence. The build record carries channel and commit separately, so PR artifacts cannot masquerade as a release. A PR records its tested integration SHA, not a claimed head SHA. A rerun of the same source has the same embedded identity. Workflow run IDs and run times belong in evidence, never compiled bytes.

A single `scripts/release/version.py` derives and validates values before any component builds. Tag builds resolve the existing tag to a commit, require that exact checkout, and verify the commit belongs to protected `master`. Fetch full history explicitly; no fallback to `git describe`, the nearest tag, or a default version after an error. Release preflight rejects tags whose core differs from the tracked manifests' core.

Each verification job independently derives its expected identity from the validated checkout and triggering event before reading candidate records or artifacts. `commit` is the checked-out full SHA matched to the event's tested commit; `channel` follows the validated PR, master-push or tag-push event; `version` follows the table and checked `VERSION` core; `sourceEpoch` is that commit's integer timestamp. The job supplies these four fields in a job-owned JSON file outside candidate directories through `verify.py --expected-identity PATH`. Validate that file against the schema's identity definition. Never take expected values from downloaded metadata, records or embedded identities, even when those candidates agree with one another. The publisher derives the same fields with its full-SHA-pinned logic from the validated checkout and event, without executing artifacts or build scripts.

- Go: generate an ignored `server/internal/buildinfo/generated.go` with constants `Version`, `Commit`, `Channel` and `SourceEpoch`. `ricevanta-server --version` reports version and commit; its runtime exposes the same values through its reviewed health/version contract.
- Rust: pass `RICEVANTA_VERSION`, `RICEVANTA_COMMIT`, `RICEVANTA_CHANNEL` and `SOURCE_DATE_EPOCH` to reviewed build scripts and embed checked constants. Every executable, including the updater when available, reports the same product identity. Workspace package versions remain the core in `VERSION`; they are not the release label.
- Console: generate an ignored typed `console/src/generated/build-info.ts`, consumed as static module data, and a public `build-info.json` containing only those four public fields. The shell displays the version and commit in its existing information surface. Never expose build secrets through Vite variables; [Vite documents their client visibility](https://vite.dev/guide/env-and-mode).
- First-party extensions and the browser extension consume the same identity when their reviewed build recipes exist. Preserve exact SemVer in the packaged metadata even when a browser or native package format needs a numeric projection. Third-party versions and interface versions remain independent (EXT-07).

`VERSION`, Cargo workspace core and the private console package core must agree. Generation must not rewrite tracked lockfiles. A drift check fails before compilation. `SourceEpoch` is the integer commit timestamp, not the build clock. `build-info.json` is a projection of the build record's `identity`, validated against the same definition in [the schema](../../schemas/build/v1/build-record.schema.json).

## 3. Required outputs and native jobs

Use standard GitHub-hosted runners. [GitHub's runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) lists free standard public-repository runners, including native Apple silicon and Linux ARM64. No larger paid runner or added hosting service is needed.

| Job / target | Runner | Required output after runtime prerequisites |
|---|---|---|
| `agent-macos-arm64` | `macos-15` | `ricevanta-agent`, target `aarch64-apple-darwin` |
| `agent-windows-x64` | `windows-2025` | `ricevanta-agent.exe`, target `x86_64-pc-windows-msvc` |
| `agent-linux-x64` | `ubuntu-22.04` | `ricevanta-agent`, target `x86_64-unknown-linux-gnu` |
| `server-linux-x64` | `ubuntu-22.04` | `ricevanta-server`, Linux amd64 container archive |
| `server-linux-arm64` | `ubuntu-22.04-arm` | `ricevanta-server`, Linux arm64 container archive |
| `console-build` | `ubuntu-22.04` | Production console assets, compressed sidecars and notices |

The plan stages this full output contract: Task 3 validates the unpacked console tree; Task 4 builds and compares unpacked native binaries and validated console assets across these six jobs. Task 5 consumes the reviewed image/deployment contract and both clean build passes to produce and compare images, distributable archives and SBOMs, then verifies the complete artifact set. Task 4 has no image or archive prerequisite.

Each recipe records its minimum OS, deployment target, linked libraries and ABI requirements in evidence. A hosted Ubuntu build does not prove compatibility with every eligible Linux distribution, and a Windows Server runner does not qualify Windows 11. The native package slice must select compatible per-distribution build roots and run loader/install probes across the platform manifest; missing ABI coverage blocks that support claim.

Server ARM64 is already required by architecture section 5; it does not add a Linux ARM64 endpoint support claim. Build each image natively, load and smoke-test it on that architecture, then export a Docker-loadable archive. No registry account or push is required. Compose consumes the image ID from the build record after `docker load`, never a floating registry tag. Images embed the identical validated console tree served by the real server and preserve its production CSP. Export the standalone console bundle too.

A checked-in recipe inventory under `scripts/release/` lists every first-party executable, browser build, extension, package and target actually introduced by reviewed slices. Every added component must add its recipe and tests in the same PR. Compare Cargo binary targets, Go command directories, browser manifests and first-party extension directories against that inventory. Unknown components fail; do not silently build only the six rows forever. This slice's mandatory floor is the six rows above. An updater or native helper required by a package cannot be omitted from that package's inventory.

Archive names use `ricevanta-<component>_<version>_<target>_unsigned-dev.tar.gz`, or `.zip` on Windows. Server images use `ricevanta-server_<version>_linux-<arch>_unsigned-dev.image.tar`. Each archive contains the payload, public identity and applicable LICENSE/NOTICE files. Native installers use the same basename with their package extension when their lifecycle slice enables them. No enrollment token, organization trust root or deployment secret enters an artifact.

## 4. Reproducibility and toolchain admission

Use exact existing language pins from the component manifests, reviewed full-SHA action references and digest-pinned container bases. The reviewed `scripts/ci/toolchains.lock.json` from [CI hardening section 8](ci-hardening.md#8-one-validator-environment-and-admitted-tools-ci-04-to-ci-07) records the HTTPS URL, exact version, platform, byte size and SHA-256 of every downloaded toolchain and build tool: Go, Rust distribution components, Python, Node, pnpm, SBOM tooling and any native SDK additions. Verify bytes before extracting, installing or executing them. A setup action's commit pin does not authenticate its downloaded payload.

The initial shell, OS utilities and GitHub runner image form the bootstrap trust boundary. Record runner image version, OS, architecture, Xcode/SDK or MSVC/SDK versions and compiler/linker versions. Validate required native tool versions before building; additions fetched by the workflow require lock entries. GitHub labels are mutable images, not immutable toolchains. Reproduction means two clean builds with the same recorded toolchain/image identity; it is not a promise of byte equality across arbitrary future runner images.

Authoritative build and test jobs never restore compiled outputs: no `target/`, Go build or test cache, compiler cache, `node_modules`, Vite output or precompiled extension code from another run. Set empty per-job `GOCACHE` and `CARGO_TARGET_DIR`; use fresh directories for each reproducibility pass. Disable setup-go's combined cache. Tag runs restore and save no Actions caches, including dependency caches. Ordinary CI may cache downloaded source archives only when the package manager rechecks recorded content hashes before use. Keep the source dependency and compiled-output paths distinct.

| Build | Required settings and checks |
|---|---|
| Go | `GOTOOLCHAIN=local`, `-mod=readonly`, `-trimpath`, `-buildvcs=false`; generated identity provides provenance. Run `go mod verify`. Freeze CGO, compiler and system-library choices per executable recipe; do not force CGO off for a future consumer that requires it. [Go build flags](https://pkg.go.dev/cmd/go) |
| Rust | `cargo build --locked --release --target <target> --bin ricevanta-agent`; `CARGO_INCREMENTAL=0`; fixed release profile, no `target-cpu=native`, path remapping for checkout and temporary roots, pinned C toolchain for zstd. Preserve panic semantics selected by the runtime. [Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html), [rustc options](https://doc.rust-lang.org/rustc/codegen-options/index.html), [path remapping](https://doc.rust-lang.org/rustc/command-line-arguments.html#--remap-path-prefix-remap-source-names-in-output) |
| Console | Frozen pnpm install, script suppression and audits from [console foundation](console-foundation.md); static identity generation before each clean build; retain both clean builds and compare sorted path/digest lists |
| Archives/images | Sorted paths, fixed permissions and owners, no absolute paths, fixed entry times from `SourceEpoch`, gzip header time zero; deterministic image config/layers with fixed base digests. Do not strip security metadata to make comparison pass |

Compare unsigned payload bytes and console trees from two separate clean roots on each native target in Task 4; Task 5 independently packs both passes and compares normalized archive/image outputs and SBOMs. A mismatch fails and retains both manifests and the diff. Signatures, notarization tickets and trusted timestamps added by a later offline process change bytes; rehash the final packages and qualify those exact bytes separately.

## 5. Build records, checksums and SBOM

[Build record schema](../../schemas/build/v1/build-record.schema.json) defines diagnostic metadata, not an update authorization. Validate its example with `python3 -B -m jsonschema -i schemas/build/v1/example.json schemas/build/v1/build-record.schema.json` from the repository root; the plan adds semantic artifact verification. [The example](../../schemas/build/v1/example.json) uses synthetic hashes and validates only the contract; it is not a real build. Version, commit, channel, target, artifact name, byte count and SHA-256 must agree with actual outputs. An image-producing record also requires `image.id` (the Docker image/config SHA-256), `image.platform` and the native base manifest digests in `image.baseDigests`; verify the image ID and platform by inspection after loading, never from a supplied label. Verify base manifest digests against the reviewed base lock and fetched native manifests before building, and retain that evidence; image inspection alone cannot recover a base registry manifest digest. Verify layer ancestry when the recipe requires it. [The image example](../../schemas/build/v1/example-image.json) is synthetic too. Validate it with the same command using its filename. Missing image metadata on an image recipe or image metadata on a non-image recipe fails semantic verification. A record lists payload and SBOM artifacts, never its own hash or `SHA256SUMS`; the checksum file covers the record without a hash cycle. The semantic build verifier compares records against a closed recipe inventory and files, rejects missing, duplicate or extra artifacts, and requires every record and embedded identity to match all four independently derived expected fields: `version`, `commit`, `channel` and `sourceEpoch`. Per-field mismatch controls and a complete self-consistent PR artifact set offered to a pre-release verifier must fail even when candidate hashes and identities agree. Schema validation alone cannot establish those facts.

Emit sorted `SHA256SUMS` for every published payload, image archive, SBOM, build record and evidence archive, excluding only `SHA256SUMS` itself. Hash final bytes after packing. Use basename-only entries, lowercase hex and LF. Reject paths, links, duplicate or case-colliding names, malformed hashes and an incomplete set. The publisher recomputes all hashes independently after download; GitHub's artifact digest check is useful but is not the Ricevanta publication gate. [Artifact documentation](https://docs.github.com/en/actions/tutorials/store-and-share-data) describes the service digest behavior.

Generate an SPDX JSON SBOM locally with [Syft](https://github.com/anchore/syft), licensed in [licensing](../licensing.md). Disable update checks and network enrichment; use only the staged source, installed locked packages, binaries and image archives. Record tool version and input digests. Use stable document identity from source/target digests, creation time from `SourceEpoch` and sorted package/relationship output; normalize only nondeterministic generator metadata before final hashing. Compare two SBOM outputs as well as payloads. Reconcile Go modules, Cargo.lock, pnpm's resolved closure, native libraries, base-image packages and every shipped first-party extension against the SBOM; missing entries fail. Keep build-only and shipped dependencies distinguishable and retain license notices. An SBOM is an inventory, not a signature or proof that vulnerabilities are absent. No Anchore account, hosted SBOM service, Sigstore or transparency service is required.

Actions retains PR/master payloads for 14 days and build/failure evidence for 30 days. Tag-run staging lasts 30 days; GitHub release assets are the retained distribution copy and have no automatic expiry in this design. The owner sets repository retention high enough for those periods. Expired staging requires a fresh tag rebuild, never recovery from a PR artifact. [GitHub retention controls](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/remove-workflow-artifacts) govern Actions storage.

## 6. Workflow trust and required checks

Builds join the PR/master entry and reusable workflows defined by [CI hardening](ci-hardening.md). Its sections 2 to 4 own triggers, cancellation, routing and `ci-required`; section 6 owns execution evidence, including native matrix receipts, selected tests, fuzz mutation counts and nested measurements. A dispatch result cannot satisfy the PR required check. Release jobs add their units and consumer inputs to the shared inventory rather than creating a second branch aggregate.

Tag builds select the full set, including ordinary, split race, fuzz, interop, browser, schema, license, compatibility and footprint jobs. An independent `release-ready` aggregate depends on all of them plus artifact verification in the same run and tested SHA. Consume the exact helpers and contracts in [CI hardening section 12](ci-hardening.md#12-release-build-handoff), including full tag routing, reviewed-base catalogue comparison, the single Python closure and digest-checked bootstrap. Unresolved CI audit fixes block this slice's dependent jobs.

Each agent build runs the AG-09 core/helper footprint harness on its native hosted runner. The runtime slice must supply a reviewed harness, per-OS metrics, budgets and signed-off initial baseline before the first executable recipe is enabled. With no earlier release, record an explicit initial baseline and enforce absolute budgets; never pass a missing baseline as a zero regression. Later comparisons use the retained last release baseline on a matched environment. Sensor measurements, power loss, Secure Enclave/TPM and driver qualification remain real-machine work; run every test that hosted CI can support, with no self-hosted runner exposed to PR code.

Default token permissions are `contents: read`; checkout never persists credentials. Build/test jobs have no release, signing, environment or deployment credentials. Full-SHA pins apply to every action and reusable cross-repository workflow. Do not use `pull_request_target` or privileged `workflow_run` promotion. Event strings enter scripts as validated arguments or environment values, never interpolated shell code. [GitHub workflow permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions).

## 7. Tag publication and owner settings

The tag workflow triggers on `push.tags: ['v*']` and validates the exact pre-release grammar before work. An owner creates the tag on an approved `master` commit. A release attempt checks that the tag exists, resolves to the event commit, belongs to master, and has no published release. The workflow never creates, moves or repairs a tag.

1. Rebuild the tag in clean native jobs under sections 3 to 6. Concurrency groups by tag, with `cancel-in-progress: false`.
2. Verify every staged artifact and `release-ready` result for this run and commit against the independently derived expected identity in section 2. The expected set is fixed before build, never inferred from whatever files arrived.
3. A fresh `publish` job receives only the verified artifacts from this run. It does not execute artifacts or build scripts. Only this job has `contents: write`, with all other token permissions absent. Its full-SHA-pinned publisher logic independently derives the expected identity, parses every record and embedded identity to check all four fields, validates the set and hashes again, and rechecks the remote tag immediately before publication.
4. Create a draft release for the existing tag with `prerelease: true` and `make_latest: false`. Upload all expected assets using the Releases API, read back their names, sizes and hashes, then publish the draft only after exact equality. [Releases API](https://docs.github.com/en/rest/releases/releases), [asset API](https://docs.github.com/en/rest/releases/assets).
5. If upload or verification fails, leave the draft unpublished. A retry may resume only an unpublished draft for the identical commit and exact byte set; conflicting assets fail without overwrite. A published pre-release is never mutated by reruns. Changed bytes require a new tag and version.

The release text names the version, source SHA, unsigned status, included components, missing roadmap capabilities and testing instructions. It states that checksums detect changed bytes but do not authenticate a publisher independently of GitHub. A compromised GitHub owner or publisher token can replace unsigned assets; offline signing is the later trust boundary.

Owner settings, verified before enabling publication:

- Protect `master` with exact `ci-required` from GitHub Actions and current integration-state checks; separate any review bypass from enforcement of CI. Preserve force-push and deletion protection.
- An active tag ruleset targeting `v*` restricts creation to the release owner. Use a separate ruleset with no routine bypass for tag updates and deletions, so permission to create does not grant permission to move tags. Prove an unauthorized creation, tag move and deletion each fail.
- Do not assume a tag ruleset runs branch CI before tag creation. The release workflow independently requires master ancestry and reruns its complete gates. Rulesets govern refs, not the bytes of release assets. [Available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets), [creating rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository).
- Restrict workflow edits and release write access to reviewed maintainers; require full-SHA actions and read-only defaults. Allow artifact retention of at least 30 days. Record the actual settings and denial tests as release evidence, without claiming this document configured them.

## 8. Signing and installation boundary

CI holds no offline release root or successor private key, extension publisher key, Apple identity or Microsoft signing key. CI performs no publisher or release signing. Apple documents [automatic ad hoc signing for Apple silicon](https://developer.apple.com/documentation/xcode/embedding-a-helper-tool-in-a-sandboxed-app). The linker may emit that local Mach-O signature; that is not a Developer ID identity or an AG-07 signature. Never label such bytes signed releases. Platform development signing, if later needed for sensors, belongs to a separate reviewed lab procedure with a recorded identity.

Before an artifact is called signed: offline maintainers verify the source and complete build evidence, obtain the platform signatures required by [project facts](../project.md), then hash the final bytes and sign the packages and expiring release manifest with the offline AG-07 keys. A verifier must check the compiled-in trusted release key, final hashes, target, expiry, monotonic manifest counter and required OS signatures before admission. First-party extension and index signatures use their separate offline publisher key. The exact release payload schema, key transition, freshness, rollback record and ceremony remain a separate blocking spec and plan. This build record cannot substitute for them.

AG-12 selects native packaging: macOS `.pkg` with launchd and the host app when needed, Windows per-machine `.msi` with Services, Linux `.deb` and `.rpm` with systemd. Their separate lifecycle slice owns paths, service identities, ACLs, atomic replacement, uninstall authorization, rollback and package-manager version mapping. A numeric MSI version cannot carry SemVer prerelease text; [Microsoft limits ProductVersion](https://learn.microsoft.com/en-us/windows/win32/msi/productversion). Preserve full product identity inside every package and define a collision-free numeric mapping before MSI publication, not an improvised conversion in CI. Packaging tools require license rows before use; no packaging service or new vendor registration is allowed.

Tester procedures for development artifacts:

| OS | Inspection now; installation after package lifecycle gate |
|---|---|
| macOS ARM64 | Verify SHA-256, extract the native archive for foreground tests. For an unsigned `.pkg`, use Apple's per-item Open Anyway path if local policy permits, then Installer with administrator approval. Never globally disable Gatekeeper or SIP to install the core. Unsigned core testing cannot exercise entitlement-gated system extensions. [Apple guidance](https://support.apple.com/en-us/102445) |
| Windows x64 | Verify with `Get-FileHash -Algorithm SHA256`, extract ZIP for foreground tests. Install the unsigned user-mode MSI with administrator approval using `msiexec /i <package> /norestart`; local application control may refuse it. Use a dedicated test policy or produce a signed package instead of weakening production policy. No unsigned driver is loaded. [msiexec](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/msiexec) |
| Linux x64 | Verify with `sha256sum -c SHA256SUMS`, extract archive for foreground tests. After package qualification, use `sudo dpkg -i ./<package>.deb` after installing its declared dependencies, `sudo dnf install ./<package>.rpm` or `sudo zypper install ./<package>.rpm` on the matching distribution. No downloaded root shell script; no global signature-check disable. Package-manager trust policy may require a locally signed package. [Debian](https://www.debian.org/doc/manuals/debian-reference/ch02), [Fedora](https://fedoraproject.org/wiki/User_Guide_-_Managing_Software), [openSUSE](https://manpages.opensuse.org/Leap-16.0/zypper/zypper.8.en.html) |

A manual unsigned install is an explicit development path only. It never causes the updater to accept unsigned bytes or removes its signature gate. Testers receive enrollment configuration separately through the root/SYSTEM-only path in [PKI design](../design/pki.md), never through shell arguments, CI output or a baked image. These alpha limits end by v1.0.0; the full signing, updater and platform gates remain required.

## 9. Real-machine handoff and attacker outcomes

The tester needs a disposable eligible machine, administrator access, a recorded OS/security configuration, verified exact artifacts, and a reachable test server with PostgreSQL, independent authority storage, blob volume, DNS, time and pinned trust configured. Compose and first-start setup need their own reviewed deployment slice. No enrollment test runs until the journal, issuer, approval and device-protocol prerequisites pass. The software-key stage ends at v0.3.x under the roadmap; it does not establish hardware-backed identity.

The handoff records package/image hashes, source SHA, product version, toolchain/runner evidence, signature state, server migration/configuration identity without secrets, test-suite revision and every case result. Map install, token approval, mTLS check-in, renewal, restart, uninstall and update cases to [platform qualification](platform-qualification.md) sections 2, 3, 6, 7 and 8. Hosted smoke tests and development signatures supply diagnostic evidence only. Qualified state still requires the production packages and complete required-unit coverage.

The protocol is: reviewed source and owner-created tag → isolated builds → verified artifacts → unprivileged tester download → explicit administrator install → separately delivered root pin and token → locally generated key/CSR → jobs-authorized issuance → mTLS. A production update adds offline release/OS signing → core mTLS download → authenticated local staging → independent updater verification → package install → local health check and retained-package rollback. All runtime steps retain their existing blockers.

| Attacker | What the attacker gets and what remains required |
|---|---|
| Stolen enrollment token | A single-use token permits a scoped request and a race against the legitimate device, with CSR-bound approval where required and one-use consumption. A telemetry-only multi-use token may admit multiple attacker-controlled telemetry identities without approval when configured that way. The Windows imaging exception admits only pending OMA-DM requests until approval. No class permits hardware-ID-only takeover, broader group authority or release signing. Enrollment remains blocked on the executable authority protocol |
| Compromised agent host | Can abuse its local device identity and falsify local evidence within that host's privileges. Does not obtain CI or offline keys or another device's authority. Root/admin limits remain those in platform support; build integrity cannot repair a compromised host |
| Compromised console session | Gets that principal's API scope and may request allowed work; protected operations still need their bound approvals. Cannot publish GitHub releases, mint offline signatures or relax the updater check through console state. Runtime session/approval implementation is a separate prerequisite |
| Rogue extension publisher | Can sign its own packages only; cannot add first-party build recipes, acquire release keys or bypass approved prefixes, grants and tombstones. CI never executes submitted extension packages to decide publication; first-party content still needs its separate offline publisher signature |
| Network position between agent and server | Can delay or deny traffic; pinning protects enrollment and mTLS protects later traffic. Unsigned artifacts downloaded manually rely on authenticated GitHub access and independent source review, not AG-07. Checksums delivered by the same compromised channel add no authenticity. Production updater signatures protect code after transport compromise |
| Database writer without signing keys | Can corrupt stored blobs, rows and availability but cannot sign releases. Updater rejects altered/unsigned packages. Forged enrollment state must fail against the independent committed authority projection; unresolved BE-12 means no secure enrollment claim yet |
| Server restored from backup | Cannot move GitHub tags or endpoint release floors. Restored tokens/approvals stay unusable across the sealed recovery and epoch transition; release bytes require the same updater verification. Lost independent journal evidence leaves serving sealed. No debug restore flag is introduced |

## 10. Benefits, limits and alternatives

Benefits: one source identity across components, native CI before scarce machine testing, no new hosted service, reviewable artifacts and a clear offline-signing boundary. Costs: clean builds repeat compilation, dual server architectures add CI work, local SBOM reconciliation and separate package qualification require maintained tests.

Dependencies for unsigned archive publication: reviewed executable entry points, console serving, complete CI audit fixes, footprint harness/baseline and native image/deployment build contracts. Missing members of that set fail release readiness. Native installed enrollment additionally needs package lifecycle, server setup and enrollment/authority contracts; signed updates additionally need the offline release protocol. An archive build may start a real service in its reviewed sealed state, but may not implement or enable an authority consumer whose contract is blocked. Limits: mutable runner images, unsigned artifacts, unqualified sensors and unresolved authority recovery prevent production support claims.

Rejected: cross-compiling the required endpoint matrix instead of native execution; promoting PR binaries; restoring compiled caches; putting offline keys in CI; a registry or online signing service; calling archives installers; a no-op binary to satisfy the release job. Native packages follow their lifecycle contract, and a container archive serves the existing Compose design without registry dependence.

## 11. Questions for prerequisite slices

- Which proved authority fence and exact enrollment/renewal schemas close the BE-12 and PKI runtime gates?
- Which native package lifecycle and numeric version mapping prove install, update, rollback and removal on each required OS?
- Which per-distribution build roots and linkage choices meet every eligible Linux ABI, and which measured core/helper baseline starts AG-09?
- Which exact Syft release and complete toolchain/base-image digest set pass the audited bootstrap and license checks?

These questions block their named consumers; they do not authorize fallback security behavior. The build-contract and existing-console tasks can proceed within their stated boundary.
