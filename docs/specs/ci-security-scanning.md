# CI security scanning

Every PR and master push requires Gitleaks secret detection, Semgrep Code static application security testing (SAST), and Semgrep Supply Chain software composition analysis (SCA). Gitleaks is the required repository and history secret scanner. The Semgrep Secrets product is forbidden. SH-06 owns the choice; [CI hardening](ci-hardening.md) owns routing and receipts. [The plan](../plans/ci-security-scanning.md) defines implementation tasks. This document specifies work, not evidence that the scanners pass.

## 1. Boundary and admission

Add two direct leaf jobs, `gitleaks` and `semgrep`, to `.github/workflows/ci.yml`. Both use `ubuntu-26.04` ([CI hardening section 8](ci-hardening.md#runner-images-and-lock-platforms)), `contents: read`, the admitted checkout action, `persist-credentials: false`, full Git history and the route's exact `testedSha`. Each runs on every accepted event, including documentation-only PRs. Keep all native component checks and the console OSV audit. Linux scanner execution does not establish endpoint platform support; [platform support](../platform-support.md) remains authoritative.

Use the standalone [Gitleaks CLI v8.30.1](https://github.com/gitleaks/gitleaks/releases/tag/v8.30.1), without the licensed organization Action. Use [Semgrep 1.178.0](https://github.com/semgrep/semgrep/releases/tag/v1.178.0) in its official Linux AMD64 container. `scripts/ci/security-tools.toml` owns exact versions, Gitleaks HTTPS asset URL, byte size and SHA-256, and Semgrep native image manifest digest and image/config digest, and the bundled Pro engine path, size, SHA-256 and version-marker bytes. No placeholder digest is an admitted tool.

`scripts/ci/security_scan.py` validates the closed lock shape and host, bounds the Gitleaks download, verifies size and digest before safe extraction, and checks executable versions. For Semgrep, pull by the native manifest digest, verify the resolved image/config digest and Linux AMD64 platform, and run with `--pull=never`. [Docker digest pulls](https://docs.docker.com/reference/cli/docker/image/pull/#pull-an-image-by-digest-immutable-identifier) bind image content. A tag alone or a checksum fetched during execution is not authority. Review upstream notices and exact payloads before committing their pins. Record runner image and Docker versions as bootstrap inputs.

The general `bootstrap.py` and `toolchains.lock.json` contract in CI hardening owns compiler and interpreter admission. The bounded scanner admission helper separately owns scanner payloads through `security-tools.toml`; a shared bootstrap success does not admit a scanner or replace its checks. Consolidating these locks requires a reviewed change to both contracts. No scanner or rule code is linked into or shipped with Ricevanta. [Licensing](../licensing.md) owns permitted use; [project facts](../project.md#ci-analysis-service) owns the owner-managed service dependency.

Full tag routing also selects these scanner groups, but this PR/master integration admits no tag event or release-workflow credential. Before enabling tag release jobs, a separate reviewed tag scanner consumer must define event admission, step-scoped credentials, exact tag-SHA evidence and release aggregate checks. Do not skip the scanner groups, reuse PR receipts or widen the current token exception to make tag builds pass. [Release builds](release-builds.md#6-workflow-trust-and-required-checks) consumes this prerequisite.

## 2. Credential and source path

Only `.github/workflows/ci.yml` job `semgrep`, step ID `scan`, may contain `env.SEMGREP_APP_TOKEN: ${{ secrets.SEMGREP_APP_TOKEN }}`. No workflow/job environment, reusable secret mapping, inherited secrets, outputs, command-line value, file, cache or artifact may carry that token. Account changes, token provisioning and billing remain owner operations.

The job first validates the GitHub event and route without a token; cold image admission also occurs before the token-bearing step. Admit a push only to this repository's `master`. Admit a PR only when its head repository ID equals its base repository ID and both match this repository. Reject fork PRs and Dependabot PRs with a failing preflight and a short explanation. Missing or invalid tokens fail the scan step. No job-level skip, conditional success receipt, `pull_request_target`, `workflow_run`, dispatch substitute or privileged retry can satisfy the gate. GitHub documents [fork secret restrictions](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflows-in-forked-repositories).

For an external contribution, a maintainer reviews the complete diff, especially workflow, helper, rule and exclusion changes, before copying the contribution to a maintainer-owned branch in this repository and opening a replacement PR. Scan that PR's actual integration commit in its own run. The fork PR remains failed; do not transfer receipts or attest that the fork scan passed. Re-review any later contributor changes before copying them. A maintainer-controlled branch is a trust decision, not a scanner sandbox.

Token-free admission verifies the bundled Pro engine before the token-bearing helper starts the admitted scanner. The token is used only for authenticated scanning, not tool acquisition. Do not run repository builds, tests, package installs, hooks, local Actions, dependency scripts, `--allow-local-builds` or rule validators in that step or container. Use a fresh home, fixed PATH, read-only source mount, separate writable output mount, dropped capabilities, no Docker socket, and no privileged mode. The host helper remains part of reviewed CI code; a malicious same-repository author who changes it can steal the token. Independent review and restricted repository write access are required.

Create the Semgrep process environment from a fixed allowlist. Pass the token by environment name to Docker, never its value in argv. Pass fixed repository name and HTTPS URL, `SEMGREP_COMMIT=testedSha`, a validated branch identifier and a GitHub run URL. Omit GitHub event variables, all other CI-provider variables, baseline overrides, audit overrides, project configuration overrides, proxy overrides and inherited Semgrep settings. Do not pass a PR ID: these are full scans of the integration tree, associated with a unique `ci/pr/<number>/<testedSha>` branch identifier for PRs and `master` for pushes.

This isolation is necessary for identity: [Semgrep 1.178.0 CI source](https://github.com/semgrep/semgrep/blob/v1.178.0/cli/src/semgrep/commands/ci.py) calls `fix_head_if_github_action`, which switches a GitHub PR scan to its head commit and restores the checkout on exit. A final HEAD check alone does not prove which tree it scanned. [Its metadata implementation](https://github.com/semgrep/semgrep/blob/v1.178.0/cli/src/semgrep/meta.py) supports generic-CI metadata overrides. Verify scan-reported commit and source file hashes against the route before producing evidence.

## 3. Scan commands and finding policy

The fixed Semgrep invocation is:

```text
semgrep ci --code --supply-chain --pro --no-suppress-errors --verbose --disable-nosem --disable-version-check --metrics=off --json-output=/out/semgrep.json
```

[The CLI reference](https://docs.semgrep.dev/cli-reference) defines the product flags and build-execution flag. [The pinned CI implementation](https://github.com/semgrep/semgrep/blob/v1.178.0/cli/src/semgrep/commands/ci.py) defaults error suppression to true. Both product flags are mandatory: bare `semgrep ci` can select account-enabled products. `--secrets`, historical secret scanning and secret validation are forbidden. The wrapper treats every nonzero status as failure and also inspects the complete output on status zero. Semgrep Code can return credential-pattern SAST findings, which retain the ordinary severity gate. Rule names containing `secrets` do not identify the Secrets product and grant no exception. [The pinned rule classifier](https://github.com/semgrep/semgrep/blob/v1.178.0/cli/src/semgrep/rule.py) distinguishes products through native rule metadata; [Semgrep Secrets](https://docs.semgrep.dev/semgrep-secrets/conceptual-overview) is a separate product with validation capabilities.

The pinned `ci` parser does not accept `--strict`; that option belongs only to `scan`. CI uses native non-strict defaults. [Its output handler](https://github.com/semgrep/semgrep/blob/v1.178.0/cli/src/semgrep/output.py) can leave warning-level structured errors and special interfile-analysis errors without a failing exit status. `--no-suppress-errors` controls failure suppression; it does not promote those diagnostics to fatal errors. The repository therefore rejects every native report/core error, regardless of level, plus dependency-parser errors, timeout and incomplete-scan evidence under section 4, even when the process exits zero. Do not substitute another unsupported flag or alter native scanner methods to force strict mode. This contract does not classify every free-form log warning as an error; raw logs remain private.

`--pro` selects the admitted Pro engine already bundled in the pinned image. Before injecting the token, verify `/usr/lib/python3.12/site-packages/semgrep/bin/semgrep-core-proprietary`: size `399642553`, SHA-256 `acde62f2dfb45edb1ea695daf8efb04b2d6cce7939eaab971471208226dee71e`. Verify adjacent `pro-installed-by.txt` contains exactly the eight bytes `1.178.0` followed by LF, then require the pinned CLI's installed-engine check and engine version check to pass. These bytes were verified in the admitted image layer; the tool lock owns runtime admission. Keep the image filesystem read-only and reject a missing or incompatible binary or marker. Do not download, stage or install a separate Pro payload, invoke auto-install, or fall back to another engine. [The pinned installer](https://github.com/semgrep/semgrep/blob/v1.178.0/cli/src/semgrep/commands/install.py) defines the binary layout and marker; [JavaScript coverage](https://docs.semgrep.dev/languages/javascript) explains why framework rules require Pro.

Token-free synthetic controls use `semgrep scan --oss-only --no-rewrite-rule-ids --strict` with local fixture rules in the same admitted image. [The pinned scan options](https://github.com/semgrep/semgrep/blob/v1.178.0/cli/src/semgrep/commands/scan.py) select the OSS engine explicitly and preserve exact fixture rule IDs; [the pinned core runner](https://github.com/semgrep/semgrep/blob/v1.178.0/cli/src/semgrep/core_runner.py) requires authentication for every Pro scan. Keep the token absent from these controls and retain token-free Pro hash, marker, installed-engine and version admission. Do not supply a fake token, bypass the authentication check or interpret an authentication failure as a passed control.

Run required Go, Python and TypeScript positive controls separately from isolated Rust and Vue probes. Required controls must finish successfully and return their exact expected rule IDs and targets. Do not put Rust or Vue in the required controls' multi-language rule. A probe proves support only through successful native execution with the expected synthetic finding. Classify a probe as unsupported only from an explicit unsupported-language/engine outcome verified against the pinned CLI; retain that sanitized outcome. A completed probe without the expected finding leaves its coverage unqualified. Other configuration, authentication, parsing or runtime errors fail qualification; no blanket error suppression is allowed.

Label cold results with the OSS engine, synthetic inputs and observed parser/rule coverage. They qualify only those controls, not Pro-only framework analysis, service access, Code/SCA product completion or upload. In particular, an OSS Vue script probe establishes only the observed OSS script behavior; it cannot qualify Pro framework or template analysis. The authenticated repository scan still uses the fixed `--pro` command and must provide native Code and Supply Chain evidence. Cold success cannot issue or replace a production scan receipt. This split preserves credential isolation at the cost of qualifying Pro/service behavior during authenticated CI. Moving the token into cold controls expands its exposure; switching the production scan to OSS loses required Pro behavior. Both alternatives are rejected.

Gitleaks runs `git` mode over every commit reachable from `testedSha`, with `--log-opts=<testedSha>`, `--redact=100`, `--exit-code=1`, `--report-format=json` and a new report path. It also runs `dir` mode over the exact tracked working-tree snapshot with the same redaction and exit policy. The working-tree pass covers merge resolution content. [Gitleaks usage](https://github.com/gitleaks/gitleaks/tree/v8.30.1) defines Git patch scanning, directory scanning and redaction. No shallow clone, baseline report, default changed-path-only scan or broad ignore is accepted.

The helper uses the pinned default Gitleaks rule set through an explicit config, disables inline `gitleaks:allow` suppression, and supplies a fixed empty ignore file. No candidate `.gitleaks.toml` or `.gitleaksignore` may silently change coverage. Block every finding except the exact reviewed fixture identities below. The scanner still reports those findings; only the final local gate applies exceptions. No exception changes Gitleaks rules, native report contents or scan coverage.

Block returned active Semgrep Code and Supply Chain findings of severity `ERROR`, `HIGH` or `CRITICAL`, independent of account monitor/block policy, except the exact reviewed local SCA identity below. Apply SCA blocking to reachable, unreachable and unknown-reachability results, including Rust. Unknown severity or product metadata fails parsing. Lower severities remain visible as counts and locations. No inline suppression, account audit mode or unsupported/empty product result may bypass the local gate. The pinned CLI removes account-triaged ignored findings before writing JSON; the local gate cannot inspect them. Explicit owner-managed account triage is trusted policy authority and must be reviewed there. The gate makes no claim about all findings before that filter and needs no broader API token or interception of native results. Existing console OSV exceptions do not automatically waive Semgrep findings.

There are exactly 13 identities per mode. The admitted blob SHA-256 is `020860808f72ce3119a8a2c168ce57ccd98a1fd9de3f85c152f36d605c57e085`.

A finding in another commit never matches, even with identical text and coordinates.
- Tree entries require an empty native `Commit` and fingerprint `schemas/dsse/v1/vectors.json:generic-api-key:<line>`. Verify the scanned snapshot file's complete bytes against the admitted hash. Match all identity fields, not the fingerprint alone. Reject duplicate native findings and malformed coordinates. Missing blobs, linked files, path aliases or hash mismatches cannot authorize an exception. Keep 13 entries per mode in the committed set; additions or changed identities need a fresh independent review. Inactive tree entries do not waive findings after fixture edits; report the disabled count and require a reviewed replacement set if findings remain.

These findings identify `key` row references in the [DSSE vector corpus](dsse-envelope.md#9-machine-readable-vectors-and-regeneration), not key material or credentials. Independent verification confirms both key derivations and all 20 positive vectors' PAE, signatures, key hints, envelopes and digests. Native history and tracked-tree scans confirm these exact identities; the two scanned blobs match the admitted hash. Preserve that safe provenance and native identity metadata with the exception fixtures, without `Secret`, `Match`, raw source snippets or raw scanner logs.

Accept Gitleaks exit status 1 only when its ordinary completion evidence passes, its report is valid and nonempty, and every finding matches an active reviewed exception. Exit status 0 requires no findings; a contradictory exit/report pair fails. Any other status, scanner error, incomplete report or unexcepted finding fails. Check history and tree runs separately, then require both before the leaf receipt. Diagnostics expose total, excepted, disabled and blocking counts and safe identities, so 13 accepted fixture-label findings never appear as zero findings.

The exception gate grants no new authority to the attackers in section 6: endpoint credentials, runtime database state and restored server data cannot edit it. A contributor's changed snapshot bytes or new history commit cannot inherit an exception. A maintainer who changes both the exception set and CI code remains inside the existing repository review boundary.

## 6. Threat boundary and trade-offs

The source-to-sink path is GitHub event admission, exact Git tree, admitted scanner, step-scoped token, HTTPS Semgrep policy/scan service, validated output, same-run receipt and required check. Scanners parse repository content; they never run repository build scripts with the token. TLS authenticates the service; immutable tool pins authenticate the admitted payload. Rule policy and explicit account triage remain owner-controlled online inputs, whose identity and rule counts belong in evidence. A service outage or changed incompatible policy fails CI.

| Attacker | What the attacker gets |
|---|---|
| Stolen enrollment token | No GitHub or Semgrep credential, no CI result authority. |
| Compromised agent host | No access to repository CI secrets through the endpoint protocol. A leaked CI runner token instead grants its actual Semgrep account scope; revoke and rotate it. |
| Compromised console session | No CI authority from a Ricevanta session. A compromised GitHub maintainer or Semgrep administrator can change CI or scanning policy and remains outside receipt integrity guarantees. |
| Rogue extension publisher | Published packages cannot change scanner pins or jobs. A fork contribution gets token-free Gitleaks and a failed authenticated preflight until a maintainer trusts a replacement PR. |
| Network position between agent and server | No CI authority. On scanner download/API paths, mismatched bytes or TLS failure fail admission; blocking service access prevents a green check. |
| Database writer without signing keys | No authority over GitHub secrets, tool pins or same-run receipts. Runtime database content is not a scan input. |
| Server restored from backup | Restores no CI credential or gate authority; old receipts cannot match a fresh run/attempt and SHA. |

A compromised runner image, admitted scanner or reviewed helper can read the step token. Scope the token to scanning the authorized Semgrep organization, never account administration; record its actual scope before landing. No masking mechanism makes arbitrary token-bearing code safe. Independent adversarial review covers workflow, helper and exclusion changes.

Benefits are explicit product selection, secret detection without an Action license, and evidence that SAST/SCA actually ran. Costs are full-history/full-tree scan time, an online service dependency, pinned-output maintenance and maintainer work for forks. Set 15-minute Gitleaks and 20-minute Semgrep job limits; timeouts fail. Static analysis cannot prove absence of vulnerabilities. The OSV audit remains an independent console dependency gate.

Rejected alternatives: a bare Semgrep command can enable Secrets; paid Gitleaks Actions add an unnecessary license; fork skipping yields false success; privileged fork follow-up exposes credentials; token-bearing builds execute candidate code; floating tools bypass admission; replacing OSV loses its exact dependency/exception contract; accepting only reachable SCA findings hides Rust and unknown-reachability vulnerabilities.
