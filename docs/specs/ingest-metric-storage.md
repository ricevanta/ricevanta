# Ingest scalar metric storage

The cost child gives its parent and asynchronous sampler distinct reusable two-metric buffers. This is a bounded correction to test machinery, subject to independent design and implementation review. Head `6b12b6b` remains **failed** in run `38866731117` under [qualification section 5.2](ingest-cost-qualification.md#52-retained-corrected-candidate-failure). This design establishes no qualification for a metric-storage candidate; section 5 requires exact-candidate evidence and disposition. The [plan](../plans/ingest-metric-storage.md) permits one next normal qualification of the reviewed changed candidate, not an unchanged retry.

## 1. Evidence and selected scope

The independently reviewed [ownership audit](ingest-cost-qualification.md#53-bounded-receive-ownership-audit) proves that `usedMemory` allocates an 80-byte two-`metrics.Sample` array at each call on the pinned Linux amd64 target. After baseline, the audited child makes `R + 1` synchronous calls plus `K` asynchronous calls, where `K` is not retained. For the six audited receive-only paths, `R=32`, so these array allocations cumulatively occupy `80 × (33 + K)` class-slot bytes. This is neither simultaneous memory nor a scalar-peak contribution.

The pinned [Go metrics API](https://pkg.go.dev/runtime/metrics@go1.27.1#Read) encourages slice reuse. Concurrent reads must use separate backing memory; values must not be inspected during an outstanding read into their storage. Its [source](https://github.com/golang/go/blob/go1.27.1/src/runtime/metrics/sample.go) fills the supplied samples. The audited runtime path for these two uint64 metrics retains no backing pointer and allocates no histogram. A caller-owned buffer can therefore remove repeated array allocation without changing the requested metric or its read position.

Only post-baseline two-metric reads change. The baseline's existing `usedMemory()` implementation and call stay byte-identical, including the temporary array and first metrics initialization. `readUint64Metric` and all five of its calls stay byte-identical: its 40-byte payload rounds to 48; two calls precede sampler startup and three follow shutdown. They are bounded, nonrepeated reads and are outside this slice's repeated-array defect. Reusing them would change more lifecycle/diagnostic accounting without being necessary for the selected correction.

The failed 18,309.6-byte scalar excess is not attributed to these arrays. One receive backing still occupies 5,005,312 bytes against logical `C=5,000,000`. Page/span topology, small-span occupancy, stacks, caches, GC work demand, timer registration, pools and collection/reuse/scavenging timing remain named unknowns in the ownership audit. This slice changes no charge or production storage and does not close a whole-process bound by summing live objects.

## 2. Storage and ownership contract

Use test-only `costMemorySamples`, an array of exactly two `metrics.Sample` values, stored inline as `samples costMemorySamples` followed by `peak *atomic.Uint64` in `costMemorySampler`. Each reader owns one `costMemorySampler`; only the peak atomic is shared. A noinline `newCostMemorySampler(peak *atomic.Uint64) *costMemorySampler` allocates one fresh owner object, initializes sample index 0 to `/memory/classes/total:bytes` and index 1 to `/memory/classes/heap/released:bytes`, and stores the supplied peak pointer. It performs no metric read, peak update, logging or runtime initialization. There is no separately allocated sample array, global instance, pool, singleton or injected reader.

The embedded array's read method passes its full two-element slice to `metrics.Read` exactly once and returns index 0's `Uint64()` minus index 1's `Uint64()`, preserving the existing arithmetic and failure behavior. The owner's direct `sample()` method reads that value and executes the existing peak `Load`/`CompareAndSwap` loop unchanged. Neither method allocates backing or retains new state per call. Names remain unchanged. The owner is never copied after construction.

| Owner | Allocation position | Read positions and lifetime |
|---|---|---|
| Parent goroutine | Immediately after the existing `peak.Store(baseline)`, replacing the sample-function construction | All existing synchronous loop samples and the final synchronous sample call `parentSampler.sample()` directly. One owner pointer replaces the sample-function local; no second buffer pointer or function value is retained. |
| Sampler goroutine | Inside the existing goroutine, after `defer close(sampled)` and immediately before `time.NewTicker(time.Millisecond)` | Only the existing tick branch calls its separate `sampler.sample()` directly. The goroutine captures the peak atomic, not the parent owner, and keeps its own owner through its last read. |

Remove the peak-update closure and its explicit buffer argument. Do not bind a method value or wrap either method in a new closure. The only existing sampler goroutine closure captures `sampled`, `done` and the peak atomic in place of the sample function. Each method reads only its own embedded array; neither reader inspects the other's values. No mutex, channel, readiness handshake, artificial `KeepAlive`, clear or release is added. Existing goroutine shutdown remains unchanged.

Both owner allocations occur after baseline and the memory-limit installation. The noinline factory keeps owner construction out of `costChild`'s inline body; compiled placement must prove that neither object nor new setup is moved before baseline. The source construction removes the separately live parent buffer pointer and sample-function value seen in the rejected candidate, replacing them with one owner pointer. This is a falsifiable way to avoid its extra frame slot, not a guaranteed compiler result.

On the explicit amd64 audit target, the intended object is 80 bytes of samples plus an 8-byte peak pointer, an 88-byte payload expected to occupy class 96. Two such owners replace the separate arrays and shared peak-update closure. Actual type size, pointer map, allocation count/class, goroutine capture, frames and last references must be proved; no inferred size substitutes for compiler evidence. New closure allocation or separately escaping array backing fails the construction contract.

The sampler owner is allocated even if no tick arrives. Fixed owner storage can increase live storage when `K=0` and can change runtime allocation/GC behavior while removing allocation requests that grow with tick count. No lower peak or allocation-counter delta is promised. Both owners stay in the unadjusted runtime metric until normal collection/release permits otherwise; no subtraction is applied.

## 6. Benefits, trade-offs, dependencies and authority

The benefit is fixed caller-owned observer backing with API-safe concurrency and unchanged measurement coverage. The cost is two longer-lived owner objects containing arrays and peak pointers, plus possible runtime/scheduling differences. Combining ownership adds object payload but removes the separate parent buffer handle and peak-update closure; the compiler proof must establish the frame benefit. These effects remain measured and require compiler review; removing allocation requests is not equivalent to removing committed pages.

Dependencies are the pinned Go standard library, completed ownership evidence and existing CI wrapper. No package, service, vendor program or schema is added. Sharing one buffer violates the metrics concurrency contract; a lock changes sampler scheduling; reusing the baseline buffer changes baseline ownership; warming buffers before baseline hides setup; rewriting single-metric reads expands the slice unnecessarily. Keeping per-tick allocations preserves the demonstrated observer churn. Returning a closure that captures a separately allocated array would add function-object ownership and indirection; the selected direct-method object keeps one handle and one allocation per reader. Relaxing the 8-byte frame guard or subtracting it from baseline would hide the actual failed proof and is forbidden. A production receive-buffer/charge redesign addresses another question and requires its own reviewed contract.

This test-only storage grants no authority. The [admission threat trace](ingest-admission.md#8-threat-trace) still covers authenticated receive, decode, refusal, release and retry. A stolen enrollment token gains no upload bypass; a compromised host retains only its existing device authority; a compromised console cannot change harness constants; a rogue publisher gains no ingest path; a network intermediary gains no identity; a database writer without keys gains no limiter control; a restored server remains subject to recovery sealing. No artifact acknowledges or stores device content, and endpoint classification/redaction rules remain unchanged.

The retained scalar peak composition and missing badid CPU value remain unresolved. Exact receive rounding and runtime-state inputs remain design limits, not permission to inflate charge. Is any unexplained storage or setup moved before baseline in the compiled candidate? That is a blocking proof question for implementation review, not an assumed property of a source edit.
