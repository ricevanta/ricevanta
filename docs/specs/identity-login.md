# Identity login

How an administrator proves who they are: SP-initiated OIDC with the authorization code flow and PKCE, SP-initiated SAML with the HTTP-POST binding, break-glass local accounts with a generated password and TOTP, the first-start administrator, external-principal links and identity-provider administration. Every successful login ends in the server-side session of [identity sessions](identity-sessions.md); the browser never receives a token from an identity provider.

Authorities: BE-01, BE-02, BE-09 and BE-17 in [decisions](../decisions.md), [backend design](../design/backend.md) sections 1.1 and 6, [console design](../design/console.md) sections 2 and 3.2, [API foundation](api-foundation.md). Operations, schemas and fixtures are in [`schemas/openapi/v1/`](../../schemas/openapi/v1/openapi.yaml).

## 1. Boundary and authority

The `identity` module owns providers, principal links, link requests, break-glass accounts, pre-login records, the SAML replay cache and sessions. Users, principal links, enabled state, break-glass credentials, provider trust and role grants are authority under BE-12 (backend design section 6.1): a database writer who could insert a link or enable a user would own the console. The login engines therefore read them only through an `identity.AuthorityReader` interface.

| Part | State |
|---|---|
| OIDC and SAML protocol engines, TOTP, generated credentials, return paths, cookies, pre-login records, decision order, login and enrollment handlers against store and authority interfaces | Isolated qualification models only; production consumers need reviewed design and plan |
| End-to-end tests against the real binary with test OIDC and SAML providers | Future isolated qualification harness only; release artifacts must exclude fixture authority |
| PostgreSQL stores for pre-login records, link requests, replay cache, accounts and sessions | Blocked on the PostgreSQL platform slice |
| Production `AuthorityReader`, provider and link administration, break-glass lifecycle, first start | Blocked on BE-12 (committed projection, read lease, approval consumption and the recovery manifest) |
| Alerting on break-glass use through notifier connectors | Blocked on the `notifier` connector contract (EXT-05); the audit record exists without it |

The server needs its public console origin for redirect URIs, SAML endpoints and origin checks. The future identity integration adds `api.public_origin`: an `https` origin with no path, query or fragment, required when the `api` role serves `/api/v1`. The BE-15 runtime does not yet accept this key. Its schema, environment mapping, startup checks and HTTPS listener/proxy qualification must change together in a reviewed implementation plan. Direct TLS must use that origin; reverse proxies must preserve it, strip untrusted forwarding headers, and have separately qualified transport. No authentication over loopback plaintext is enabled by this design. The TCP peer remains the source for limits; forwarded headers are ignored.

## 2. Shared login mechanics

### 2.1 Pre-login records and cookies

Starting a login or re-authentication creates a pre-login record: a 256-bit random cookie value, whose SHA-256 is the record key; the purpose (`login` or `reauth`); the provider uid; for re-authentication the session uid, credential generation and the purpose binding (`general` or `approval:<uid>`); the return path; for OIDC the 256-bit `state`, the 256-bit `nonce` and the PKCE verifier from 32 random octets ([RFC 7636](https://www.rfc-editor.org/rfc/rfc7636.html) section 4.1), encrypted under the derived prelogin-aead key; for SAML the request ID; the creation time; and an expiry 10 minutes later. A callback with a matching cookie/provider atomically consumes the record before protocol validation, whatever the later outcome. The record MAC covers every field, provider revision, epoch and bound credential generation; replay and consumption require the current authority projection (identity sessions section 8). A second start in the same browser overwrites the cookie, and the earlier tab's callback then fails as `state_mismatch`. At most 10,000 unexpired records exist organization-wide and 32 providers may be configured. Atomic admission enforces both caps; expired records stop authorizing immediately and hourly cleanup removes their payloads after consumption/expiry evidence is retained. Login starts with an unknown, disabled or wrong-protocol provider return the same `provider_disabled` redirect. A request carrying a session never switches principals during re-authentication.

| Cookie | Attributes | Purpose |
|---|---|---|
| `__Host-rv_login` | `Path=/; Max-Age=600; HttpOnly; Secure; SameSite=Lax` | OIDC; `Lax` lets it travel on the provider's top-level `GET` to the callback |
| `__Host-rv_saml` | `Path=/; Max-Age=600; HttpOnly; Secure; SameSite=None` | SAML; the identity provider's form `POST` is cross-site, and only `None` cookies travel on it |
| `__Host-rv_enroll` | `Path=/; Max-Age=600; HttpOnly; Secure; SameSite=Strict` | Binds the two break-glass enrollment steps (section 6.4) |

The `__Host-` prefix requires `Secure`, `Path=/` and no `Domain` ([RFC 6265bis-22](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis) section 4.1.3.2), which blocks injection from sibling hosts. A pre-login cookie is cleared with `Max-Age=0` when its record is consumed. The exact strings, in `net/http` `Cookie.String` attribute order, are fixtures in `sessions.json`.

### 2.2 Return paths

`return_to` must match `^/[A-Za-z0-9._~/-]{0,511}$`, contain no empty, `.` or `..` segment, and not be or lie under `/api`, `/agent`, `/ext`, `/assets`, `/brand`, `/mdm`, `/scep`, `/acme`, `/healthz`, `/readyz`, `/metrics`, `/login` or `/__test__`. Anything else becomes `/`. No query or fragment survives; the console restores view state from `sessionStorage`. The `303` `Location` is that path, which the browser resolves against the callback's own origin, so no callback is an open redirect. `return-paths.json` fixes the vectors.

### 2.3 Navigation outcomes and limits

Start, callback and assertion-consumer endpoints are browser navigations and always answer `303`: to the provider, to the return path on success, or to `/login?error=<code>` with a code from `LoginErrorCode` in the document. Start endpoints refuse `Sec-Fetch-Site: cross-site` or `same-site` with `cross_site_start` ([Fetch Metadata](https://www.w3.org/TR/fetch-metadata/), W3C Working Draft, section 4.1); a typed URL (`none`) is allowed. The callback and consumer accept cross-site navigations by design and rely on the pre-login record instead.

| Endpoint group | Limit per source address |
|---|---|
| Start and callback, OIDC and SAML | 20 per minute, burst 10 |
| `loginLocal`, `reauthenticateLocal` | 10 per minute, burst 5 |
| Enrollment and first start | 5 per minute, burst 3 |

Each actual attempt writes an administrative audit record; repeated rate refusals aggregate by source and minute without retaining request values. Every admission and result must satisfy the EV-06 audit publication gate. Each attempt records with the provider, outcome code, source and user agent, never a code, token, assertion, password or TOTP value (`design/events.md` section 6).

### 2.4 Principal resolution and link requests

A validated authentication yields a principal key: OIDC provider uid, exact `iss` and `sub`; SAML provider uid, issuer, persistent `NameID` format and `NameID` (backend design section 1.1). OpenID Connect Core 1.0 section 5.7 makes `iss` with `sub` the only guaranteed unique identifier and forbids using `email` or `preferred_username` as one ([OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html)); SAML Core section 8.3.7 defines persistent identifiers as pseudo-random values with no correspondence to the user name ([SAML core](https://docs.oasis-open.org/security/saml/v2.0/saml-core-2.0-os.pdf)).

A key with a link resolves to its internal user. A key without one creates or refreshes a link request holding the key, the claimed display name and email for the reviewer, and first and last seen times, then answers `link_pending`. A request expires 7 days after first sighting; refresh never extends that deadline. It binds provider revision, epoch and the verified principal key under the record MAC; a database-inserted or retargeted request is never link authority. Display claims are untrusted text. An expired request needs a fresh successful login and a new uid; at most 100 open requests exist per provider, beyond which the answer is `rate_limited`. Turning a request into a link is the protected `createPrincipalLink` operation (section 5). Claims never create, merge or match users, and claim-to-group mapping is not part of this slice (section 10).

## 3. OIDC

### 3.1 Provider configuration

An OIDC provider stores the issuer (`https`, no query or fragment), client id, client authentication method (`client_secret_basic` or `client_secret_post`), the client secret under envelope encryption (backend design section 6), extra scopes (`profile`, `email`) and the allowed ID token algorithms from `RS256`, `RS384`, `RS512`, `PS256`, `PS384`, `PS512`, `ES256`, `ES384`, `ES512` and `EdDSA`. Configuration fetches the discovery document with `go-oidc` `NewProvider`, which fails unless the discovered issuer matches exactly ([go-oidc](https://pkg.go.dev/github.com/coreos/go-oidc/v3/oidc)). Create requires a nonempty client secret; update omission retains its exact committed ciphertext. Provider protocol and issuer are immutable: replacing them requires a new provider and explicit new links. Omitted extra scopes mean none; omitted signing algorithms mean `[RS256]`. The provider must list `code` in `response_types_supported` and `S256` in `code_challenge_methods_supported`; [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html) section 2.1.1 recommends PKCE for confidential clients, and Ricevanta requires it. `authorization_response_iss_parameter_supported` is recorded ([RFC 9207](https://www.rfc-editor.org/rfc/rfc9207.html) section 3). The redirect URI is `https://<public origin>/api/v1/auth/oidc/<provider_uid>/callback`, distinct per provider as RFC 9700 section 4.4.2.2 requires of clients with several issuers.

Provider outbound requests use HTTPS and normal certificate/hostname verification with system roots, no redirects, no ambient proxy credentials, at most 10 seconds total and 256 KiB for discovery/JWKS. Discovery, token and JWKS endpoints must have the issuer's exact origin; cross-origin providers require a separately reviewed explicit endpoint allow-list and are not admitted by this profile. The browser authorization endpoint is also HTTPS on that origin. Resolve and pin addresses per request, reject loopback, link-local, multicast and unspecified addresses, and revalidate after DNS changes; private unicast is allowed for self-hosted providers. Implementation must verify the Go/library transport prevents DNS rebinding and enforces these bounds before SSO is enabled. No URL supplied by a callback may direct a server request.

### 3.2 Authorization request

`startOidcLogin` creates the pre-login record and redirects to the authorization endpoint with `response_type=code`, `client_id`, the exact redirect URI, `scope=openid` plus the configured extras, `state`, `nonce`, `code_challenge` (`S256`, RFC 7636 section 4.2) and `code_challenge_method=S256`. Re-authentication adds `prompt=login` and `max_age=0`: with `prompt=login` the provider "MUST reauthenticate the End-User even if the End-User is already authenticated" (OpenID Connect Core section 3.1.2.3), and with `max_age` the ID token "MUST include an auth_time Claim Value" (section 3.1.2.1). The default `query` response mode is used; `form_post` would be a cross-site `POST`.

### 3.3 Callback

`completeOidcLogin` applies these steps in order; `login.json` fixes the outcome of each:

1. The `__Host-rv_login` cookie must name an existing, unconsumed record for this provider path, else `state_mismatch`; an expired record is `expired`. The record is consumed now.
2. `state` must equal the stored value (constant-time), else `state_mismatch`. RFC 9700 section 4.7.1 lists `state`, PKCE and `nonce` as request-forgery defences; Ricevanta uses all three.
3. A disabled provider is `provider_disabled`; an `error` parameter is `provider_error`.
4. `iss`: present and different from the issuer, or absent when the provider advertises support, is `invalid_response` (RFC 9207 section 2.4).
5. Without `code`, `invalid_response`. The token request uses the stored verifier, a 10-second timeout and a 64 KiB response limit; a 4xx answer is `provider_error`, a network failure or 5xx is `unavailable`.
6. The ID token passes `go-oidc` `Verify` with the client id and the allowed algorithms (signature from the provider's JWKS, `iss`, `aud`, `exp`). Ricevanta then checks what `go-oidc` leaves to the caller: `nonce` equals the stored nonce, which "Verify does NOT do" (go-oidc documentation); `azp` equals the client id when present and is present when `aud` has more than one value; `iat` is no more than 60 seconds ahead and no more than 10 minutes old. Any failure is `invalid_response`. Require nonempty `sub` of at most 255 ASCII characters, correctly typed nonempty issuer/audience claims and bounded numeric dates. Reject duplicate JSON claims and unknown critical JOSE headers. A present `auth_time` must be a valid timestamp no more than the skew ahead; absence grants no freshness. Access/refresh tokens are discarded, userinfo is not fetched and `offline_access` is never requested.
7. Re-authentication only: `auth_time` must be present, no earlier than the record's creation minus 60 seconds and no later than receipt plus 60 seconds, else `reauth_stale`; the bound session must still be valid, else `session_required`.
8. Principal resolution (section 2.4): `link_pending` or `rate_limited` for unlinked keys; a disabled user is `user_disabled`; a re-authentication whose principal resolves to another user is `reauth_user_mismatch`.
9. Login creates a session; re-authentication updates and rotates the bound one ([identity sessions](identity-sessions.md) sections 2 and 5). Both answer `303` to the return path and clear the pre-login cookie. The response sets `__Host-rv_session` although it answers a cross-site navigation: a top-level navigation may set a cookie with any `SameSite` value (RFC 6265bis-22 section 5.7, step 18.3).

## 4. SAML

### 4.1 Provider configuration

A SAML provider is configured by importing the identity provider's metadata, at most 256 KiB: its entity ID, the `SingleSignOnService` location for the HTTP-Redirect binding, one to four signing certificates and `WantAuthnRequestsSigned`. Metadata is never fetched at login time. The server generates one RSA-3072 service-provider key per provider under envelope encryption and publishes its certificate, the entity ID `https://<public origin>/api/v1/auth/saml/<provider_uid>/metadata` and the consumer URL `https://<public origin>/api/v1/auth/saml/<provider_uid>/acs` through `getSamlServiceProviderMetadata`. The key signs every authentication request; metadata advertises signed requests. XML assertion encryption is not accepted in this profile: TLS carries signed assertions, and a provider configured to require encrypted assertions fails admission explicitly. Supporting encrypted assertions requires a separately reviewed algorithm and decryption profile, not silent library defaults. The SP certificate is self-signed SHA-256/RSA-3072, valid for one year, with renewal requiring a protected provider update; no external CA account is needed. Key/certificate generation and custody require source qualification before implementation (verify). The clock skew is 60 seconds by default and at most 180.

The candidate is `github.com/russellhaering/gosaml2` v0.12.0 with `goxmldsig` v1.6.1, `beevik/etree` and `mattermost/xml-roundtrip-validator` (verify source and compatibility). These dependencies lack the required licensing rows and are not admitted for implementation. No library behavior may substitute for the acceptance predicates below.

### 4.2 Authentication request

`startSamlLogin` sends an `AuthnRequest` over the HTTP-Redirect binding with a fresh `ID` of `_` plus 40 hexadecimal characters, `Destination` the SSO location, `AssertionConsumerServiceURL` the consumer URL, `ProtocolBinding` HTTP-POST, `Issuer` the service-provider entity ID and `NameIDPolicy` persistent with `AllowCreate="true"`. Re-authentication sets `ForceAuthn="true"`, which obliges the identity provider to "authenticate the presenter directly rather than rely on a previous security context" (SAML Core section 3.4.1). No `RelayState` is sent; the pre-login record holds the return path. IdP-initiated responses are refused because they carry no request to bind (BE-09).

### 4.3 Assertion consumer service

`completeSamlLogin` accepts `application/x-www-form-urlencoded` with `SAMLResponse` up to 262,000 characters and ignores `RelayState`. Reject duplicate form fields, invalid base64, decoded XML over 192 KiB, depth over 32, more than 10,000 elements, DTDs, external entities and external signature references before library processing. Permit only SHA-256/384/512 digest and RSA-SHA256/384/512 or ECDSA-SHA256/384/512 signatures, enveloped signatures and exclusive canonicalization without comments; reject SHA-1, XSLT and duplicate XML IDs. Select the exact signed assertion node and extract identity only from it. Verify these algorithm names and parser controls against the selected library before enabling SAML. Steps, fixed at the decision level by `login.json`:

1. The `__Host-rv_saml` cookie must name an unconsumed record for this provider path (`state_mismatch`, `expired`); the record is consumed. The response's `InResponseTo` must equal the stored request ID, so unsolicited responses fail as `state_mismatch`.
2. A disabled provider is `provider_disabled`.
3. The response `Destination` must be present and equal the consumer URL; the HTTP-POST binding requires the recipient to verify it for signed messages ([SAML bindings](https://docs.oasis-open.org/security/saml/v2.0/saml-bindings-2.0-os.pdf) section 3.5.5.2). `gosaml2` checks `Destination` only when present, so the absence check is Ricevanta's.
4. A non-success status is `provider_error`.
5. The issuer must equal the configured entity ID; the response must hold exactly one assertion, because `gosaml2` evaluates only the first; that assertion must carry its own valid signature from a configured certificate. The Web Browser SSO profile requires assertions delivered by HTTP-POST to be signed ([SAML profiles](https://docs.oasis-open.org/security/saml/v2.0/saml-profiles-2.0-os.pdf) section 4.1.4.5); a signature over the response alone does not satisfy Ricevanta. Library assertion-level verification, XML wrapping refusal and warnings must be verified against source and adversarial fixtures before implementation; a boolean fixture cannot establish them.
6. The assertion needs exactly one bearer `SubjectConfirmation` whose signed data contains `InResponseTo` equal to the stored request ID and names the consumer URL as `Recipient` and an unexpired `NotOnOrAfter` at most one hour ahead; required `Conditions` NotBefore and NotOnOrAfter, with expiry after receipt under the configured skew and no later than issue time plus one hour; every `AudienceRestriction` must include the service-provider entity ID and at least one restriction must exist; exactly one `AuthnStatement` with a nonfuture AuthnInstant under the skew; and a persistent `NameID` of at most 256 characters (profiles section 4.1.4.2 and 4.1.4.3). `gosaml2` reports audience and time failures only as `WarningInfo` flags, so any set flag fails. Every failure is `invalid_response`.
7. Replay: the assertion ID is recorded as `(provider_uid, provider_revision, assertion_id)` until the latest accepted expiry plus skew in a unique-keyed cache, and a second use is `invalid_response`, as profiles section 4.1.4.5 requires.
8. Re-authentication only: `AuthnInstant` no earlier than the record's creation minus the skew, else `reauth_stale`; require the still-valid bound session, resolve the same user, then rotate as section 3.3 steps 8 and 9. Do not read OIDC claims in a SAML callback.

## 5. Identity providers and principal links

`createIdentityProvider`, `updateIdentityProvider` and `deleteIdentityProvider` change an authentication authority, and `createPrincipalLink` and `deletePrincipalLink` change who an external principal is. All five are identity-authority actions (BE-02, console design section 3.2): they need recent authentication, answer `202` with an approval request, and are approved only by a different enabled user with a direct `identity.authority.approve` assignment whose decision re-authentication is bound to the request and uses a method outside the affected set ([identity sessions](identity-sessions.md) section 6). The affected set of a provider change is that provider; of a link change, the link's provider and the target user's current methods. The request binds the before and after resource hashes, the provider uid, the principal key and the target user uid. Applying a provider update that changes its issuer, client, certificates or endpoints, or deleting it, revokes every session authenticated through it and every link request it holds. The request stores recoverable encrypted secret after-images in protected storage and includes their keyed fingerprints and ciphertext hashes in the binding; a hash alone cannot apply a provider secret. Metadata is parsed and frozen at request creation, never fetched again at application. Approval inspection shows the parsed issuer/endpoints, public signing-certificate fingerprints and secret-change indicators, never secrets or raw XML. OIDC JWKS refresh may change signing keys only under the exact approved issuer/origin, allowed algorithms and TLS policy; that provider can already impersonate all its own subjects. Other discovery changes require a new protected provider revision. All provider updates, including disable, invalidate dependent sessions, pre-login records and link requests. Delete freezes every dependent link and its affected users; it leaves irreversible link tombstones. A new link must consume an unexpired verified link request once and enforce uniqueness in both directions at application; links never grant roles by themselves. The catalogue names are in [API foundation](api-foundation.md) section 8. Execution is gated on BE-12.

## 6. Break-glass accounts

### 6.1 Credentials

A break-glass account is a local account bound to one internal user (BE-01). Its credentials are generated, never chosen: a password of 24 RFC 4648 base32 characters (120 bits), compared by uppercasing ASCII letters and removing only ASCII spaces and hyphens; reject every character outside the base32 alphabet after that normalization. The separate TOTP seed contains 20 random bytes. [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238.html) section 5.1 asks for keys as long as the HMAC output, 20 bytes for SHA-1. Because the password is 120 random bits, the stored verifier is `HMAC-SHA-256(K_local, JCS({account_uid, password}))`, not a slow password hash: offline guessing of a 120-bit secret is infeasible, and the key keeps a database writer from installing a verifier for a password of its choice. The seed is stored under envelope encryption. The console renders the seed as text and as a QR matrix of `0` and `1` rows that the server encodes with `rsc.io/qr`, drawn as SVG rectangles, so no `data:` image or new console dependency is needed.

### 6.2 TOTP

Codes are 6 digits over HMAC-SHA-1 with 30-second steps from the Unix epoch (RFC 6238 section 4.1). The verifier accepts the current and the previous step only, following "at most one time step is allowed as the network delay" (section 5.2), and stores the last accepted step per credential generation as a BE-12 irreversible floor with an atomic consumption, so a code is never accepted twice: "The verifier MUST NOT accept the second attempt of the OTP" (section 5.2). `totp.json` carries the public appendix B ASCII seed, derives its base32 encoding in the model, and verifies both the eight-digit vectors and their six-digit truncation and the window and replay decisions.

### 6.3 Login

`loginLocal` takes user name, password and TOTP code as JSON under the `origin` request guard. In order: per-source rate limit; strict decoding; account lookup, computing a verifier for a fixed dummy account when the name is unknown so that both paths do the same work; constant-time password comparison; the account's TOTP throttle; TOTP verification; account `active` and user enabled. Ordinary credential failure answers `401 invalid_credentials` without identifying the factor; throttled checks answer `429 rate_limited`. Disabled accounts perform equivalent dummy verification work, never consume an active factor or disclose enabled state. After three consecutive TOTP failures with a correct password, further TOTP checks for that account wait 30 seconds, doubling to at most 15 minutes, and are answered `429` until then; this throttle starts only after a correct password, so a guesser without the password cannot lock out the holder, and the first such failure is a critical audit event and notifier alert because someone holds the password. Success creates a `break_glass` session, revokes any other session of the account, writes a critical audit event and raises a notifier alert (section 1 states the connector dependency).

### 6.4 Enrollment

Creating, resetting or replacing a factor is an identity-authority request. `createBreakGlassAccount` names an existing `user_uid`; it does not create a privileged user or assign a role. The binding includes that uid, account uid, credential generation, action and requester as credential recipient. A user has at most one non-deleted local account; user names are globally unique and never silently reused. First start alone creates the initial user and grant (section 7).

After application the requester, still enabled and holding the original action permission, uses recent authentication to claim one enrollment code. `claimBreakGlassEnrollmentCode` is a requester-only subject exemption, not a permission to claim another user's request.

Under the session/synchronizer guard and BE-12 fence, recheck the enabled requester, original action permission, verified recent authentication, applied request, current epoch and account credential generation, live claim deadline and unconsumed claim entitlement; consume that entitlement atomically with code issuance. A queue-read or authority-approval grant confers no claim right. Reset, disable, deletion or an epoch change invalidates the entitlement. The permission coverage refresh must add this exemption and these checks; it is an integration gate, not a new permission.

Generate 26 independent base32 symbols (130 bits), store its keyed digest and authenticated binding, and expose it once with a 24-hour deadline from claim. The claim entitlement expires 24 hours after application. No replay returns the code. A lost claim response requires a new protected reset, or the offline ceremony for first start.

`startBreakGlassEnrollment` atomically consumes the code and creates a ten-minute enrollment record, generates pending credentials, and sets the enrollment cookie. Reusing the code fails; it never replaces a pending challenge. Create/reset returns password and seed once; factor replacement returns only a seed and `mode: replace_factor`, retaining the existing password verifier. The response schema makes password conditional on mode. The `otpauth` URI format and QR interoperability require qualification (verify); use issuer `Ricevanta`, percent-encoded username label, SHA1, six digits and 30 seconds. QR size must equal both row count and each row's length.

Completion requires the current cookie, epoch, account generation and a valid code from the pending seed. It permits at most five failed code checks before consuming the challenge as failed. On success atomically activate the credentials, record the accepted TOTP floor, consume the challenge, revoke all account-dependent sessions, clear the cookie and audit. No session is created. On expiry or failure the account remains `pending_enrollment`; a new approved reset is necessary. Disable/delete cancels outstanding claims/challenges. Credentials and enrollment cookies never appear in URLs, logs, browser storage or approval views.

A stolen code can enroll the exact approved account before its holder does; it is a credential-delivery capability, not a second approver. The approver must inspect its recipient and target. Possession of an old session or a database copy cannot reset or replay that capability after consumption. Pending plaintext is discarded immediately after response construction; encrypted pending seed/verifier state lasts only until completion or expiry.

### 6.5 Lifecycle

Accounts are `pending_enrollment`, `active` or `disabled`. Reset or factor replacement revokes sessions and moves the account to pending enrollment when approved, so old factors no longer log in. Disable preserves current credentials but cancels pending enrollment; enable is allowed only with a complete, current-epoch credential generation and otherwise requires reset. Delete is a permanent tombstone and releases no uid for reuse. Enable, disable, reset, factor replacement and deletion are identity-authority requests (catalogue rule `identity_authority`). Disabling or deleting an account revokes its sessions when applied. A break-glass session uses the shorter timeouts and the persistent banner of [identity sessions](identity-sessions.md) section 3.

## 7. First start

`completeFirstStartSetup` consumes the one-time setup token: 256 random bits written by `ricevanta-server` to a file readable only by the server user, whose path, never value, is logged (console design section 2.1). Before the endpoint opens, the offline recovery quorum manifest must be verified and the authority journal genesis written (backend design section 6.1). The request names the first administrator's user name and display name; the server creates the internal user with the built-in administrator role and a direct `identity.authority.approve` assignment, creates a break-glass account in `pending_enrollment`, deletes the token file, and returns enrollment credentials and the enrollment cookie as section 6.4 does. Consume the setup-token digest in the journal before returning credentials; deleting the file alone is not consumption. Concurrent calls produce one authority operation. If its one-time response is lost, an exact offline repair re-enrolls the administrator; restarting never generates a replacement setup bypass. The first-start marker for release-fixed extension admission follows backend section 6.1 separately and cannot keep this token valid. The token grants nothing after this call. The operation is gated on BE-12.

## 8. Security trace

Path: browser navigation → start (record, cookie) → provider authentication → callback or consumer (record consumed, protocol checks) → principal link → authority reader → session. Break-glass: JSON login → verifier and TOTP → authority reader → session.

| Attacker | What the attacker gets |
|---|---|
| Stolen enrollment token | Nothing: agent enrollment tokens are not login credentials anywhere in this flow |
| Compromised agent host | Network access to public login options and SAML metadata; no credential that resolves to an administrator |
| Compromised console session | Within the session, it can start re-authentication but must pass the provider or present the password and a fresh TOTP code; only verified recent evidence lets it request provider, link and break-glass changes, which wait for a different approver with bound, unaffected re-authentication; if it requested a break-glass change, it can claim that enrollment code after approval |
| Rogue extension publisher | Console module frames lack top-level navigation and the bridge excludes authentication and identity-authority operations (EXT-04), so a module cannot start or complete a login |
| Network position between agent and server | Not on this channel. Between browser, server and provider, TLS protects codes and assertions; a party able to obtain a publicly trusted certificate for the provider's host could serve forged discovery and keys to the server, so OIDC trust rests on the Web PKI with the deployment's system trust roots (section 10) |
| Database writer without signing keys | Cannot forge authenticated records or decrypt secrets; can delete or replay valid old records. Current projection checks must reject substituted providers, links, pre-login records, enabled state, enrollment consumption and lower TOTP floors. Proving those checks and publication requires BE-12; production is blocked |
| Server restored from backup | Serving remains sealed through reconciliation and an offline epoch transition. All old pre-login/enrollment proofs and local verifiers fail epoch binding; fresh local enrollment is part of the exact repair set (identity sessions section 8). No lost replay-cache entry reopens a callback |
| Compromised identity provider | Can authenticate any principal of that provider, so can log in as its linked users; cannot use that provider to approve a change affecting it. It may impersonate an assigned approver for an unrelated authority when that provider is outside the affected set; independence is relative to the change, not a guarantee against every compromised provider |

## 9. Benefits, trade-offs, dependencies, limits, alternatives

Benefits: three request-forgery defences in OIDC, InResponseTo, Destination and replay binding in SAML, single-use pre-login records and per-provider endpoints remove login request forgery and mix-up; generated break-glass secrets make online and offline guessing pointless and let the account delay apply only after a correct password; identity-authority protection keeps a compromised provider from extending its own reach.

Trade-offs: one pre-login cookie per protocol means parallel logins in two tabs of one browser fail one of them; generated passwords must be stored by the holder rather than remembered; IdP-initiated SAML is unsupported; logout ends only the Ricevanta session, and the provider's session may log the user in again silently, which `prompt=login` and `ForceAuthn` counter for re-authentication.

Dependencies: `github.com/coreos/go-oidc/v3` v3.21.0 with `github.com/go-jose/go-jose/v4` and `golang.org/x/oauth2`; `github.com/russellhaering/gosaml2` v0.12.0, `github.com/russellhaering/goxmldsig` v1.6.1, `github.com/beevik/etree`, `github.com/jonboulle/clockwork` and `github.com/mattermost/xml-roundtrip-validator`; `rsc.io/qr`; Go standard library `crypto/hmac`, `crypto/sha1`, `crypto/hkdf`. These are candidates, not newly admitted dependencies. [Licensing](../licensing.md) records go-oidc and rsc.io/qr but lacks the listed SAML and transitive JOSE/OAuth rows; those rows and source/license verification are required before implementation. Library activity, pins, assertion-selection behavior and transitive closure remain verify claims because this work cannot fetch sources.

Limits: OIDC trust in the provider's discovery and keys rests on the Web PKI by default; SAML trust rests on imported certificates and changes only through a protected update; the source-address limits share a bucket behind a load balancer (API foundation section 7); the notifier contract and delivery qualification block complete break-glass alerting; audit-only behavior is not the v1.0.0 end state.

Alternatives considered: one callback for all providers (rejected: RFC 9700 mix-up defence needs distinct redirect URIs); `form_post` response mode (rejected: a cross-site `POST` needs a `SameSite=None` cookie for no benefit); unsigned AuthnRequests (rejected: the generated SP key can authenticate every request); operator-chosen break-glass passwords with Argon2id (rejected: a memorized password is guessable and the hash needs a new dependency, while a generated secret needs neither); automatic link creation from email or directory attributes (rejected: BE-01 forbids mutable identifiers); `crewjam/saml` (alternative candidate; activity and dependency comparison require source verification).

## 10. Unresolved questions

- Which SAML candidate and complete licensed dependency closure pass the exact parser, signature, wrapping and interoperability predicates above?
- Which BE-12 gate proves callback, enrollment and TOTP consumption, and which notifier contract delivers the required break-glass alerts?

Manual linking is the fixed choice for this slice; directory/claim mappings belong to their separate identity-authority design. OIDC uses system roots and same-origin endpoints; private CA roots are deployment trust configuration, not a new online trust-edit API. Production login always waits for BE-12.
